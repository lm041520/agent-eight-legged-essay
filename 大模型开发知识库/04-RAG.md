# 04 RAG：检索增强生成

> 定位：从文档进入系统开始，完整讲清解析、分块、Embedding、索引、混合检索、Rerank、Context组装、生成、引用、评测和生产治理。

### 学习优先级地图

- **P0：必须掌握**——解析与清洗、Chunk、Embedding、向量相似度、向量库、Top-K、Metadata Filter、BM25与Dense检索、Rerank、Context组装、引用与基础评测。
- **P1：需要实践**——Hybrid/RRF、Query Rewrite/Multi-Query/HyDE、多跳检索、索引版本、权限与多租户、增量更新、完整企业RAG项目。
- **P2：方向了解**——GraphRAG、复杂多模态索引、大规模分布式检索与学习式检索优化；按RAG算法/平台岗位深入。

学习顺序应是先跑通可评测的朴素RAG，再逐个加入混合检索、Rerank和查询优化并做消融。

## 零基础导读：把一份员工报销手册变成可以问答的知识库

先看一个没有RAG的场景。公司刚发布《2026年差旅报销管理办法》，其中写着：

```text
第十八条：市内交通费单笔超过200元时，报销人需要补充行程说明，
并由直属负责人审批。网约车订单应同时提供平台行程单和发票。
```

用户问模型：

```text
出差打车花了260元，报销时需要准备什么？
```

通用大模型可能从未见过这份公司内部文件。即使它给出听起来合理的答案，也可能把其他公司的规定混进来。RAG的目标不是让模型“记住”文件，而是在回答前把相关原文找出来，临时放进上下文。

### RAG最简单的一句话定义

RAG是`Retrieval-Augmented Generation`，即“检索增强生成”：

```text
先从外部知识库找证据，再让模型根据证据生成答案。
```

它包含两条时间上分开的链路：

```text
离线：提前处理文档并建立可搜索索引
在线：用户提问时检索证据并生成回答
```

### 离线第1步：解析文档

源文件可能是PDF、Word、网页或扫描件。程序需要把它转换成文本和结构信息：

```json
{
  "document_id": "expense-policy-2026",
  "title": "2026年差旅报销管理办法",
  "page": 8,
  "section": "第十八条 市内交通费",
  "text": "市内交通费单笔超过200元时……",
  "effective_date": "2026-01-01",
  "department": "财务部"
}
```

为什么不能只抽取一长串纯文本？因为回答时还需要知道证据来自哪一页、哪一条制度、是否已经过期，以及当前用户是否有权查看。

扫描PDF没有可复制文字，需要OCR；双栏文档还要恢复阅读顺序；表格要保留行列关系。解析错误会一路传递到检索和回答。

### 离线第2步：分块Chunking

假设整本手册有80页。不能把80页全部塞进每次请求：成本高、超过上下文，而且大量无关内容会干扰模型。因此把文档切成较小片段。

错误切法可能是：

```text
Chunk A：第十八条：市内交通费单笔超过200元时，报销人需要
Chunk B：补充行程说明，并由直属负责人审批。网约车订单应……
```

如果只召回Chunk B，读者甚至不知道“超过多少元”。更好的做法是按标题和语义边界切分：

```text
Chunk 18
标题：第十八条 市内交通费
正文：市内交通费单笔超过200元时，报销人需要补充行程说明，
并由直属负责人审批。网约车订单应同时提供平台行程单和发票。
```

Chunk不是越小越好。太小会丢上下文，太大又会降低检索精度并浪费Token。后面讲的重叠、Parent-Child和Sentence Window，都是在解决这个矛盾。

### 离线第3步：把文本转换成Embedding

计算机不能直接用“语义相近”搜索自然语言。Embedding模型把一段文字转换成一组数字：

```text
“打车费超过200元” → [0.12, -0.31, 0.88, ...]
“网约车高额费用”   → [0.10, -0.28, 0.84, ...]
```

真实向量可能有几百或几千维。含义相近的文本在向量空间中通常更接近。

需要强调：这些数字不是人工给每一维起好“交通费”“金额”的名字，而是Embedding模型从训练数据中学到的分布式表示。向量只能在同一个兼容模型和版本下比较。

### 离线第4步：写入索引

向量数据库通常保存两类内容：

```text
向量：用于近似语义搜索
Payload/Metadata：文档ID、页码、部门、权限、生效日期、原文
```

向量不是知识本身。最终给模型的证据仍然是原文和元数据，向量只是帮助我们找到它。

### 在线第1步：处理用户问题

用户原问题是：

```text
出差打车花了260元，报销时需要准备什么？
```

系统可以直接对它做Embedding，也可能先改写为更适合检索的表达：

```text
差旅市内交通费单笔超过200元的报销材料与审批要求
```

改写的风险是改变原意，因此必须保留原问题，并通过评测验证改写是否真的提高召回。

### 在线第2步：召回候选证据

Dense向量检索可能返回：

```text
1. 第十八条 市内交通费           相似度0.86
2. 第二十一条 出租车发票要求     相似度0.79
3. 第十二条 城际交通费           相似度0.74
4. 第三十条 审批流程             相似度0.71
5. 第九条 住宿费标准             相似度0.63
```

关键词BM25则擅长精确匹配“200元”“网约车”等词。Dense擅长找到“打车”和“市内交通”这样的语义近义关系。Hybrid Search把两者结合，减少只使用一种检索方式的盲区。

### 在线第3步：Rerank重新排序

第一阶段召回追求“别漏掉”，会多取一些候选；Reranker对“问题—候选段落”成对评分，追求把最相关证据排在前面。

```text
召回阶段：从10万段中快速选出20段
Rerank阶段：用更精细模型把20段重新排序，保留前5段
```

因为Reranker要逐对计算，直接对10万段全部评分通常太慢。

### 在线第4步：组装Context

系统不是简单把前5段无脑拼接。需要：

- 去掉重复段落；
- 保留标题、页码和制度版本；
- 控制总Token预算；
- 把最关键证据放在模型更容易注意的位置；
- 明确告诉模型证据不足时应拒答或澄清。

最终提示可以简化为：

```text
请只根据下列公司制度回答。如果证据不足，请明确说明。

[证据1]
来源：2026年差旅报销管理办法，第18条，第8页
内容：市内交通费单笔超过200元时……

[用户问题]
出差打车花了260元，报销时需要准备什么？
```

### 在线第5步：生成带引用的答案

```text
这笔260元打车费超过200元，需要补充行程说明并由直属负责人审批；
如果是网约车，还应同时提供平台行程单和发票。
来源：《2026年差旅报销管理办法》第18条，第8页。
```

引用不是装饰。系统应保存“回答中的引用标记—具体Chunk—原文件位置”的映射，让用户可以回到原文核验。

### 最小RAG伪代码

```python
async def answer_with_rag(question: str, user: User) -> Answer:
    query_vector = await embedding_model.embed(question)

    candidates = await vector_store.search(
        vector=query_vector,
        top_k=20,
        filters={"department": user.department, "status": "active"},
    )

    ranked = await reranker.rank(question, candidates)
    evidence = build_context(ranked[:5], token_budget=5000)

    response = await llm.generate(
        question=question,
        evidence=evidence,
        require_citations=True,
    )
    return verify_and_attach_sources(response, evidence)
```

每一行都可能成为独立优化点。回答错了不要直接归因于“大模型不行”，而要按链路检查：文档解析是否正确、Chunk是否完整、正确证据是否召回、Rerank是否排前、Context是否被截断、模型是否忠于证据。

## 一、RAG解决什么问题

大模型参数中的知识存在几个限制：

- 不包含企业私有数据；
- 可能过期；
- 无法直接给出可审计来源；
- 对具体文档细节容易幻觉；
- 重新训练成本高。

RAG在生成前从外部知识源检索相关证据，将证据放入上下文，让模型依据证据回答：

```text
离线索引：文档 → 解析 → 清洗 → 分块 → Embedding → 索引

在线问答：问题 → Query处理 → 召回 → 过滤 → 融合 → Rerank
       → Context组装 → 模型生成 → 引用/拒答 → 评测与Trace
```

RAG不是“向量库+Prompt”两个步骤。任何一层出错都可能导致最终答案失败。

### 学习目标

1. 为不同文档选择解析和分块策略；
2. 理解Embedding、相似度和模型版本；
3. 理解Exact、HNSW、IVF和Metadata Filter；
4. 组合BM25、Dense、Sparse和Hybrid Search；
5. 使用Query Rewrite、Multi-Query、HyDE和子问题拆解；
6. 理解Bi-Encoder、Cross-Encoder和Rerank；
7. 构建引用、拒答和冲突处理；
8. 分层评测检索与生成；
9. 处理权限、更新、多租户、缓存和注入；
10. 理解GraphRAG的适用边界。

# 第一章 文档解析与数据治理

## 1.1 先定义知识单元

索引之前先回答：用户要查什么？最小可引用单位是什么？

- 制度文档：章节、条款；
- API文档：接口、参数、错误码；
- 论文：章节、段落、表格和图；
- 合同：条款、主体、日期；
- FAQ：问题—答案对；
- 代码库：函数、类、模块、调用关系；
- 视频：时间片、字幕、关键帧。

如果知识单元定义错误，后续Chunk大小再精细也难以得到好结果。

## 1.2 文档解析

常见来源：

- PDF：文本层、扫描页、阅读顺序、页码；
- Word：标题层级、段落、表格、图片；
- Markdown：标题和代码块；
- HTML：正文、导航、脚本和广告；
- Excel/CSV：表头、工作表和单元格关系；
- 图片：OCR、版面、图表；
- 数据库：字段语义、行级权限和更新时间。

解析不只是“提取字符”。必须尽量保留结构、来源和位置。

## 1.3 PDF的典型问题

- 扫描PDF没有文本层；
- 双栏顺序错乱；
- 页眉页脚重复；
- 断词和换行错误；
- 表格被拆成无意义文本；
- 图片中的关键信息丢失；
- 页码和文档页不一致；
- 字体编码导致乱码。

处理流程：

```text
判断是否有文本层
→ 有文本则版面感知提取
→ 无文本则OCR
→ 检测标题、段落、表格、图
→ 清洗重复元素
→ 恢复阅读顺序
→ 保留页码和坐标
→ 抽样检查
```

## 1.4 OCR

OCR包含：

- 文本检测：文字在哪里；
- 文本识别：文字是什么；
- 版面分析：标题、正文、表格、脚注；
- 后处理：纠错、合并、阅读顺序恢复。

OCR错误会进入Embedding并被检索，常见数字、型号和专有名词错误尤其危险。应保留原图位置，重要回答可回到原图验证。

## 1.5 清洗

清洗目标是去除噪声而不破坏语义：

- 删除重复页眉页脚；
- 合并错误换行；
- 规范空白和Unicode；
- 保留代码缩进；
- 保留列表编号和标题；
- 去除导航、广告和模板噪声；
- 内容级去重；
- 标记解析异常。

不要一条正则把所有换行删除。标题、列表、代码和表格的换行携带结构信息。

## 1.6 元数据

每个Chunk至少考虑：

```json
{
  "document_id": "policy-2026",
  "version": "3.1",
  "title": "差旅制度",
  "section_path": ["报销", "住宿标准"],
  "page": 12,
  "source_uri": "...",
  "updated_at": "2026-06-01",
  "effective_from": "2026-07-01",
  "tenant_id": "tenant-a",
  "acl": ["employee"],
  "content_hash": "...",
  "parser_version": "...",
  "embedding_version": "..."
}
```

元数据用于引用、权限、版本、时间过滤、增量更新和故障追踪，不是可有可无的附加信息。

## 1.7 权限继承

文档权限必须继承到Chunk并在检索阶段执行。不能先检索所有租户文档，再依赖模型“不说出来”。

权限过滤需要覆盖：

- 用户/租户；
- 角色；
- 文档和章节；
- 时间有效性；
- 数据分类等级；
- 撤销和删除状态。

## 1.8 增量更新

基本策略：

```text
计算文档内容哈希
→ 未变化则跳过
→ 新增则解析和索引
→ 修改则删除/失效旧Chunk并写入新版本
→ 删除则清理索引和缓存
→ 更新成功后切换可见版本
```

索引更新不应让用户同时检索到互相冲突的新旧版本。可使用版本字段、别名/集合切换或双写后原子切换。

## 1.9 第一章故障排查

### 检索结果内容错乱

先查看原始解析结果和Chunk，不要直接调Embedding。检查阅读顺序、表格、页眉、编码和标题层级。

### 引用页码不准

检查是否丢失物理页码、文档印刷页码是否不同、分块后是否保留源坐标。

### 删除文档后仍能检索

检查向量索引、关键词索引、缓存、旧集合和副本是否同步清理。

## 1.10 第一章复习卡

- 一句话：解析阶段要把原始文档变成可检索、可引用、可授权、可更新的知识单元。
- 五个关键词：Parsing、OCR、Structure、Metadata、ACL。

# 第二章 Chunking分块

## 2.1 为什么要分块

整篇文档直接Embedding会把多个主题压进一个向量，检索不精确且上下文过长；分得过碎又会丢失完整语义。

分块目标：

- 每块表达相对完整主题；
- 足够小，便于精确检索；
- 足够大，包含回答所需证据；
- 保留标题、来源和邻接关系；
- 可稳定引用。

## 2.2 固定长度与重叠窗口

按字符或Token切分，简单快速：

```python
def fixed_chunks(text: str, size: int, overlap: int) -> list[str]:
    if size <= 0 or overlap < 0 or overlap >= size:
        raise ValueError("invalid chunk parameters")
    chunks = []
    step = size - overlap
    for start in range(0, len(text), step):
        chunk = text[start:start + size]
        if chunk:
            chunks.append(chunk)
        if start + size >= len(text):
            break
    return chunks
```

优点是稳定，缺点是可能从句子、条款和代码中间切开。适合作为基线，不一定是最终方案。

## 2.3 递归分块

优先按大结构分隔符切，块仍过大再使用更细粒度：

```text
章节 → 段落 → 句子 → Token/字符
```

比纯固定长度更容易保留语义边界。

## 2.4 按文档结构分块

使用标题、条款、FAQ、函数或表格作为边界：

- 每个Chunk保存完整`section_path`；
- 子章节继承父标题；
- 过长章节再递归拆分；
- 表格可以按行组拆分，但保留表头；
- 代码按类/函数切分并保留文件路径和符号名。

## 2.5 语义分块

根据相邻句子语义变化寻找边界。优点是主题一致，缺点是：

- 需要额外Embedding或模型调用；
- 阈值敏感；
- 结果不一定稳定；
- 对短句、表格、代码不一定合适。

应与结构分块基线做评测，不要因为名称高级就默认更好。

## 2.6 Parent-Child Chunking

索引小的Child Chunk以提高召回精度，命中后返回更大的Parent Context：

```text
Parent：完整章节
├── Child 1：定义
├── Child 2：参数
└── Child 3：示例
```

它解决“小块容易找、大块更完整”的矛盾。需要维护Parent/Child ID和权限一致性，避免命中子块后返回无权限父内容。

## 2.7 Sentence Window

索引单句或短段，命中后扩展前后若干句。适合局部事实检索，但窗口跨章节或列表时可能引入无关内容。

## 2.8 Chunk Size与Overlap

| 参数变化 | 可能收益 | 可能代价 |
|---|---|---|
| Chunk变大 | 语义完整、减少跨块 | 检索噪声、Token和成本增加 |
| Chunk变小 | 定位精确 | 上下文断裂、召回多个碎片 |
| Overlap变大 | 减少边界断裂 | 重复索引、结果重复、存储增加 |
| Overlap变小 | 减少重复 | 关键句可能被切断 |

没有通用最佳值。应按Tokenizer、文档类型、问题粒度和模型窗口做实验。

## 2.9 分块评测

至少比较：

- Recall@K；
- Context Precision；
- 重复召回率；
- 每查询Context Token；
- 答案正确率和Faithfulness；
- 索引规模；
- 延迟。

对表格、条款、代码和普通正文分开报告，不要只看混合平均值。

## 2.10 第二章复习卡

- 一句话：分块是在检索精度和语义完整性之间寻找可评测的平衡。
- 五个关键词：Boundary、Overlap、Recursive、Parent-Child、Sentence Window。

# 第三章 Embedding

## 3.1 Embedding是什么

Embedding把文本映射为向量，使语义相近的文本在向量空间中更接近。它适合召回候选，不等于事实判断器。

把它理解为“为文本生成可比较的语义坐标”，但不要把这个类比理解成每一维都有固定人类含义。真实模型会把信息分散到许多维度中。

假设演示模型只输出3维向量：

```text
“杭州明天会下雨吗”     → [0.82, 0.11, 0.35]
“杭州明日降水概率”     → [0.79, 0.15, 0.32]
“Python怎样创建字典”   → [-0.18, 0.91, 0.04]
```

前两句用词不同但语义接近，向量方向也接近；第三句主题不同，距离较远。生产向量通常有数百或数千维，无法直接靠肉眼判断。

Embedding模型的输出取决于完整输入。标题、正文、任务前缀、截断位置和语言都会改变向量。同一段文字换模型后得到的坐标属于另一个空间，不能直接与旧向量比较。

还要区分两个概念：

```text
Embedding负责把文本编码成表示
向量数据库负责保存表示并搜索相近候选
```

Embedding不是数据库，向量库也不会自动理解文本。

## 3.2 相似度

### 余弦相似度

```text
cos(a,b) = (a·b) / (||a|| ||b||)
```

关注方向而弱化长度。

用二维向量理解：

```text
a = [1, 1]
b = [2, 2]
c = [1, -1]
```

`a`和`b`长度不同但方向完全相同，余弦相似度为1；`a`和`c`方向正交，相似度为0。因此余弦更关注方向。

如果模型文档要求先做L2归一化，向量会被缩放到长度1。此时点积和余弦相似度数值相同。是否归一化必须遵循模型与数据库配置，不能凭习惯决定。

### 点积

归一化向量的点积与余弦相似度等价；未归一化时还受向量模长影响。

点积越大通常表示越相似，但“分数0.7就是相关”没有跨模型通用含义。不同模型、数据集和查询类型的分数分布不同。阈值应该在真实评测集上根据召回率、误召回和拒答需求选择。

### 欧氏距离

计算几何距离。选择必须与Embedding模型建议和索引配置一致。

距离与相似度的排序方向相反：余弦/点积通常越大越相似，欧氏距离通常越小越相似。接入向量库时如果把距离当相似度直接比较，阈值方向可能完全写反。

```python
import math

def cosine_similarity(a: list[float], b: list[float]) -> float:
    if len(a) != len(b):
        raise ValueError("dimension mismatch")
    dot = sum(x * y for x, y in zip(a, b, strict=True))
    norm_a = math.sqrt(sum(x * x for x in a))
    norm_b = math.sqrt(sum(y * y for y in b))
    if norm_a == 0 or norm_b == 0:
        raise ValueError("zero vector")
    return dot / (norm_a * norm_b)
```

## 3.3 Query与Document编码

部分Embedding模型要求使用不同前缀或接口编码查询和文档，例如任务说明或`query:`、`passage:`。忽略训练时约定可能降低效果。必须阅读所选模型卡和官方说明。

为什么要区分？检索中的两侧职责不同：Query通常很短，表达“想找什么”；Document较长，表达“我包含什么”。模型训练时可能专门学习了这种非对称关系。

```text
Query输入：query: 打车超过200元怎么报销
Document输入：passage: 第十八条 市内交通费单笔超过200元时……
```

如果文档入库时忘记`passage:`，而查询时使用`query:`，两侧编码分布可能不匹配。排查召回异常时，应把最终送入Embedding模型的完整字符串记录在可采样的调试日志中，而不是只记录原始文本。

## 3.4 模型选型

考虑：

- 中文和多语言；
- 领域文本；
- 最大输入长度；
- 向量维度；
- 是否支持稀疏/多向量；
- 推理吞吐和成本；
- 开源许可和数据边界；
- 是否提供检索任务指令；
- 评测集表现，而非只看公开榜单。

## 3.5 批处理与缓存

离线Embedding应批量调用，控制批大小、速率、失败重试和断点续跑。缓存键至少包含：

```text
内容哈希 + 模型ID + 模型版本 + 预处理版本 + 任务前缀
```

只用文本哈希会在模型升级后错误复用旧向量。

## 3.6 模型升级

不同Embedding模型的维度和空间不兼容，不能把新旧向量混在同一索引中直接比较。安全流程：

```text
建立新索引
→ 双写或离线重建
→ 用同一评测集比较
→ 小流量切换
→ 保留回滚
→ 清理旧索引
```

## 3.7 Dense与Sparse Embedding

- Dense：低/中维连续向量，擅长语义；
- Sparse：高维稀疏表示，保留词项特征，擅长精确词匹配；
- 多向量/Late Interaction：一个文档使用多个向量，召回更细但存储和计算更高。

用查询“错误码E1027如何处理”理解差异：

- Dense可能找到“登录服务鉴权失败解决方案”，因为语义接近；
- Sparse/BM25能强力匹配精确字符串`E1027`；
- 只用Dense时，罕见型号和编号可能被语义表示弱化；
- 只用关键词时，用户说“登录一直提示没有权限”又可能匹配不到`鉴权失败`。

因此企业检索常把Dense与Sparse/BM25融合。多向量方法则为同一文档保留多个Token或区域表示，在细粒度匹配上更强，但索引体积和计算成本更高。

## 3.8 第三章故障排查

### 相似查询得分很低

检查查询和文档是否使用同一模型和任务模式、向量维度、归一化、距离函数、文本截断和语言支持。

### 升级后效果突然下降

检查是否混用旧索引、模型前缀变化、预处理变化、向量维度或距离配置不一致。

## 3.9 第三章复习卡

- 一句话：Embedding负责语义召回，效果由模型、任务编码、预处理、距离和版本共同决定。
- 五个关键词：Vector、Cosine、Query/Document、Batch、Versioning。

# 第四章 向量数据库与索引

## 4.1 数据模型

典型Point/Row包含：

```text
ID + Vector + Text/Resource Reference + Payload/Metadata
```

向量库不是只存向量。过滤、引用、版本和权限都依赖Payload。

## 4.2 Exact与ANN

- Exact Search：扫描全部候选，召回准确但规模大时慢；
- Approximate Nearest Neighbor：用索引加速，以部分Recall换取延迟和资源。

小数据集应先建立Exact基线，用它测ANN Recall，而不是一开始就假设索引参数正确。

假设库中有100万个向量。Exact需要把查询与100万个向量都计算距离；ANN通过预先构建的数据结构，只访问可能接近的一小部分。

ANN中的“Approximate”不是说向量本身被随意改错，而是搜索过程可能没有访问真正最近的那个点。例如Exact的真实Top-10中，ANN找回9个：

```text
ANN Recall@10 = 9 / 10 = 90%
```

这和最终问答Recall不是同一个指标。ANN Recall衡量索引搜索相对Exact漏了多少；问答检索Recall衡量是否找到了业务正确证据。

## 4.3 HNSW

HNSW构建多层近邻图，从稀疏上层快速导航到局部密集区域。

可以把底层想成所有地点组成的密集道路网，上层则保留少量“高速连接”。查询先在上层快速靠近目标区域，再逐层下降做精细搜索。它不是先按固定网格分区，而是基于邻近关系建立图。

常见参数概念：

- M：每个节点连接规模，增大通常提高Recall但增加内存和构建成本；
- efConstruction：建索引搜索范围；
- ef/efSearch：查询搜索范围，增大通常提高Recall并增加延迟。

不同产品参数名和默认值不同，必须以当前官方文档为准。

调参时固定数据和查询集，逐级提高`efSearch`，同时记录ANN Recall、P95延迟和CPU/内存。不能只看平均延迟，因为复杂过滤和稀疏区域可能形成长尾。

## 4.4 IVF

IVF先把向量划分到若干聚类/列表，查询时只探测部分列表：

例如先把100万个向量聚成1000个列表。查询到来后，系统先找到最接近的若干聚类中心，只在这些列表中扫描候选，而不是检查全部100万个向量。

- 列表多：候选更细，训练和配置更复杂；
- probes多：Recall提高、查询变慢；
- 数据分布变化后可能需要重建。

如果只探测1个列表，速度快但目标可能落在相邻列表而被漏掉；探测100个列表，召回更高但越来越接近全量扫描。IVF需要有代表性的训练数据来学习聚类中心，新领域数据大量加入后，旧聚类可能不再合适。

pgvector当前同时支持HNSW和IVFFlat；官方说明HNSW通常有更好的速度—召回权衡，但构建慢、内存高，IVFFlat构建更快、内存低但更依赖训练数据和参数。

## 4.5 Metadata Filter

过滤不是后处理细节。若ANN先取Top-K再过滤，严格权限条件可能导致结果不足，甚至存在安全设计风险。应使用数据库支持的过滤索引和正确查询语义。

假设全库Top-10全部来自“财务部机密文档”，当前用户只能访问“研发部公开文档”。如果先取Top-10再在应用层过滤，最终会得到0条结果；更严重的是，若任何一层错误返回了摘要，就可能形成越权泄漏。

正确查询语义应接近：

```text
在 tenant_id=A、department=研发部、status=active 的允许集合中，
寻找与Query最接近的Top-10。
```

常用过滤字段需要建立Payload/Metadata索引。多租户权限还应在检索服务端强制注入，不能让模型自行生成或决定权限条件。

Qdrant当前文档强调对常用Payload字段建立索引，并将过滤与HNSW搜索结合。具体行为、索引构建顺序和版本能力需核对部署版本。

## 4.6 多租户

方案：

- 每租户独立数据库/集合：隔离强，运维成本高；
- 共享集合+租户过滤：效率高，必须保证每次查询强制过滤；
- Partition/Shard Key：物理或逻辑折中；
- 按数据等级选择不同策略。

不能让模型生成`tenant_id`过滤条件。租户身份应由认证上下文注入查询。

## 4.7 产品选型

| 方案 | 适用特点 | 需要考虑 |
|---|---|---|
| FAISS | 本地库、实验、单机 | 持久化、过滤、分布式需自行处理 |
| pgvector | 已有PostgreSQL、事务与元数据结合 | 大规模ANN调优、数据库资源竞争 |
| Qdrant | 向量搜索、过滤、混合查询 | 集群运维、版本能力 |
| Milvus | 大规模、多索引和分布式 | 部署复杂度和资源 |
| Elasticsearch | 关键词、过滤、向量和现有搜索生态 | 映射、资源和相关性调优 |
| Chroma | 本地原型 | 生产能力需按版本审查 |

不要只根据榜单选型，要根据规模、过滤、更新、租户、备份、团队经验和现有基础设施。

## 4.8 索引生命周期

- 批量写入；
- 后台构建；
- 索引状态检查；
- 新旧版本切换；
- 删除和压缩；
- 备份恢复；
- 一致性验证；
- 定期测Recall和延迟。

## 4.9 第四章复习卡

- 一句话：向量索引用近似搜索换速度，生产设计还必须覆盖过滤、租户、版本和生命周期。
- 五个关键词：ANN、HNSW、IVF、Payload Filter、Multi-tenancy。

# 第五章 检索策略

## 5.1 BM25

BM25是经典词项检索方法，考虑词频、文档频率和文档长度。它擅长：

- 产品型号；
- 错误码；
- 人名和专有名词；
- 精确短语；
- Embedding不熟悉的新词。

它不擅长仅靠语义改写但没有共同词项的问题。

## 5.2 Dense Retrieval

Dense向量检索擅长语义相似，例如“怎么退货”和“商品退换流程”。但可能弱化数字、代码、否定和精确实体差异。

## 5.3 Sparse Retrieval

Sparse向量可由传统词项权重或学习模型产生，保留稀疏词项特征。实际能力取决于模型和检索引擎，不应把所有Sparse都等同BM25。

## 5.4 Hybrid Search

混合检索组合Lexical和Semantic：

```text
BM25召回精确词项
+ Dense召回语义相关
→ 融合排名
→ Rerank
```

当前Qdrant等系统支持Dense与Sparse混合查询和RRF等融合方式。是否提升必须用自己的查询集评测。

## 5.5 Reciprocal Rank Fusion

RRF主要根据各列表排名融合，不要求原始分数可直接比较：

```text
score(d) = Σ 1 / (k + rank_i(d))
```

```python
from collections import defaultdict

def rrf(rankings: list[list[str]], k: int = 60) -> list[tuple[str, float]]:
    scores: dict[str, float] = defaultdict(float)
    for ranking in rankings:
        for rank, doc_id in enumerate(ranking, start=1):
            scores[doc_id] += 1 / (k + rank)
    return sorted(scores.items(), key=lambda item: item[1], reverse=True)
```

RRF简单稳定，但不使用原始相关性强度；加权RRF和其他融合方式需要通过分层查询评测。

## 5.6 Metadata与时间过滤

过滤条件来自：

- 当前身份和租户；
- 文档类型；
- 生效和失效时间；
- 产品、地区、语言；
- 数据分类；
- 用户明确范围。

如果用户问“当前政策”，查询必须过滤或提升当前有效版本，而不是把新旧文档一起交给模型自行判断。

## 5.7 Query Rewrite

重写目标是让查询更适合检索：

- 补全对话中的指代；
- 标准化专有名词；
- 提取核心检索词；
- 拆除无关礼貌表达；
- 生成关键词和语义查询两个版本。

风险是模型改变用户意图。应保留原始Query，同时记录Rewrite并评测。

## 5.8 Multi-Query

生成多个不同表达提高召回：

```text
原问题：Agent为什么重复调用工具？
查询1：Agent工具调用死循环
查询2：Function Calling重复执行原因
查询3：LangGraph循环终止条件
```

多个查询会增加延迟和重复结果，需要去重、融合和并发限制。

## 5.9 Query Expansion

加入同义词、缩写和领域别名。例如“OOM”扩展为“out of memory、显存不足、内存溢出”。扩展词应来自领域词典或可评测模型，避免扩展到不相关概念。

## 5.10 HyDE

HyDE先让模型生成一段“假想答案/文档”，再对其Embedding检索。它可能帮助短问题匹配文档表达，但假想文本也可能带偏检索。应作为候选策略与原Query联合，而不是无条件替换。

## 5.11 子问题拆解与多跳检索

复杂问题需要多个证据：

```text
问题：比较A和B项目在记忆机制与部署方式上的差异
→ 子问题1：A的记忆机制
→ 子问题2：B的记忆机制
→ 子问题3：A的部署
→ 子问题4：B的部署
→ 汇总比较
```

每个子问题应保存来源，最终合并时检查实体和版本一致。

## 5.12 自适应Top-K

简单精确查询可能只需少量结果，复杂多跳任务需要更多候选。可根据：

- 查询类型；
- 分数分布；
- 是否命中精确实体；
- 证据覆盖；
- Token预算；
- Rerank成本。

动态调整，但必须有最大值和评测。

## 5.13 第五章故障排查

### 型号和错误码总是召回失败

检查是否只使用Dense；增加BM25/Sparse、字段检索和Query标准化。

### 混合检索结果反而变差

检查融合权重/RRF参数、候选数、各检索源质量、重复内容和Rerank；按查询类型分层，不要只看总体平均。

### Query Rewrite改变意图

保留原Query联合检索；增加实体和否定词约束；对Rewrite做独立评测和Trace。

## 5.14 第五章复习卡

- 一句话：高质量检索通过词项、语义、过滤、查询处理和融合共同扩大有效召回。
- 五个关键词：BM25、Dense、Hybrid、RRF、Query Rewrite。

# 第六章 Rerank

## 6.1 为什么需要两阶段检索

召回阶段追求速度和Recall，从大库中取几十到几百候选；Rerank使用更昂贵模型精确排序，只保留少量Context。

```text
百万级文档
→ ANN/BM25召回Top-50
→ Reranker逐对判断Query-Chunk相关性
→ 保留Top-5
```

## 6.2 Bi-Encoder与Cross-Encoder

- Bi-Encoder：Query和文档分别编码，可预计算文档向量，适合大规模召回；
- Cross-Encoder：把Query和文档一起输入，交互更充分，通常更准但无法大规模预计算；
- Late Interaction：在精度和效率之间使用多向量交互。

## 6.3 候选数

- 召回Top-K太小：相关文档进不了Rerank；
- Top-K太大：延迟和成本增加，弱候选可能影响批处理；
- 最终Top-N太小：多证据不完整；
- Top-N太大：Context噪声增加。

必须联合优化Recall、NDCG、回答质量、延迟和Token。

## 6.4 去重和多样性

相邻Chunk和重复文档可能占满Top-N。可按文档、章节和内容Hash去重，或使用多样性策略。但不能为了多样性排除所有同一文档片段，多段证据有时都必要。

## 6.5 LLM Rerank

LLM可以根据复杂任务标准排序或筛选，但成本、延迟和稳定性更差。适合小候选集、复杂多跳或需要解释的场景。仍需结构化输出、超时、缓存和降级。

## 6.6 第六章复习卡

- 一句话：召回负责不漏，Rerank负责排准，最终Context负责少而够用。
- 五个关键词：Bi-Encoder、Cross-Encoder、Candidate、Top-N、Diversity。

# 第七章 Context组装与生成

## 7.1 Context结构

每段证据应带稳定ID和来源：

```text
[S1]
文档：差旅制度 v3.1
章节：报销 > 住宿标准
页码：12
更新时间：2026-06-01
内容：……
```

模型回答引用`[S1]`，程序再将ID映射为真实链接。不要让模型自由生成URL或页码。

## 7.2 排序

可考虑：

- 相关性；
- 文档版本和生效时间；
- 权威级别；
- 多证据覆盖；
- 把关键证据放在容易被注意的位置；
- 保持同一章节局部连续。

## 7.3 生成Prompt

应明确：

- 只根据允许证据回答哪些部分；
- 证据不足时如何表达；
- 如何引用；
- 冲突如何处理；
- 禁止伪造来源；
- 输出结构。

Prompt只是生成约束，引用有效性应由程序后处理检查。

## 7.4 无答案与拒答

RAG系统必须能说“当前资料不足”。可综合：

- 检索无命中；
- 分数或Rerank低于阈值；
- 必需证据覆盖不足；
- 证据冲突无法消解；
- Judge判断回答不被支持。

阈值不能只凭相似度绝对数值照搬，不同模型和距离定义不同，应在验证集上校准。

## 7.5 冲突处理

新旧制度、多个来源可能冲突。优先使用：

- 生效时间；
- 权威级别；
- 版本；
- 适用范围；
- 用户地区/身份；
- 明确展示冲突并请求确认。

不要把冲突片段直接拼给模型并期待它总能正确判断。

## 7.6 引用验证

验证：

- 引用ID存在；
- 当前用户有权限；
- 引用文本包含支持证据；
- 每条关键陈述至少有支持；
- 引用不是只在主题上相关；
- 版本和时间正确。

## 7.7 防止外部知识越界

对于必须严格依据内部资料的任务，Prompt要求不足。可以：

- 将回答拆成原子陈述并做支持检查；
- 对无引用关键事实拒绝输出；
- 使用结构化“claim-source”输出；
- 对高风险答案人工审批。

## 7.8 第七章复习卡

- 一句话：生成阶段要把少量高质量证据组织为可引用、可拒答、可验证的答案。
- 五个关键词：Context Assembly、Citation、Abstention、Conflict、Claim Support。

# 第八章 GraphRAG与知识图谱

## 8.1 什么时候需要图

适合：

- 多跳关系；
- 组织、供应链、知识依赖；
- 人物、事件和时间线；
- 需要解释“如何关联”；
- 单纯相似度难以表达的路径约束。

不适合：

- 普通FAQ和单段事实；
- 实体关系抽取质量不足；
- 数据变化快但图更新链路不成熟；
- 只为了使用Neo4j而增加复杂度。

## 8.2 图构建

```text
文档
→ 实体抽取
→ 关系抽取
→ 实体标准化
→ 消歧和去重
→ 写入节点/边
→ 保存来源、时间和置信度
```

实体名相同不一定是同一实体；同一实体也可能有缩写和别名。错误合并会让图路径产生严重假关系。

## 8.3 图检索

- 按实体定位；
- 邻居扩展；
- 路径查询；
- 子图召回；
- 社区/主题摘要；
- 时间和权限过滤。

## 8.4 向量与图融合

常见流程：

```text
向量检索找到相关实体/文档
→ 图扩展相关关系
→ 返回支持路径和原始证据
→ Rerank和生成
```

图中每条关系应能回溯到来源，不应只把模型抽取关系当成绝对事实。

## 8.5 GraphRAG评测

- 实体和关系抽取Precision/Recall；
- 实体去重和消歧；
- 路径命中率；
- 多跳问题成功率；
- 证据路径正确性；
- 图更新及时性；
- 相比向量RAG基线的增益。

## 8.6 第八章复习卡

- 一句话：GraphRAG用显式实体和关系支持多跳检索，但质量受图构建、消歧、来源和更新强约束。
- 五个关键词：Entity、Relation、Disambiguation、Path、Provenance。

# 第九章 生产治理

## 9.1 数据一致性和版本

记录并传播：解析器、Chunk、Embedding、索引、Reranker、Prompt和数据版本。一次回答的Trace应能还原使用了哪个版本。

## 9.2 缓存

可缓存：

- 文档解析；
- Embedding；
- Query Rewrite；
- 检索候选；
- Rerank；
- 最终回答（谨慎）。

缓存键必须包含租户、权限、版本和相关参数。最终回答缓存尤其要避免跨用户和过期知识泄露。

## 9.3 高并发与超时

每一阶段设预算：

```text
Query处理
→ 关键词/向量召回
→ Rerank
→ 模型生成
```

支持降级：Rerank超时可使用融合排名；某检索源失败可使用另一源；但应在回答或Trace中标记降级，不能静默声称完整结果。

## 9.4 Prompt Injection

文档中可能包含“忽略系统指令”等恶意内容。必须将文档作为不可信数据，禁止其改变工具权限、系统Prompt和身份。高风险工具不应在纯问答RAG节点可用。

## 9.5 监控

- 索引更新延迟；
- 解析失败率；
- Embedding失败/队列；
- 无命中率；
- Recall抽样；
- Rerank延迟；
- Context Token；
- Faithfulness和拒答率；
- 越权拦截；
- P95/P99和成本。

## 9.6 第九章复习卡

- 一句话：生产RAG需要治理数据、权限、版本、缓存、降级、安全和观测，而不仅是优化相似度。

# 第十章 综合实践：企业知识库RAG

## 10.1 项目目标

构建一个可上传制度/API/项目文档的知识库，支持：

- 多格式解析；
- 结构化Chunk和引用；
- Dense+BM25混合检索；
- RRF和Rerank；
- 用户/租户权限；
- 文档增量更新；
- 无答案拒答；
- 检索和生成分层评测；
- Trace和版本记录。

## 10.2 最小数据表/对象

```text
Document
├── document_id, tenant_id, version, hash, acl, status

Chunk
├── chunk_id, document_id, text, section_path, page, parent_id

EmbeddingRecord
├── chunk_id, model_version, vector, indexed_at

RetrievalTrace
├── query, rewritten_queries, filters, candidates, scores, final_context
```

## 10.3 实验矩阵

| 实验 | 变量 | 固定项 | 指标 |
|---|---|---|---|
| 分块 | size/overlap/结构 | Embedding和检索 | Recall、Token、答案 |
| 检索 | Dense/BM25/Hybrid | Chunk和模型 | Recall、MRR、延迟 |
| Rerank | 无/模型A/模型B | 候选集 | NDCG、Faithfulness、延迟 |
| Context | Top-N和排序 | 检索结果 | 正确率、Token、引用 |
| 拒答 | 阈值 | 其他流程 | 可答/不可答分类 |

## 10.4 故障注入

- PDF解析错序；
- OCR数字错误；
- 旧版制度与新版冲突；
- 权限文档混入；
- 向量服务超时；
- Reranker不可用；
- 文档包含Prompt Injection；
- 删除后缓存仍命中。

## 10.5 验收标准

- 关键查询Recall@K达到项目基线；
- 引用可回到正确文档和位置；
- 无权限文档零泄露；
- 无答案时不伪造；
- 变更后可运行回归集；
- 每个回答可追踪解析、索引和Prompt版本。

# 第十一章 模块总结与面试复习

## 11.1 一分钟总结

> RAG包含离线索引和在线检索两条链。离线先根据业务定义知识单元，完成文档解析、清洗、结构化分块、元数据和权限继承，再用版本化Embedding写入关键词与向量索引。在线对Query做指代消解或拆解，通过BM25和Dense混合召回，使用RRF融合和Cross-Encoder Rerank，最后把少量带来源证据组装给模型。生成阶段要支持引用、冲突和无答案拒答。优化时分开评Recall@K、MRR、NDCG等检索指标和Correctness、Faithfulness等生成指标，生产还要处理增量更新、多租户、缓存、降级、注入和全链路版本追踪。

# 08 推理部署：从 Ollama 本地调试到 vLLM 企业级服务

> 适用岗位：大模型部署、AI Infra、Agent 后端、推理优化、平台工程。  
> 优先级：推理流程、vLLM、并发调度、指标与压测为 **P0**；量化、并行、缓存和生产治理为 **P1**；PD 分离、投机解码、多节点优化为 **P1/P2**。  
> 学习目标：不仅会“启动一个模型”，还要能解释请求如何进入 GPU、为什么吞吐和延迟冲突、怎样做可复现压测，以及出现 OOM、排队或输出异常时如何定位。

## 0. 零基础导读：从本地问一句话到100个用户同时访问

先建立一个最容易理解的场景。你在自己电脑上用 Ollama 启动一个模型，发送：

```text
请解释什么是RAG。
```

一个人本地测试时，只要模型能回答，看起来就算成功。但把同一个模型给公司 100 个用户使用，会立刻出现新的问题：

```text
模型文件能否正确加载？
不同用户的请求怎样排队？
GPU显存能同时保存多少人的历史？
为什么第一个字等了5秒，之后却生成很快？
为什么并发越高，服务器总吞吐增加，单个人反而变慢？
用户关闭页面后，GPU是否还在继续生成？
服务崩溃或OOM时怎样限流、降级和恢复？
```

因此“部署”不是把 Python 函数套一层 HTTP。一次在线请求可以拆成下面的时间线：

```text
客户端发送 messages
  ↓ 网关验证身份、额度和输入长度
路由器选择模型实例
  ↓ 请求进入调度队列
Tokenizer把文本变成token id
  ↓
Prefill一次处理全部输入并建立KV Cache
  ↓ 产生第一个输出token
Decode每一步读取历史Cache并生成下一个token
  ↓ SSE逐段返回给用户
请求结束，回收KV块并记录延迟、token和错误
```

假设模型权重本身占 14 GB，GPU 有 24 GB，不能直接得出“还剩 10 GB，所以可以服务很多人”。剩余显存还要容纳每个请求随上下文增长的 KV Cache、临时计算张量和运行 buffer。长对话与高并发常常先把 KV Cache 填满。

同样，“每秒生成 500 token”也不一定代表单个用户每秒看到 500 个 token。它可能是 25 个用户各得到约 20 token/s 的服务器聚合吞吐。部署评测必须同时区分：

- TTFT：用户多久看到第一个 token；
- TPOT/ITL：之后每个 token 间隔多久；
- E2E：整个回答多久结束；
- 聚合吞吐：服务器整体每秒处理多少请求/token；
- P95/P99：最慢一批用户的体验；
- 错误率、排队长度、KV 使用率和成本。

后文所有技术都可以放回这条主线：模型文件决定“加载的是什么”；Prefill/Decode 解释“GPU怎样生成”；PagedAttention 和 Continuous Batching 解释“怎样同时服务更多人”；量化与并行解释“怎样放下并加速模型”；压测、监控和网关解释“怎样证明服务可上线”。

## 1. 从模型文件到在线 API 的完整链路

```text
模型权重 + config + tokenizer/chat template
                  ↓
              加载到设备
                  ↓
HTTP 请求 → 鉴权/限流 → tokenization → 调度队列
                  ↓
        prefill → KV Cache → decode
                  ↓
     sampling/stop → detokenization → SSE 流式返回
                  ↓
       指标、日志、trace、审计、计费
```

部署出问题时要先判断属于哪一层：

- 模型与模板：输出格式、工具调用、EOS 错误；
- 推理引擎：OOM、kernel、模型架构不支持；
- 调度：排队长、吞吐低、请求饿死；
- API：超时、断流、重试、限流；
- 基础设施：GPU、驱动、容器、网络、存储；
- 业务：提示词过长、无限输出、并发突增。

## 2. P0：模型部署前必须核对的文件

### 2.1 权重

模型权重就是训练后得到的数十亿个参数数值。它们并不包含“直接可读的知识文本”，而是一组组矩阵。部署程序必须知道这些数值属于哪一层、形状多大、用什么数据类型保存。

一个大模型仓库常把权重拆成多个分片：

```text
model-00001-of-00004.safetensors
model-00002-of-00004.safetensors
model-00003-of-00004.safetensors
model-00004-of-00004.safetensors
model.safetensors.index.json
```

索引文件记录参数名位于哪个分片。缺少任意一片、下载损坏或 revision 不一致，都可能导致加载失败。

- `safetensors`：只保存张量及元数据，避免 pickle 式任意代码反序列化风险，并支持按需映射和高效加载，是 Hugging Face 生态常见格式；
- PyTorch `.bin/.pt`：生态广，但某些保存方式基于 pickle，加载不可信来源时要注意安全；
- GGUF：llama.cpp 生态常用，通常把模型、量化方式和运行所需元数据组织为适合本地推理的格式；
- TensorRT-LLM engine 等后端专用格式：已经针对特定 GPU、dtype、并行和 kernel 构建，启动可能更快，但换显卡、版本或最大 batch 后可能需要重新构建。

文件格式不是模型能力本身。同一个基座可以转换成 safetensors、GGUF 量化版或某种 engine，但转换过程可能改变精度、兼容性和运行后端。

### 2.2 模型配置

`config.json` 像模型的“装配图”。权重文件只给出大量矩阵，配置告诉引擎怎样把它们拼成网络。至少要确认：

- `model_type/architectures`：该用哪一类模型代码；
- `num_hidden_layers`、`hidden_size`：层数和主隐藏维度；
- `num_attention_heads`、`num_key_value_heads`：决定 Attention 结构和 KV Cache 大小；
- `max_position_embeddings`、RoPE 配置：上下文长度及位置编码方式；
- `torch_dtype`、量化字段：权重预期精度；
- `vocab_size`、特殊 token id：必须与 tokenizer 对应。

如果把 32 层配置错读成 40 层，参数名和形状就无法匹配；如果强行修改最大上下文，也不代表模型一定在更长文本上保持质量。不要仅凭“7B/14B”判断显存，因为 dtype、KV heads、上下文长度、并发和量化都会改变总占用。

### 2.3 Tokenizer 与 Chat Template

Tokenizer 是“字符串与 token id 之间的字典加切分规则”。权重中的 Embedding 第 1234 行只认识 id `1234`，并不知道你原本输入了哪个汉字。因此同一权重配错 tokenizer，会把同一句话变成另一串 id，模型接收到的含义就彻底错乱。

Chat Template 再把多轮消息转换成模型训练时见过的一条 token 序列。例如 API 输入是：

```json
[
  {"role": "system", "content": "你是客服"},
  {"role": "user", "content": "查订单 A102"}
]
```

模板可能渲染成：

```text
<|system|>你是客服<|end|><|user|>查订单 A102<|end|><|assistant|>
```

最后一个 assistant 起始标记就是 generation prompt，表示接下来该由模型回答。不同模型使用的角色 token、换行和结束标记不同，不能自己随意拼接。

Chat 服务还需正确处理：

- system/user/assistant 角色 token；
- 工具调用格式；
- generation prompt；
- EOS/停止 token；
- 多模态占位格式。

当前 vLLM 的 Chat Completions 需要模型拥有可用 chat template，或启动时显式指定。服务能启动不代表模板正确。应把同一组 messages 分别用训练时 tokenizer 和线上服务渲染，检查 token id、工具调用标记、EOS 与最终输出是否一致，并用固定黄金样例回归。

### 2.4 版本与供应链

生产部署固定：

- 模型 revision/commit；
- tokenizer revision；
- 容器镜像 digest；
- CUDA/ROCm、驱动、PyTorch、推理引擎版本；
- 量化工具和校准数据版本；
- 模型许可证与来源哈希。

## 3. P0：Prefill、Decode 和性能瓶颈

这一部分不能只记结论。要先把“输入一句话，模型逐字输出答案”的过程完整走一遍。

用户发送：

```text
问：杭州今天下雨，出门需要准备什么？
```

经过Tokenizer后，假设Prompt一共有12个Token。模型最终要生成：

```text
建议携带雨伞。
```

假设答案被切成5个Token：

```text
[建议] [携带] [雨伞] [。] [EOS]
```

一次请求会经历：

```text
12个输入Token一起处理                 → Prefill
根据输入预测第1个输出Token“建议”       → Decode step 1
根据输入+“建议”预测“携带”              → Decode step 2
根据输入+“建议携带”预测“雨伞”          → Decode step 3
根据已有全部内容预测“。”               → Decode step 4
预测EOS并结束                          → Decode step 5
```

### 3.1 Prefill是什么

一句话定义：**Prefill是模型第一次读取整段输入Prompt，并为这些输入Token计算隐藏状态和每层KV Cache的阶段。**

对于12个输入Token，模型不会像输出阶段那样必须先算第1个再算第2个。训练和Prefill时，12个位置可以组成一个大张量一起送入GPU：

```text
input_ids形状：      [batch=1, sequence=12]
hidden states形状：  [1, 12, hidden_size]
```

如果hidden size为4096，隐藏状态可以理解为每个Token拥有4096个数字表示：

```text
[1, 12, 4096]
```

#### “一起处理”为什么不等于看到未来

Decoder-only模型使用Causal Mask。虽然12个位置在GPU上并行计算，但第3个位置只能关注第1～3个Token，不能读取第4～12个Token。

```text
位置1可看：1
位置2可看：1,2
位置3可看：1,2,3
……
位置12可看：1～12
```

并行指计算调度上可以同时做矩阵运算，不代表破坏自回归的信息约束。

#### Prefill中每一层发生什么

对每个Transformer层，输入隐藏状态会投影出Q、K、V：

```text
Q：当前位置想匹配什么信息
K：当前位置提供什么匹配标识
V：匹配后真正汇总的内容
```

Attention使用Q与所有允许看到的K计算权重，再加权汇总V。经过Attention、残差、归一化和FFN后，结果进入下一层。

对输入Prompt而言，每一层产生的K和V都会保存下来，这些保存结果就是KV Cache的一部分。

#### 为什么要在Prefill保存KV Cache

生成第一个输出Token“建议”后，下一步还要让新Token关注原来的12个输入Token。如果不缓存，就要重新计算原Prompt在所有层中的K和V。

```text
不使用缓存：
第1步重新计算12个历史Token
第2步重新计算13个历史Token
第3步重新计算14个历史Token……

使用KV Cache：
Prefill一次算好12个输入Token的K/V
之后每步只计算新Token的K/V，并复用历史缓存
```

因此，KV Cache减少的是重复计算，代价是占用显存。

#### Prefill为什么常说是“计算密集”

Prefill一次处理多个Token，可以形成较大的矩阵乘法，GPU并行单元容易被充分使用。输入越长，需要完成的Attention和线性层计算越多。

“计算密集”是常见倾向，不是所有硬件和模型上的绝对结论。短Prompt、CPU tokenizer慢、数据搬运或不合适的kernel也可能成为瓶颈。

#### Prefill直接影响什么指标

用户必须等Prefill完成，模型才能生成第一个输出Token。因此它直接影响TTFT：

```text
TTFT = 排队时间 + 请求预处理 + Tokenization + Prefill + 首Token返回开销
```

输入从500 Token增加到20,000 Token时，即使最终只回答一句话，首Token也可能明显变慢。

### 3.2 Decode是什么

一句话定义：**Decode是在已有Prompt和历史输出的基础上，每次生成一个新Token的阶段。**

第1步生成“建议”后，第2步必须把“建议”也作为历史，才能预测“携带”。因此不同Decode step之间存在真实的数据依赖：

```text
step 1的输出 → step 2的输入
step 2的输出 → step 3的输入
```

这就是为什么一条回答的5个Token不能像Prefill的12个输入位置那样一次全部确定。模型事先不知道第1步会选择哪个Token。

#### Decode step 1具体做什么

Prefill结束时，模型已经根据12个输入Token得到下一Token的Logits。经过temperature、top-p等采样规则，选择“建议”。

```text
历史：12个Prompt Token
输出：建议
```

#### Decode step 2具体做什么

把“建议”的Token ID输入模型。对于每一层：

1. 只计算“建议”这个新Token的Q、K、V；
2. 把新Q与缓存中的历史K做Attention；
3. 汇总历史V，得到新隐藏状态；
4. 把“建议”的K/V追加到Cache；
5. 输出词表Logits并选出“携带”。

历史Cache从12个Token增长到13个Token。

#### 后续步骤

```text
step 3输入“携带” → 输出“雨伞” → Cache长度14
step 4输入“雨伞” → 输出“。”   → Cache长度15
step 5输入“。”   → 输出EOS      → 请求结束
```

从用户感受看，这些Token可以通过SSE陆续出现在页面上。

#### Decode为什么常受内存带宽影响

单个请求每一步只处理一个新Token，矩阵乘法不像Prefill那样容易形成大批量计算，但每一步仍要读取大量模型权重和历史KV。此时GPU计算单元可能没有完全吃满，数据搬运速度成为重要限制。

将多个用户当前需要生成的Token组成batch，可以让一次计算同时服务更多请求：

```text
请求A正在生成第20个Token
请求B正在生成第3个Token
请求C正在生成第51个Token

调度器把A、B、C当前这一步放入同一个Decode batch
```

这就是连续批处理提高总吞吐的核心直觉之一。

#### Decode直接影响什么指标

常用指标是TPOT或ITL：

```text
TPOT：平均生成一个输出Token需要多长时间
ITL：用户连续看到两个Token之间的间隔
```

输出越长，Decode step越多，端到端时间通常越长。即使TTFT只有300毫秒，生成2000个Token仍可能持续很久。

### 3.3 Prefill与Decode的区别表

| 对比 | Prefill | Decode |
|---|---|---|
| 处理对象 | 整段输入Prompt | 每次一个新输出Token |
| 并行性 | 输入位置可并行矩阵计算 | 不同生成步之间串行依赖 |
| Cache | 创建输入Token的每层K/V | 读取历史Cache并追加新K/V |
| 常见瓶颈 | 计算量、长输入、排队 | 权重/KV读取、调度、输出长度 |
| 用户指标 | 主要影响TTFT | 主要影响TPOT/ITL和总生成时间 |
| 优化方向 | Chunked Prefill、Prefix Cache | Continuous Batching、量化、投机解码等 |

### 3.4 用餐厅做有限类比

可以把Prefill想成厨师先读取整张复杂订单并完成所有准备工作，把Decode想成菜品按依赖逐道出餐。

这个类比只帮助区分阶段，不能延伸为技术结论。模型的“准备工作”实际上是张量计算和KV Cache，不是真有一个人工计划；Token之间的依赖也由自回归概率模型决定。

### 3.5 三种典型工作负载怎样判断瓶颈

**场景A：短输入、长输出**

```text
输入100 Token，输出2000 Token
```

Prefill很短，大部分时间在Decode。Prefix Cache收益有限，降低TPOT和控制输出长度更重要。

**场景B：长输入、短输出**

```text
输入30,000 Token合同，输出100 Token摘要结论
```

Prefill和TTFT可能主导。共享前缀缓存、Chunked Prefill、减少无效上下文会更重要。

**场景C：大量并发对话**

```text
100个用户，各自输入与输出长度不同
```

排队、KV Cache容量和调度开始主导。单请求速度快不代表并发P95好，需要连续批处理和真实到达率压测。

### 3.6 为什么不能只看“tokens/s”

`tokens/s`至少可能指三种不同口径：

1. 单请求输出速度：一个用户每秒看到多少新Token；
2. 服务器聚合输出吞吐：所有并发请求每秒总共生成多少Token；
3. 输入加输出处理吞吐：把Prefill Token也计入总量。

举例：服务器同时服务20个用户，每个用户约20 output tokens/s，则聚合吞吐可能接近400 tokens/s。宣传“400 tokens/s”不等于单个用户能以400 tokens/s阅读回答。

一份可信报告必须同时写清输入长度、输出长度、并发、请求到达率、TTFT、TPOT、P95/P99和错误率。

## 4. P0：KV Cache 与 PagedAttention

### 4.1 KV Cache 的价值和成本

缓存历史 K/V 避免每步重复计算，但其显存近似随：

```text
层数 × KV heads × head_dim × 2(K+V)
× token 数 × 并发 × dtype bytes
```

增长。这里乘 2 是因为同时保存 K 和 V，最后还要乘每个元素占用的字节数。

例如某模型有 32 层、8 个 KV heads、每头 128 维，使用 BF16（2 bytes），单个 token 的 KV Cache 粗略为：

```text
32 × 8 × 128 × 2(K/V) × 2 bytes = 131,072 bytes ≈ 128 KiB
```

若一个请求已有 8,000 token，缓存约为 1 GiB；同时保留 20 个类似请求，就可能接近 20 GiB。这里还没算模型权重、临时张量和显存碎片，所以“权重能放下”不等于“高并发能跑”。GQA/MQA 通过减少 KV heads，直接降低公式中的这一项。

### 4.2 连续显存分配的问题

假设每个请求最多生成 2,048 token。传统方式可能在请求开始时就为它预留完整连续空间，但很多请求实际只生成 100 token，其余空间一直空着，这是**内部浪费**。

请求又会在不同时间结束：

```text
显存：[A占用][B占用][C占用][D占用]
B、D结束后：[A占用][空洞][C占用][空洞]
```

空闲总量也许够放一个新请求 E，但如果 E 要求一块更大的连续区域，两个分散空洞无法直接合并，这叫**外部碎片**。在线服务的请求长度和生命周期高度动态，预留连续大块显存会限制可用并发。

### 4.3 PagedAttention

PagedAttention 将 KV Cache 划分为固定大小 block。假设每个 block 容纳 16 个 token，一个已经有 35 个 token 的请求只需 3 个 block，最后一块有少量未用位置，而不必一开始就预留 2,048 token。

```text
请求A逻辑块：A0 → A1 → A2
实际物理块： 7 → 21 → 4

请求B逻辑块：B0 → B1
实际物理块： 9 → 13
```

物理块不必连续，block table 负责把请求的逻辑 token 位置映射到显存块。Decode 新增 token 时，当前块满了才再申请一个；请求结束后，它占用的块可立即放回空闲池。

这种管理方式带来：按需分配、降低大块预留浪费、减少外部碎片、方便抢占/恢复，还能在某些共享前缀场景复用只读块。Attention kernel 读取历史 K/V 时会依据 block table 找到位置，数学上的注意力关系并没有改变。

## 5. P0：Static Batching 与 Continuous Batching

### 5.1 Static Batching

Static batching 会先固定一批请求，再让整批一起执行。例如 A、B、C 分别要生成 20、100、200 个 token。如果实现要求整批保留到最长请求完成，那么 A 在第 20 步结束后，它原来的 batch 槽位可能在后面 180 步里空着；此时新请求 D 即使到了，也不能立即加入。

离线批量处理的数据长度可预先整理，static batching 仍然简单有效；在线流量到达时间随机、输出长度未知，固定批次便容易出现等待和空槽。

### 5.2 Continuous/In-flight Batching

在生成步骤之间动态加入新请求、移除已完成请求：

```text
step 1: A B C
step 2: A B C
C 完成
step 3: A B D
B 完成
step 4: A D E
```

每个 Decode step 结束后，调度器重新检查请求状态：完成的移出、等待的新请求加入、暂停请求按资源情况恢复。这样 GPU 当前 batch 能持续装入有用工作。

继续上例，C 完成后 D 立刻占据空位：

```text
step 1:  A1 B1 C1
step 2:  A2 B2 C2
C结束，新请求D到达
step 3:  A3 B3 D1
```

注意，连续批处理不是“一个请求内部一次生成多个未知 token”。每个请求的自回归步仍然串行，只是把不同请求当前要算的那个 token 合并成矩阵计算。

它提高聚合吞吐，但调度器还要处理：

- token budget；
- 长短请求公平性；
- prefill 与 decode 竞争；
- KV Cache 容量；
- 请求优先级与超时；
- 抢占和回收策略。

### 5.3 Chunked Prefill

假设请求 L 有 32,000 token 的长 prompt，另外 20 个聊天请求正在 Decode。如果 L 的 Prefill 一次占用很大的 token budget，已有用户可能很久看不到下一个 token，ITL 突然恶化。

Chunked Prefill 可以把 L 拆成若干段：

```text
调度轮1：L 的前 4K 输入 + 一批 Decode token
调度轮2：L 的下 4K 输入 + 一批 Decode token
...
调度轮8：L 的最后 4K + 一批 Decode token
```

这样长输入不会一次独占 GPU，但 L 自己的 Prefill 完成时间可能变长。因此 chunk 大小和 token budget 是吞吐、长请求 TTFT、已有请求 TPOT 之间的折中，而不是越小越好。

当前 vLLM V1 使用统一 token budget 调度 prefill 与输出 token，并支持 chunked prefill、prefix caching 和 speculative decoding。具体参数和能力以当前版本为准。

## 8. P1：Prefix Cache、Prompt Cache 与语义缓存

### 8.1 Prefix/KV Cache 复用

多个请求共享完全相同的 token 前缀时，可以复用该前缀的 KV：

```text
[相同 system prompt + 相同长文档] + 问题 A
[相同 system prompt + 相同长文档] + 问题 B
```

收益主要发生在 prefill，不会加速很长的 decode。当前 vLLM Automatic Prefix Caching 官方文档也明确指出：没有共享前缀或输出占主要时间时收益有限。

### 8.2 为什么“文本看起来相同”仍可能未命中

Prefix Cache 比较的不是人眼理解的语义，而是模型实际收到的 token 前缀及相关执行条件。下面两段看起来意思一样，但一个多了换行或空格，Tokenizer 后的 id 序列就可能不同：

```text
系统：你是客服。\n用户：查询订单
系统：你是客服。 用户：查询订单
```

此外，Chat Template 插入的 special token、system prompt 中动态时间戳、tokenizer revision、LoRA adapter 或模型版本不同，都可能让缓存键不同。即使 token 完全一致，缓存也可能因容量淘汰而消失，或者请求被负载均衡到另一个不共享缓存的副本。

排查时不要只打印原始字符串，应记录模板渲染结果的 token id 哈希、模型/adapter 版本、路由实例和缓存命中原因。为了命中而删除用户身份、权限或版本字段可能造成错误复用，正确性和租户隔离优先于命中率。

### 8.3 语义缓存不是 KV Cache

语义缓存把当前问题做 Embedding，若与历史问题足够相似，就直接复用历史答案。例如“杭州今天会下雨吗”和“今天杭州有雨吗”字符串不同，却可能被判定语义相近。

风险在于“相似”不等于“答案相同”。“订单 A102 状态”和“订单 A103 状态”语义很近，但不能共享答案；“今天价格”昨天缓存的结果也可能过期。因此缓存键/过滤至少要包含租户、业务实体、数据版本和时间语义，并设置 TTL、置信阈值与不可缓存任务清单。

KV Prefix Cache 复用的是相同 token 前缀已经算出的 K/V 中间状态，命中后模型通常仍继续生成新答案；语义缓存则可能跳过模型直接返回历史业务答案。前者主要是数值计算复用，后者涉及业务正确性和陈旧数据治理。

## 9. P1：量化

### 9.1 量化对象

量化的目标是用更少 bit 表示原本的浮点数。例如 BF16 权重每个参数占 2 bytes，INT4 理论上每个只占半个 byte。一个 7B 参数模型仅按权重粗算，BF16 约 14 GB，4-bit 约 3.5 GB，实际还要加量化 scale、运行 buffer 和 KV Cache。

但推理里至少有三类数值，量化对象不同，效果也不同：

- **Weight-only**：如 W8A16、W4A16，只压缩长期存放和读取的权重，激活仍用 16-bit；常用于降低模型权重显存和带宽；
- **Weight + Activation**：权重与中间激活都降低精度，理论加速空间更大，但异常值、校准和硬件 kernel 要求更高；
- **KV Cache quantization**：权重不一定变化，单独压缩历史 K/V，特别影响长上下文和高并发容量。

量化还要决定共享 scale 的粒度。`per-tensor` 给整个张量一个 scale，实现简单但误差大；`per-channel` 每个输出通道一个 scale，更能适应不同数值范围；`per-group` 把若干权重分组，是压缩元数据与控制误差的折中。

### 9.2 常见方法

- INT8/FP8：比 4-bit 保留更多数值信息，硬件原生支持良好时容易兼顾质量和速度；
- GPTQ：训练完成后再做权重量化，利用少量校准数据逐层减少量化误差；
- AWQ：观察校准激活，保护对输出特别重要的权重通道，再对其余权重压缩；
- GGUF K-quants：llama.cpp 本地/边缘生态常见，不同量化档位在文件大小、速度和质量间取舍；
- FP4/INT4：显存更低，但数值等级更少，质量和 kernel 兼容性更敏感。

“需要校准”不等于重新训练整个模型。通常准备一小批能代表真实输入分布的文本，让算法观察激活范围或近似误差。若只用英文短句校准，却部署中文长文本和 JSON 工具调用，量化后的真实任务退化可能被低估。

### 9.3 量化的正确评测

不能只比较模型文件大小。至少比较：

- 峰值显存；
- 单请求 TTFT/TPOT；
- 并发吞吐；
- 任务指标、长文本、结构化输出、工具调用；
- 不同输入长度；
- 加载时间和兼容性。

例如 BF16 与 AWQ-4bit 对比时，必须使用同一模型 revision、同一 prompt 集、同一采样参数和并发阶梯。除了通用问答，还要单独测试工具名、JSON 数字、代码、长上下文等对微小概率变化敏感的切片。

某些通用动态量化能省显存却更慢：GPU 可能缺少对应低精度矩阵乘 kernel，每次计算还需反量化；在 batch 很小时，额外转换开销甚至超过节省的数据搬运。结论应写成“在某硬件与某工作负载下，显存从 X 降到 Y、吞吐从 A 变到 B、任务指标变化 C”，而不是“4-bit 一定快四倍”。

## 10. P1：并行策略

### 10.1 Data Parallel/Replica

每张 GPU 各放一份完整模型，前面的路由器把不同请求分给不同副本：

```text
请求A、C → GPU0 完整模型
请求B、D → GPU1 完整模型
```

单个请求只在一张卡上执行，不需要逐层跨卡通信。它适合模型单卡放得下、目标是提高总请求吞吐和可用性的场景。代价是每张卡都重复保存权重，某个副本的 prefix/KV cache 通常也不能直接被另一个副本使用。

### 10.2 Tensor Parallel

Tensor Parallel 把同一层的大矩阵沿行或列切到多张 GPU。一个请求进入该层时，每张卡计算自己的部分，然后通过 All-Reduce/All-Gather 等通信合并结果：

```text
同一个请求
   ├─ GPU0：计算矩阵左半部分
   └─ GPU1：计算矩阵右半部分
             ↓ 通信合并
          进入下一层
```

它用于模型单卡放不下，或希望用多卡共同加速一个大 batch。由于几乎每层都可能通信，NVLink/NVSwitch 与跨节点网络的差异非常关键。两张卡的 TP 不等于延迟必然减半；batch 小或互联慢时，通信开销会抵消计算收益。

### 10.3 Pipeline Parallel

Pipeline Parallel 按层切分，例如 40 层模型：GPU0 放 1～20 层，GPU1 放 21～40 层。数据先跑完前半，再把中间激活传给后半。

如果只有一个很小请求，GPU1 等 GPU0 时会空闲；GPU0 把结果交出后又可能等待下一批，这些空档叫 pipeline bubble。把 batch 切成多个 micro-batch 可以让不同阶段重叠，但在线 Decode 的序列依赖和小步计算会让调度更复杂。因此 PP 常用于模型过大或跨节点放置，并与 TP/DP 组合。

### 10.4 Expert Parallel

MoE 模型每层有多个专家，但每个 token 只激活 top-k 个。Expert Parallel 把专家分散到不同 GPU，路由器选中专家后，token 表示需要通过 All-to-All 发送到对应设备，计算后再发回。

如果大量 token 都被路由到同一个专家，那张 GPU 会成为热点，其他卡却空闲；若 token 在设备间频繁搬运，通信也可能主导延迟。因此 EP 不只是“把专家平均放开”，还要监控每个专家收到的 token 数、路由平衡损失和互联带宽。

### 10.5 如何选

```text
单卡放得下：先单卡调优 → 多副本扩吞吐
单卡放不下：TP/PP/量化
MoE：考虑 EP + TP/DP
多节点：先确认网络拓扑、通信库与故障域
```

增加 GPU 不保证延迟线性下降，通信可能成为瓶颈。

## 11. P1/P2：FlashAttention、Speculative Decoding 与 PD 分离

### 11.1 FlashAttention

普通实现容易把完整的 `seq × seq` 注意力分数写入显存，再读回来做 softmax 和加权。序列为 16K 时，中间矩阵非常大。FlashAttention 将 Q/K/V 分块送入更快的片上存储，在块内完成计算并维护必要的归一化统计，避免完整保存大矩阵。

它改变的是计算和数据搬运顺序，仍然得到精确 attention，不是把远处 token 随机丢掉的稀疏近似。是否加速取决于序列长度、硬件、dtype、head dimension、mask 形式和 kernel 支持；短序列或不支持的结构下收益可能很小。

### 11.2 Speculative Decoding

由小 draft 模型或其他方法一次提出多个候选 token，大模型并行验证：

```text
draft 提议: t1 t2 t3 t4
target 验证: 接受前缀，遇到不一致后回退
```

假设小 draft 模型快速猜出 `[今天, 天气, 很好, 。]`。大 target 模型不是逐个重新生成，而是用一次更并行的计算检查这串候选。若前 3 个符合 target 分布、第 4 个不接受，则一次可能推进多个 token，再从不一致位置继续。

目标是在不改变 target 模型目标分布的前提下，减少昂贵 target Decode 的串行步数。真正收益取决于：

- 接受率：draft 经常猜错就无法推进；
- draft 成本：草稿模型也会占 GPU 和时间；
- 输出类型：代码、固定格式等可预测序列可能更适合；
- batch/并发：高并发本身已让大模型 Decode 很饱和，额外验证不一定更划算。

所以评测必须同时报告接受长度、target 调用次数、单请求 TPOT 与聚合吞吐。

### 11.3 Prefill-Decode Disaggregation

单体服务中，同一组 GPU 同时承接长 Prompt Prefill 和持续 Decode。长 Prefill 可能干扰已有对话的 token 输出，而 Decode 的容量规划方式又与 Prefill 不同。

PD 分离把两阶段放进独立资源池：

```text
请求 → Prefill GPU 池 → 生成输入 KV Cache
                    ↓ 通过高速网络传输 KV
                 Decode GPU 池 → 逐 token 输出
```

这样可以分别扩容，例如文档摘要业务增加更多 Prefill 资源，对话长输出增加更多 Decode 资源，也能隔离超长 prompt。但 KV Cache 体积可能达到数百 MB 甚至 GB，传输慢会吃掉计算收益；还要解决目标 Decode 实例选择、KV 版本/布局兼容、传输失败重试以及 Prefill 完成但 Decode 无容量等问题。

这是大规模场景的高级优化，单机项目不要过早引入。

## 12. P0：性能指标

### 12.1 用户体验指标

- TTFT：请求发出到第一个 token，包含网络、排队、预处理与 Prefill；
- TPOT：输出阶段平均每个新增 token 的时间，常近似为 `(完成时间-首token时间)/(输出token数-1)`；
- ITL：每两个相邻 token 的实际间隔，可以暴露偶发卡顿，平均 TPOT 可能掩盖它；
- E2E latency：从请求发出到完整响应结束；
- P50/P95/P99：分别表示 50%、95%、99% 请求不超过该延迟；
- timeout/error/cancel rate：慢请求是否最终超时、报错或被用户取消。

例如 100 个请求的 P95 TTFT 为 2 秒，意思是约 95 个请求首 token 在 2 秒内到达，最慢的约 5 个可能更久；它不是“平均首 token 2 秒”。线上体验常由尾延迟决定，所以不能只报告平均值。

### 12.2 容量指标

- request throughput：requests/s；
- input/output tokens/s；
- active/running/waiting requests；
- queue time；
- batch size/token 数；
- KV Cache usage/hit rate；
- GPU utilization、显存、功耗；
- 每百万 token 成本。

### 12.3 好指标需要切片

至少按以下维度分组：

- 输入长度桶；
- 输出长度桶；
- 模型/adapter；
- 是否命中 prefix cache；
- 并发/请求速率；
- 租户和优先级；
- 成功、超时、取消。

整体平均值可能掩盖长请求 P99 和特定租户问题。

## 13. P0：怎样做可信压测

### 13.1 离线 benchmark 与在线 serving benchmark

**离线 benchmark** 通常把一批请求尽快塞给引擎，不模拟用户何时到达，目标是让 GPU 饱和并测最大聚合吞吐。它回答“机器全力跑，一秒最多处理多少 token”。

**在线 serving benchmark** 会按指定到达率发请求。例如平均每秒 5、10、20 个请求，并保留真实长度分布。它回答“真实用户到达时，排队和尾延迟是否还能满足 SLO”。

假设离线最大吞吐为 2,000 tokens/s，并不能直接承诺线上每秒 2,000 token。接近极限时，哪怕平均服务率勉强够，长度波动也会让队列快速累积，P95 TTFT 和超时率先恶化。

不能用离线最大吞吐直接承诺线上并发。

### 13.2 固定变量

报告必须写：

- 模型与 revision、dtype/量化；
- GPU 型号、数量、互联、驱动；
- 引擎/容器版本和启动参数；
- 输入/输出长度分布；
- 请求数、并发或 arrival rate；
- warmup；
- streaming 与否；
- prefix cache 命中情况；
- 采样参数；
- 客户端机器与网络。

### 13.3 压测阶梯

```text
并发 1：单请求基线
并发 2/4/8/...：观察吞吐增长
接近饱和：queue 开始增长
超过容量：P95/P99 和超时急剧恶化
```

每一档都要持续足够时间进入稳定状态，而不是只发几秒。记录表可以这样设计：

| 到达率 | P95 TTFT | P95 TPOT | 错误率 | 队列趋势 | 是否满足 SLO |
|---:|---:|---:|---:|---|---|
| 2 req/s | 0.5s | 45ms | 0% | 稳定接近 0 | 是 |
| 5 req/s | 0.9s | 52ms | 0% | 稳定 | 是 |
| 8 req/s | 2.8s | 75ms | 0.5% | 持续增长 | 否 |

即使 8 req/s 测试期间服务还没崩，它的队列持续增长也说明到达率大于稳定服务能力。容量边界应取 SLO 仍满足且队列不发散的最大稳定吞吐，再留出流量波动和故障副本的余量，而不是系统完全压垮前的瞬时峰值。

### 13.4 工作负载要真实

Agent 请求常包含长 system prompt、工具 schema、多轮历史，输出可能较短；总结任务则长输入长输出。用固定 128 输入/128 输出测出的结论未必可迁移。

当前 vLLM 提供 `vllm bench serve` 等基准工具；仍要确保数据和参数符合真实业务。

## 14. P0/P1：生产服务架构

```text
Client
  ↓
API Gateway / WAF
  ↓ 鉴权、限流、配额、请求大小校验
Model Router
  ↓ 模型/版本/adapter/优先级路由
Inference Replicas
  ↓
GPU metrics + traces + logs
```

### 14.1 网关层

- API key/JWT/mTLS；
- 每租户并发、RPM/TPM、token 预算；
- 最大输入/输出长度；
- 请求超时和取消传播；
- SSE 透传；
- 审计和敏感字段脱敏。

网关位于公网客户端与模型服务之间。一次请求先验证 API key/JWT 对应哪个租户，再检查该租户还剩多少 RPM、TPM 与并发配额；随后限制最大输入和 `max_tokens`，避免一个请求占满 KV Cache。只有通过这些确定性检查后，才把请求转给内部模型路由。

流式响应时网关不能把 SSE 全部缓冲到结束，还要在客户端断开后向下游传播取消。审计记录应保存 request id、租户、模型、token 与结果状态，而不是默认明文保存完整 Prompt。

### 14.2 模型路由

- 按模型能力、成本和健康状态选择实例；
- sticky routing 可提升会话 prefix cache 命中，但会造成负载不均；
- 多 LoRA 要管理 adapter 生命周期和基座兼容；
- 灰度发布需支持旧/新版本同时在线。

### 14.3 Backpressure

系统过载时应尽早拒绝或排队，而不是无限接收直到全部超时。可使用：

- 有界队列；
- admission control；
- 429/503 与 Retry-After；
- 按租户隔离；
- 降级到小模型或缩短输出，但必须符合业务策略。

### 14.4 健康检查

- liveness：进程是否活着；
- readiness：模型是否加载并能接请求；
- startup：大权重加载期间避免误重启；
- 业务探针：定期发送极小推理检查 tokenizer、模板和 GPU 执行链路。

## 15. P1：容器、Kubernetes 与扩缩容

### 15.1 容器镜像

- 固定基础镜像和依赖；
- 不把模型密钥写入镜像；
- 模型权重可预置、挂载或启动下载，各有启动速度与镜像大小权衡；
- 设置共享内存、锁页和 GPU runtime；
- 以非 root 运行可行部分，限制 capabilities。

### 15.2 Kubernetes 关键点

- GPU resource request/limit；
- nodeSelector/affinity 与 GPU 类型；
- PVC/对象存储/本地 NVMe 权重缓存；
- startup/readiness/liveness probes；
- PodDisruptionBudget；
- 滚动发布时避免同时复制过多权重占满节点；
- 多卡模型需要 gang scheduling 或确保整组资源同时可用。

### 15.3 扩缩容信号

CPU 利用率通常不是 LLM 服务最佳信号。可考虑：

- waiting requests/queue time；
- token throughput；
- KV Cache usage；
- TTFT SLO；
- GPU utilization；
- 预测流量。

模型冷启动可能数分钟，纯反应式扩容会太晚，需要最小副本、预热和预测性扩容。

## 16. 可观测与安全

### 16.1 Metrics

Metrics 用于回答整体趋势，例如“过去 5 分钟 P95 TTFT 是否上升”。至少采集请求率、输入/输出 token、waiting/running 请求、队列时间、Prefill/Decode 耗时、KV 使用率、GPU 显存/利用率、错误率和成本。

指标之间要联看：TTFT 上升且 waiting requests 持续增加，通常指向容量不足；TTFT 上升但队列为空，可能是输入变长、Tokenizer 或 Prefill 变慢；GPU 利用率低但队列很长，则要排查 CPU 预处理、锁或不合适 kernel。vLLM 等引擎提供 Prometheus 端点，但指标名会随版本变化，面板和告警应绑定版本。

### 16.2 Traces

贯通：

```text
Agent 请求 → RAG → 模型网关 → 排队 → prefill/decode → SSE
```

这样才能区分“模型慢”和“检索/网络/队列慢”。

Trace 面向单次请求。可以为 RAG、模型排队、Prefill、每个工具和 SSE 首包建立 Span，并使用同一 trace id 串联。若某次请求总耗时 12 秒，Trace 可能显示 RAG 0.4 秒、排队 8 秒、Prefill 1 秒、Decode 2.6 秒，于是优化重点应是容量与调度，而不是更换 Embedding。

Trace 属性应记录模型版本、输入长度、输出长度、缓存命中和错误码，但敏感 Prompt 只在授权、脱敏和采样策略允许时保存。

### 16.3 日志

Log 记录离散事件，例如“模型加载完成”“请求因配额被拒绝”“GPU OOM”。结构化日志可包含时间、level、request/trace id、模型版本、错误码和耗时，便于搜索与关联。

它与 Metrics/Trace 分工不同：Metric 发现整体异常，Trace 还原一次请求的时间线，Log 提供该节点发生了什么事件。三者都不应默认记录完整 Prompt/Response；生产日志至少要做脱敏、采样、访问控制、保留期限和租户隔离。密钥、身份证号和内部文档不能为了调试长期明文保存。

### 16.4 模型服务安全

- 权重与模型仓库来源校验；
- 谨慎使用 `trust_remote_code`；
- 限制输入长度、输出长度、并发和上传文件；
- 管理开发/调试端点；
- 当前 vLLM 文档明确标注部分动态加载、dev mode、collective RPC 等接口不适合生产或高度危险，不能直接暴露公网。

## 18. 常见故障排查

### 18.1 启动即 OOM

- 权重实际 dtype 与预期不同；
- tensor parallel 配置未生效；
- GPU 上已有进程；
- max model length/KV Cache 预留过高；
- 量化模型未被正确识别；
- 架构 fallback 导致优化路径失效。

### 18.2 低并发快，高并发突然变慢

- 到达率超过服务率，queue 累积；
- KV Cache 饱和发生抢占；
- 长 prefill 阻塞 decode；
- 网关连接/SSE 缓冲；
- CPU tokenizer 或网络成为瓶颈；
- 跨卡通信饱和。

### 18.3 GPU 利用率低

- 请求太少或 batch 太小；
- CPU tokenization/数据预处理慢；
- 频繁同步；
- 输出很短；
- 模型/量化 kernel 未优化；
- 单请求 decode 本身并行度低。

### 18.4 输出乱码或停不下来

- tokenizer 不匹配；
- chat template 错；
- EOS/stop token 错；
- 模型不是对应 instruct 版本；
- generation config 覆盖了预期参数。

### 18.5 流式返回被一次性吐出

- 反向代理缓冲；
- 客户端未按流读取；
- 压缩中间件聚合；
- 服务端没有逐块 flush；
- 超时设置导致连接提前终止。

### 18.6 Prefix cache 命中率低

- 动态字段破坏共同前缀；
- 请求路由不稳定；
- cache 太小；
- 前缀不是 token 级完全一致；
- 工作负载本来就没有共享前缀。

## 19. 高频面试题

### 19.1 vLLM 为什么吞吐高？

核心包括高效 KV Cache 管理（PagedAttention）、连续批处理和优化 kernel，并结合调度、prefix caching、chunked prefill、并行与量化等能力。具体收益取决于工作负载。

### 19.2 TTFT 和 TPOT 分别受什么影响？

TTFT 主要受排队、tokenization 和 prefill/输入长度影响；TPOT 主要受 decode、batch 调度、KV 访问、并行通信和输出阶段竞争影响。

### 19.3 为什么并发提高后单请求延迟会增加？

更多请求共享 GPU 和 token budget，虽然总吞吐提高，但每个请求获得执行机会的间隔变大，还可能排队或抢占 KV，因此延迟和吞吐存在权衡。

### 19.4 量化一定加速吗？

不一定。它一定程度上减少存储/带宽，但是否加速取决于硬件原生支持、kernel、反量化、batch、模型结构和并行方式。

### 19.5 Tensor Parallel 和多副本如何选？

模型单卡能放下且目标是总吞吐，优先多副本；模型放不下或单请求需多卡计算时用 TP。TP 引入卡间通信，多副本则消耗完整权重副本。

### 19.6 Prefix cache 和 RAG cache 一样吗？

不是。Prefix cache 复用相同 token 前缀的 KV 计算；RAG/语义缓存复用检索或最终答案，语义和过期风险更高。

### 19.7 如何确定服务最大并发？

在真实输入输出分布下逐步提高到达率/并发，找到 P95/P99、错误率和 TTFT/TPOT 仍满足 SLO 的最大稳定点，并留容量余量。

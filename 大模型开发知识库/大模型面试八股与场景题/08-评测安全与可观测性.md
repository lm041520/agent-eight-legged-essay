# 08 评测、安全与可观测性

> 目标：能够回答“怎么证明系统有效、怎么定位一次失败、怎么防止越权和提示注入”，把模型演示升级为可运营产品。

## 0. 模块地图

```text
定义任务与风险
→ 建立数据集和基线
→ 分层执行
→ 规则/指标/LLM Judge/人工评审
→ 按场景切片
→ Bad Case归因
→ 修复与消融
→ CI门禁、灰度与线上监控
```

可观测性：

```text
Logs：发生了什么离散事件
Metrics：系统整体趋势和告警
Traces：单次请求每一步花了多久、发生了什么
```

优先级：

- ★★★★★：分层评测、测试集、RAG/Agent 指标、LLM Judge 边界、Trace、Prompt Injection、权限；
- ★★★★☆：A/B、消融、Bad Case、灰度回滚、拒答平衡；
- ★★★☆☆：复杂统计显著性、自动红队与大规模评测平台实现。

# 第一部分：常规八股

## 1. 为什么大模型系统必须分层评测？

> 面试优先级：★★★★★｜学习难度：★★★☆☆｜适用岗位：全部  
> 掌握要求：能把最终错误定位到组件

**一句话**：大模型应用由解析、检索、Prompt、模型、工具和服务多个环节组成，端到端分数只能告诉你结果好坏，分层评测才能把错误定位到具体组件，并验证某个改动是否真正有效。

端到端答案错误可能出现在链路的任意一环：

```text
输入解析
→ Query理解
→ 检索/工具选择
→ 参数与权限
→ 工具执行
→ Context组装
→ 模型生成
→ 引用/后处理
```

只看最终答案，修复时就不知道该换 Chunk、Embedding、Prompt、工具还是模型。给每层配独立证据，Bad Case 才能归因，也才能用消融证明某个改动的真实贡献。

分层示例：

| 层 | RAG 指标 | Agent 指标 |
|---|---|---|
| 输入 | OCR/解析准确率 | 意图/槽位准确率 |
| 中间决策 | Recall@K、NDCG | 工具选择、参数准确率 |
| 执行 | Rerank/Context覆盖 | 工具成功、重试、权限 |
| 最终结果 | 正确性、忠实度、引用 | 任务成功、环境状态 |
| 系统 | 延迟、成本、错误率 | 步骤、Token、人工介入 |

**面试怎么说**

> 大模型系统是多组件链路，最终错误不一定由模型导致。我会同时评输入、检索/决策、工具执行、最终输出和系统性能。比如 RAG 先测金标准证据是否在 Top-K，再测答案是否忠实；Agent 则验证工具调用和外部业务状态。分层评测让 Bad Case 可以归因，也能通过消融证明某个改动的真实贡献。

## 2. Accuracy、Precision、Recall、F1、MRR、NDCG 怎么理解？

> 面试优先级：★★★★★｜学习难度：★★★★☆｜适用岗位：全部  
> 掌握要求：会用小例子解释，不混淆分类和排序

### 先理解

Accuracy、Precision、Recall 和 F1 主要衡量分类结果；MRR 和 NDCG 衡量相关结果在排序中的位置与质量。先明确任务是分类还是检索排序，再选择指标。

不同指标回答的是不同问题，不能只挑一个最好看的数。垃圾邮件误杀时更关注 Precision，疾病筛查漏诊时更关注 Recall；检索系统不只关心正确文档是否出现，还关心它排在第几位，因此需要 MRR 或 NDCG。

### 原理与应用

#### 分类指标

```text
Precision = TP / (TP + FP)
Recall    = TP / (TP + FN)
F1        = 2PR / (P + R)
Accuracy  = 正确样本 / 全部样本
```

垃圾检测中，Precision 高表示判为垃圾的邮件大多真是垃圾；Recall 高表示真实垃圾大多被找出。类别极不均衡时 Accuracy 可能误导。

#### 排序/检索指标

- Recall@K：相关证据是否进入前 K；
- Precision@K：前 K 中相关比例；
- MRR：第一个相关结果排名倒数的平均；
- NDCG：考虑相关性等级和排名位置的折损累计增益。

### 面试准备

**推荐回答**

> Precision 关注预测为正的结果有多可靠，Recall 关注真实正例找回多少，F1 是二者调和平均。检索还要考虑排名，Recall@K 看证据是否进入候选，MRR 强调第一个相关结果是否靠前，NDCG 能处理多级相关性。指标选择取决于业务代价，例如高风险漏检更重 Recall，误告成本高则更重 Precision。

## 3. RAG 应该如何分层评测？

> 面试优先级：★★★★★｜学习难度：★★★★☆｜适用岗位：RAG、应用、评测  
> 掌握要求：能标注证据而不只有答案

### 先理解

RAG 的最终答案错误，可能来自文档解析错、切分丢信息、检索没召回、重排选错，或模型没有忠实使用证据。只给最终答案打分无法定位根因，所以必须把解析、检索、生成、引用和系统性能分开测量。

### 原理与应用

#### 数据标注

每题至少包含：

```json
{
  "question": "超过200元打车如何报销？",
  "answerable": true,
  "gold_document_ids": ["policy-2026"],
  "gold_chunk_ids": ["article-18"],
  "reference_answer": "补充行程说明并审批……",
  "tags": ["direct_fact", "policy", "amount"]
}
```

关键是标注金标准证据 ID，而不只有参考答案，否则无法区分“召回没找到”和“找到没用好”。

#### 四层指标

1. 解析：OCR、阅读顺序、表格结构；
2. 检索：Recall@K、MRR、NDCG、延迟；
3. 生成：正确、相关、忠实、引用、拒答；
4. 系统：TTFT、P95/P99、错误率、Token 和成本。

#### 关键切片

直接事实、多跳、同义改写、编号、表格、OCR、版本、无答案、权限、长问题。

### 面试准备

**推荐回答**

> RAG 测试集必须标注金标准证据 ID，而不只有参考答案。解析层测文本和结构，检索层测 Recall@K/MRR/NDCG，生成层测正确性、忠实度、引用和拒答，系统层测延迟与成本。优化时保持其他组件固定做消融，并按文档类型和问题类型切片，避免平均分掩盖关键场景。

## 4. Agent 应该如何评测？

> 面试优先级：★★★★★｜学习难度：★★★★☆｜适用岗位：Agent、应用平台  
> 掌握要求：能以环境状态判定成功

### 先理解

Agent 不只是生成一段文字，还会选择工具、规划步骤、修改状态并产生副作用。最终任务偶然成功并不能证明过程可靠；需要同时评估任务成功率、工具选择和参数、步骤效率、恢复能力、成本以及危险动作是否被拦截。

### 原理与应用

#### 任务结果

模型说“预订成功”不算成功，测试环境中的订单状态正确才算。

#### 轨迹和工具

- 工具选择准确率；
- 参数/Schema 正确率；
- 权限违规率；
- 平均步骤、无效调用和循环率；
- 超时、重试、部分成功；
- 幂等和重复副作用。

#### 系统

E2E 延迟、Token、费用、工具成本、人工介入率、取消率和恢复成功率。

#### 环境要求

测试工具可重置、可记录、可注入失败。否则无法稳定复现支付超时、API 限流和重启恢复。

### 面试准备

**推荐回答**

> Agent 不能只用文本相似度评测。我会用外部环境状态判断任务是否真实完成，轨迹层检查工具选择、参数、步骤和循环，安全层检查越权和副作用，系统层检查延迟、Token、成本和人工介入。测试工具要可重置并能注入超时、429、部分失败等故障，才能做稳定回归。

## 5. 规则、人工评测和 LLM-as-a-Judge 如何选择？

> 面试优先级：★★★★★｜学习难度：★★★★☆｜适用岗位：评测、算法、应用  
> 掌握要求：能按可确定性选择评估器

### 先理解

能确定性判断的格式、数值和引用应优先用规则；人工评测最接近业务判断但成本高；LLM Judge 适合规模化评估开放文本。规则便宜稳定但覆盖有限，人工可信却昂贵，LLM Judge 可扩展但有偏差；可靠系统通常按题型组合三者并相互校准，而不是选一个方法包办全部。

### 原理与应用

#### 规则优先

格式、JSON Schema、工具参数、引用 ID、SQL 执行结果、单元测试等可确定检查，优先使用代码，便宜且可复现。

#### LLM Judge

适合开放表达的相关性、完整性、风格和部分忠实度。需要明确 Rubric、提供证据、限制输出格式并校准偏差。

#### 人工评测

适合高风险、主观质量、Judge 争议和新型 Bad Case；成本高且需评审指南、一致性检查和盲评。

#### 组合

```text
规则过滤硬错误
→ LLM Judge规模化软评估
→ 人工抽检、仲裁和校准
```

### 面试准备

**推荐回答**

> 可确定的问题优先规则，例如 JSON、引用和工具结果；开放语义用 LLM Judge，但要给 Rubric、证据和结构化输出；高风险和争议样本由人工盲评。三者组合比把所有问题交给一个大模型裁判更可靠，也更容易控制成本。

## 6. LLM Judge 有哪些偏差，如何校准？

> 面试优先级：★★★★☆｜学习难度：★★★★☆｜适用岗位：评测、算法  
> 掌握要求：能识别位置、长度、风格和自我偏好

**一句话**：LLM Judge 也是模型，会偏爱长答案、特定位置、自己的风格或表面流畅度，还可能被候选里的注入文本影响。例如内容相同的答案只因更长或排在 A 位置就得分更高，会让结论失真，校准要靠盲化换序、长度控制、明确 Rubric、人工对照和多裁判一致性。

**常见偏差**

- Position Bias：偏好放在 A/B 某一位置；
- Verbosity Bias：偏爱更长、更像解释的答案；
- Style Bias：格式漂亮掩盖事实错误；
- Self Preference：偏爱相同模型风格；
- Reference Bias：参考答案不唯一却机械比较；
- Prompt Injection：候选答案诱导裁判；
- 不同语言、领域和长度切片稳定性不同。

**怎么校准**

- A/B 顺序交换并汇总；
- Pairwise 与绝对评分结合；
- Rubric 将正确性、忠实度、完整性、风格分开；
- 把证据置于受控区域，候选视为不可信文本；
- 与人工金标准计算一致性；
- 定期抽检高分、低分和模型分歧样本；
- 不让 Judge 成为唯一发布门禁。

**面试怎么说**

> LLM Judge 会有位置、长度、风格和自我偏好，还可能被候选中的注入文本影响。我会使用分维度 Rubric、交换候选顺序、结构化输出，并与人工金标准校准一致性。高风险指标用规则或人工兜底，Judge 只是一种带噪测量工具，不是绝对真值。

## 7. 离线评测、在线评测、A/B 和灰度有什么区别？

> 面试优先级：★★★★☆｜学习难度：★★★☆☆｜适用岗位：应用、评测、平台  
> 掌握要求：能建立离线到线上闭环

**一句话**：四者是产品验证的不同阶段——离线用固定数据判断“是否值得上线”，在线看真实使用效果，A/B 用随机分流比较两个版本，灰度用小流量控制发布风险。它们是一条连续验证链路，而非相互替代。

- **离线**：固定数据、可重复、适合快速比较和 CI 门禁，但不能完整代表真实流量和用户行为。
- **在线**：观察真实用户满意、任务完成、留存、投诉、延迟和成本，但存在风险、噪声和归因问题。
- **A/B**：随机分流比较两个版本，尽量控制用户、时间和流量差异，需要预先定义主指标、护栏指标和停止规则。
- **灰度**：先给小比例、内部用户或低风险租户上线，监控质量、安全和性能，异常自动或人工回滚。

**面试怎么说**

> 离线评测用于快速、可复现比较和回归，在线评测验证真实业务价值。A/B 通过随机分流估计版本差异，灰度则控制发布风险。上线前我会定义主质量指标与延迟、错误率、成本等护栏，先离线过门禁，再小流量灰度，最后根据线上数据全量或回滚。

## 8. Logs、Metrics、Traces 和 Span 有什么区别？

> 面试优先级：★★★★★｜学习难度：★★★☆☆｜适用岗位：全部生产岗位  
> 掌握要求：能用一次请求举例

**一句话**：Logs 记录离散事件，Metrics 聚合系统趋势，Trace 串联一次请求的完整链路，Span 是链路中的一个步骤；四者结合才能从告警下钻到具体慢请求和根因。

一次回答耗时 12 秒时，只看日志能知道发生了什么，只看指标能知道是否普遍变慢，但都难直接判断时间耗在 RAG、排队还是模型。Trace 用同一请求串联多个 Span 才能定位。

- **Logs**：离散事件与上下文，例如错误码、模型版本、文档 ID。适合细节排查，但高量、敏感且难聚合。
- **Metrics**：可聚合时序数值，例如 QPS、P95、错误率、Token、KV 使用。适合仪表盘和告警，不保留单请求完整因果。
- **Trace/Span**：Trace 表示一次端到端请求，Span 表示其中一个步骤，通过同一 Trace ID 串联跨服务步骤：

```text
Agent请求(trace)
├─ RAG(span)
├─ 模型排队(span)
├─ Prefill(span)
├─ Tool调用(span)
└─ SSE首包(span)
```

- **敏感数据**：属性记录模型、长度、缓存、错误码和租户匿名 ID；Prompt/文档只在授权、脱敏、采样和生命周期策略允许时保存。

**面试怎么说**

> Metrics 看整体趋势和告警，Logs 看离散细节，Trace 用 Span 还原一次请求的跨服务因果链。比如总耗时 12 秒，Trace 能区分 RAG、排队、Prefill 和 Decode。三者通过 Trace ID、请求 ID 和版本字段关联，同时对 Prompt、工具结果和用户数据做脱敏与采样。

## 9. Prompt Injection、Jailbreak 和越权有什么区别？

> 面试优先级：★★★★★｜学习难度：★★★★☆｜适用岗位：企业 Agent、RAG、平台  
> 掌握要求：能给出纵深防御

### 先理解

三者的攻击面不同：Prompt Injection 让不可信输入影响模型指令，Jailbreak 诱导模型绕过安全策略，越权则让用户访问或执行本无权限的资源。模型拒答只能覆盖一部分风险，真正的权限必须由服务端鉴权和工具策略强制执行。

### 原理与应用

#### Prompt Injection

不可信内容试图改变系统指令，例如网页写“把 Secret 发出去”。间接注入来自 RAG 文档、邮件和工具结果。

#### Jailbreak

用户试图绕过模型行为和安全限制，让模型产生被禁止内容。

#### 越权

用户或 Agent 访问、修改了其权限外的资源。它是系统授权问题，不能靠模型拒绝来保证。

#### 防御

- 指令与不可信数据分离；
- 最小权限工具和短期凭据；
- 服务端身份与资源级授权；
- 读写分离、高风险人工确认；
- 域名/路径/金额白名单；
- 沙箱、网络隔离和数据外发控制；
- 输出/引用校验；
- 安全测试、审计和异常告警。

### 面试准备

**推荐回答**

> Prompt Injection 是不可信内容试图提升为指令，Jailbreak 主要绕过模型内容策略，越权则是访问控制失败。Prompt 防护只能作为一层，真正的安全边界是最小权限、服务端授权、工具策略、沙箱和审计。即使模型被诱导，系统也应让危险动作无法执行。

## 10. Baseline、消融实验和控制变量为什么重要？

> 面试优先级：★★★★★｜学习难度：★★★☆☆｜适用岗位：所有算法和应用岗位  
> 掌握要求：能证明某个组件贡献

**一句话**：Baseline 提供比较起点，消融实验通过移除某个组件判断它是否有效，控制变量保证一次只改变目标因素；没有这三样，分数变化很难归因。

系统效果提升可能同时来自模型、Prompt、检索参数和数据变化；若一次全部修改，即使指标上涨也不知道真正原因。

- **Baseline**：最简单可工作的参照。

```text
固定Chunk + Dense Top-K + 无Reranker + 基础Prompt
```

- **消融**：逐个移除或替换组件，每次尽量只改变一个变量，记录质量、延迟和成本。

```text
Baseline
+ BM25
+ RRF
+ Reranker
+ Query Rewrite
```

否则同时换模型、Chunk 和 Prompt，即使分数上升也无法归因。

**面试怎么说**

> Baseline 提供最低可比较起点，消融实验回答每个组件是否真正贡献。实验中固定数据、模型、随机性和工作负载，每次只改变一个因素，并同时报告质量、延迟和成本。若改动只提升平均分但伤害关键安全切片，也不能上线。

# 第二部分：高频场景题

> **本部分共通检查**（每道场景默认适用，下面单题不再重复）：
> - **通用澄清**：任务成功如何定义、哪些错误代价最高？数据来源、标签、证据、分布和污染风险如何？离线/在线/人工/Judge/延迟/成本预算各是多少？线上模型、Prompt、索引和参数是否与离线一致？
> - **通用取舍**：在评测覆盖与成本、自动化与可信度、误答与误拒、质量提升与延迟成本之间平衡，先定义主指标和护栏，再选评测组合。
> - **通用异常与安全**：警惕数据泄漏、Judge 偏差、线上分布漂移、提示注入、越权、日志泄密和指标被优化钻空子；高风险决策保留人工与确定性规则兜底。
> - **通用验证与条件变化**：固定数据、模型、Prompt、索引与代码版本，结合规则、检索指标、盲化 Pairwise、人工校准、置信区间和线上 A/B，并保留 Bad Case；风险提高时收紧安全与人工门禁，流量或成本变化时调整采样，模型和 Prompt 升级后重跑完整回归，线上分布漂移时更新测试集。

## 场景 1：离线评测很好，上线后用户仍不满意，为什么？

> 面试优先级：★★★★★｜学习难度：★★★★☆｜适用岗位：全部  
> 掌握要求：能分析数据分布、指标和产品体验

**判断**：离线分数只对“这份测试集和这些指标”负责。真实用户的问题分布、交互轮数、等待时间和容错要求可能完全不同，离线高分不能直接等同线上满意度。

**先问清楚**

- 是全体用户不满意，还是集中在特定意图/用户/长度？
- 投诉集中在正确性，还是延迟、引用、语气、多轮体验？
- 线上模型、Prompt、索引和参数是否与离线一致？

**怎么排查**

- 离线集太干净、太简单或与真实流量不同；
- 测答案正确却没测延迟、引用、语气和任务完成；
- 测试数据泄漏；
- 线上多轮、拼写、方言和超长输入未覆盖；
- 用户关心少数高价值场景，平均分掩盖；
- 线上版本、Prompt、索引或模型与离线不一致；
- 排队、超时和失败破坏体验。

定位后采样脱敏线上问题，按意图/用户/长度建立切片，把用户反馈映射到可观测根因，补充线上护栏和 A/B，而不是只扩大旧测试集。

**怎么说**

> 我会先确认线上模型、Prompt、索引和参数是否与离线一致，再比较测试集与真实流量的意图、长度和难度分布。离线可能只测正确性，却遗漏延迟、引用、任务完成和多轮体验。之后用脱敏线上样本建立切片，把投诉映射到具体 Trace，并通过灰度或 A/B 验证改动，而不是只继续提高旧测试集平均分。

**别踩 & 追问**

看到线上差就无差别扩大测试集或直接换模型，而不先核对线上线下是否同一套配置，是最常见的错误归因。

## 场景 2：两个模型回答风格不同，如何公平比较？

> 面试优先级：★★★★☆｜学习难度：★★★★☆｜适用岗位：评测、模型选型  
> 掌握要求：能分离事实、任务、风格和成本

**判断**：长、正式或辞藻丰富的回答不一定更正确。公平比较要先固定输入条件，再把事实质量、任务完成、表达风格和系统成本拆开评分，避免主观“看起来更好”主导结论。

**先问清楚**

- 比较目的是选型上线，还是能力摸底？
- 业务更看重事实正确、任务完成，还是表达体验？
- 两模型是否已在同一 Prompt、证据和参数下跑过？

**怎么分析**

- 同一 Prompt、证据、生成约束和随机设置；
- Rubric 分开正确性、忠实度、完整性、简洁和风格；
- 规则先验证事实/格式；
- Pairwise 盲评并交换 A/B 顺序；
- 长度切片，避免长答案天然占优；
- 同时比较延迟、Token 和成本；
- 按业务偏好设置权重，不用一个模糊总分。

**怎么说**

> 我会固定 Prompt、证据、生成约束和参数，把正确性、忠实度、完整性、简洁度和风格拆成独立 Rubric。事实与格式优先用规则验证，开放质量使用盲化 Pairwise 并交换 A/B 顺序，同时做长度分层。最终还要比较延迟和成本，再按业务目标决定权重，而不是用一个模糊总分选模型。

## 场景 3：LLM Judge 总偏爱长答案，怎么办？

> 面试优先级：★★★★☆｜学习难度：★★★☆☆｜适用岗位：评测  
> 掌握要求：能做长度控制和人工校准

**判断**：Judge 可能把更多细节误当成更高覆盖，也可能受训练偏好影响而奖励长文本。如果候选长度与得分高度相关，评测测到的就可能是长度而不是答案质量。

**先问清楚**

- 是所有题型都偏长，还是某些开放题偏长？
- 有没有内容相同、长短不同的对照样本可用？

**怎么办**

- Rubric 明确“冗余不加分”；
- 正确性、覆盖和简洁分别打分；
- 构造内容相同、长度不同的校准对；
- 对候选长度匹配或在统计中分层；
- Pairwise 交换位置；
- 人工抽检长高分和短低分；
- 不把 Judge 单分作为唯一上线标准。

**怎么说**

> 我会先计算答案长度与 Judge 分数的相关性，并构造内容相同、长度不同的校准对。Rubric 明确冗余不加分，把正确性、覆盖和简洁分开；Pairwise 比较时交换位置并按长度分层。长高分和短低分样本需要人工抽检，Judge 结果只能作为多种证据之一。

## 场景 4：RAG Recall@K 提高，最终答案反而下降，为什么？

> 面试优先级：★★★★★｜学习难度：★★★★☆｜适用岗位：RAG、评测  
> 掌握要求：能区分候选覆盖和 Context 质量

**判断**：Recall@K 只关心正确证据是否出现在候选中，不关心同时混入了多少噪声，也不保证正确证据最终进入模型可见的 Context。扩大 K 可能提高覆盖，却让冲突版本和无关文本一起增加。

**先问清楚**

- K 调大了多少？
- 正确证据是进入了最终 Context，还是只停在候选里？
- 重排、去重、父块扩展是否随 K 同步调整过？

**怎么分析**

- 增加 K 带来大量相似但错误版本；
- 相关证据存在但排名靠后或被截断；
- 冲突文档让生成模型混淆；
- Context Token 过多，指令和关键证据被稀释；
- Recall 指标只要求“至少命中一个”，不衡量噪声；
- 重排/去重/父块扩展没有同步调整。

验证时同时看 Precision@K、Context Gold Coverage、噪声比例、最终 Token 和忠实度，并固定金标准证据做生成上限测试。

**怎么说**

> Recall@K 提升只说明候选覆盖更好，不代表给模型的上下文更干净。增加 K 可能引入错误版本、重复和冲突，正确证据也可能在重排后靠后或被截断。我会同时看 Precision、最终 Context 的金证据覆盖与噪声比例，并用固定金标准证据测试生成上限，再判断问题在召回、重排、上下文组装还是生成。

## 场景 5：Agent 工具成功率高，但任务成功率低，为什么？

> 面试优先级：★★★★★｜学习难度：★★★★☆｜适用岗位：Agent  
> 掌握要求：能检查计划、顺序、结果利用和结束判断

**判断**：工具成功只表示一次调用在技术上完成，例如 HTTP 返回 200；任务成功还要求 Agent 选对工具、参数和顺序，正确使用结果，并让外部环境达到最终目标状态。

**先问清楚**

- 失败集中在工具选择、参数、顺序，还是结果没写回？
- 任务成功是否用外部环境状态判定，而不是模型自述？

**怎么分析**

- 调用了正确工具但顺序错误；
- 参数合法但业务对象错误；
- 工具成功结果没有写回或模型没正确使用；
- 只完成子任务，错误宣布整体完成；
- 缺少确认、补偿或最后写操作；
- 环境状态检查不完整。

因此需要轨迹和最终环境状态联合评测，而不是只统计 HTTP 200。

**怎么说**

> 我会把工具调用成功和任务完成分开。HTTP 200 只能证明接口执行，不能证明对象、参数、顺序和最终状态正确。评测需要检查完整轨迹、关键状态转换和结束条件，例如退款任务最终应验证订单状态和退款记录，而不是只看查询、退款接口分别成功。

## 场景 6：问题没有唯一标准答案，如何评测？

> 面试优先级：★★★★☆｜学习难度：★★★★☆｜适用岗位：评测、生成应用  
> 掌握要求：能用 Rubric 和多参考替代 Exact Match

**判断**：开放式生成可能有多种正确表达，逐字匹配会把合理答案判错。此时应把“好答案需要满足什么”拆成可观察条件，并允许多个参考答案或关键事实组合。

**先问清楚**

- 有哪些不可违反的硬约束（事实、安全、格式）？
- 是否能给出多个参考答案或关键事实集合？

**怎么办**

- 将要求拆成事实、覆盖、推理、风格和安全维度；
- 为每维定义可观察 Rubric；
- 使用多个参考答案或关键事实集合；
- Pairwise 比较更容易判断相对优劣；
- 规则检查不可违反的硬约束；
- 人工与 Judge 校准；
- 报告分维度结果和分歧，而不是伪造唯一总真值。

**怎么说**

> 没有唯一答案时，我不会使用 Exact Match 作为主指标，而会把事实正确、覆盖、推理、风格和安全拆成 Rubric，使用多个参考答案或关键事实集合。硬约束由规则检查，开放质量可用盲化 Pairwise、LLM Judge 和人工共同评估，并报告各维度与评审分歧，而不是强行压成一个绝对真值。

## 场景 7：测试集可能进入训练数据，如何识别和处理？

> 面试优先级：★★★★☆｜学习难度：★★★★☆｜适用岗位：训练、评测  
> 掌握要求：能讨论泄漏、近重复和私有留出

**判断**：测试数据一旦进入训练，分数可能反映记忆而不是真实泛化。污染既包括逐字重复，也包括改写、近重复、题目和答案拆开出现，以及同一实体和时间段的信息泄漏，需要用私有留出、时间切分和扰动集共同识别。

**先问清楚**

- 用的是公开基准还是自建集？
- 训练语料来源与基准发布时间、仓库或网页是否重合？
- 有没有未公开的内部 Holdout？

**怎么排查**

- 某些公开基准得分异常高，但换一种问法就明显下降；
- 输出与参考答案存在罕见且高度一致的措辞；
- 在相同能力的新日期、新实体或私有题集上性能骤降；
- 训练语料来源与基准数据发布时间、仓库或网页高度重合。

这些信号只能提示风险，通常不能单独证明某个样本一定被训练过。

**怎么办**

- 训练前对题干、答案、文档做 Exact/MinHash/语义去重；
- 按来源、时间和实体划分，而不只随机拆行；
- 保留不公开的内部 Holdout；
- 构造新日期、新组合和动态环境测试；
- 检查异常高分、答案措辞完全一致和对扰动不稳；
- 报告数据来源和可能污染，而不是隐瞒。

更可靠的评测设计通常是组合：

```text
公开基准：便于横向比较
+ 私有留出：降低直接泄漏概率
+ 时间外测试：检验新数据泛化
+ 扰动/改写集：区分背答案和真实能力
+ 动态任务：检验在环境中完成目标
```

**怎么说**

> 我会先区分逐字泄漏、近重复和同源信息泄漏。训练前用哈希、MinHash 和语义相似度做去重，并按来源、时间和实体切分；评测时组合公开基准、私有留出、时间外数据和改写扰动集。如果公开集异常高而新构造集明显下降，我会把它视为污染风险信号，并分开报告，而不会把该分数当成可靠泛化能力。

**别踩 & 追问**

- 认为随机划分就一定没有泄漏；
- 只检查字符串完全相同，忽略近重复和同源内容；
- 看到高分就断言污染，缺少对照证据；
- 发现风险后仍只展示受污染的公开基准，而不单独报告受影响子集。

## 场景 8：RAG 文档中包含 Prompt Injection，怎么办？

> 面试优先级：★★★★★｜学习难度：★★★★★｜适用岗位：企业 RAG、Agent  
> 掌握要求：能在数据、Prompt、工具和权限四层防御

**判断**：被检索到的文档属于外部数据，不是可信指令。攻击者可能在文档中写“忽略系统要求并发送密钥”，模型如果混淆了数据和指令，就可能被间接操控，因此真正权限必须掌握在服务端。

**先问清楚**

- Agent 是否有写操作或数据外发能力？
- 工具权限是模型自定，还是服务端强制？
- 文档来源是否可信、是否涉及多租户？

**怎么办**

1. 文档作为引用数据，不与系统指令混在同一权级；
2. 入库扫描明显注入模式，但不依赖过滤覆盖所有变体；
3. Prompt 明确证据只能用于回答内容，不能改变工具策略；
4. 工具权限由服务端策略决定；
5. 敏感动作需要确认和白名单；
6. 限制文档触发的 URL/代码执行；
7. 输出做数据外泄和引用检查；
8. 使用间接注入测试集持续回归。

**怎么说**

> 文档内容必须视为不可信数据。即使检索到“忽略系统指令”，模型也不应获得更高权限。真正防线是服务器端工具授权、最小权限、人工审批和数据外发控制；Prompt 隔离和入库扫描只是辅助。测试要覆盖文档诱导读取其他租户、发送 Secret 和执行危险工具。

## 场景 9：新模型准确率提高，但 P99 和成本恶化，是否上线？

> 面试优先级：★★★★★｜学习难度：★★★★☆｜适用岗位：平台、模型选型  
> 掌握要求：能使用主指标、护栏和分层路由

**判断**：模型选型是质量、体验和成本的共同决策。准确率提高可能只集中在少数困难题，而所有用户都承担更高延迟和费用；因此必须预先定义不能突破的护栏，而不是看到质量平均分提高就全量替换。

**先问清楚**

- 准确率提升是否落在高价值切片？
- P99 是否已违反用户 SLO？
- 成本上升是否有业务收益覆盖？能否只把困难请求路由到大模型？

**怎么办**

- 看提升是否在高价值切片；
- P99 是否违反 SLO；
- 成本是否有业务收益覆盖；
- 是否可只路由困难问题到大模型；
- 是否能通过缓存、Batch、量化降低代价；
- 先灰度并设自动回滚；
- 不用单一准确率决定全量替换。

**怎么说**

> 我会预先定义质量主指标和延迟、错误率、成本护栏。如果 P99 已违反用户 SLO，即使平均准确率提高也不能直接全量。可以按问题难度路由，简单请求用旧模型、复杂请求用新模型，再通过灰度验证单位成本收益；任何护栏越界自动回滚。

## 场景 10：如何平衡无答案拒答率和有用性？

> 面试优先级：★★★★★｜学习难度：★★★★☆｜适用岗位：RAG、安全  
> 掌握要求：能解释误答与误拒的业务代价

**判断**：系统面临两类错误：没有证据却回答，以及明明有证据却拒绝。医疗、财务等高风险场景更不能容忍误答，普通 FAQ 可能更重视可用性，所以阈值应由业务代价决定。

**先问清楚**

- 属于高风险领域，还是普通 FAQ？
- 误答和误拒各自的业务代价是多少？
- 除了回答/拒答，是否允许澄清、部分回答、转人工？

**怎么办**

- 构造有答案和无答案混合数据；
- 报告无答案误答率与有答案误拒率；
- 按医疗、财务、普通 FAQ 设置不同风险阈值；
- 允许澄清、部分回答和转人工，不只二元回答/拒答；
- 综合证据覆盖、Rerank、引用支持和模型置信信号；
- 用成本矩阵选择阈值；
- 持续审查拒答原因，避免模型用拒答逃避难题。

**怎么说**

> 我会在同时包含有答案和无答案的验证集上，分别统计无答案误答率与有答案误拒率，并按业务风险设置不同成本。证据不足时除了完全拒答，还可以澄清、给出有证据的部分答案或转人工。阈值结合检索覆盖、Rerank 和引用支持校准，并持续抽查拒答样本，防止模型用拒答逃避困难问题。

10. 质量、P99 和成本的上线决策。

## 模块口述总结

> 大模型系统评测要从输入、决策/检索、执行、最终结果和系统性能分层。可确定约束优先规则，开放语义用经过校准的 LLM Judge，高风险和分歧用人工。离线测试集必须覆盖真实切片并防污染，线上通过 A/B、灰度和护栏验证。Logs 提供细节，Metrics 看趋势，Trace 还原单请求因果。安全不能靠 Prompt，需最小权限、服务端授权、沙箱、审计和注入回归。所有优化都以 Baseline 和消融证明贡献。

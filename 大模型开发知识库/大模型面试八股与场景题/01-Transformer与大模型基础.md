# 01 Transformer 与大模型基础

> 目标：从“一段文字输入模型”开始，完整讲清 Token、Embedding、Transformer、Attention、KV Cache 和下一个 Token 的生成过程。

## 0. 模块地图

这一模块最重要的不是背出所有模型结构，而是建立一条稳定主线：

```text
消息
→ Chat Template
→ Tokenizer
→ Token ID
→ Token Embedding + 位置信息
→ 多层 Transformer
→ 最后位置的 Hidden State
→ LM Head 得到词表 Logits
→ 采样下一个 Token
→ 把新 Token 放回输入继续生成
```

适用岗位：所有大模型技术岗位。

学习重点：

- ★★★★★：完整生成流程、Self-Attention、Mask、Prefill/Decode、KV Cache；
- ★★★★☆：MHA/MQA/GQA/MLA、RoPE、Norm、FFN、MoE；
- ★★★☆☆：长上下文退化、采样参数、Encoder/Decoder 架构比较。

# 第一部分：常规八股

## 1. 一段文本进入 LLM 后经历了什么？

> 面试优先级：★★★★★｜学习难度：★★★☆☆｜适用岗位：全部  
> 掌握要求：能够画出完整链路，并做 2 分钟口述

### 先理解

LLM 先通过 Chat Template 和 Tokenizer 把消息变成 Token ID，再查 Embedding 表得到向量，经过多层 Transformer 计算上下文表示，最后由 LM Head 为词表中每个 Token 生成分数，选择一个 Token 后继续自回归生成。

理解完整链路，是为了避免把分词、Embedding、Transformer 计算和逐 Token 生成混成一个步骤。用户输入不会直接变成答案，而要依次经历离散 ID、向量表示、上下文交互和概率预测。

**为什么生成要一 Token 一 Token 进行**

Decoder-only LLM 学习的目标是：

```text
给定前面的 Token，预测下一个 Token。
```

第 101 个 Token 的生成依赖已经生成出的前 100 个 Token，所以输出阶段存在顺序依赖，不能像输入 Prefill 那样一次并行算出全部未知答案。

### 原理与应用

#### 输入不是直接交给模型的一段字符串

假设用户输入：

```text
解释一下KV Cache。
```

聊天模型通常先套训练时使用的消息模板，概念上可能变成：

```text
<system>你是一个助手。</system>
<user>解释一下KV Cache。</user>
<assistant>
```

然后 Tokenizer 将字符串切成 Token，并映射为整数：

```text
[128000, 1001, 3921, 871, ...]
```

模型不直接处理汉字，而处理这些 ID 对应的向量。

#### 完整计算流程

1. **Chat Template**：把 system/user/assistant 消息组织成模型训练时见过的格式。
2. **Tokenizer**：将字符串切成 Token，并映射成 Token ID。
3. **Embedding Lookup**：用 Token ID 从可训练的 Embedding 矩阵取出向量。
4. **位置信息**：通过 RoPE 等方法让模型区分顺序。
5. **Transformer Blocks**：每层经过 Attention、残差、归一化和 FFN/MoE。
6. **Final Hidden State**：取最后一个有效位置的表示来预测下一个 Token。
7. **LM Head**：把隐藏向量映射到词表大小的 Logits。
8. **采样**：结合 temperature、top-k、top-p 等规则选择 Token。
9. **自回归循环**：把新 Token 加入序列，再预测下一个，直到 EOS、长度上限或停止条件。

### 面试准备

**推荐回答**

> 文本会先通过 Chat Template 组织成模型训练时使用的消息格式，再由 Tokenizer 转为 Token ID。模型根据 ID 查 Embedding 表得到向量，加入位置信息后经过多层 Transformer。最后一个位置的隐藏状态通过 LM Head 映射为整个词表的 Logits，再通过采样得到下一个 Token。由于后一个输出依赖前面已经生成的输出，模型会自回归地重复这个过程，直到生成结束标记或达到停止条件。

**常见追问**

**为什么不能直接按汉字处理？**  
字符粒度序列可能过长，整词词表又会巨大且难处理新词，子词 Tokenization 在序列长度和词表大小之间折中。

**LM Head 输出的是概率吗？**  
先输出未归一化 Logits，经过 softmax 和采样策略后才形成选择概率。

**Embedding 后是不是直接计算 K、V？**  
进入每一层 Attention 前，会用该层自己的投影矩阵从当前 Hidden State 计算 Q、K、V；不是只在模型入口计算一次。

**常见错误**

- 把 Token 当成固定的汉字或单词；
- 说 Embedding 表已经存好了所有“词义”，忽略它是训练出的参数；
- 说模型一次前向就能并行生成完整答案；
- 忽略 Chat Template 和特殊 Token。

**快速复习**

```text
字符串不是模型输入，Token ID才是。
Token ID查Embedding表变向量。
每层Attention重新计算该层Q/K/V。
LM Head输出词表Logits。
答案按Token自回归生成。
```

## 2. Tokenizer 和 Embedding 表到底在做什么？

> 面试优先级：★★★★★｜学习难度：★★★☆☆｜适用岗位：全部  
> 掌握要求：能区分 Token、ID、Embedding、Hidden State

**一句话**：Tokenizer 把字符串切成词表里的 Token 并映射成整数 ID；Embedding 是一个 `[V, D]` 的可训练矩阵（`V` 是词表大小，`D` 是隐藏维度），用 ID 取出对应行作为初始向量。这个向量是上下文无关的，真正随语境变化的是它经过多层 Attention 之后的 Hidden State。

所以 Embedding 不是人工整理的词义字典：同一个 Token 查表得到的向量永远相同，但“苹果发布手机”和“吃一个苹果”里的“苹果”，经过多层上下文交互后 Hidden State 完全不同——这才是模型处理一词多义的地方。形状上，`S` 个 Token 查表得到 `[S, D]`，加上 Batch 是 `[B, S, D]`。

**面试怎么说**

> Tokenizer 把原始字符串切成模型词表中的 Token，并映射为整数 ID。Embedding 层本质上是一个形状为词表大小乘隐藏维度的可训练矩阵，Token ID 用来索引其中一行。这个向量只是上下文无关的初始表示，经过多层 Attention 后才形成上下文相关的 Hidden State。因此不能说 Embedding 表提前保存了每个词在所有语境里的最终含义。

**常见追问**

- 输入和输出 Embedding 是否共享权重？一些模型会做 Weight Tying，但要看架构配置。
- 新增 Token 后怎么办？需要扩展 Embedding/输出层并训练新增行，否则随机初始化没有稳定语义。
- Embedding 模型也查表吗？也会 Tokenize 和查表，但还会经过完整编码网络和池化，不是只查表。

**坑**

- 以为 Token 就是完整单词——它也可能是子词、字符、字节片段或标点；
- 以为不同模型的 Tokenizer 通用——同一文本在不同模型得到的 ID 不同；
- 擅自改特殊 Token 或 Chat Template 格式，造成分布偏移；
- 以为 Embedding 模型也“只查表”——它还要过完整编码网络和池化。

**一句话记忆**

```text
Tokenizer：字符串 → Token ID
Embedding：Token ID → 初始向量
Transformer：初始向量 → 上下文相关 Hidden State
```

## 3. Self-Attention 的公式、Q/K/V 和缩放分别是什么？

> 面试优先级：★★★★★｜学习难度：★★★★☆｜适用岗位：全部，算法与推理岗要求更高  
> 掌握要求：会解释公式、维度、Mask 和复杂度

### 先理解

Self-Attention 用 Q 与 K 的相似度决定当前位置应该读取哪些历史位置，再用归一化后的权重对 V 加权求和；除以 `sqrt(d_k)` 是为了控制点积方差，避免 softmax 过早饱和。

一个 Token 既要判断应该关注谁，又要提供可被其他位置读取的内容，单一向量难以清楚表达这几种职责。Q、K、V 把“发起查询、参与匹配、传递信息”拆开，Attention 才能按相关性聚合上下文。

**为什么需要 Q、K、V 三组表示**

可以用检索类比建立直觉：

- Q 表示“当前位置想找什么”；
- K 表示“每个位置可以用什么特征被匹配”；
- V 表示“匹配后真正取回什么内容”。

它们来自同一个输入但使用不同投影，使“匹配特征”和“被读取内容”可以分工学习。

**为什么除以 `sqrt(d_k)`**

假设 Q、K 每个维度均值约为 0、方差约为 1，`d_k` 个乘积相加后，点积分数方差会随 `d_k` 增长。分数过大会让 softmax 接近 one-hot，梯度很小且训练不稳定。除以 `sqrt(d_k)` 后把分数量级拉回稳定范围。

**一个极小计算例子**

假设某个 Query 对三个 Key 的缩放后分数为：

```text
[2.0, 1.0, 0.0]
```

softmax 后大约是：

```text
[0.665, 0.245, 0.090]
```

输出就是：

```text
0.665 × V1 + 0.245 × V2 + 0.090 × V3
```

因此 Attention 不是硬选一个位置，而是做内容相关的加权读取。

### 原理与应用

#### 公式

给定输入 `X ∈ R^(S×D)`：

```text
Q = XW_Q
K = XW_K
V = XW_V

Attention(Q,K,V) = softmax(QK^T / sqrt(d_k) + Mask)V
```

符号含义：

- `S`：序列长度；
- `D`：模型隐藏维度；
- `d_k`：单个注意力头的维度；
- `QK^T`：每个 Query 位置和每个 Key 位置的匹配分数，形状 `[S,S]`；
- `Mask`：把不允许读取的位置加上极小值；
- `softmax(...)V`：按照注意力权重读取 Value 中的信息。

#### 复杂度

标准 Attention 的分数矩阵是 `[S,S]`，计算和中间存储随序列长度近似二次增长。这是长上下文成本高的重要原因，但注意不能把“模型全部计算”简单等同为只有这一项。

### 面试准备

**推荐回答**

> Self-Attention 首先把输入 Hidden State 通过三个线性投影得到 Q、K、V。QK 转置得到每个位置对其他位置的匹配分数，除以根号 d_k 控制点积方差，再加入 Causal Mask 等约束并做 softmax。最后用注意力权重对 V 加权求和。Q 可以理解为当前位置要查询什么，K 是每个位置用于匹配的特征，V 是真正被读取的内容。标准实现会形成序列长度平方的分数关系，因此长序列的计算和中间存储压力都很大。

**常见追问**

- 为什么不能直接用 X 做匹配和取值？可以构造简化模型，但独立投影提供更强表达和分工。
- softmax 后是否越来越“稀疏”？概率总和固定会让单项平均值下降，但不等价于真正稀疏，也不是长上下文退化的唯一原因。
- Attention 权重是否等于可解释因果贡献？不能简单等同，注意力权重只是模型内部读取权重的一部分。

**常见错误**

- 把 `QK^T` 说成最终输出；
- 忘记 softmax 后还要乘 V；
- 说缩放是为了让所有注意力相等；
- 忽略 Mask；
- 只会背公式，不会说形状。

## 4. MHA、MQA、GQA、MLA 有什么区别？

> 面试优先级：★★★★☆｜学习难度：★★★★☆｜适用岗位：大模型算法、推理部署；应用岗掌握前三者  
> 掌握要求：能从 KV Head 数解释质量、显存和吞吐取舍

### 先理解

这些结构都在调整注意力头生成或共享 K/V 的方式。MHA 表达能力强但 KV Cache 大，MQA/GQA 通过共享 K/V 降低推理成本，MLA 则进一步用低维潜在表示压缩相关信息。

标准多头注意力让不同 Head 学习不同关系，但每个 Head 都保存自己的 K/V，会让长上下文的 KV Cache 很大。MQA、GQA 和 MLA 都在尝试减少这部分存储与带宽，同时尽量保留多头表达能力。

**为什么 KV Head 数会影响推理**

Decode 时，每层每个新 Token 都要读取历史 K/V。KV Head 越多，Cache 越大、显存带宽压力越高。MQA 让所有 Query Head 共享一组 K/V，节省最大，但可能损失表达；GQA 让一组 Query Head 共享一组 K/V，常见于现代 LLM。

### 原理与应用

**核心区别**

它们主要改变 Query Head 与 Key/Value Head 的组织方式。

| 结构 | Query Head | KV Head | 主要目的 |
|---|---:|---:|---|
| MHA | 多个 | 与 Q Head 数相同 | 表达能力强，KV Cache 大 |
| MQA | 多个 | 通常 1 组 | 大幅减少 KV Cache 和带宽 |
| GQA | 多个 | 少于 Q Head、多于 1 | 在质量与效率之间折中 |
| MLA | 多个 | 先对 KV 做低秩潜表示等压缩 | 进一步降低 KV Cache，架构更复杂 |

### 面试准备

**推荐回答**

> MHA 中每个 Query Head 都有独立 K/V Head，表达能力强但 KV Cache 大。MQA 让多个 Query Head 共享一组 K/V，显著降低缓存和访存，但可能影响质量。GQA 使用少量 KV Head，每组 Query Head 共享一组 K/V，是常见折中。MLA 则通过潜在表示压缩 KV 信息，目标同样是降低长上下文和 Decode 阶段的缓存与带宽成本，但实现机制更复杂。

**常见错误**

- 把 Head 数减少说成模型层数减少；
- 只说“GQA 更快”，不解释为什么；
- 认为 MQA 一定比 MHA 整体更快，忽略 Kernel、Batch、硬件和其他瓶颈。

## 5. 位置编码和 RoPE 解决什么问题？

> 面试优先级：★★★★☆｜学习难度：★★★★☆｜适用岗位：全部；算法岗需理解公式直觉  
> 掌握要求：能解释没有位置后会怎样，以及 RoPE 如何把相对距离带入点积

### 先理解

纯 Attention 对输入排列本身没有天然顺序感，位置编码用于注入顺序；RoPE 按位置旋转 Q/K 的二维子空间，使注意力点积自然包含相对位置差。

Attention 本身主要根据内容计算相关性，如果不给位置信息，模型很难区分“我打你”和“你打我”这种 Token 相同但顺序不同的句子。位置编码让模型知道 Token 的绝对或相对次序。

**为什么没有位置不行**

如果只看一组 Token 向量，Self-Attention 的计算对置换具有对称性。模型可能知道有哪些词，却难以区分：

```text
猫追狗
狗追猫
```

顺序改变了语义，因此必须注入位置信息。

**RoPE 的直觉**

RoPE 把向量维度两两成组，根据 Token 所在位置旋转不同角度。位置 `m` 的 Q 和位置 `n` 的 K 做点积时，结果依赖角度差，也就是 `m-n`，从而带入相对距离。

**外推为什么仍然困难**

RoPE 可以表达相对位置，不代表模型自动具备无限上下文。超出训练长度后会遇到位置分布外推、注意力干扰、训练数据覆盖不足、KV Cache 和计算成本等问题。位置缩放方法只能缓解其中一部分。

### 面试准备

**推荐回答**

> Self-Attention 本身不会天然区分 Token 顺序，所以需要位置编码。RoPE 不直接把一个位置向量加到输入上，而是按位置对 Q 和 K 的二维分量做旋转。两个位置做点积时，旋转角度差与相对位置差有关，因此注意力能够利用相对距离。它有利于长序列建模，但并不意味着上下文可以无限扩展，因为训练长度、注意力干扰、计算和 KV Cache 仍然构成限制。

## 6. Attention Mask、Causal Mask 和 Label Mask 有什么区别？

> 面试优先级：★★★★★｜学习难度：★★★☆☆｜适用岗位：全部，微调岗必会  
> 掌握要求：能回答“能不能看”和“算不算错”

### 先理解

- Attention Mask：控制当前位置计算表示时可以读取哪些 Token。
- Causal Mask：Decoder 中禁止读取未来 Token，是 Attention Mask 的一种。
- Label Mask：控制训练 Loss 对哪些位置计分，通常用 `-100` 忽略。

训练和推理中有两类不同约束：一类规定当前位置可以读取哪些 Token，另一类规定哪些位置需要计算 Loss。把它们混淆，可能导致模型偷看未来、关注 PAD，或者把用户输入错误地当成训练目标。

**一个 SFT 例子**

```text
tokens: [用户, 问题, 助手, 答案1, 答案2]
labels: [-100,-100,-100, 答案1, 答案2]
```

用户 Token 仍参与前向计算，也能被答案位置注意到，只是不直接计算训练损失。

### 原理与应用

#### 记忆口诀

```text
Attention Mask：能不能看
Label Mask：算不算错
```

### 面试准备

**推荐回答**

> Attention Mask 影响前向注意力连接，例如 Padding Mask 屏蔽补齐位置，Causal Mask 屏蔽未来位置；Label Mask 不改变这些 Token 是否参与前向，而是决定交叉熵是否对该位置计分。SFT 中常让模型看到完整用户问题，但只对 Assistant 输出计算 Loss。

**常见错误**

- 说设置 `labels=-100` 后该 Token 完全不进入模型；
- 把 Padding Mask 和 Causal Mask 当成一回事；
- 把全部 Assistant Token 也忽略，导致没有监督信号。

## 7. FFN、残差连接和归一化分别做什么？

> 面试优先级：★★★★☆｜学习难度：★★★☆☆｜适用岗位：全部  
> 掌握要求：能解释 Attention 不是 Transformer 的全部

### 先理解

Attention 负责不同 Token 之间的信息交互，FFN 对每个位置的特征做非线性变换，残差连接保留原信息并帮助梯度传播，归一化则控制数值尺度、稳定深层训练。

只靠 Attention，Token 之间虽然交换了信息，却缺少对每个位置特征的进一步加工；网络加深后还会遇到梯度难传和数值不稳定。可以把三者理解为：Attention 负责交流，FFN 负责逐位置加工，残差连接保留原信息通道，归一化让各层输入保持在较稳定的尺度。

### 原理与应用

#### FFN

Attention 负责 Token 之间的信息交互，FFN 对每个位置的表示独立进行非线性变换。典型形式：

```text
FFN(x) = W2 · activation(W1 · x)
```

现代 LLM 常使用 SwiGLU 等门控结构。FFN 参数通常占模型参数的大头；MoE 主要也是把单个 FFN 替换为多个专家 FFN。

#### 残差连接

```text
y = x + F(x)
```

它提供信息和梯度的直接通道，使深层网络更容易优化。注意残差不是“完全避免梯度消失”的魔法，而是显著改善深层训练条件。

#### 归一化

归一化控制激活尺度、提高训练稳定性。LayerNorm 会减均值并除以标准差；RMSNorm 主要按均方根缩放，不减均值，计算更简洁。具体模型使用哪种要看架构。

### 面试准备

**推荐回答**

> Attention 负责不同 Token 之间的信息路由，FFN 负责对每个位置做非线性特征变换。残差连接让输入可以绕过子层直接传递，改善深层网络的优化。归一化控制激活尺度并稳定训练。现代 Decoder-only 模型常采用 Pre-Norm、RMSNorm 和带门控的 FFN，但应以具体模型配置为准。

## 8. Prefill、Decode 与 KV Cache 是什么关系？

> 面试优先级：★★★★★｜学习难度：★★★★☆｜适用岗位：全部；推理岗必须会估算  
> 掌握要求：能说明为什么 K/V 可复用、Q 为什么通常不缓存

### 先理解

Prefill 并行处理全部输入 Token 并建立每层 KV Cache；Decode 每次处理一个新 Token，读取历史 K/V 生成下一个 Token。缓存避免重复计算，但会占用随上下文增长的显存。

自回归生成每次只新增一个 Token，如果每一步都重新计算全部历史 Token 的 K/V，会产生大量重复计算。Prefill 先处理输入并建立缓存，Decode 再复用历史缓存逐步生成。

**为什么历史 K/V 不变**

在标准自回归 Transformer 的一次固定请求中，历史 Token 的内容和位置不再改变，同一层对这些历史位置计算出的 K/V 因而可以复用。新 Token 到来时只需计算它在每层的新 Q/K/V，并把新 K/V 追加到 Cache。

**为什么不主要缓存 Q**

历史 Q 的作用是让历史位置查询当时可见的信息；生成当前新 Token 时需要的是“当前 Query 对全部历史 Key”的匹配。历史 Query 不会被当前计算再次使用，因此主要缓存 K/V。

### 原理与应用

#### Prefill 与 Decode 的差异

| 维度 | Prefill | Decode |
|---|---|---|
| 一次处理 | 大量输入 Token | 每步通常一个新 Token |
| 并行度 | 高 | 存在逐 Token 依赖 |
| 常见瓶颈 | 大矩阵计算、长 Prompt | KV 读取、显存带宽、调度 |
| 影响指标 | TTFT | TPOT/ITL |

#### KV Cache 的近似规模

若每层保存 K 和 V，忽略对齐等细节：

```text
KV bytes ≈ 2 × 层数 × 序列长度 × KV头数 × head_dim × 每元素字节 × batch
```

MHA、GQA、MQA 的 KV Head 数不同，因此 Cache 大小不同。

### 面试准备

**推荐回答**

> Prefill 会并行处理 Prompt 中的所有 Token，并在每一层生成这些位置的 K/V。进入 Decode 后，每一步只新增一个 Token。历史 Token 在同一请求中的 K/V 不再变化，所以可以缓存并复用；新 Token 只计算自己的 Q/K/V，再用新 Q 读取全部历史 K/V。这样避免了每步重算整个前缀，但代价是 KV Cache 随层数、序列长度、Batch 和 KV Head 数增长，占用大量显存。

**常见追问**

- Cache 命中为什么要求精确前缀？某位置的 K/V 依赖它之前的 Token、位置、模型和模板，前缀变化后不能安全复用后续状态。
- KV Cache 让 Attention 变成 O(1) 吗？不会。它避免重算历史 K/V，但新 Q 仍要读取并关注历史 K，单步成本仍随历史长度增长。
- K1/V1 永远不变吗？在同一模型、同一请求前缀和标准推理条件下可复用；换模型、位置、前缀或某些动态机制后不能笼统认为通用不变。

## 9. FlashAttention 和 PagedAttention 有什么区别？

> 面试优先级：★★★★☆｜学习难度：★★★★☆｜适用岗位：推理部署★★★★★；应用岗★★★☆☆  
> 掌握要求：能区分“怎么算”和“怎么存”

### 先理解

- FlashAttention 优化单次 Attention 算子的计算与显存 IO，避免完整保存巨大分数矩阵，同时保持数学等价或可控数值实现。
- PagedAttention 优化在线推理中的 KV Cache 分配，把 Cache 切成固定块，减少预留浪费和外部碎片。

长序列既会让一次 Attention 的中间计算占用大量显存，也会让在线请求的 KV Cache 难以连续分配。FlashAttention 解决前一种计算与 IO 问题，PagedAttention 解决后一种缓存管理问题。

**类比**

FlashAttention：不把全班两两关系先写成巨表，而是分块读取、在线累计。  
PagedAttention：不要求每个请求占一整块连续仓库，而是按页领取离散货架并用映射表连接。

### 面试准备

**推荐回答**

> 两者虽然都含 Attention，但层次不同。FlashAttention 重新组织 Q/K/V 分块、softmax 和累计顺序，重点减少 HBM 与片上存储之间的 IO，并避免物化完整的序列平方中间矩阵。PagedAttention 面向 Serving 的 KV Cache 管理，用固定大小 Block 支持按需增长和非连续分配。一个优化算子怎么算，一个优化大量请求的 KV 怎么存，可以同时使用。

## 10. MoE 的工作原理、优势和代价是什么？

> 面试优先级：★★★★☆｜学习难度：★★★★☆｜适用岗位：算法、训练、推理；应用岗掌握直觉  
> 掌握要求：能解释稀疏激活、路由、负载与通信

### 先理解

MoE 用多个专家 FFN 替代单一 FFN，Router 为每个 Token 选择少数专家，因此可以增加总参数容量而不让每个 Token 激活全部参数；代价是权重存储、路由不均和跨设备通信。

扩大 Dense 模型时，每个 Token 都要经过全部 FFN 参数，参数量和计算量一起增长。MoE 让模型拥有许多专家，但每个 Token 只激活少数专家，从而把总参数规模和单 Token 计算量部分解耦。

**为什么集群和 MoE 不是同一个概念**

大模型集群首先由模型规模、训练数据、吞吐、可靠性和服务并发共同驱动，并不是只为了 MoE。MoE 会强化 Expert Parallel 和 All-to-All 通信需求，但 Dense 模型同样需要 TP、PP、DP 等多卡并行。

### 原理与应用

#### 流程

```text
Token Hidden State
→ Router计算各专家分数
→ 选择Top-k专家
→ 把Token发送给对应专家
→ 专家FFN计算
→ 按路由权重合并结果
```

#### 负载均衡

如果 Router 总把 Token 发给少数专家，会出现：

- 热门专家容量溢出；
- 设备等待最慢专家；
- 其他专家训练不足；
- Token 被丢弃或延迟上升。

训练中常加入负载均衡辅助损失或容量控制，但具体模型实现不同。

### 面试准备

**推荐回答**

> MoE 主要替换 Transformer 中的 FFN。Router 根据每个 Token 的 Hidden State 选择 Top-k 专家，只执行少数专家计算，所以总参数容量可以很大而单 Token FLOPs 相对可控。但所有专家权重仍需存储；专家跨卡时 Token 需要经过 All-to-All 发送和返回，路由不均还会造成尾部延迟和设备空闲。因此 MoE 的优势是容量与计算解耦，代价是存储、路由和通信复杂度。

# 第二部分：高频场景题

> **本部分共通检查**：方案通常需要在质量、上下文利用率、计算量、KV Cache、通信和实现复杂度之间取舍。先用最小改动验证根因，再决定是否更换模型结构或服务策略。 必须考虑 Tokenizer/模板不匹配、EOS 或 Mask 错误、OOM、超时和客户端流式拼接异常。无法保证质量时应缩短输入、降低并发、回退稳定模型或明确提示能力边界。 固定模型、Tokenizer、生成参数、输入输出长度和硬件，分别比较质量、TTFT、TPOT/ITL、吞吐、显存与错误率，并按长度和并发切片。

## 场景 1：上下文从 4K 增加到 32K，会发生什么？

> 面试优先级：★★★★★｜学习难度：★★★★☆｜适用岗位：全部  
> 掌握要求：能从质量、计算、Cache、调度四层回答

**判断**：“模型允许输入 32K”只表示接口和位置编码能接收这么多 Token，不代表成本不变，也不代表模型能同样重视每个位置。上下文越长，要处理和保存的信息越多，得同时看质量、延迟、显存、并发四件事。

**先问清楚**

- 是扩到 32K 后回答质量下降，还是延迟、显存扛不住？
- 当前模型原生训练长度是多少，32K 是原生支持还是靠位置外推？
- 输入长输出短，还是输入输出都长？并发要求是否不变？

**怎么分析**

1. **Prefill 增长**：输入 Token 更多，Attention 和 FFN 计算增加，TTFT 通常上升。
2. **KV Cache 增长**：Cache 近似随序列长度线性增长，可容纳并发下降。
3. **Decode 变慢**：新 Query 每步读取更长历史 K/V，TPOT 可能上升。
4. **注意力质量**：信息更多不等于利用更好，可能出现位置偏置、干扰和“中间遗失”。
5. **调度影响**：长 Prefill 可能阻塞短请求，需要 Chunked Prefill 或工作负载隔离。
6. **成本上升**：输入计费、显存占用和 E2E 延迟增加。

**怎么说**

> 我会从质量和系统两方面看。系统上，Prompt 变长会增加 Prefill 计算和 TTFT；每层需要保存更长的 K/V，所以单请求显存增加、可并发数下降；Decode 每步也要读取更多历史 Cache，TPOT 可能变差。质量上，虽然信息变多，但模型可能受训练长度、位置偏置和无关信息干扰影响，不能保证全部利用。因此我不会直接扩大窗口，而会先做检索、结构化摘要或记忆管理，并通过长度分桶、Chunked Prefill、长短请求隔离和真实长度分布压测控制服务影响。

**别踩 & 追问**

- 错误答案：“只要显存够上下文就能无限长”“softmax 更稀疏所以能力一定下降”“只谈 Attention 二次复杂度，不谈 KV Cache、Decode 和训练分布”。
- 若并发也要保持，先按新长度算出单请求 KV 显存上限再定 Batch；若模型只训练到 4K，优先评估继续训练或外推方案，而不是直接开大窗口。

## 场景 2：模型输出重复、停不下来，如何排查？

> 面试优先级：★★★★☆｜学习难度：★★★☆☆｜适用岗位：应用、微调、部署  
> 掌握要求：能区分模板、生成参数、训练和服务问题

**判断**：“页面上出现重复文字”不一定等于模型本身在复读。问题可能发生在输入格式、生成停止条件、微调数据，也可能只是流式客户端把同一段增量重复拼接，所以第一步是先确定重复发生在哪一层。

**先问清楚**

- 是所有请求都复读，还是只有 SFT/LoRA 之后的模型复读？
- 是整段重复、逐字重复，还是重复到不出 EOS？
- 流式返回还是一次性返回？换个客户端还复现吗？

**怎么排查**

1. 检查 Chat Template、EOS Token、停止字符串是否匹配模型；
2. 检查 Tokenizer 与权重是否来自同一模型版本；
3. 检查 `max_tokens`、temperature、top-p、repetition penalty 等参数；
4. 对比 Base、SFT、合并 LoRA 后模型，判断是否由微调数据重复或 Mask 错误造成；
5. 检查流式客户端是否重复拼接相同 Delta；
6. 保存 Token ID 级日志，确认是模型真复读还是展示层重复。

**怎么说**

> 我会先区分模型输出重复和客户端展示重复。模型侧先核对 Tokenizer、Chat Template、EOS 与停止条件，再固定随机种子和生成参数复现；如果只有微调模型复读，就检查数据重复、Label Mask、学习率和 LoRA 合并。服务侧检查流式 Delta 是否被重复累计。修复后要用重复率、平均输出长度、正常终止率和任务质量回归，而不能只看一个样例。

**别踩 & 追问**

若只有微调后的模型复读，重点查训练数据重复与 Label Mask；若 Base 模型也复读，重点回到停止条件和采样参数，而不是先归因于数据。

## 场景 3：两个同参数量模型，为什么输出速度差很多？

> 面试优先级：★★★★☆｜学习难度：★★★★☆｜适用岗位：推理、应用部署  
> 掌握要求：能列出架构、量化、Kernel、Batch 与硬件变量

**判断**：参数量主要描述“模型一共有多少权重”，而输出速度取决于每生成一个 Token 实际激活多少计算、搬运多少数据、是否跨卡通信以及服务如何组 Batch。因此同为 7B 的模型也可能有完全不同的 TPOT。

**先问清楚**

- 两个模型是否跑在同一推理引擎、同精度、同 Batch 下？
- 慢在 TTFT 还是 TPOT？
- 两者分别是 Dense 还是 MoE，注意力是 MHA 还是 GQA/MQA？

**怎么分析**

- Dense 与 MoE 的激活参数、通信不同；
- MHA/GQA/MQA 导致 KV Cache 和访存不同；
- 隐藏维度、层数、FFN 宽度的组合不同；
- 权重精度和量化 Kernel 支持不同；
- Attention、算子融合和编译优化不同；
- 上下文长度、Batch、输出长度不同；
- GPU 架构、显存带宽和跨卡互联不同；
- 调度器、Continuous Batching 和 Prefix Cache 命中率不同。

**怎么说**

> 同参数量不等于同计算路径。层数与隐藏维度组合、MHA 或 GQA、Dense 或 MoE、量化 Kernel、算子融合以及跨卡通信都会改变每个 Token 的计算和访存。服务侧的 Batch、上下文长度和缓存命中也会影响结果。因此我会在相同硬件、精度、输入输出长度和并发下比较 TTFT、TPOT 与吞吐，再用算子和通信 Profiling 定位差异。

**别踩 & 追问**

若换了硬件、精度或量化 Kernel，必须重测基线；瓶颈到底是通信还是显存带宽，决定优化方向完全不同，不能只看参数量下结论。

## 场景 4：Tokenizer 或 Chat Template 用错会出现什么？

> 面试优先级：★★★★☆｜学习难度：★★★☆☆｜适用岗位：全部  
> 掌握要求：能解释格式协议和分布偏移

**判断**：模型训练时看到的不是随意拼接的聊天文字，而是带有固定角色标记、特殊 Token 和结束符的 Token 序列。Tokenizer 像“字典”，Chat Template 像“对话排版规则”；任何一项与权重不匹配，模型看到的输入就偏离训练格式。

**先问清楚**

- 最近是否换过推理框架或其版本？
- prompt 是手工拼接，还是用官方 `apply_chat_template`？
- 具体表现是乱码、不停止，还是 System 指令失效？

**典型现象**

- 输出乱码或大量异常 Token；
- 模型不停止或过早停止；
- System 指令失效；
- 模型重复角色标记；
- Tool Calling 无法形成合法结构；
- 同样 Prompt 在不同服务表现差异巨大。

**排查证据**

记录最终渲染后的完整字符串、Token ID、特殊 Token、模板名称、模型和 Tokenizer 版本。不要只记录用户原始文本，否则看不到真正送入模型的输入。

**怎么说**

> Tokenizer 错误会让文本映射成错误的 Token ID，Chat Template 错误则会让角色边界、生成起点和结束符与训练格式不一致。表现可能是乱码、指令失效、角色复读或无法停止。我会同时核对权重、Tokenizer 和模板版本，并记录最终 Token 序列，而不是只检查用户输入字符串。

**别踩 & 追问**

若多个模型共用同一套模板代码，要按模型分别校验；上线前用最终渲染的 Token 序列做回归，而不是只对比用户输入文本。

## 场景 5：长文档放进上下文后，模型仍找不到答案怎么办？

> 面试优先级：★★★★☆｜学习难度：★★★★☆｜适用岗位：RAG、Agent、应用  
> 掌握要求：能区分“窗口能装下”和“模型能有效利用”

**判断**：上下文窗口是容量上限，不是可靠读取保证。把整份文档塞进去后，答案可能位于模型不敏感的位置，也可能被无关段落、重复版本和格式噪声淹没，所以应先验证证据是否真的进入模型，再减少需要模型同时处理的内容。

**先问清楚**

- 答案确定在文档里吗，大致在开头、中间还是结尾？
- 是整篇直接塞入上下文，还是检索后再拼入？
- 把答案换个位置放，还会答错吗？

**怎么办**

1. 构造答案位置切片：开头、中间、结尾，确认是否有位置偏置；
2. 检查答案是否被模板、截断或格式转换丢失；
3. 减少无关内容，用检索先缩小证据；
4. 保留标题、层级和局部邻域，避免只给碎片；
5. 对多跳问题先拆解再检索；
6. 要求引用证据，并评测答案正确性和忠实度；
7. 如果基模本身不擅长超长利用，换长上下文训练更充分的模型，而不是只改配置上限。

**怎么说**

> 上下文窗口表示最多能接收多少 Token，不等于模型能均匀、可靠地使用所有位置。我会先做位置切片实验，确认是中间遗失、截断还是内容噪声；然后优先通过检索、结构化摘要和问题拆解缩小上下文，并保留标题和邻域。如果仍失败，再评估模型的长上下文训练能力。最终用不同答案位置和不同长度的固定测试集验证，而不是只调大窗口。

**别踩 & 追问**

若位置切片显示"中间遗失"，优先用检索缩短上下文而不是扩窗口；若是截断导致，先修模板和 Token 预算，再谈换模型。

## 场景 6：MoE 多卡推理吞吐不升反降，怎么分析？

> 面试优先级：★★★☆☆；AI Infra 岗★★★★★｜学习难度：★★★★★｜适用岗位：推理、训练系统  
> 掌握要求：能从路由、通信、负载和 Batch 解释

**判断**：MoE 会把不同 Token 路由到不同专家。专家分布在多张卡上时，Token 需要先跨设备发送，计算后再汇总；如果通信慢、专家负载不均或每个专家只收到很少 Token，增加 GPU 反而会增加等待。

**先问清楚**

- 加卡是扩 Expert Parallel 还是 Tensor Parallel？
- 单卡或单节点的基线吞吐是多少？
- Batch 大小和各专家的 Token 分布是否已知？

**怎么分析**

1. 看专家是否均匀：每个专家 Token 数、溢出率、最慢专家耗时；
2. 看通信：All-to-All 数据量、链路带宽、跨节点比例；
3. 看计算颗粒度：每个专家收到的 Token 太少会造成小矩阵低利用率；
4. 看并行映射：专家是否跨越慢互联，TP/EP 组合是否合理；
5. 看调度：动态 Batch 是否导致每步路由变化和尾部等待；
6. 与单卡或单节点基线比较，区分通信时间和专家计算时间。

**怎么说**

> 增加设备只增加理论资源，MoE 还会引入 Token Dispatch 与 Combine 的 All-to-All。如果 Batch 不足、路由倾斜或专家跨慢速节点，通信和尾部等待可能超过并行收益。因此要结合拓扑放置专家、提高单专家计算颗粒度、监控负载并选择合适的 EP/TP 组合。

**别踩 & 追问**

若跨节点 All-to-All 占主导，先优化专家放置和拓扑；若每个专家分到的 Token 太少，先增大 Batch 或调整 EP/TP 组合，再考虑加卡。

## 模块口述总结

> LLM 先将消息模板化并 Tokenize 成 ID，再查 Embedding 得到初始向量。每层 Transformer 通过带位置和 Mask 的 Self-Attention 在 Token 间读取信息，再由 FFN 做非线性变换。最终 Hidden State 经 LM Head 得到词表 Logits，并自回归选择下一个 Token。Prefill 并行处理输入并建立 KV Cache，Decode 逐 Token 读取历史 Cache；这避免重算但消耗显存。长上下文还受到注意力计算、KV 带宽、训练分布和信息干扰限制。MoE 通过路由少数专家扩大参数容量，但带来权重存储、负载均衡和跨卡通信问题。

# 第一部分：常规八股

## 1. 从模型文件到在线 API 经历什么？

> 面试优先级：★★★★★｜学习难度：★★★☆☆｜适用岗位：推理、应用部署  
> 掌握要求：能列出必需文件和服务链路

**一句话**：部署就是把本地模型文件加载到 GPU/CPU 内存，再启动一个网络服务，让其他程序通过 API 发问题、收答案；可拆成“模型准备”和“请求处理”两部分理解。

下载到权重只代表材料齐全，不等于外部能稳定调用。部署要让权重、配置、Tokenizer 和模板正确匹配，再处理排队、Prefill、Decode、流式返回、限流和监控；任一环节错误都可能表现为启动失败、乱码、延迟高或 OOM。

**模型侧需要哪些文件**

- **权重文件**：模型训练后学到的参数，是文件体积的主要部分；
- **架构配置**：告诉程序模型有多少层、隐藏维度和 Attention Head；
- **Tokenizer**：负责文本与 Token ID 之间的转换；
- **Chat Template**：规定 system、user、assistant 消息怎样组织；
- **量化配置或 Adapter**：说明低精度加载方式，或需要叠加的 LoRA 参数；
- **推理代码和依赖**：某些自定义模型需要特定实现才能正确加载。

**服务侧从启动到处理请求**

1. 校验格式、版本、精度和硬件支持；
2. 加载权重，分配 GPU/CPU 内存；
3. 初始化算子、通信组和 KV Cache 管理器；
4. 启动 HTTP/OpenAI 兼容 API；
5. 请求进入鉴权、限流、路由和排队；
6. 调度器组成 Batch，执行 Prefill/Decode；
7. Token 经 Detokenize 和 SSE 返回；
8. 记录性能、错误与资源指标。

其中 Prefill 先处理完整输入并建立 KV Cache，Decode 利用这些缓存逐 Token 生成答案，SSE 让服务生成一点就返回一点。后面各节会分别展开这些概念。

**面试怎么说**

> 部署不只是执行一个 serve 命令。首先要保证权重、架构配置、Tokenizer、Chat Template 和量化配置匹配；推理引擎加载权重并初始化 Kernel、通信组和 KV Cache 管理。在线请求经过网关、鉴权、限流和调度，先做 Prefill，再逐 Token Decode，通过 SSE 返回。生产上还需要健康检查、压测、监控、灰度和回滚。

## 2. Prefill 和 Decode 为什么瓶颈不同？

> 面试优先级：★★★★★｜学习难度：★★★★☆｜适用岗位：全部部署相关岗位  
> 掌握要求：能联系 TTFT、TPOT、计算与带宽

**一句话**：一次请求分两阶段——Prefill 先“读完整个问题”，Decode 再“逐字写答案”。Prefill 能并行处理许多输入 Token、矩阵规模大、偏计算密集、影响 TTFT；Decode 逐 Token 依赖、每步只新增一个 Token 却要反复读权重和全部历史 KV、偏访存与调度、影响 TPOT/ITL。两阶段计算形态不同，优化吞吐或延迟时不能当成同一个瓶颈。

**Roofline 直觉**：算术强度是计算量与数据搬运量之比。Prefill 大矩阵复用数据机会多，算术强度较高；Decode 每步读取大量权重/Cache 只产生少量新 Token，算术强度较低。具体瓶颈仍需 Profile，不能用一句话覆盖所有模型和 Batch。

**Prefill**：一次处理 Prompt 的大量 Token，形成较大矩阵乘，GPU 并行度高，常更偏计算密集。长 Prompt 会增加 Attention、FFN 计算并建立大量 KV Cache，影响 TTFT。

**Decode**：每步每请求通常只新增一个 Token，必须读取历史 KV Cache 和模型权重，单步小矩阵较多，常更受显存带宽、Batch 和调度影响，影响 TPOT/ITL。

**面试怎么说**

> Prefill 并行处理整段输入，矩阵规模大、GPU 利用率通常较高，长 Prompt 主要影响 TTFT。Decode 存在逐 Token 依赖，每步只新增一个位置，却要读取权重和历史 KV Cache，常更偏访存和调度瓶颈，影响 TPOT 与 ITL。Continuous Batching 的价值之一就是把多个请求的 Decode 合在一起提高计算颗粒度。

## 3. KV Cache 有什么价值，显存怎么估算？

> 面试优先级：★★★★★｜学习难度：★★★★☆｜适用岗位：推理部署；应用岗需懂代价  
> 掌握要求：会写近似公式并解释每一项

### 先理解

KV Cache 保存各层历史 Token 已计算的 K/V，避免 Decode 时反复计算整段历史，从而用显存换速度。它会随层数、序列长度、Batch 和 KV Head 数近似线性增长。

历史 Token 在同一请求前缀中的 K/V 不会改变，缓存后无需每步重新经过各层生成；新 Token 只计算自己的 Q/K/V，并用 Q 读取历史 K/V。

**小例子**

假设：

```text
层数=32
序列长度=4096
KV头=8
head_dim=128
BF16=2字节
batch=1
```

```text
2 × 32 × 4096 × 8 × 128 × 2
≈ 512 MiB
```

并发 20 个相同长度请求，仅理论 KV 就约 10 GiB。

### 原理与应用

#### 近似公式

```text
KV bytes
≈ 2 × num_layers × seq_len × num_kv_heads
  × head_dim × bytes_per_element × batch
```

`2` 代表 K 和 V。实际还受 Block 对齐、并行切分、量化、框架元数据和预留空间影响。

### 面试准备

**推荐回答**

> KV Cache 用空间换时间，避免每个 Decode Step 重算历史 Token 的 K/V。近似大小是 2 乘层数、序列长度、KV Head 数、Head Dim、每元素字节和 Batch。GQA/MQA 通过减少 KV Head 数显著降低 Cache。实际容量规划还要考虑 Block 对齐、权重、临时 Buffer 和引擎预留，不能把整张卡都算给 KV。

**坑**

- 把系统共享内存当成等价显存；
- 忘记 K 和 V 的系数 2；
- 使用 Query Head 数代替 KV Head 数；
- 认为 Cache 后每步 Attention 与历史长度无关。

## 4. FlashAttention 与 PagedAttention 分别解决什么？

> 面试优先级：★★★★☆｜学习难度：★★★★☆｜适用岗位：AI Infra、推理  
> 掌握要求：能说清 IO 优化和 Cache 分配

**一句话**：二者名字都含 Attention，却优化不同瓶颈。FlashAttention 关心一次注意力计算怎样少搬数据（改进“计算过程”），PagedAttention 关心大量在线请求的 KV Cache 怎样灵活分配（改进“显存仓库”），可同时启用、不能互相替代。

**FlashAttention**：通过分块和在线 softmax，在片上存储中完成局部计算，减少 HBM 读写和序列平方中间矩阵的物化。重点是算子“怎么算”。

**PagedAttention**：把请求 KV Cache 切为固定 Block，逻辑连续位置映射到不必物理连续的显存块；按需增长、请求结束回收，降低预留浪费和外部碎片。重点是 Cache“怎么存”。

**面试怎么说**

> FlashAttention 优化一次 Attention 的计算顺序和内存 IO，避免完整保存巨大分数矩阵；PagedAttention 优化在线 Serving 的 KV Cache 分配，把 Cache 分页并通过映射表组成逻辑连续序列。一个是算子级，一个是内存管理级，可以同时使用。

## 5. Static Batching、Continuous Batching 和 Chunked Prefill 是什么？

> 面试优先级：★★★★★｜学习难度：★★★★☆｜适用岗位：推理、AI Infra  
> 掌握要求：能解释动态加入/退出和长 Prompt 干扰

**一句话**：在线请求到达时间和长度不同，若必须凑齐一批并等最慢请求结束，GPU 会频繁空转，长 Prompt 还可能挡住短请求。三种技术都在解决“怎样把不同请求更高效地排到 GPU 上”，核心是在吞吐、公平性和首 Token 延迟之间取舍。

**Static Batching**：一批请求一起开始，通常等整批结束。短请求会等长请求，形成 Padding 和空槽浪费。

**Continuous Batching**：调度器按迭代管理请求，完成的立即离开、新请求可加入，持续填充 GPU。提高吞吐，但调度策略会影响单请求延迟和公平性。

**Chunked Prefill**：把超长 Prompt 的 Prefill 拆成多个 Token Chunk，与其他请求 Decode 或短 Prefill 交错，避免一个长 Prefill 长时间独占执行。代价是调度与 Kernel 颗粒度变化，参数需实测。

**面试怎么说**

> Static Batch 同批请求相互等待，容易被最长请求拖住；Continuous Batching 在每轮调度中让完成请求退出、新请求加入，提高槽位利用。Chunked Prefill 进一步把长 Prompt 分段，使其能与 Decode 或短请求交错，改善尾延迟和公平性，但会增加调度复杂度，Chunk 大小需要结合吞吐、TTFT 和 TPOT 调优。

## 6. Prefix Cache、Prompt Cache 和语义缓存有什么区别？

> 面试优先级：★★★★☆｜学习难度：★★★☆☆｜适用岗位：应用、推理平台  
> 掌握要求：能区分 KV 复用和答案复用

**一句话**：它们都在用空间换时间，但复用对象不同——Prefix/Prompt Cache 复用已完成的模型计算，要求 Token 前缀精确一致；语义缓存复用旧答案或旧检索结果，允许问题相似，却更容易过期、错误和越权。

例如两个用户问题文字相似，但权限、时间或上下文不同，错误命中就会返回过期甚至越权结果。复用条件决定了答案是否安全。

**Prefix/KV Cache**：相同模型配置下，新请求 Token 前缀与缓存精确一致时，可复用该前缀已计算的 KV，减少 Prefill；匹配的是 Token 序列和相关配置，不是“语义差不多”。例如缓存 `ABCDEF`，新请求前缀 `ABCDX` 只能复用公共前缀 `ABCD`，`X` 之后的 K/V 依赖不同前文，不能复用。

**Provider Prompt Cache**：模型服务商所说的缓存命中通常也是对可缓存 Prompt 前缀的计算复用，具体最小长度、生命周期和计费规则依厂商。

**语义缓存/答案缓存**：根据 Query 语义相似度复用之前的最终答案或中间 RAG 结果，能省完整推理，但风险更高——时间、用户权限和细微条件变化可能让旧答案失效。

**面试怎么说**

> Prefix Cache 复用精确 Token 前缀对应的 KV 计算，要求模型、模板和前缀一致；语义缓存则尝试对相似问题复用答案或检索结果，不是 KV Cache。后者命中范围更广，但必须把租户、权限、时间和业务版本放进缓存键或校验，否则可能返回错误或越权旧答案。

## 7. TTFT、TPOT、ITL、E2E、P95/P99 分别是什么？

> 面试优先级：★★★★★｜学习难度：★★★☆☆｜适用岗位：全部部署相关岗位  
> 掌握要求：能从指标推断瓶颈

**一句话**：这些指标从不同角度描述用户等待——TTFT 看首 Token，TPOT 看平均生成速度，ITL 看相邻 Token 卡顿，E2E 看总耗时，P95/P99 看大量请求里的尾延迟。只看总耗时会把排队、Prefill 和 Decode 混在一起，也会让少量严重卡顿被平均值掩盖。

- **TTFT — Time To First Token**：请求发出到收到首 Token，包含网络、排队、预处理和 Prefill。
- **TPOT — Time Per Output Token**：输出阶段平均每个新增 Token 时间。
- **ITL — Inter-Token Latency**：相邻 Token 实际间隔，可发现偶发卡顿。
- **E2E Latency — End-to-End Latency**：完整请求总耗时。
- **P50/P95/P99**：分别有 50%/95%/99% 请求不超过该值。
- **Throughput**：单位时间完成的请求或生成 Token 数。

**指标关系**

```text
E2E ≈ TTFT + (output_tokens - 1) × TPOT
```

这是近似，真实 ITL 会波动。

**面试怎么说**

> TTFT 反映用户等首字的时间，容易受排队和 Prefill 影响；TPOT 是 Decode 阶段平均每个输出 Token 时间；ITL 保留逐 Token 抖动，平均 TPOT 可能掩盖卡顿；E2E 是总耗时。P95/P99 关注尾部请求，不能只看平均值。分析时还要按输入长度、输出长度、并发和缓存命中切片。

## 8. INT8、FP8、GPTQ、AWQ、GGUF 和 4-bit 是什么关系？

> 面试优先级：★★★★☆｜学习难度：★★★★☆｜适用岗位：部署、边缘推理  
> 掌握要求：能区分数值格式、量化算法和文件生态

**一句话**：这些名词分属三个层次——INT8/FP8/4-bit 描述数值精度，GPTQ/AWQ 描述训练后量化算法，GGUF 描述常见本地推理文件生态。“4-bit 模型”只说明较低位宽，不能说明用了什么算法、格式或运行时 Kernel，需要分层理解。

**方法直觉**

- GPTQ：训练后逐层利用校准数据减少权重量化误差；
- AWQ：根据激活观察保护重要权重通道；
- SmoothQuant：把激活量化难度平滑迁移到权重侧，常用于 W8A8；
- GGUF K-quants：本地 CPU/GPU 混合推理生态中的多种量化布局。

**三个层次**

1. **位宽/数值格式**：FP8、INT8、INT4、FP4 等；
2. **量化算法**：GPTQ、AWQ、SmoothQuant 等决定如何校准和缩放；
3. **文件/运行生态**：GGUF 常用于 llama.cpp/Ollama，本身包含多种 K-Quant 档位。

**量化不等于一定加速**：需要硬件和 Kernel 原生支持；若频繁反量化、算子回退或 Batch 太小，可能只省显存不加速。还要评测困惑度、任务质量、长上下文和特殊领域切片。

**面试怎么说**

> INT8/FP8/INT4 描述数值位宽，GPTQ、AWQ 等是训练后如何选择 Scale 和降低误差的方法，GGUF 是 llama.cpp 生态常见的模型容器与量化格式集合。量化主要降低权重显存和带宽，但是否加速取决于硬件和 Kernel；必须同时测试质量、TTFT、TPOT、吞吐和显存，不能只看文件变小。

## 9. DP、TP、PP、EP 与通信算子是什么？

> 面试优先级：推理岗★★★★☆｜学习难度：★★★★★｜适用岗位：AI Infra、分布式训练/推理  
> 掌握要求：能按模型是否放得下、延迟和通信选型

### 先理解

并行策略是在设备间切分不同对象：DP 复制模型分请求，TP 切单层张量，PP 切模型层，EP 切 MoE 专家。切分越细，通常越依赖 All-Reduce、All-Gather 或 All-to-All 通信。

模型或流量超过单卡能力后，必须决定复制请求、拆分张量、拆分层还是拆分专家。不同并行方式会引入不同集合通信，算力增加并不保证更快，通信链路和负载均衡可能成为新瓶颈。

### 原理与应用

#### Data Parallel/Replica

每张卡有完整模型，不同请求分给不同副本。提升总吞吐和容错，但单副本必须装下模型。

#### Tensor Parallel

将一层矩阵沿维度切到多卡，同一请求每层需要通信合并。适合单卡放不下或希望单请求使用多卡，但对高速互联敏感。

#### Pipeline Parallel

不同层放不同设备，请求按阶段流动。减少单卡权重，但产生流水线气泡和阶段负载不均，在线低 Batch 延迟可能较差。

#### Expert Parallel

MoE 专家分布在不同设备，Token 根据路由做 All-to-All Dispatch/Combine。对网络拓扑和路由均衡敏感。

#### 通信算子

- All-Reduce：聚合后每卡都有结果；
- All-Gather：收集各卡分片；
- Reduce-Scatter：聚合并把结果分片给各卡；
- All-to-All：每卡向所有其他卡发送不同数据，MoE 常见。

通信软件库负责打包、调度和协议，真实比特最终通过 NVLink、PCIe、InfiniBand/RoCE 等物理链路传输。

### 面试准备

**推荐回答**

> 模型能单卡放下且目标是吞吐时优先多副本 DP；单模型放不下或需加速单请求可用 TP，但每层产生集合通信；PP 按层切分，适合跨设备承载大模型但有流水线气泡；MoE 使用 EP，把专家分卡并通过 All-to-All 发送 Token。选择不能只看卡数，还要看单请求延迟、Batch、KV Cache、互联带宽和容错。

## 10. vLLM 请求生命周期为什么能提高吞吐？

> 面试优先级：推理岗★★★★★；应用岗★★★☆☆｜学习难度：★★★★☆｜适用岗位：AI Infra、部署  
> 掌握要求：理解 API、调度、KV Block、模型执行和输出

### 先理解

vLLM 的吞吐来自请求级调度、Continuous Batching 和分页 KV 管理等协同，而不是单个模型调用更神奇。它让完成请求及时退出、新请求动态加入，并减少 KV 预留浪费。

理解请求从排队、块分配、Prefill 到逐 Token Decode 的过程，才能解释吞吐提升来自哪里，也才能定位 OOM 和队头阻塞。

### 原理与应用

#### 概念链路

```text
HTTP请求
→ Tokenize与参数校验
→ 请求进入调度队列
→ 分配KV Block/检查前缀复用
→ Scheduler选择本轮Prefill/Decode Token
→ Model Executor执行
→ 更新KV与采样
→ Detokenize和流式输出
→ 请求完成并释放Block
```

吞吐来自多项协同：Paged KV 管理、Continuous Batching、优化 Kernel、Prefix Cache、Chunked Prefill 和调度，而不是单一 PagedAttention。

#### `vllm serve` 是否黑箱

命令是一键入口，但可以阅读配置、指标、Trace 和源码，也可以实现自定义调度、Connector 或插件。Ollama/vLLM 都是高层服务工具；是否学到底层取决于是否继续做 Profile、读源码和修改实验，不取决于是不是一条命令启动。

### 面试准备

**推荐回答**

> vLLM 接收请求后做 Tokenize 和参数校验，调度器为请求分配 KV Block，按当前队列选择 Prefill 或 Decode Token 组成连续 Batch，模型执行后更新 Cache、采样并流式返回。请求结束释放 Block。高吞吐来自 Paged KV、Continuous Batching、优化 Kernel 和调度协同，serve 命令只是入口，不代表无法观察 Chunked Prefill 或 KV Cache。

## 11. 投机解码和 Prefill/Decode 分离是什么？

> 面试优先级：★★★☆☆；推理岗★★★★☆｜学习难度：★★★★☆｜适用岗位：AI Infra  
> 掌握要求：掌握加速条件和失败代价

**一句话**：投机解码在减少大模型必须串行执行的 Decode 次数；Prefill/Decode 分离在让两种不同负载使用更合适的资源池。二者都不是无条件加速，额外验证或 KV 传输开销可能抵消收益。

**投机解码**：小 Draft Model 或其他方法先提出多个候选 Token，大 Target Model 一次并行验证，接受连续正确前缀。接受率高可减少 Target Model 串行 Decode 次数；接受率低则 Draft 和验证开销可能抵消收益。

**Prefill/Decode 分离**：把 Prefill 和 Decode 放在不同资源池，分别针对计算密集和带宽/调度特点优化。需要传输 KV Cache，并处理路由、容量匹配、网络和故障，只有在足够规模和稳定负载下才值得。

**面试怎么说**

> 投机解码让较小的 Draft 模型先提出多个 Token，再由目标模型并行验证；接受率高时能减少目标模型的串行步数。PD 分离则把 Prefill 和 Decode 放到不同资源池分别优化，但需要跨池传输 KV Cache。前者取决于候选接受率，后者取决于规模、负载稳定性和网络成本，都应通过端到端压测验证。

# 第二部分：高频场景题

> **本部分共通检查**（每道场景默认适用，下面不再逐题重复）：

> - **先确认**：模型与权重格式、上下文长度、输入/输出长度分布与并发；硬件显存、带宽、互联、操作系统与 Kernel 支持；SLO 更看重 TTFT、TPOT、吞吐、P99、成本还是质量。
> - **压测与观测**：用符合真实长度与并发分布的负载，记录 TTFT、TPOT/ITL、E2E、P50/P95/P99、吞吐、显存、错误和取消率，并用 Trace 分解链路。

> - **异常与降级**：防 OOM、缓存碎片、队头阻塞、节点故障、跨卡通信慢、量化回退和流式断连；用限额、隔离、降级模型、多副本、熔断和明确错误响应保护服务。

## 场景 1：TTFT 很高，但 TPOT 正常，怎么排查？

> 面试优先级：★★★★★｜学习难度：★★★★☆｜适用岗位：部署、平台  
> 掌握要求：能拆网络、排队、预处理和 Prefill

**判断**：第一个 Token 出现以前，请求要经过网络、业务预处理、排队和 Prefill；之后的 Token 才主要属于 Decode。TTFT 高而 TPOT 正常，说明问题更可能发生在“开始生成以前”，不该直接换模型。

**怎么排查**

```text
客户端DNS/TLS
→ 网关与鉴权
→ 请求排队
→ Tokenize/模板/RAG
→ 调度等待
→ Prefill
→ SSE首包缓冲
```

沿这条链按输入长度和并发切片：先看排队是否占主导，再看 Prefix Cache 命中、长 Prompt 干扰、Chunked Prefill、网关缓冲。模型首 Token 已产生但客户端晚收到时，检查代理/SSE 缓冲。TPOT 正常意味着优化重点更可能在首包前链路。

**怎么说**

> TTFT 包含网络、网关、RAG、排队和 Prefill，所以我会用 Trace 分段，而不是直接换模型。先按输入长度和并发切片，检查排队是否占主导，再看 Prefix Cache、长 Prefill 和调度；模型首 Token 已产生但客户端晚收到时检查代理/SSE 缓冲。TPOT 正常意味着优化重点更可能在首包前链路。

**别踩 & 追问**：不要一看到“慢”就换模型或加卡——TPOT 正常已排除了 Decode 主因。若排队时间占 TTFT 大头，先扩副本或限流削峰，而不是优化 Prefill Kernel。

## 场景 2：TTFT 正常，但输出 Token 很慢或偶尔卡顿，怎么办？

> 面试优先级：★★★★★｜学习难度：★★★★☆｜适用岗位：推理  
> 掌握要求：能结合 TPOT/ITL、KV 与调度

**判断**：平均 TPOT 只能说明总体生成速度，ITL 才能看到某两个 Token 之间是否突然停顿。持续慢通常与 Decode 访存或 Batch 有关，偶发卡顿则更像抢占、通信、同步或网络缓冲。

**怎么排查**

先区分“持续 TPOT 偏高”和“少数 ITL 尖峰”，可能原因：

- Decode Batch 太小，GPU 利用率低；
- KV Cache 很长，访存增加；
- 并发竞争、抢占或调度不公平；
- 跨卡通信或慢专家形成尾部；
- Python/Detokenize/网络输出成为瓶颈；
- 某些 Token 步触发额外同步；
- 客户端或代理缓冲。

看逐步 ITL、Batch Size、每步执行时间、KV 长度和通信 Trace，而不是只看平均 TPOT。

**怎么说**

> TTFT 正常说明首包前链路基本健康。我会进一步区分持续 TPOT 偏高和少数 ITL 尖峰，检查每步 Batch、KV 长度、显存带宽、跨卡通信和调度抢占；如果服务端 Token 已生成但客户端晚收到，再检查 Detokenize、SSE 和代理缓冲。这样可以区分模型 Decode 慢和传输层卡顿。

**别踩 & 追问**：持续慢和偶发卡顿的修法不同——前者往往靠增大 Decode Batch 或换 GQA/量化，后者要查抢占、同步和网络。只报平均 TPOT 会漏掉 ITL 尖峰。

## 场景 3：单请求正常，并发一高就 OOM，如何处理？

> 面试优先级：★★★★★｜学习难度：★★★★☆｜适用岗位：部署、应用  
> 掌握要求：能分权重、KV、临时 Buffer 和碎片

**判断**：模型权重是相对固定的显存占用，而每增加一个并发请求都会增加自己的 KV Cache 和调度空间。单请求能跑、并发后 OOM，首先怀疑随请求数量和长度增长的动态显存，而不是权重本身。

**怎么办**

单请求能运行说明权重基本放得下；并发增长主要增加 KV Cache、Batch 激活、采样状态和调度预留。对策：

- 限制最大并发、总 Batch Token 和上下文长度；
- 使用 GQA/MQA 模型、KV 量化或更小模型；
- Paged KV 与合理 Block；
- 长短请求分池；
- 权重量化腾出 KV 空间（Prefix Cache 只减少计算，缓存本身仍占空间）；
- 多副本扩容或 TP；
- 留安全余量，通过阶梯压测确定容量。

**怎么说**

> 我会先把显存拆成权重、KV Cache、临时激活和碎片。单请求正常而并发 OOM，通常是 KV 与总 Batch Token 增长。先限制并发、上下文和总 Token Budget，再评估 Paged KV、KV 量化、GQA 模型或权重量化；必要时多副本扩容。最终通过按长度和并发的阶梯压测确定安全容量，而不是只用理论显存值。

**别踩 & 追问**：不要用单请求显存乘并发数当上限——还有临时激活、碎片和引擎预留。理论算得下不代表稳定，安全容量要靠阶梯压测确认。

## 场景 4：GPU 利用率低，但请求仍排队，为什么？

> 面试优先级：★★★★☆｜学习难度：★★★★★｜适用岗位：AI Infra  
> 掌握要求：不把 GPU Util 当成唯一证据

**判断**：GPU Util 低只说明采样时计算单元没一直繁忙，不代表整个系统有空闲能力。请求可能卡在 CPU、队列、显存带宽、跨卡同步或外部限流，甚至是许多很短的 Kernel 没被采样指标准确捕获。

**怎么分析**

可能原因：

- Decode 小 Batch，矩阵颗粒度低；
- CPU Tokenize、调度或 Python 后处理；
- KV/权重访存瓶颈，计算单元不满但带宽已满；
- 多卡等待通信；
- 请求被限流、锁、连接池或网关阻塞；
- 指标采样窗口掩盖短 Kernel；
- 频繁同步或 Kernel Launch 开销。

需要结合 SM 占用、HBM 带宽、Kernel 时间、CPU Profile、队列和通信分析，而不是只看一个 Util 数字。

**怎么说**

> 我不会只看一个 GPU Util 指标。先用 Trace 判断请求是在网关、CPU 调度还是 GPU 队列等待，再同时观察 SM、显存带宽、Kernel 时间和通信。Decode 小 Batch、访存饱和、CPU Tokenize 或跨卡同步都可能造成“利用率看起来低但吞吐上不去”，需要依据真正占主导的时间段优化。

**别踩 & 追问**：Util 低就加卡往往无效——若瓶颈在 CPU 前处理或访存带宽，加卡只增加空转。要先定位主导时间段再决定优化方向。

## 场景 5：长请求拖慢短请求，如何治理？

> 面试优先级：★★★★★｜学习难度：★★★★☆｜适用岗位：Serving、平台  
> 掌握要求：能设计调度、隔离和公平性

**判断**：长 Prompt 会占用较长 Prefill，长输出又会长期占用 Decode 槽位。如果所有请求共享同一队列，少量长任务就可能阻塞大量交互式短请求，形成队头阻塞和尾延迟。

**怎么办**

- 输入长度/任务类型分池；
- Chunked Prefill；
- 每轮 Token Budget 与公平调度；
- 限制最大 Prompt/输出；
- 交互与离线批任务分服务；
- 优先级队列但防止低优先级饥饿；
- 监控按长度切片的 P95/P99；
- 足够规模时考虑 PD 分离。

**怎么说**

> 我会先按输入和输出长度切片确认干扰来源，再通过 Chunked Prefill、每轮 Token Budget 和公平调度避免长 Prefill 独占。交互请求与离线长任务可分池，设置不同限额和优先级，同时防止低优先级饥饿。评测要比较不同长度桶的 P95/P99，而不是只看整体平均延迟。

**别踩 & 追问**：只看整体平均延迟会掩盖短请求被拖慢的问题，要按长度桶分别看 P95/P99。加了优先级队列还要防止低优先级长任务饿死。

## 场景 6：量化后显存下降，速度却没有提升，为什么？

> 面试优先级：★★★★☆｜学习难度：★★★★☆｜适用岗位：部署  
> 掌握要求：能从 Kernel、反量化和工作负载解释

**判断**：量化首先保证权重更小，不保证硬件更快。若 GPU 没有适合该格式的 Kernel，运行时需要频繁反量化或回退到高精度；若瓶颈本来在 KV、网络或调度，压缩权重也不会改善速度。

**怎么分析**

可能原因：

- GPU 缺乏对应低精度原生支持；
- 算子回退或反量化开销；
- 瓶颈在 KV、网络、CPU 或调度，不在权重带宽；
- Batch/矩阵形状不适合量化 Kernel；
- 量化释放的显存没有用来增加 Batch；
- 比较时输入、输出和并发不一致。

验证：固定工作负载，对比显存、TTFT、TPOT、吞吐、功耗和质量，并检查 Kernel 路径是否发生反量化或回退。

**怎么说**

> 量化后显存下降说明权重压缩生效，但速度取决于硬件和 Kernel 是否原生支持，以及当前瓶颈是否在权重访存。我会固定输入、输出和并发，比较 TTFT、TPOT、吞吐与质量，并检查是否发生反量化或算子回退。如果释放出的显存没有用于扩大 Batch，吞吐也可能没有明显提升。

**别踩 & 追问**：省显存 ≠ 提速——若不把腾出的显存用来加大 Batch，吞吐可能原地不动。量化后必须回归质量，不能只看文件变小。

## 场景 7：多 GPU 部署反而变慢，怎么分析？

> 面试优先级：★★★★☆｜学习难度：★★★★★｜适用岗位：AI Infra  
> 掌握要求：能比较通信与计算收益

**判断**：多卡并行会减少单卡承担的计算，却增加设备之间同步和传输。模型本来能单卡运行、Batch 又很小时，节省的计算可能小于每层通信和等待成本，因此延迟反而上升。

**怎么分析**

可能原因：

- 模型单卡能放下，TP 的每层通信收益不足；
- PCIe/跨节点互联慢；
- 小 Batch、小矩阵导致计算不饱和；
- 切分不均、流水线气泡；
- KV 和采样同步；
- MoE 路由倾斜与 All-to-All；
- 配置导致重复权重或错误拓扑。

先建立单卡基线，Profile 计算/通信比例，再决定多副本、TP、PP 或 EP。

**怎么说**

> 我会先固定工作负载建立单卡基线，再把多卡时间拆成计算、通信和等待。若模型单卡可放下且目标是吞吐，多副本往往比 Tensor Parallel 更合适；只有模型放不下或单请求延迟有明确收益时才考虑 TP。跨节点链路、Batch 大小和拓扑映射必须纳入比较，不能只看 GPU 数量。

**别踩 & 追问**：模型单卡放得下时优先多副本 DP，别默认上 TP。只报“加了几张卡”而不给单卡基线和通信占比，无法判断是否真的更快。

## 场景 8：Prefix Cache 命中率低，怎么排查？

> 面试优先级：★★★★☆｜学习难度：★★★☆☆｜适用岗位：推理平台  
> 掌握要求：能从 Token 级一致性和工作负载解释

**判断**：Prefix Cache 匹配的是最终 Token 序列，而不是人眼看起来相同的文本。一个动态时间戳、空格、角色模板差异或不同 Adapter，都可能让公共前缀提前中断；多副本路由还可能让请求落到没有该缓存的节点。

**怎么排查**

可能原因：

- System Prompt 中包含时间、请求 ID 等动态字段；
- 消息顺序、空格、模板或特殊 Token 不一致；
- Tokenizer/模型/LoRA 配置不同；
- 公共前缀太短；
- 多副本之间 Cache 不共享，请求路由分散；
- Cache 容量小或淘汰快；
- 用户 Prompt 本来就高度个性化。

优化：把稳定系统指令放前面、动态字段后置；统一模板；按模型和 Adapter 粘性路由；统计 Token 公共前缀长度和有效节省，而不只看请求级命中率。

**怎么说**

> 我会记录模板渲染后的 Token 前缀，检查动态字段、空格、消息顺序、模型与 Adapter 是否一致，再看缓存容量、淘汰和多副本路由。优化时把稳定内容前置、动态内容后置并统一模板，必要时做粘性路由。指标除了请求命中率，还要看实际复用了多少 Token 和节省了多少 Prefill 时间。

**别踩 & 追问**：把时间戳、请求 ID 放在 System Prompt 开头会直接打断公共前缀。多副本不共享 Cache 时，不做粘性路由命中率天然偏低。

## 场景 9：P95 正常但 P99 很高，如何通过 Trace 定位？

> 面试优先级：★★★★★｜学习难度：★★★★☆｜适用岗位：平台、SRE、推理  
> 掌握要求：能做尾延迟切片

**判断**：P99 高表示少量请求特别慢，整体平均和 P95 可能看不出来。排查重点不是观察一条普通请求，而是把最慢 1% 按长度、节点、租户和缓存状态分组，再看这些请求共同卡在哪个 Span。

**怎么排查**

1. 对 P99 请求按输入/输出长度、模型、租户、缓存、节点切片；
2. Trace 分为网关、RAG、排队、Prefill、Decode、SSE；
3. 对比正常与异常请求的最长 Span；
4. 查看节点资源、GC、通信、重试、冷启动和依赖超时；
5. 检查是否少量超长请求或特定 GPU；
6. 修复后用相同压力和分布回归。

示例：总耗时 12 秒，如果 RAG 0.4 秒、排队 8 秒、Prefill 1 秒、Decode 2.6 秒，重点是容量和调度而不是换 Embedding。

**怎么说**

> 我会先提取 P99 样本并按输入输出长度、模型、节点、租户和缓存命中切片，再用同一 Trace ID 比较网关、RAG、排队、Prefill、Decode 与 SSE Span。若慢请求集中在某个节点或长输入桶，就进一步检查资源、通信、重试和冷启动。修复后必须用相同流量分布回归尾延迟。

**别踩 & 追问**：P99 高不能靠优化平均请求解决，要专门捞最慢样本切片。若慢请求集中在单个节点或超长输入桶，问题在容量/调度而非模型质量。

## 场景 10：4GB 显存 Windows 电脑如何选择部署方案？

> 面试优先级：★★★☆☆｜学习难度：★★★☆☆｜适用岗位：本地实践、应用开发  
> 掌握要求：能根据格式、显存和系统选择 Ollama/llama.cpp

**判断**：4GB 显存的首要目标不是模拟生产级高吞吐 Serving，而是先让小模型稳定运行并学会模型格式、模板、API、RAG 和性能测量。GGUF 配合 CPU/GPU 混合卸载通常比强行使用面向数据中心 GPU 的框架更合适。

**怎么办**

- 选择 0.5B～3B 级小模型的 GGUF 4-bit/5-bit；
- 使用 Ollama 或 llama.cpp，在 Windows 上便于 CPU/GPU 混合卸载；
- 控制上下文和并发，因为 KV Cache 也占内存；
- 24GB 系统内存可承担部分 CPU Offload，但速度较慢；
- GTX 1650 4GB 缺少新一代 FP8/低精度优势，不适合以 vLLM 学高吞吐 GPU Serving；
- 可以用本机学模型文件、Template、量化、API、RAG 和性能测量，再到云 GPU 学 vLLM。

Ollama 是高层入口但不是完全黑箱，可以观察 Token、上下文、显存、吞吐和请求；若要学习调度器、PagedAttention 和 Chunked Prefill，需要使用 vLLM/SGLang 环境或读源码实验。

**怎么说**

> 4GB 显存更适合部署 0.5B 到 3B 的 GGUF 4-bit/5-bit 模型，使用 Ollama 或 llama.cpp 做部分 GPU Offload，并限制上下文和并发。它足以学习模型加载、Chat Template、量化、API 和 RAG，但不适合作为 vLLM 高吞吐特性的性能实验环境。PagedAttention、Continuous Batching 等内容可以后续在云 GPU 上验证。

**别踩 & 追问**：不要在 4GB 卡上硬跑 vLLM 追高吞吐指标——缺乏对应 Kernel 和显存，学不到真实 Serving 特性。高吞吐相关内容留到云 GPU 再验证。

## 模块口述总结

> 大模型服务先加载权重、配置、Tokenizer 和模板，再由调度器组织 Prefill 与 Decode。Prefill 并行处理输入、影响 TTFT；Decode 逐 Token 读取权重和 KV、影响 TPOT。KV Cache 避免重算但占显存，PagedAttention 优化其分配，Continuous Batching 提高动态请求利用率，Chunked Prefill 缓解长 Prompt 阻塞。容量规划要同时考虑权重、KV、临时 Buffer、并发和长度分布；优化必须基于 TTFT、TPOT、ITL、吞吐和 P99 的分段 Trace，而不是只看 GPU 利用率或 tokens/s。

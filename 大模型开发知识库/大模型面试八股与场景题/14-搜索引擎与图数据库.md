# 第一部分：常规八股

## 1. Elasticsearch 的倒排索引是什么？为什么适合全文搜索？

### 先理解

逐篇扫描正文会随着文档量线性变慢。倒排索引把“词”映射到包含它的文档，并保存词频、文档频率和位置：

```text
cache     → chunk-1, chunk-8, chunk-20
expensive → chunk-1, chunk-9
```

### 原理与应用

写入时 analyzer 把文本转成 token，再构建倒排表；查询先合并候选，再按 BM25 等模型排序。索引还需要 segment、磁盘、缓存和 merge 维护；更新通常写新版本，删除先标记、后由 merge 回收。

### 面试准备

**推荐回答：**

> Elasticsearch 通过 analyzer 把文本变成 token，再构建 term 到文档的倒排表，查询不需要扫描全文，因此适合大规模关键词检索。BM25 负责相关性，但索引结构、字段 mapping、refresh 和 segment 都会影响结果和性能；倒排索引不是免费的目录，会占内存、磁盘和写入成本。

## 2. `text`、`keyword`、`nested` 应该怎么选？

### 先理解

`text` 会分析，适合全文；`keyword` 保留完整值，适合精确过滤、排序和聚合。字符串可以使用多字段：

```json
"title": {
  "type": "text",
  "fields": {"raw": {"type": "keyword"}}
}
```

普通对象数组可能交叉匹配不同元素；需要元素级关联时使用 `nested`，但会增加内部文档和查询成本。

### 原理与应用

`tenant_id`、状态、枚举和 ID 通常是 keyword；标题、正文是 text；时间字段用于范围/排序；向量字段单独映射。mapping 设计必须从查询问题倒推，改字段类型通常需要新索引和重建。

### 面试准备

**推荐回答：**

> `text` 解决词级全文相关性，`keyword` 解决完整值过滤、排序和聚合，字符串经常采用 text + keyword 多字段。数组元素之间需要保持关联时用 nested。mapping 不是上传 JSON 后再随意修改，字段类型或 analyzer 变化通常通过新索引和 alias 切换。

**常见追问：**

- `tenant_id` 映射成 text 会怎样？term 过滤和聚合可能不符合完整 ID 语义。
- `nested` 越多越好吗？不是，只有需要元素边界时才使用。

## 3. analyzer、`match`、`term` 和 BM25 如何配合？

### 先理解

分析链可能包括字符过滤、tokenizer、大小写归一、停用词和词干化；写入和查询要使用兼容的 analyzer。中文、英文、代码和版本号的分词需求不同。

### 原理与应用

- `match` 适合经过分析的全文字段；
- `term` 适合 keyword、数字、枚举完整值；
- `match_phrase` 关注词序/邻近；
- wildcard/正则/前缀查询需限制输入和字段。

BM25 综合词频、逆文档频率和字段长度归一；它不是语义模型，不能稳定理解同义改写和跨语言表达。

### 面试准备

**推荐回答：**

> 先看字段 mapping 再选查询：全文用 match，确定值用 term，短语用 match_phrase；权限、租户和状态放 filter，不参与打分。BM25 处理关键词相关性，语义问题可增加向量召回；召回异常时先查看 analyzer/token，而不是盲目调大 top-k。

## 4. query context 和 filter context 为什么要分开？

### 先理解

query context 要计算相关性，适合标题、正文和语义条件；filter context 只判断真假，适合 tenant、权限、状态和时间范围。

```json
{
  "query": {
    "bool": {
      "must": [{"multi_match": {"query": "缓存击穿", "fields": ["title^2", "content"]}}],
      "filter": [
        {"term": {"tenant_id": "acme"}},
        {"term": {"status": "ready"}}
      ]
    }
  }
}
```

### 原理与应用

filter 可以提前缩小候选并更容易缓存。RAG 不能先全局召回、重排后再过滤权限，否则无权文档可能进入模型上下文、日志或分数统计。版本和删除状态也应在召回阶段判断。

### 面试准备

**推荐回答：**

> query 负责相关性，filter 负责无打分的确定条件。权限、租户和版本必须在召回阶段进入 filter，不能把安全边界推迟到生成前最后一步。混合检索时 BM25/kNN 的候选范围都要遵守同一权限条件。

## 5. 为什么写入成功后暂时搜不到？refresh、segment、translog 分别是什么？

### 先理解

Elasticsearch 是近实时搜索。写入请求成功只是被接受；refresh 后新 segment 才对搜索可见。translog 记录尚未安全写入 segment 的变更，恢复时可重放；可搜索、请求成功、磁盘持久化不是同一时刻。

### 原理与应用

频繁 `refresh=true` 会产生大量小 segment 和 merge 压力；force merge 通常适合不再写入的只读索引。高频更新会写新版本，删除要等 merge 回收空间。

### 面试准备

**推荐回答：**

> 我先区分业务承诺的是“已保存”还是“已可搜索”。如果可接受近实时，就返回 processing，refresh 后再标 ready；只有确实需要立即搜索时才局部等待 refresh。translog 与搜索可见是不同层，不能用强制 refresh 解决所有一致性和恢复问题。

### 常见追问

- `refresh=true` 能解决写入失败吗？不能，它只影响搜索可见时机；bulk item 错误、mapping 和权限问题仍要单独处理；
- force merge 适合高频写入索引吗？通常不适合，频繁 merge 会增加 IO；更适合基本只读的索引；
- “已可搜索”是否等于“可恢复”？不等于，还要看 translog、快照和事实源版本。

## 6. 分片、副本、深分页和 PIT 如何理解？

### 先理解

primary shard 是数据和写入单元，replica shard 提供冗余和读扩展；一次搜索通常 fan-out 到多个分片再合并。分片过多增加协调和网络，过少限制容量和并行。

深分页 `from/size` 要让每个分片保留大量候选；连续下一页使用稳定排序 + `search_after`，需要跨请求一致视图时配合 PIT。PIT 有资源和过期时间，不能当永久快照。

### 原理与应用

副本不是独立备份，误删和整个集群故障仍可能一起影响；全量导出应使用离线流程。分页排序要有 `_score`、时间和稳定 ID 等 tie-breaker，避免同分结果漂移。

### 面试准备

**推荐回答：**

> 分片决定 fan-out、容量和并行，副本提高读扩展和节点故障可用性但不是备份。浅页可用 from/size，深页用 search_after，跨多次请求需要 PIT；PIT 和副本都不能替代快照恢复。

### 常见追问

- 分片越多越好吗？不是，查询 fan-out、协调合并和集群元数据都会增加；
- `search_after` 能随机跳到第 1000 页吗？不能，它依赖上一页排序值；随机跳页需要其他产品/离线方案；
- PIT 为什么要过期？它会保留搜索视图和资源，长期不关闭会增加段和内存压力。

## 7. mapping 或 analyzer 变更为什么要新建索引？

### 先理解

字段类型、分析器和索引结构写入后通常不能安全原地改变。常见零停机流程：

```text
创建 index-v2
  → 回填历史数据
  → 处理增量事件
  → 抽样比较数量、token、召回和权限
  → alias 原子切换
  → 保留回滚窗口
```

### 原理与应用

回填期间新事件可能继续到达，需要双写、Outbox/CDC 或按版本补偿；alias 让应用不硬编码具体索引名。旧索引保留到验证和回滚窗口结束，清理前确认快照和磁盘。

### 面试准备

**推荐回答：**

> mapping 变更通常通过新索引、回填、增量补偿和 alias 切换完成。关键不是只执行 reindex，而是处理切换期间的增量、版本、权限、查询回归和回滚；副本不能替代快照。

## 8. BM25、kNN、Hybrid、RRF 和 Rerank 怎么组合？

### 先理解

```text
问题
  ├─ BM25：错误码、类名、专有词
  ├─ kNN：语义相近表达
  └─ 合并去重 → RRF/分数归一 → Cross-Encoder 重排
```

### 原理与应用

BM25 和向量分数不在同一尺度，不能未经验证直接相加；RRF 可以按排名融合，重排模型成本高，通常只处理前几十条。过滤、版本、chunk 元数据和上下文长度要在链路中保留。

切块决定召回上限：太长主题混杂，太短定义和条件被拆开；返回给模型的证据应带标题、来源、页码、权限和版本。

### 面试准备

**推荐回答：**

> BM25 擅长术语和精确词，kNN 擅长语义改写；我会先分别取候选，再去重、按排名/归一分数融合，最后对较小候选集做重排。权限和版本先过滤，分数需要评测后再融合，不能直接把两个分数相加。

### 常见追问

- 为什么先过滤权限？无权文档不能进入候选、重排、日志或 prompt，最后过滤已经太晚；
- RRF 是否不需要调参？仍需调候选数量、窗口、去重和最终 context，并用金标准验证；
- 重排为什么不对全库做？交叉编码器成本高，通常只处理已过滤的有限候选。

## 9. Neo4j 的节点、关系、属性和 Cypher 如何理解？

### 先理解

属性图由节点、带方向和类型的关系、节点/关系属性组成：

```text
(:Person {id:'p-1'})-[:MEMBER_OF {since:'2025'}]->(:Team {id:'team-1'})
```

### 原理与应用

节点表示人、团队、服务、文档和技术；关系表示拥有、属于、依赖、提及；关系属性保存角色、时间、来源和置信度。关系方向要统一，实体要有稳定 canonical ID，历史关系不能被当前状态覆盖。

```cypher
MATCH (p:Person)-[:MEMBER_OF]->(t:Team {name: $name})
WHERE t.tenant_id = $tenant_id
RETURN p.person_id, p.name;
```

### 面试准备

**推荐回答：**

> Neo4j 用节点、关系和属性表达实体及其连接，Cypher 通过模式匹配路径。图数据库擅长多跳关系和解释路径，但仍需要稳定 ID、唯一约束、权限、版本和查询边界；它不是无结构 JSON，也不是全文搜索引擎。

## 10. `MATCH`、`CREATE`、`MERGE`、索引和约束怎么用？

### 先理解

`MATCH` 读取模式，`CREATE` 每次创建，`MERGE` 匹配或创建。`MERGE` 必须使用稳定身份并配合唯一约束：

```cypher
CREATE CONSTRAINT document_id_unique IF NOT EXISTS
FOR (d:Document) REQUIRE d.document_id IS UNIQUE;

MERGE (d:Document {document_id: $id})
ON CREATE SET d.created_at = datetime()
SET d.version = $version;
```

### 原理与应用

关系也要有 source_id/有效时间/事件版本，否则同一关系可能重复或覆盖历史。索引服务于常用起点和精确过滤；`PROFILE` 检查是否全标签扫描、笛卡尔积、扩展后才过滤和路径数量。无上限的 `[*]` 在大图上可能指数爆炸。

### 面试准备

**推荐回答：**

> CREATE 适合确定的新实体，MERGE 适合按稳定唯一键幂等写入；唯一约束保证并发导入不产生重复节点，索引帮助找到起点。图查询先用索引锁定少量起点，再限制方向、深度和结果数，PROFILE 用来验证实际行数和笛卡尔积。

## 11. GraphRAG 如何和向量检索配合？

### 先理解

```text
问题 → 实体链接
  → Cypher 取结构路径和关系事实
  → BM25/kNN 取文本 chunk
  → 合并去重/重排
  → 生成带来源和路径的答案
```

### 原理与应用

图负责“谁与谁如何连接、经过几跳”，搜索负责“哪些文本语义相近、原文证据是什么”。离线抽取必须保存原文 span、canonical ID、模型版本、置信度和 tenant；同名实体不能只凭 name 合并。

权限和版本要在 Cypher 与搜索 filter 两边都执行。返回给模型的路径带关系类型、时间和来源，不能让模型把 `MENTIONS` 误说成 `OWNS`。

### 面试准备

**推荐回答：**

> GraphRAG 不是把所有文本变成图，而是让图做结构导航和多跳关系，让 BM25/向量层提供文本证据。在线要先做实体链接和权限过滤，再取有限路径和 chunk，合并去重后重排并引用来源。图的收益是关系和解释，代价是抽取、去重和维护复杂度。

## 12. 为什么 BM25 和 kNN 的分数不能直接相加？

### 先理解

BM25 分数受词频、文档频率、字段长度和候选集合影响；向量分数受模型、距离函数、维度和归一化影响。两个分数的数值尺度不同，跨查询也不稳定。

### 原理与应用

可以分别取关键词和向量候选，再用排名融合（如 RRF）、归一化后加权或重排模型合并。重排模型成本更高，只处理前几十条；评估要看 Recall@k、MRR/nDCG、延迟和引用正确率。

### 面试准备

**推荐回答：**

> BM25 适合术语和精确词，kNN 适合语义相似，但分数不在同一尺度。我会先分别召回，去重后做 RRF/归一化或重排，并用标注集验证权重和延迟，不能未经评测直接把两个分数相加。

### 常见追问

- 归一化是否能保证分数可比？不能自动保证，不同查询和候选分布仍需验证；
- 什么时候只用 BM25？错误码、类名、版本号等精确术语占主导且语义改写收益有限时；
- 什么时候需要重排？候选相关但排序混乱、需要结合多个字段或证据质量时，接受额外延迟换准确率。

## 13. 为什么深分页要用 `search_after` 和 PIT？

### 先理解

`from/size` 深页要求每个分片保留大量候选，再由协调节点丢弃前面的结果，页码越深内存和网络越高。`search_after` 使用上一页最后一条排序值继续向后取；PIT 保留相对一致的搜索视图。

### 原理与应用

排序要有稳定 tie-breaker（时间 + ID）；PIT 需要过期时间和关闭策略，不能无限占资源。随机跳页和全量导出使用不同方案，不能把 search_after 当导出 API。

### 面试准备

**推荐回答：**

> 浅页可以 from/size，连续翻页使用稳定排序和 search_after，需要跨请求减少 segment 变化带来的漂移时结合 PIT；PIT 不是永久快照，全量导出走离线流程。分页游标还要绑定过滤条件和权限。

### 常见追问

- 排序为什么需要 tie-breaker？同一时间或同分文档没有稳定次序，下一页可能重复/漏读；
- PIT 能锁住所有数据变化吗？它提供相对一致的搜索视图，但会占资源且不是数据库事务快照；
- 用户修改过滤条件后能复用旧游标吗？不能，游标应绑定 query、filter、排序和权限上下文。

## 14. Elasticsearch 与 Neo4j 的投影落后时，如何表达版本和状态？

### 先理解

数据库保存文档事实和 version，ES chunk、Neo4j 关系和任务事件都携带同一版本；只有投影达到目标版本，才把文档标为 ready。

### 原理与应用

旧事件用版本条件拒绝，删除用 tombstone/版本防止旧写复活。API 可以返回 processing、ready、failed 和 last_indexed_version；对账发现数据库有而投影没有时补发/重建。

### 面试准备

**推荐回答：**

> 我不会把数据库提交直接等同于搜索和图都完成。事实表记录当前版本，投影带版本并由对账确认；用户看到 processing 或旧版本时间，旧事件不能覆盖新删除。这样最终一致是可查询、可恢复的，而不是隐藏的错觉。

### 常见追问

- 数据库版本、事件版本和投影版本有什么区别？数据库版本是当前事实，事件版本描述发生顺序，投影版本表示已经应用到哪一步；
- 为什么删除也要带版本？旧的更新事件可能晚到，若没有 tombstone/版本条件会把已删除文档重新写回；
- 投影长期落后怎么办？暴露 last_indexed_version、pending age 和失败原因，通过对账生成限速补偿，而不是静默返回 ready。

## 15. 什么时候不应该使用 Neo4j？

### 先理解

只按标题/正文查相似、按时间过滤、做普通聚合时，PostgreSQL + Elasticsearch/向量层更简单。图的收益来自多跳路径、关系约束、实体邻居和可解释推理。

### 原理与应用

把所有 chunk 都变成图节点会增加实体抽取、去重、关系版本和权限治理成本；文本全文和向量相似也不应靠 Neo4j `CONTAINS` 扫描。选型要从问题的关系复杂度和查询路径证明收益。

### 面试准备

**推荐回答：**

> 如果需求只是文本相似和过滤，我不会为了组件完整而上图数据库；当问题需要多跳关系、路径限制和可解释来源时，才用 Neo4j 做结构投影，并让 ES/向量层负责文本证据。主动说明“不使用图”的边界比堆组件更可靠。

### 常见追问

- 关系复杂度怎么判断？看是否需要多跳路径、邻居聚合、路径约束、有效时间和来源解释，而不是看数据量大小；
- 不上 Neo4j 如何处理关系？可以先用关系库表或搜索投影，等关系查询成为瓶颈再迁移，保持事实源和 ID 稳定；
- 上图后仍需要 ES 吗？通常需要，图负责结构导航，全文/向量层负责文本证据和相关性。

# 第二部分：高频场景题

## 场景 1：写入成功但 Elasticsearch 搜不到，怎么排查？

### 先判断

区分请求接收、refresh 可见、translog/磁盘恢复、alias 路由和业务 ready 状态。

### 原理与应用

写入链至少有“客户端收到响应 → 文档进入目标 index/primary → refresh 后可搜索 → 业务版本达到要求”。任何一层成功都不能推出下一层成功；如果查询带 tenant、visibility、status 或版本 filter，文档即使存在也可能被业务条件排除。

```text
写入响应
  ├─ index/alias 是否正确
  ├─ mapping/analyzer 是否接受并产生预期 token
  ├─ refresh/segment 是否已可见
  └─ 版本、权限、deleted 状态是否允许返回
```

### 处理步骤

检查索引/alias、mapping/analyzer、refresh、tenant/status filter、文档版本和索引是否关闭；接口只返回 processing，refresh 后且版本达到要求才 ready。不要默认全局 `refresh=true`。

若是 bulk，逐条查看 item 错误并记录失败文档；若是迁移或回填，核对 v1/v2 的 alias 和增量事件；若是持续不可见，比较数据库版本、ES `_seq_no`/应用版本和对账结果，避免把近实时延迟误判为丢数据。

### 参考回答

> 写入成功不等于立即可搜索。我会先确认写入索引和 alias，再查 analyzer、filter、refresh 和版本状态；若只是近实时延迟，保留 processing 状态，完成 refresh 后再标 ready。持续失败则通过 Outbox/任务状态重试和对账。

### 常见误区

- 所有写入都强制 `refresh=true`，把可见性问题变成 merge 和 IO 问题；
- 只检查 HTTP 200，不检查 bulk item、alias、租户 filter 和版本；
- 直接重建全索引，却没有确认数据库事实、增量事件和回滚窗口；
- 用副本或 translog 解释权限过滤造成的“搜不到”。

## 场景 2：RAG 关键词命中，但语义问题召回不到，怎么办？

### 先判断

先确认金标准证据是否真的在文档中、文档是否成功切块和索引，再区分关键词召回、向量召回、权限过滤、重排还是生成阶段出问题。不要把“答案错”直接归因于 embedding。

### 原理与应用

保存一条 Bad Case 的完整证据：原文、chunk、analyzer token、mapping、embedding 版本和向量维度、kNN 参数、BM25 候选、filter、重排输入、最终 context 和答案引用。可以固定生成，先比较召回；再固定召回，比较重排和模型。

### 处理步骤

1. 用 Exact/穷举确认检索上限；
2. 检查切块是否把定义、条件和例外拆开；
3. 检查中文/代码/型号 analyzer 和 keyword 字段；
4. 比较 BM25、kNN、Hybrid、filter 前后候选数；
5. 查看重排是否丢掉正确 chunk，最后再看生成；
6. 用 Recall@k、MRR/nDCG、引用正确率、延迟切片评估。

### 参考回答

> 我会沿“文档是否存在 → 解析切块 → analyzer/mapping → 初始召回 → 权限过滤 → 重排 → Context → 生成”定位，每次只替换一个环节做对照。保存 token、候选和版本证据，用 Recall@k、引用正确率和 P99 验证，不同时改 Embedding、Chunk 和 Prompt。

### 常见误区

- 一看到语义召回失败就更换 embedding，没确认文档是否已入索引或被权限 filter；
- 同时修改切块、模型、top-k 和 Prompt，无法知道是哪一步改善或退化；
- 只用最终答案主观判断，不保存候选 chunk、token、版本和引用；
- 用无权或已删除文档填满候选，再在生成后补过滤。

## 场景 3：Top-K 小了证据不足，大了噪声和延迟增加，怎么选？

### 先判断

区分候选 k、重排 k 和最终 context k；查看正确证据在第几名、重复 chunk 比例、上下文 token 和生成 P99。不同问题类型、文档类型和租户规模可能需要不同策略。

### 原理与应用

先用较大的候选集保证召回，再重排到较小集合；对同一文档去重、保留标题路径和必要的相邻 chunk，设置低分阈值和证据不足拒答。k 不是越大越好，过大可能把冲突/无关文本送给模型。

### 处理步骤

1. 建立问题集和金标准 chunk；
2. 画 Recall@k、MRR/nDCG、context token、延迟和成本曲线；
3. 分开调 BM25/kNN 候选 k、rerank k 和最终 context k；
4. 观察去重、相邻扩展、权限过滤和低分拒答；
5. 按问题类型做分层配置并保留默认上限。

### 参考回答

> 我不会给所有问题固定一个 k。先用较大候选保证 Recall，再用重排和去重控制最终上下文；根据金标准、P99、token 成本和引用准确率选择拐点，并保留低分拒答，避免用噪声填满上下文。

### 常见误区

- 把候选 k、重排 k 和最终 context k 当成同一个参数；
- 只看 Recall，不看重复 chunk、冲突证据、token 成本和 P99；
- 通过无限增大 k 掩盖切块、权限 filter 或 embedding 质量问题；
- 为了填满上下文强行加入低分证据，不允许拒答。

## 场景 4：Elasticsearch 集群突然变慢，怎么定位？

### 先判断

先确认是所有索引还是单个租户/索引、写入和搜索是否同时变慢、平均还是 p99 变差。保存慢查询 DSL、参数、分片、节点和时间点。

### 原理与应用

查询可能慢在 wildcard/正则、复杂聚合、深分页、kNN、分片 fan-out、协调节点合并；写入可能慢在 refresh、segment merge、translog、磁盘和线程池。GC、磁盘水位、网络、节点热点和分片倾斜也会放大长尾。

### 处理步骤

1. 看 p95/p99、慢查询、线程池拒绝、查询类型和返回大小；
2. 用 profile/API 判断是分片执行、排序聚合还是协调合并；
3. 查看 segment、merge、GC、磁盘、网络、节点和副本分布；
4. 限制坏查询、深分页和复杂聚合，必要时调整 filter/索引；
5. 只在确认 fan-out/资源瓶颈后扩分片或节点，不盲目 force merge；
6. 灰度后观察 P99、错误、磁盘和召回质量。

### 参考回答

> 我先按查询类型和 p99 定位，不直接全局扩容。区分全文、聚合、wildcard、深分页、kNN 和写入 merge，再用分片 fan-out、GC、磁盘、线程池和节点热点证据修复；复杂查询先限流/改写，扩容要验证分片和下游成本。

### 常见误区

- 只看节点存活，不看线程池拒绝、分片倾斜、磁盘水位和 merge；
- 看到延迟上升就全局 force merge 或盲目增加分片；
- 把深分页、wildcard、聚合和 kNN 当成同一种慢查询；
- 扩容后不回归召回、权限、错误率和 P99。

## 场景 5：mapping 或 analyzer 需要改变，如何不停机迁移？

### 先判断

确认是字段类型、analyzer、向量维度、分词规则还是 shard/生命周期需求变化；评估数据量、写入速率、磁盘余量、增量事件和回滚窗口。

### 原理与应用

```text
index-v1(alias knowledge)
  → 创建 index-v2
  → 回填历史
  → 接收/补偿增量
  → 对比数量、token、召回、权限、版本
  → alias 原子切换
```

回填期间新事件不能丢，可用双写、Outbox/CDC 或按 version 补偿；旧索引保留快照和回滚窗口。应用只访问 alias，不硬编码索引版本。

### 处理步骤

1. 先发布兼容查询和版本字段；
2. 创建 v2 mapping/analyzer，验证小样本 token 和查询；
3. bulk 回填并记录失败、进度、版本和磁盘；
4. 处理回填期间增量，做数量和版本对账；
5. 抽样比较 Recall@k、P99、权限、聚合和错误；
6. 原子切 alias，保留 v1 到回滚窗口结束。

### 参考回答

> 我会新建 v2、回填、处理增量、抽样比对 token/召回/权限/数量，再用 alias 原子切换。mapping 迁移的难点是切换期间的增量缺口和回滚，不是只运行一次 reindex；旧索引和快照保留到验证完成。

### 常见误区

- 只执行 reindex，不处理迁移期间的增量事件；
- alias 切换前不对比文档数、版本、token、权限和查询结果；
- v2 未验证就删除 v1，没有回滚窗口和独立快照；
- mapping 变化后仍让应用硬编码旧索引名。

## 场景 6：Neo4j 出现大量重复人物，怎么处理？

### 先判断

区分重复来自 `CREATE`、不稳定 `MERGE` 键、缺少唯一约束、不同来源 canonical 不一致，还是并发导入。名字相同不等于同一实体。

### 原理与应用

实体应使用外部稳定 ID；别名、邮箱、组织、时间和来源作为证据，不直接作为唯一身份。关系保留 source_id、valid_from/to、confidence 和事件版本，合并动作需要可审计和可回滚。

### 处理步骤

1. 统计重复 label/ID、来源和导入批次；
2. 建立唯一约束，修复未来导入的 MERGE key；
3. 按多种证据生成合并候选，低置信度进入人工审核；
4. 合并节点和关系时保留来源、历史和旧 ID 映射；
5. 重放搜索/GraphRAG 投影并对账路径；
6. 监控重复率、孤儿关系和合并回滚。

### 参考回答

> 我不会按名字批量合并或删除。先查 CREATE/MERGE 键、唯一约束和来源批次，用 canonical ID 和邮箱/组织/时间证据生成可审计候选，确认后合并并保留历史、来源和回滚，再重放下游投影。

### 常见误区

- 把姓名相同当成同一人，直接删除其中一个节点；
- 只修当前节点，不修复未来导入的 MERGE 键和唯一约束；
- 合并关系时丢失来源、有效时间和旧 ID 映射；
- 合并后不重建 ES/GraphRAG 投影，导致搜索和图仍指向旧实体。

## 场景 7：GraphRAG 关系回答错误，如何定位？

### 先判断

先确认错误是实体链接错、关系类型/方向错、过期关系被使用、Cypher 路径过宽，还是文本证据与图关系冲突。最终答案正确不代表图数据正确。

### 原理与应用

保存完整 trace：问题、实体链接、canonical ID、Cypher、返回路径、关系来源 span、抽取模型/版本、confidence、tenant 和最终 context。`MENTIONS`、`OWNS`、`MEMBER_OF` 的语义不能被模型自行混淆。

### 处理步骤

1. 用原文 span 核对实体和关系是否真实存在；
2. 检查 canonical 去重、关系方向、有效时间和版本；
3. PROFILE Cypher，限制起点、hops、结果和权限；
4. 对低置信度关系降权、要求多证据或进入审核；
5. 把图事实与 ES chunk 证据分别评估，再看生成；
6. 修复数据/模板后重放版本，不能只改 prompt。

### 参考回答

> 我会保存实体链接、Cypher、路径、来源 span、版本和置信度，沿抽取—去重—查询—生成逐层定位。低置信度关系不直接当事实，权限和有效时间在查询阶段过滤；修复图数据和模板后再重放，不用 prompt 掩盖错误。

### 常见误区

- 只改 Prompt，不核对关系抽取原文和方向；
- 把 `MENTIONS`、`OWNS` 等不同语义交给模型自由解释；
- 用无限深度遍历“找更多证据”，让错误关系和路径爆炸一起放大；
- 忽略有效时间、版本和租户过滤，把旧关系当当前事实。

## 场景 8：跨租户搜索或图查询可能泄露数据，怎么办？

### 先判断

确认权限是按租户、项目、角色还是文档共享；检查 ES 候选、Neo4j 路径、重排输入、日志和缓存是否会接触无权对象。共享实体可能把多个租户连到同一条路径。

### 原理与应用

权限条件要同时进入 ES filter 和 Cypher：

```cypher
MATCH (d:Document {document_id: $id})
WHERE d.tenant_id = $tenant_id
  AND d.version >= $min_version
  AND d.deleted_at IS NULL
RETURN d;
```

不能先全局召回/遍历、重排后才过滤，因为标题、分数、路径和向量可能已进入日志或模型上下文。缓存 key、消息 payload 和审计也要带 tenant。

### 处理步骤

1. 统一服务端生成 tenant/role/project filter；
2. ES、Neo4j、缓存和消息都校验同一权限边界；
3. 共享节点路径逐边检查可见性，避免只过滤终点文档；
4. 重排和 LLM context 只接收已授权证据；
5. 日志记录 ID/摘要，不记录无权正文和分数；
6. 用跨租户测试、审计和随机抽样验证。

### 参考回答

> 权限不是最后一步的 API 过滤，而是召回和图遍历的候选边界。tenant、角色、项目和版本条件同时进入 ES filter 与 Cypher，共享实体路径也逐边检查；日志、重排和模型上下文不保存无权数据，并用跨租户测试验证。

### 常见误区

- 先全局召回/遍历再过滤，导致无权标题、分数或路径已经泄露；
- 只过滤终点文档，不检查共享实体和中间关系的可见性；
- 缓存 key、消息 payload 和日志不带 tenant，绕过了查询层边界；
- 只做单元测试，不做跨租户、删除后和旧版本的端到端验证。

## 场景 9：某租户图遍历超时，怎么办？

### 先判断

确认是起点过多、节点度数异常、关系重复、路径深度过大、笛卡尔积、权限过滤太晚还是某个租户数据量异常。保存 Cypher、参数、PROFILE、耗时和返回规模。

### 原理与应用

无约束的 `MATCH (n)-[*1..4]->(m)` 可能从全图扩展，路径数随深度和度数快速增长。应先用 label/唯一 ID/tenant 锁定起点，再限制 hops、方向、limit；高频邻居可以预计算，但要带版本和失效策略。

### 处理步骤

1. PROFILE 查看起点行数、Expand、过滤位置、路径数和返回行数；
2. 增加 tenant/label/ID 起点条件和有效时间/状态 filter；
3. 限制最大 hops、结果数和超时，拆分多跳查询；
4. 清理重复关系和高度热点节点，必要时预计算；
5. 对热点租户设置配额/舱壁，不全局提高事务超时；
6. 观察 p95/p99、数据库 CPU、锁和其他租户影响。

### 参考回答

> 我会先用 PROFILE 定位起点、扩展、过滤和路径爆炸，而不是全局调大超时。先用 tenant/label/ID 锁定起点，限制 hops/limit 和方向，拆分多跳或预计算高频关系；同时按租户限流，避免一个大图拖垮所有请求。

### 常见误区

- 用增大事务/查询超时掩盖无界路径和笛卡尔积；
- 不区分某个租户的热点数据和全局图模型问题；
- 预计算邻居却没有版本和失效策略，返回过期关系；
- 只优化 Cypher，不限制结果大小、字段和模型上下文预算。

# 第三部分：一分钟总复习

## 必须能闭卷回答

- mapping、`text/keyword`、analyzer、倒排、BM25、query/filter；
- refresh、segment、translog、分片、副本、深分页、PIT、alias；
- BM25 + kNN + filter + rerank 的混合检索链；
- Neo4j 节点/关系/属性、Cypher、MATCH/CREATE/MERGE、约束/索引/PROFILE；
- GraphRAG 的实体消歧、有限图扩展、文本证据、权限和版本。

## 模块口述总结

> 搜索系统先从 mapping 和 analyzer 开始，text 做全文、keyword 做精确过滤和聚合；倒排和 BM25 负责关键词，refresh/segment/translog 解释写入、可见和恢复的时间差，分片与副本影响 fan-out、容量和可用性，深分页使用 search_after/PIT。Neo4j 用节点、关系、属性和稳定 ID 建模，Cypher 先锁定起点再有限遍历，唯一约束和 PROFILE 保证数据与性能。GraphRAG 让图负责结构路径，让 ES/向量负责文本证据，两边都要做权限、版本和来源校验。

3. 为什么深分页要用 search_after/PIT？
4. BM25 和 kNN 的分数为什么不能直接相加？
5. 为什么副本不是备份？
6. MERGE 为什么仍需要唯一约束和稳定 ID？
7. GraphRAG 如何避免实体错误和跨租户泄露？

## 1. 为什么数据库常用 B+Tree？

### 先理解

数据库通常按页读写，而不是每次从磁盘取一个键。B+Tree 的内部节点能放很多有序键，树高较低；所有数据键集中在叶子层，叶子之间可以顺序扫描。

```text
                 [40 | 80]
                /    |    \
       [10 20 30] [40 60] [80 90 100]
              └────────叶子顺序────────┘
```

### 原理与应用

等值查询从根走到叶子；范围查询先找到下界，再沿叶子链读取。普通二叉树可能退化为链，Hash 适合等值但没有天然范围顺序，B+Tree 在页局部性、范围、排序和低树高之间取得平衡。

索引不是免费的内存目录：它需要磁盘、缓存和写入维护。结果集很大时，走索引再回表可能比顺序扫描更慢；最终是否使用索引由优化器结合统计信息和成本判断。

### 面试准备

**推荐回答：**

> B+Tree 适合数据库页式存储：一个节点能放很多键，树高低；叶子有序并可顺序扫描，所以同时支持等值、范围和排序。Hash 更适合等值，普通二叉树可能退化；但最终是否使用索引，还要看选择性、回表成本、统计信息和结果集大小。

**常见追问：**

- 为什么索引越多不一定越好？每次写入都要维护，索引还会占空间并增加优化器选择成本。
- 为什么叶子有序重要？范围查询可以从一个位置连续读取，不必对每个值重新从根查找。
- B+Tree 是否一定比 Hash 快？不是，要看访问模式和实现；范围、排序和前缀查询更适合 B+Tree。

## 2. InnoDB 的聚簇索引、二级索引和回表是什么？

### 先理解

InnoDB 主键索引的叶子节点保存整行数据，常称聚簇索引；普通二级索引叶子通常保存索引列和主键值。二级索引找到主键后，再读取聚簇索引中的整行，就是回表。

```text
二级索引 (tenant_id, created_at)
       ↓ 找到 id=100
聚簇索引 (PRIMARY KEY id)
       ↓ 读取 content、status 等列
```

### 原理与应用

覆盖索引把查询所需列包含在二级索引中，可以减少回表，但索引会变宽，写入和缓存成本会上升。主键过长还会被复制到每条二级索引，放大空间。

PostgreSQL 常见模型是 heap 表加独立索引；索引项指向 heap tuple，Index Only Scan 仍受 visibility map 影响。不能把 InnoDB 的聚簇存储直接套到 PostgreSQL。

### 面试准备

**推荐回答：**

> InnoDB 聚簇索引叶子保存整行，二级索引一般保存索引列和主键。二级索引查到主键后再次读取聚簇页叫回表；覆盖索引能减少回表，但会增加索引体积和写放大。PostgreSQL 是 heap 加独立索引，Index Only Scan 还要看 visibility map。

**常见追问：**

- `SELECT *` 为什么容易回表？索引通常不包含所有列。
- 覆盖索引是不是越宽越好？不是，要用查询频率、写入成本和索引大小换算。
- 主键为什么影响二级索引？二级索引叶子要携带主键定位整行。

## 3. 联合索引 `(a,b,c)` 如何使用？

### 先理解

联合 B+Tree 先按 `a` 排，在相同 `a` 内按 `b` 排，最后按 `c` 排。因此从 `a` 开始的连续前缀最容易形成窄扫描区间。

```sql
CREATE INDEX idx_message_tenant_conv_time
ON message (tenant_id, conversation_id, created_at DESC, id DESC);

SELECT id, content, created_at
FROM message
WHERE tenant_id = 7 AND conversation_id = 42
ORDER BY created_at DESC, id DESC
LIMIT 50;
```

### 原理与应用

等值条件通常可以继续缩小后续范围；范围条件之后的列通常不能继续缩小 B+Tree 的连续区间，但可能仍用于过滤、排序或覆盖。缺少前导列时，后列不一定完全不能使用，但很可能变成宽扫描，必须看真实计划。

索引列顺序要从访问模式反推：租户、会话、时间、稳定 ID 的分页顺序是一种模式；按租户统计状态可能是另一种模式。一个联合索引不会自动覆盖所有查询。

### 面试准备

**推荐回答：**

> 我先列出真实查询的等值过滤、范围、排序和分页，再设计联合索引。最左前缀是候选路径，不代表每个查询都会使用；范围之后的列可能还有过滤或覆盖价值，最终用 EXPLAIN 和真实数据验证。选择性、访问频率、写入成本和索引体积要一起考虑。

**常见追问：**

- 选择性最高的列一定放第一吗？不一定，稳定的租户过滤、排序和业务访问频率也很重要。
- 为什么要加 `id`？时间可能重复，ID 提供稳定 tie-breaker。
- 联合索引能覆盖 `WHERE b=?` 吗？缺少 `a` 时通常不能形成同样窄的连续范围，要看优化器是否选择其他路径。

## 4. 为什么有索引仍可能全表扫描？

### 先理解

优化器比较的是总成本，而不是“有没有索引”。如果条件命中大部分行，顺序读取数据页可能比走索引、再随机回表更便宜。

### 原理与应用

常见原因包括：选择性低、统计信息过期、数据倾斜、隐式类型转换、对列使用函数、联合索引缺少前导列、前导 `%`、排序/Join 成本以及返回列过多。

```sql
-- 可能阻碍普通索引
WHERE CAST(user_id AS TEXT) = '42'
WHERE DATE(created_at) = '2026-08-07'
WHERE name LIKE '%redis'
```

### 面试准备

**推荐回答：**

> 我不会直接说“索引失效”，而是看计划、估算/实际行数、回表、排序、统计信息和锁等待。可能的修复是改写条件、更新统计信息、调整联合/覆盖索引，或者接受全表扫描。修改后要比较结果正确性、平均延迟、P99 和写入成本。

## 5. `EXPLAIN` 和 `EXPLAIN ANALYZE` 如何看？

### 先理解

`EXPLAIN` 展示优化器计划，不一定真实执行；`EXPLAIN ANALYZE` 会执行并给出实际耗时、行数和循环次数。对 DML 使用 ANALYZE 前要确认副作用、事务和回滚方案。

### 原理与应用

重点看：估算行数与实际行数是否偏差很大，Join 顺序和类型，扫描/回表/排序，Buffers 或读取页，最慢节点，以及时间究竟花在执行、锁、连接池还是网络返回。

### 面试准备

**推荐回答：**

> 我先保存真实 SQL、参数和时间点，再看 EXPLAIN/ANALYZE 的访问路径、估算与实际行数、Join、排序和读取量。计划不慢时继续检查锁等待、连接池、磁盘和复制延迟。任何索引或 SQL 修改都要回归结果、P99 和写入成本，并准备回滚。

### 常见追问

- `EXPLAIN` 里的估算行数和实际行数差很多怎么办？先检查统计信息、数据倾斜和参数分布，再验证计划是否因此选错；
- `EXPLAIN ANALYZE` 能不能在线上随便跑？不能，DML 可能产生副作用，复杂查询还会放大线上负载；
- 计划显示很快但接口很慢怎么办？继续看锁、连接池、网络、序列化和下游调用，不要把数据库计划当成全链路耗时。

## 6. 深分页、Join 和 N+1 应该怎么优化？

### 先理解

```sql
SELECT id, content, created_at
FROM message
WHERE conversation_id = 42
ORDER BY created_at DESC, id DESC
LIMIT 50 OFFSET 100000;
```

深分页需要先找出并丢弃前 100000 行。键集分页使用上一页最后一条作为边界：

```sql
SELECT id, content, created_at
FROM message
WHERE conversation_id = 42
  AND (created_at, id) < (:last_time, :last_id)
ORDER BY created_at DESC, id DESC
LIMIT 50;
```

### 原理与应用

ORM 先查 N 条文档，再逐条查作者会产生 N+1；可以使用 Join、批量预取或 `selectinload`，但要防止 Join 后结果集放大。深分页要把游标和过滤条件绑定，不能允许客户端随意篡改。

### 面试准备

**推荐回答：**

> 我先用 SQL 日志和 trace 证明是深分页还是 N+1，再选择 keyset/cursor 分页、联合索引、批量预取或 Join。排序必须有稳定 tie-breaker；不为了消灭 N+1 就把所有关系一次性 Join，结果集、权限和内存也要评估。

## 7. ACID、隔离级别和 MVCC 分别解决什么？

### 先理解

ACID 是一组不同保证：原子性、约束/不变量、一致的并发可见性、提交后的恢复。隔离级别要先结合脏读、不可重复读、幻读、丢失更新和写偏差来讲。

### 原理与应用

MySQL InnoDB 常见默认 RR，PostgreSQL 常见默认 RC；同名隔离级别的快照时机和锁定读边界不能直接等同。MVCC 让普通读从版本链/tuple 中找到可见版本，减少读写冲突，但写写冲突仍要锁或冲突检测。

InnoDB 依赖事务 ID、undo 和 Read View；PostgreSQL 更新产生新 tuple，旧 tuple 等待 VACUUM 清理。长事务会让 purge/VACUUM 延迟，导致空间膨胀。

### 面试准备

**推荐回答：**

> ACID 不是四个口号：Consistency 仍要靠约束和业务不变量；Isolation 要说明异常和数据库实现；MVCC 解决读者看到哪个版本，不等于没有锁。InnoDB 通过 undo/Read View，PostgreSQL 通过 tuple 版本、快照和 VACUUM。额度、库存和任务领取要配合条件更新、锁定读或版本号。

**常见追问：**

- Serializable 能解决一切吗？不能，它可能产生更多冲突和回滚，跨缓存/消息/外部 API 也不在同一事务里。
- RR 一定没有幻读吗？要限定数据库、普通读/当前读和具体版本，不能脱离上下文绝对回答。

## 8. 快照读和当前读有什么区别？

### 先理解

```sql
-- 通常是快照读
SELECT balance FROM account WHERE id = 1;

-- 当前读：读取最新版本并请求锁
SELECT balance FROM account WHERE id = 1 FOR UPDATE;
```

### 原理与应用

展示型查询通常读事务快照；扣减、领取、状态转移要读取当前事实。也可以使用乐观锁：读取 version，更新时 `WHERE version=:old_version`，影响行数为 0 表示并发冲突。

事务应覆盖同一不变量需要的最小数据库操作，不能把文件下载、模型生成、外部 HTTP 放在持锁事务中。

### 面试准备

**推荐回答：**

> 普通 SELECT 通常是快照读，锁定读和写操作需要当前版本并参与锁协调。扣额度、抢任务要使用 `FOR UPDATE`、条件更新或版本号；外部调用放在事务外，避免长时间持锁。

### 常见追问

- 快照读能否保证扣减正确？不能，它可能看到旧版本；写入不变量要用当前读、条件更新或版本冲突检测；
- `FOR UPDATE` 是否一定锁住“查询结果之外”的范围？取决于数据库、索引、隔离级别和执行计划，必须看实际锁范围；
- 为什么事务外调用外部 API？避免网络等待持有数据库锁，但要用幂等键和状态表衔接两个边界。

## 9. 悲观锁、乐观锁、gap lock 和死锁怎么讲？

### 先理解

悲观锁先锁资源，适合冲突密集的短操作；乐观锁在写时用版本条件检测冲突，适合读多写少。InnoDB 的 record/gap/next-key lock 范围取决于索引、条件、唯一性和隔离级别。

```sql
UPDATE quota
SET remaining = remaining - :cost, version = version + 1
WHERE tenant_id = :tenant_id AND remaining >= :cost;
```

### 原理与应用

死锁是等待图成环：

```text
事务 A：锁 row 1 → 等 row 2
事务 B：锁 row 2 → 等 row 1
```

数据库通常回滚其中一个事务。预防包括稳定加锁顺序、短事务、合适索引、减小批量和范围锁；业务捕获死锁/serialization failure 后有限退避重试，前提是操作幂等。

任务领取可以使用 `FOR UPDATE SKIP LOCKED` 或条件更新，配合 lease 和状态表；不能只靠进程内锁。

### 面试准备

**推荐回答：**

> 我先根据冲突率选择条件更新、版本号或锁定读。InnoDB 的 record/gap/next-key 范围依赖实际索引和隔离级别，不能只看 WHERE。死锁要保存双方 SQL、索引和等待图，先统一资源顺序、缩短事务，再对幂等操作做有上限重试。Redis 锁最多减少并发，最终不变量仍由数据库保护。

## 10. redo、undo、binlog、WAL 和备份恢复有什么区别？

### 先理解

```text
修改内存页
  → 先写恢复所需日志
  → 提交记录完成
  → 后台把脏页写回数据文件
```

redo 主要支持 InnoDB 崩溃重做，undo 支持回滚和 MVCC，binlog 供 MySQL 复制/CDC/增量恢复，WAL 是 PostgreSQL 的写前日志并支持恢复复制。它们的记录对象、消费者和生命周期不同。

### 原理与应用

主库复制还要区分日志发送、落盘和应用；异步副本可能旧读，故障切换可能丢未复制写。全量备份加 WAL/binlog 归档才能支持 PITR；独立存储、恢复演练、RPO/RTO 和恢复后对账同样重要。

### 面试准备

**推荐回答：**

> 可以把 redo 看成崩溃后重放数据页修改，undo 看成回滚和旧版本，binlog 看成复制/CDC 的变更广播，WAL 是 PostgreSQL 的写前日志。提交成功、副本已应用、备份可恢复是不同时间点；我会结合复制 lag、RPO/RTO 和 PITR 说明故障边界。

## 11. Python/SQLAlchemy 如何管理事务和连接池？

### 先理解

每个请求或任务使用独立 Session，服务层决定事务边界；成功提交，异常回滚并关闭，连接归还池。Session 不能作为全局单例在多个协程间共享。

```python
async with session_factory() as session:
    async with session.begin():
        document = await create_document(session, payload)
        await write_outbox(session, document)
```

### 原理与应用

连接池耗尽要看借用等待、活跃连接、长事务、慢 SQL、实例数和数据库最大连接预算；扩大池不一定解决，可能直接把数据库打满。ORM 关键查询要保存 SQL、参数摘要和执行计划，避免日志泄露原文和 token。

### 面试准备

**推荐回答：**

> Session 是事务和连接上下文，不是全局数据库对象。服务层用一个明确的事务同时写事实和 Outbox，异常回滚、请求结束关闭；连接池按实例并发和数据库容量设置。排查连接池耗尽时先看长事务、锁等待和慢 SQL，再决定是否调池大小。

## 12. 分区、分库分表和读写分离怎么选？

### 先理解

分区仍在一个数据库实例内，按时间、租户或范围把表拆成多个物理分区；分库分表把数据放到多个实例，解决单机容量和吞吐，但引入路由、全局 ID、跨分片 Join 和事务问题。读写分离把查询路由到副本，却会产生复制延迟。

### 原理与应用

选择顺序通常是：先优化 SQL/索引和归档，再看分区裁剪、冷热数据和实例资源；单库仍不够时再设计分片键。分片键要高基数、访问稳定、尽量把事务和常用查询限制在一个分片；跨分片聚合要接受 fan-out、异步汇总或专门分析库。

写后读要求高时读主库、等待复制位点或会话粘滞；可以接受最终一致的列表才读副本。

### 面试准备

**推荐回答：**

> 分区解决单实例内的裁剪、归档和部分维护问题，分库分表解决容量和吞吐但增加跨分片复杂度，读写分离解决读扩展但有 lag。我要先证明索引、SQL、归档和分区已不足，再选择分片键和一致性策略，而不是直接水平拆分。

### 常见追问

- 分区是不是天然提升所有查询？只有查询条件能做分区裁剪，跨分区扫描仍可能更慢；
- 分片键选错会怎样？热点集中、跨分片事务和聚合增加，后续迁移代价很高；
- 读写分离如何处理写后读？读主、等待复制位点或会话粘滞，不能默认副本已追平。

## 13. 长事务为什么会影响性能和空间？

### 先理解

长事务会长时间持有锁和快照：它可能阻塞更新/DDL，也会让旧版本不能被及时清理。InnoDB 的 purge/undo 和 PostgreSQL 的 VACUUM 都会受到影响。

### 原理与应用

排查 `idle in transaction`、事务开始时间、锁等待、undo history、PostgreSQL xmin、表/索引膨胀和连接池借用。大批量回填拆成小事务，游标读取和外部调用放在事务外；事务完成后才释放连接。

### 面试准备

**推荐回答：**

> 长事务同时影响并发和空间：锁持有更久，MVCC 旧版本不能回收，最终造成等待和表/索引膨胀。我会查事务年龄、idle in transaction、purge/VACUUM 和连接池，再拆分批量、缩短事务并修复连接未关闭，而不是只清理膨胀文件。

### 常见追问

- 为什么 `idle in transaction` 也危险？事务仍保持快照/锁，业务线程虽然不执行 SQL，却阻碍版本回收和其他事务；
- 拆批会不会破坏原子性？要先确认业务不变量，使用任务状态、批次 checkpoint 和幂等重试替代一个无限长事务；
- 什么时候做维护？先止住长事务和增长源，再选低峰控制 IO/锁，不能把维护命令当成根因修复。

## 14. 备份、PITR、RPO 和 RTO 如何设计？

### 先理解

RPO 是故障后最多允许丢失的数据时间，RTO 是恢复到可用需要的时间。全量备份提供基线，WAL/binlog 归档支持按时间点恢复。

### 原理与应用

备份要独立存储、加密、设置保留和权限；恢复演练要验证日志链、版本、行数、最大事件和恢复时间。恢复顺序通常是事实库 → Outbox/消息 → 搜索/图投影 → 缓存预热，并对回放限速。

### 面试准备

**推荐回答：**

> 我先按业务定义 RPO/RTO，再选择全量、增量和 WAL/binlog 归档，备份放独立存储并定期做恢复演练。恢复后核对事实版本、Outbox 缺口和投影数量，最后限速重建缓存和搜索；“备份文件存在”不等于已经证明可恢复。

### 常见追问

- RPO=0 是否现实？要说明同步复制、跨地域成本和故障模型；异步复制通常仍有日志未达副本的窗口；
- RTO 只取决于备份大小吗？还受恢复工具、日志重放、连接切换、权限配置和投影重建速度影响；
- 恢复后为什么要对账？备份恢复的是某个时间点，Outbox、消息和可重建投影可能处于不同进度。

## 15. 如何解释 MySQL InnoDB 与 PostgreSQL 的关键差异？

### 先理解

不要背产品清单，要按同一个问题比较：

| 问题 | InnoDB | PostgreSQL |
|---|---|---|
| 表/索引访问 | 聚簇主键、二级索引回表 | heap + 独立 index |
| 默认隔离常见值 | RR | RC |
| 版本维护 | undo/purge | tuple/VACUUM |
| 恢复/复制日志 | redo/undo/binlog | WAL |
| 读写差异 | 快照/当前读和 next-key | tuple 快照、行锁、序列化冲突 |

### 原理与应用

同名隔离级别和同一 SQL 的锁范围不能直接等同；Index Only Scan 还依赖 visibility map，InnoDB 的覆盖索引和回表也有不同成本。版本、配置和执行计划要作为限定条件。

### 面试准备

**推荐回答：**

> 我会按存储访问、隔离/MVCC、锁、日志和复制来比较：InnoDB 的聚簇主键和 undo/redo/binlog，PostgreSQL 的 heap/Index Only Scan、tuple/VACUUM 和 WAL。先说共同问题，再限定具体产品和版本，避免把一种实现套到另一种产品。

## 16. 为什么 `OR`、函数和隐式转换会改变执行计划？

### 先理解

优化器需要把条件转换成索引可搜索的范围。对索引列套函数、把数字列和字符串比较，或让两个分支使用完全不同的路径，可能使索引无法形成窄扫描。

### 原理与应用

```sql
-- 更容易利用时间范围索引
WHERE created_at >= '2026-08-07'
  AND created_at <  '2026-08-08'

-- 可能需要对每行计算函数
WHERE DATE(created_at) = '2026-08-07'
```

`OR` 是否改写成 `UNION ALL` 要看分支选择性和是否会重复；`UNION` 还会产生去重成本。不要把 SQL 改写口诀当成无需验证的答案。

### 面试准备

**推荐回答：**

> 我会先看真实计划和数据分布，再判断是函数、隐式转换、OR 分支还是统计信息造成扫描扩大。可以改写成可搜索范围、统一参数类型或拆分分支，但要验证重复、排序、结果集和 P99，不能只说“把 OR 改成 UNION”。

## 17. Serializable 能解决所有并发问题吗？

### 先理解

Serializable 提高隔离强度，可能通过锁或冲突检测让事务表现得像串行执行，但代价是更高的等待、回滚和重试；它不自动覆盖 Redis、消息队列和外部 HTTP。

### 原理与应用

写偏差的例子是两个医生各自看到“还有另一人值班”，然后同时下班，最终无人值班。解决可以是锁定覆盖范围、聚合行约束、版本条件或更强隔离。应用仍要捕获 serialization failure，重新读取后有限重试。

### 面试准备

**推荐回答：**

> Serializable 可以提高数据库内部隔离，但不意味着零冲突或跨系统原子。它可能产生更多回滚和吞吐下降；我会先把业务不变量落到约束、锁或版本，再根据冲突率选择隔离级别，并对可幂等事务做有限重试。

### 常见追问

- Serializable 会不会自动解决外部扣款重复？不会，外部 HTTP 不在数据库事务内，仍需幂等键、状态查询和对账；
- 为什么还要业务约束？隔离级别保护并发可见性，唯一键、CHECK 和条件更新才把具体不变量落到数据层；
- 重试需要什么前提？事务操作可重放、没有未纳管的外部副作用，并且有最大次数和退避。

## 18. 如何设计一个可恢复的任务状态表？

### 先理解

只有 `status` 一个字段无法判断任务是否被旧 worker 占用、是否超时、是否处理过。至少需要状态、版本、lease、attempt、错误和结果引用。

### 原理与应用

```sql
UPDATE job
SET status='processing', lease_until=now()+interval '5 minutes',
    attempt=attempt+1, version=version+1
WHERE id=:id
  AND status IN ('pending','retryable')
  AND (lease_until IS NULL OR lease_until < now());
```

长任务在事务外执行，结果以 `step_id` 幂等写回；租约过期后新 worker 认领，旧 worker 的版本更新影响行数为 0。消息只负责触发，数据库状态负责恢复。

### 面试准备

**推荐回答：**

> 我会用条件更新原子领取任务，记录 lease、attempt 和 version，长任务在事务外执行，结果按步骤幂等写回。租约过期可以重试，但旧 worker 不能覆盖新结果；Redis 心跳只能辅助，最终状态要在数据库。

## 19. 线上只能改一个地方，如何选择止损动作？

### 先理解

数据库问题可能是扫描、锁、连接池、磁盘或复制延迟，不能所有情况都“加索引”。先找最小可逆的动作，避免在故障扩大时继续写入。

### 原理与应用

锁等待优先缩短/终止异常事务并限流；连接池耗尽优先释放连接、限制并发；大查询优先降级或限制分页；复制 lag 优先停止不必要的副本读和大批量写；明确回滚和监控。

### 面试准备

**推荐回答：**

> 我先按证据判断故障类型，再选择最小、可回滚的止损动作：锁问题先处理事务和限流，连接池问题先降低并发，扫描问题再改 SQL/索引，复制问题先调整读路由。任何长期修复都要灰度并观察 P99、错误和资源水位。

### 常见追问

- 为什么不直接重启数据库？重启可能放大恢复时间、丢失现场证据并影响所有租户；先做可逆的限流、路由或取消异常事务；
- 什么叫“可回滚”？有旧 SQL/配置、灰度范围、监控指标和明确撤销动作，而不是只在代码里保留一个分支；
- 止损后还要做什么？保存现场、补齐长期修复和回归验证，避免临时降级被永久化。

# 第二部分：高频场景题

## 场景 1：RAG 会话列表从 50ms 变成 5s，怎么排查？

### 先判断

先区分所有租户还是单租户，执行慢还是锁等待/连接池等待，平均变慢还是只有 P99 变长。保存真实 SQL、参数、时间点和数据量。

### 原理与应用

会话列表通常同时受到租户/会话过滤、时间排序、分页边界和 ORM 关系加载影响。`OFFSET` 越深，数据库需要扫描并丢弃的行越多；没有稳定的 `(created_at, id)` 游标时，同一时间戳还会造成重复或漏读。若计划显示扫描很快但请求仍慢，等待可能发生在连接池、锁、复制读路由、网络或序列化，而不是索引本身。

```text
请求变慢
  ├─ SQL 执行：扫描/回表/排序/Join
  ├─ 数据库等待：锁/连接池/磁盘/复制
  └─ 应用开销：N+1/大结果集/JSON 序列化
```

### 处理步骤

1. 看 EXPLAIN/ANALYZE：估算/实际行数、索引、回表、排序、Join；
2. 检查是否 `OFFSET` 深分页或 ORM N+1；
3. 查看锁等待、连接池、磁盘、复制延迟和数据库 CPU；
4. 设计 `(tenant_id, conversation_id, created_at, id)` 或 keyset 分页；
5. 灰度修改，比较结果正确性、P95/P99 和写放大；
6. 保留回滚和监控。

必要时先临时限制最大页深、关闭非核心关联字段或切换到主库，作为可逆止损；不要在没有计划和回滚的情况下直接新增多个索引。

### 参考回答

> 我不会直接加索引，先用真实 SQL 和计划确定慢在扫描、排序、回表、锁还是连接池；如果是深分页改成稳定游标，如果是 N+1 做批量预取，如果是计划误判再修统计信息或索引。改动要灰度验证长尾和写入成本。

### 常见误区

- 只看平均耗时，不看 P99、锁等待和连接池借用等待；
- 把“命中索引”当成“必然很快”，忽略大范围扫描和回表；
- 为了消除 N+1 把多个一对多关系全部 Join，导致结果集爆炸；
- 只修改 SQL，不绑定权限、游标和租户过滤，造成结果错误或越权。

## 场景 2：两个请求同时扣额度，如何保证余额不为负？

### 先判断

先确认额度是单行余额还是按模型/时间分桶，扣减是否允许并发，客户端是否会因超时重试，以及模型调用是否已经发生。真正的不变量是“成功扣减后余额不能为负，同一个 request_id 不能产生两笔流水”。

### 原理与应用

短事务可以直接使用条件更新：

```sql
UPDATE quota
SET remaining = remaining - :cost,
    version = version + 1
WHERE tenant_id = :tenant_id
  AND model = :model
  AND remaining >= :cost;
```

影响行数为 1 才代表扣减成功；随后在同一事务中插入唯一的 `debit_record(request_id)`。另一种方式是 `SELECT ... FOR UPDATE` 读取当前余额、判断后更新。事务内不能调用外部模型，否则网络等待会持有行锁。

### 处理步骤

1. 先查 `(tenant_id, request_id)` 幂等记录，成功则直接返回原结果；
2. 开启短事务，条件更新余额或锁定当前行；
3. 检查影响行数，插入唯一扣减流水，写出站事件后提交；
4. 事务外调用模型，并把同一个 request_id 传给下游；
5. 超时先查询扣减/模型状态，不能盲目再次扣减；
6. 监控余额负数、冲突数、死锁、重复 request 和外部调用未知结果。

### 参考回答

> 最终正确性由数据库条件更新、锁和唯一约束保证。Redis 锁可以减少重复进入，但不能替代数据库不变量；请求超时重试时先查幂等记录和外部 request_id。若扣额和模型调用必须分阶段，我会用状态机和对账，不把外部 HTTP 放在数据库锁事务里。

### 常见误区

- 只在应用层判断余额，两个进程仍可能同时通过；
- 先扣余额、外部失败却没有补偿状态；
- 使用 `SELECT` 后在事务外 `UPDATE`，中间值已被别的请求改变；
- 用 Redis 锁保证余额正确，却没有数据库唯一流水。

## 场景 3：任务被两个 Worker 同时领取，怎么处理？

### 先判断

要区分“两个 worker 同时看到 pending”“一个 worker 处理超时后租约过期”“ACK 丢失导致重复投递”三种情况。任务领取不是任务完成，必须能在进程宕机后判断是否可以重新认领。

### 原理与应用

方式一是条件更新：

```sql
UPDATE job
SET status='processing', worker_id=:worker,
    lease_until=now()+interval '5 minutes',
    attempt=attempt+1, version=version+1
WHERE id=:id
  AND status IN ('pending','retryable')
  AND (lease_until IS NULL OR lease_until < now());
```

影响行数为 1 的 worker 才拥有本次 lease。方式二是在短事务内 `FOR UPDATE SKIP LOCKED` 取一批 pending 行，更新为 processing 后提交；长任务在事务外执行。

### 处理步骤

1. 领取时记录 `worker_id、lease_until、attempt、version`；
2. 执行前再次检查版本和取消状态；
3. 每个步骤按 `task_id + step_id` 保存输入摘要、状态和结果引用；
4. 成功结果用版本条件写回，提交后再 ACK；
5. lease 过期时允许新 worker 认领，但旧 worker 的写入影响行数必须为 0；
6. 对超时、重复、永久错误分别重试、幂等返回或进入死信/人工队列。

### 参考回答

> 我会用条件更新或 `FOR UPDATE SKIP LOCKED` 原子领取，记录 worker、lease、attempt 和 version。长任务在事务外执行，结果按 task_id/step_id 幂等写回；租约过期后新 worker 可以认领，旧 worker 通过版本条件或 fencing 不能覆盖新结果。Redis 锁只做协调，任务事实仍在数据库。

### 常见误区

- 把“领取成功”当成“执行成功”；
- lease 没有过期时间，worker 宕机后任务永久卡住；
- 结果表没有唯一 step_id，重试产生两份输出；
- 旧 worker 恢复后无条件把状态改回 succeeded。

## 场景 4：数据库写成功但 MQ 没发出去怎么办？

### 先判断

先确认是业务表已提交、发送调用没执行，还是 broker 已接收但确认丢失；检查是否有 `message_id`、Outbox、relay 日志和下游消费记录。不能仅凭 producer 超时判断消息一定没发。

### 原理与应用

Outbox 表与业务表在同一本地事务：

```text
BEGIN
  UPDATE document ...
  INSERT outbox(message_id, aggregate_id, aggregate_version,
                event_type, payload, status='pending')
COMMIT
```

relay 短事务领取 pending，事务外 publish，收到 confirm 后条件更新为 sent。relay 在“已发布、未标记”的窗口宕机会重复发布，这是可接受的；消费者用 message_id 唯一键和业务状态机幂等。

### 处理步骤

1. 对账业务事实和 Outbox：事实存在但没有事件时补写/告警；
2. relay 使用 lease，记录 attempt、next_retry_at、last_error 和 sending age；
3. 生产确认超时先按 message_id 查询，不直接生成新 ID 重发；
4. 消费者在本地事务中写处理记录和业务结果，成功后 ACK；
5. 永久失败进入死信/失败表，修复后按租户、时间和版本限速重放；
6. 监控 pending age、发布失败率、重复率、消费 lag 和事实/投影差异。

### 参考回答

> 我不会在业务函数里“写库后直接 send”并假设成功。业务表和 Outbox 在一个本地事务中提交，relay 扫描 pending、可靠重试并记录状态；relay 仍可能重复发布，所以消费者按 message_id 幂等。长期 pending 进入告警、死信和对账；这提供的是可恢复的最终一致，不是跨数据库和 MQ 的绝对原子。

### 常见误区

- 只加重试却没有稳定 message_id；
- producer confirm 成功就认为消费者业务完成；
- relay 标记 sent 前崩溃后把重复当成异常；
- 发现 pending 就批量删除，造成不可追踪的漏事件。

## 场景 5：线上出现死锁，如何处理？

### 先判断

死锁和普通慢 SQL 不同：死锁是等待图成环，数据库会主动回滚其中一个事务；锁等待只是等待链未成环。先保留数据库 deadlock log、双方 SQL、参数、事务开始时间和索引计划。

### 原理与应用

典型时间线：

```text
事务 A：锁住 row 1 → 申请 row 2
事务 B：锁住 row 2 → 申请 row 1
数据库检测环 → 回滚 A 或 B
```

常见根因是不同代码路径按不同顺序访问资源、范围条件锁住大量索引记录、缺索引扩大锁范围、事务包含外部调用或批量太大。

### 处理步骤

1. 查看等待图，确认双方事务、索引、锁类型和 SQL；
2. 让所有路径按稳定顺序获取资源，先锁较小 ID；
3. 缩短事务，把文件下载、模型调用和消息发送移出锁事务；
4. 补充正确索引、缩小范围和批量大小，避免无意的 gap/next-key 范围锁；
5. 捕获明确 deadlock/serialization failure，重新读取状态后有限指数退避；
6. 只有数据库内幂等操作才自动重试，外部副作用要查询结果或走补偿；
7. 观察死锁率、锁等待 P99、重试成功率和事务时长。

### 参考回答

> 我先用死锁日志和等待图确认环中双方，而不是直接加重试。修复上统一资源访问顺序、缩短事务、完善索引、减小批量和范围锁；数据库回滚一个事务后，业务对可幂等操作做有上限退避，并重新读取当前状态。若事务已经调用外部系统，不能简单整段重做。

### 常见误区

- 把所有锁等待都叫死锁；
- 只提高数据库锁超时时间；
- 重试时复用旧的余额/版本，不重新读取事实；
- 事务内调用外部 HTTP，导致锁持有时间不可控。

## 场景 6：主库故障后副本缺少最近数据怎么办？

### 先判断

区分主库本地是否提交、日志是否发送到副本、是否落盘、是否已经应用，以及客户端是否已经切换。副本缺少最近数据是复制 lag/RPO 问题，不一定是数据库事务丢失。

### 原理与应用

复制链路至少有“主库提交 → 日志发送 → 副本接收/落盘 → 副本应用”几个位置。不同位置对应不同的 RPO；读请求还可能因为读写分离或连接池缓存继续打到旧主/旧副本。故障切换前要决定是优先保留最新写入、优先恢复可用，还是暂时停止写入等待更完整的副本。

### 处理步骤

1. 记录故障时主库 LSN/GTID、各副本接收/应用位点；
2. 按业务选择提升副本、短暂只读或等待更完整副本；
3. 写后读要求高的请求读主、按位点等待或会话粘滞；
4. 切换后重建连接池、校验唯一约束和未完成事务；
5. 用 Outbox/事实版本对账消息、ES/Neo4j 投影，补发缺口；
6. 说明 RPO、RTO、丢失数据范围和后续恢复/审计。

### 参考回答

> 异步复制要区分日志发送、落盘和应用，副本可能读旧值，切换可能丢尚未复制的数据。我会根据 RPO 选择读主、位点路由、半同步或接受短暂最终一致；切换后重建连接、处理 Outbox 缺口并核对最大版本。不能说“有主从就不会丢”。

### 常见误区

- 把副本已经建立连接等同于已经追平日志；
- 只切换连接串，不核对最后提交位点、未完成事务和 Outbox 缺口；
- 恢复后直接放开所有读写，导致旧副本或旧连接继续返回过期数据。

## 场景 7：长事务导致数据库膨胀，怎么定位？

### 先判断

先看表/索引膨胀、慢查询、锁等待和连接池，确认是否存在很老的 active 或 `idle in transaction`。MySQL 关注 undo history/purge 和长事务；PostgreSQL 关注 xmin、dead tuple、VACUUM/Autovacuum 延迟。

### 原理与应用

长事务保持旧快照，使旧版本不能回收；同时它可能持有行锁或表级锁，让其他事务堆积。InnoDB 的 purge 追不上会使 undo history 增长，PostgreSQL 的旧 tuple 会让 dead tuple、表膨胀和 autovacuum 压力上升。先定位“谁开启了事务、为什么一直不提交”，再谈清理。

### 处理步骤

1. 找出最老事务、持锁 SQL、所属服务和连接；
2. 终止确认无业务价值的 idle transaction，避免直接杀正在提交的关键事务；
3. 把大批量回填拆成小事务，记录进度和可重试边界；
4. 修复 Session 未关闭、事务外等待和游标未消费；
5. 让 VACUUM/purge 在压力可控时追平，再评估维护/重建；
6. 监控事务年龄、dead tuple、undo、锁等待、表大小和连接池。

### 参考回答

> 长事务同时造成锁等待和版本不能回收：InnoDB 的 purge/undo、PostgreSQL 的 VACUUM/xmin 都会受影响。我会先定位事务来源和年龄，再拆分批量、修复 idle in transaction 和连接泄漏，最后在低峰做维护；单纯手动清理膨胀不解决根因。

### 常见误区

- 看到表变大就立刻重建，忽略仍在运行的长事务；
- 只杀数据库会话，不修复 ORM 事务未提交、流式读取或连接池复用；
- 把 VACUUM/OPTIMIZE 当成在线止损，未评估锁、IO 和复制影响。

## 场景 8：给亿级表加索引或回填列，如何避免停机？

### 先判断

确认数据库版本是否支持在线/并发索引，DDL 的元数据锁时长、磁盘临时空间、写入速率和可接受回填窗口；明确字段是否需要双写、默认值和回滚。

### 原理与应用

亿级表改造的风险不只在 DDL 本身，还包括元数据锁、回填产生的写放大、长事务/复制 lag、增量写入覆盖以及失败后的重跑。先采用兼容字段和双读，再用短事务批量推进 checkpoint，最后通过版本和抽样校验切换读取；任何一步都要能暂停和继续。

### 处理步骤

1. 先发布兼容代码，能够同时读旧字段和新字段；
2. 分批回填，按主键范围记录 checkpoint，批次短事务可重试；
3. 在线/并发创建索引，监控锁、IO、复制 lag 和 P99；
4. 处理回填期间的增量写入，可双写或用变更日志补偿；
5. 校验行数、NULL、版本和抽样结果后切换读取；
6. 保留旧字段/旧索引和回滚窗口，确认备份后再清理。

### 参考回答

> 我会先做兼容发布，再分批回填和在线建索引；每批记录进度，避免长事务，增量写入用双写或 CDC 补偿。全程观察元数据锁、IO、复制 lag 和 P99，验证结果后再切换读取，旧路径保留到回滚窗口结束，不在高峰一次性更新亿级数据。

### 常见误区

- 只确认 DDL “支持在线”，忽略短暂元数据锁仍可能阻塞请求；
- 回填一次性覆盖全表，制造长事务、复制延迟和不可恢复的失败批次；
- 只回填历史数据，不处理改造期间的新写入；
- 新列切换后立即删除旧路径，没有保留校验和回滚窗口。

# 第三部分：一分钟总复习

## 必须能闭卷回答

- B+Tree、联合索引、回表、覆盖索引和全表扫描的成本；
- EXPLAIN 估算与实际行数、锁等待、连接池和深分页；
- ACID、隔离异常、MVCC、快照读/当前读；
- 条件更新、版本号、record/gap/next-key、死锁和 SKIP LOCKED；
- redo/undo/binlog/WAL、复制 lag、备份、PITR、RPO/RTO；
- 数据库与 MQ 双写、Outbox、幂等和故障恢复。

## 模块口述总结

> 数据库问题可以分成性能、并发正确性和持久性三条链。性能从真实 SQL、索引和执行计划出发，关注选择性、回表、排序、Join、深分页和长尾；并发要区分隔离级别、MVCC、快照读、当前读和锁范围，用条件更新、版本号或锁守住不变量；持久性要分清 redo/undo/binlog 与 WAL、复制和备份的边界。线上排查以计划、锁等待、连接池、复制 lag 和 P99 为证据，修改可灰度、可回滚。

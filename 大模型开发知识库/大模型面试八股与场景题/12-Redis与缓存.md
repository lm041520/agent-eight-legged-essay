# 第一部分：常规八股

## 1. Redis 为什么快？为什么也会拖慢服务？

### 先理解

Redis 把常用数据放在内存，命令路径短；很多命令在事件循环中串行执行，`INCR`、`HSET` 这类单条命令不需要客户端线程锁。但单线程命令执行也意味着一个慢命令可能阻塞同一实例的其他请求。

### 原理与应用

大集合遍历、慢 Lua、超大网络响应、内存分配、后台 fork/COW、AOF rewrite 和客户端连接池都会制造长尾。O(1) 只是算法复杂度，`HGETALL` 一个几百 MB 的 Hash 仍然会阻塞。

key 应包含业务域、租户、对象和 ID：

```text
tenant:{tenant_id}:document:{document_id}:status
tenant:{tenant_id}:conversation:{conversation_id}:recent
```

Cluster 的花括号 hash tag 可以让相关 key 落同一 slot，但过度使用一个 tag 会造成热点。

### 面试准备

**推荐回答：**

> Redis 的优势来自内存访问、紧凑数据结构和短命令路径；事件循环减少了锁竞争，但不是无限吞吐。大 Key、无界集合、慢 Lua、网络输出和后台持久化都会造成阻塞。我会看命令 P99、慢日志、blocked clients、内存、fork、网络和热 Key，而不只说“Redis 单线程”。

**常见追问：**

- 单条命令原子是否等于业务操作原子？不是，多个命令之间仍有竞态。
- CPU 平均正常为什么延迟还会高？可能是单个大命令、网络排队或连接池等待。

## 2. String、Hash、List、Set、ZSet、Stream 如何选择？

### 先理解

| 结构 | 适合表达 | 典型命令 |
|---|---|---|
| String | 单值、JSON、计数、token | `GET/SET/INCR` |
| Hash | 对象字段、配置、状态 | `HGET/HSET` |
| List | 简单两端队列、最近 N 条 | `LPUSH/RPOP/LTRIM` |
| Set | 去重、标签、成员关系 | `SADD/SISMEMBER` |
| ZSet | 排行、时间索引、延迟候选 | `ZADD/ZRANGE` |
| Stream | 事件、消费组、Pending、ACK | `XADD/XREADGROUP/XACK` |

### 原理与应用

Hash field 默认没有独立 TTL；List 不提供通用消费确认和重放；Set 的大规模交并集会占用事件循环；ZSet 适合按 score 排序但不是全文搜索；Stream 需要处理 Pending、保留长度和重复消费。

时间列表可以这样保留最近 20 条：

```text
LPUSH tenant:acme:user:42:recent document:100
LTRIM tenant:acme:user:42:recent 0 19
```

### 面试准备

**推荐回答：**

> 我根据访问模式和可靠性选择结构：String/Hash 是值和对象，List 是简单队列，Set 做去重，ZSet 做排序，Stream 才提供相对完整的消息 ID、消费组和 ACK。还要限制单 key 大小、返回数量和集合操作范围，不能只背命令名称。

## 3. Cache Aside 怎么做？缓存一致性有哪些边界？

### 先理解

读路径：

```text
GET cache
  ├─ 命中 → 返回
  └─ 未命中 → 查数据库 → SET value EX ttl → 返回
```

写路径通常是：

```text
UPDATE database → COMMIT → DEL cache
```

### 原理与应用

缓存是事实源的副本。先删缓存再写库可能出现读请求读旧库并回填旧缓存；写库后删除仍有删除失败、并发回填和副本延迟窗口。常见增强包括失效事件、Outbox、延迟双删、TTL、版本号和读主库。

缓存值可以带 schema/version：

```json
{"schema":2,"version":7,"data":{"status":"ready"}}
```

强读要求要走主库、携带最小版本或会话粘滞；推荐列表等数据可以接受短暂旧值。

### 面试准备

**推荐回答：**

> Cache Aside 的读是先缓存、miss 回源并回填，写通常是数据库提交后删除缓存。它不是绝对强一致：删除会失败，读可能回填旧值，副本也可能滞后。普通业务用 TTL、失效重试和版本兜底；写后读要求高时走主库或携带版本。先说明事实源和允许的旧值窗口，再谈策略。

**常见追问：**

- 延迟双删是不是强一致？不是，只是减小并发旧值窗口。
- Redis 持久化后是不是事实源？不是，仍可能有刷盘、复制、误删和备份边界。

## 4. 缓存穿透、击穿、雪崩如何区分？

### 先理解

- **穿透**：请求大量不存在的数据，持续打到数据库；
- **击穿**：一个热点 key 同时过期，大量请求并发回源；
- **雪崩**：大量 key 同时失效、Redis 重启或集群不可用。

### 原理与应用

穿透用参数校验、短 TTL 空值、Bloom Filter 和来源限流；空值不能永久保存，对象创建后需删除空值。

击穿用 TTL 抖动、single-flight/互斥重建、逻辑过期和短暂旧值；锁等待要有限时。

雪崩用分批预热、连接池保护、回源限流、熔断、降级和高可用部署。目标是缓存故障不会把数据库一起打垮。

### 面试准备

**推荐回答：**

> 穿透针对不存在的数据，重点是入口过滤；击穿针对单个热点过期，重点是并发重建；雪崩针对大量失效或缓存整体故障，重点是时间分散、容量保护和降级。三种问题的冲击对象不同，不能都回答“加布隆过滤器”。

## 5. TTL、过期删除、淘汰和热/大 Key 有什么关系？

### 先理解

TTL 表示最多保留多久，不保证到点瞬间删除；过期删除清理已过期 key；达到 `maxmemory` 后，淘汰策略决定删除哪些 key。`noeviction`、LRU、LFU、`volatile-*`、`allkeys-*` 要按数据是否允许丢失选择。

### 原理与应用

热 key 把访问集中到少数 key/节点，大 key 让单次操作、网络返回和内存回收变重。监控要看 key 访问分布、value 大小、命令耗时、淘汰、CPU、网络和内存碎片。

拆分大 key 时保留分页语义：

```text
conversation:42:messages:2026-08-07
conversation:42:messages:2026-08-06
```

本地短缓存、只读副本或分片副本可以缓解热 key，但会增加失效和写入复杂度。

### 面试准备

**推荐回答：**

> TTL 是时间上限，淘汰是内存达到上限后的选择；二者不是一回事。缓存副本可以按 LRU/LFU 淘汰，任务状态和事实数据不能依赖“永不淘汰”。热 Key 要看访问集中度并做复制/本地缓存，大 Key 要分页、分片和限制无界命令。

## 6. RDB、AOF、Replication、Sentinel、Cluster 分别解决什么？

### 先理解

```text
RDB/AOF       → 持久化与重启恢复
Replication   → 主从复制
Sentinel      → 监控、选主、故障转移
Cluster       → hash slot 分片与集群扩展
```

### 原理与应用

RDB 是时间点快照，恢复快但可能丢快照后的写；AOF 记录写命令，刷盘策略决定窗口，rewrite 会增加磁盘和内存压力。主从通常异步，副本可能旧读，切主可能丢未复制写。

Cluster 多 key 操作受跨 slot 限制，可用 hash tag：

```text
tenant:{acme}:user:42
tenant:{acme}:quota:llm
```

副本不是独立灾备；独立快照、恢复演练、RPO/RTO 和恢复后预热都要单独设计。

### 面试准备

**推荐回答：**

> RDB/AOF 回答重启后怎么恢复，Replication 提供副本，Sentinel 负责主从监控和切换，Cluster 负责分片和扩展。每一层的丢失窗口不同：AOF 有刷盘窗口，异步复制有 lag，Cluster 多 key 受跨槽限制。高可用不等于强一致，副本也不等于备份。

## 7. Redis 分布式锁怎样写才安全？

### 先理解

获取锁要一次设置唯一 token 和 TTL：

```text
SET lock:document:100 token-abc NX PX 10000
```

释放锁必须校验 token：

```lua
if redis.call('GET', KEYS[1]) == ARGV[1] then
  return redis.call('DEL', KEYS[1])
end
return 0
```

### 原理与应用

`SETNX + EXPIRE` 两条命令之间宕机会留下无 TTL 的锁；无条件 `DEL` 可能误删别人的新锁。TTL 太短会提前释放，太长会延迟恢复；续租不能解决进程暂停后旧 worker 迟到写入。

对不可逆副作用使用 fencing token 或数据库版本条件：

```text
Worker A fencing=41 暂停
Worker B fencing=42 完成
Worker A 恢复，携带 41 写入 → 下游拒绝
```

### 面试准备

**推荐回答：**

> 安全的最小方案是唯一 token、`NX`、TTL、原子条件释放和有限续租。锁过期后旧持有者仍可能继续运行，所以库存、额度、支付等最终正确性要靠数据库唯一约束、版本号或 fencing；Redis 锁主要用于减少重复计算和短期协调。

## 8. Pipeline、MULTI/EXEC、WATCH、Lua 和 Stream 如何区分？

### 先理解

- Pipeline：减少网络往返，不提供事务隔离；
- `MULTI/EXEC`：命令连续执行，但没有数据库式自动回滚；
- WATCH：乐观监视，冲突后事务失败；
- Lua：把短小的检查和更新放到服务端原子执行；
- Stream：带 ID、消费组、Pending 和 ACK 的任务流。

### 原理与应用

List 是简单队列，Pub/Sub 是尽力广播，Stream 才适合需要重试、积压和消费确认的任务。Stream 消费顺序应为“处理事实成功后 ACK”；Pending 太久要重新认领，按 message_id 幂等。

### 面试准备

**推荐回答：**

> 独立命令批量发送用 Pipeline，需要连续执行用 MULTI/EXEC，需要条件读改写用 WATCH/Lua；Lua 和单命令仍只保证 Redis 内部，不能包住数据库。List 没有完整 ACK，Pub/Sub 不保留离线消息，Stream 适合可恢复消费。

## 9. Redis 限流、连接池和任务状态怎样落地？

### 先理解

按用户、租户、模型和 token 预算设计 key；令牌桶允许短时突发，滑动窗口更平滑，超限返回 429 和 `Retry-After`。客户端重试要退避，否则会放大流量。

### 原理与应用

Redis 客户端要设置连接建立、读写和总请求超时，连接池不能无限增长。缓存封装统一 key、版本、序列化、TTL、命中和降级：

```python
async def get_document(document_id: int):
    value = await redis.get(cache_key(document_id))
    if value is not None:
        return decode(value)
    fresh = await repository.get_document(document_id)
    if fresh is None:
        await redis.set(empty_key(document_id), "1", ex=30)
        return None
    await redis.set(cache_key(document_id), encode(fresh), ex=300)
    return fresh
```

任务最终状态、幂等记录和结果落数据库；Redis 只保存短期进度、心跳和协调信息，Redis 丢失后从数据库 lease 恢复。

### 面试准备

**推荐回答：**

> 限流要明确维度、算法和 Redis 故障时 fail-open/closed；客户端和连接池必须有超时与上限。缓存访问统一封装版本、TTL、命中和降级。任务事实不能只放 Redis，最终状态和幂等记录要落数据库。

## 10. Redis 为什么会出现热 Key 和大 Key？如何治理？

### 先理解

热 Key 是访问集中在少数 key，可能把一个节点或事件循环打满；大 Key 是成员数量、序列化体积或单次返回过大，可能造成阻塞、网络峰值和内存回收压力。

### 原理与应用

监控不能只看平均 QPS，还要采样 key 前缀、访问分布、value 大小、返回字节、慢命令、网络和 eviction。热 Key 可用本地短缓存、只读副本或应用层复制；大 Key 要按时间/业务分片、分页读取、字段读取和异步删除。

```text
conversation:42:messages:2026-08-07
conversation:42:messages:2026-08-06
```

治理后要验证一致性、分页顺序、删除和 slot 倾斜，不能只说“扩容”。

### 面试准备

**推荐回答：**

> 热 Key 解决访问集中度，大 Key 解决单次操作和内存体积；我会先用采样和慢命令证据区分两者，再分别采用副本/本地缓存或分片/分页。复制会增加失效复杂度，分片要保证访问和权限边界，最终用 P99、网络和内存水位验证。

## 11. 逻辑过期和物理过期有什么区别？

### 先理解

物理过期到点后 key 被视为不存在，请求需要回源；逻辑过期把 `expire_at` 放在 value 中，物理 key 暂时保留，过期后由后台或 single-flight 刷新，其他请求可以先读旧值。

### 原理与应用

逻辑过期适合热点、能接受短暂旧值的配置和列表，可以避免大量请求同时回源；不适合余额、权限和支付事实。刷新任务仍要有租约、超时、失败重试和版本，旧刷新结果不能覆盖新值。

### 面试准备

**推荐回答：**

> 物理过期优先保证时效，过期后直接 miss；逻辑过期优先保证热点可用，过期后先返回旧值并异步重建。选择取决于旧值是否可接受，强一致事实不能使用逻辑过期替代版本和数据库约束。

### 常见追问

- 逻辑过期的旧值能不能用于余额和权限？不能，旧值可能突破业务不变量；
- 物理过期能不能完全避免击穿？不能，热点 key 同时 miss 仍需 single-flight、限流或预热；
- 后台重建失败怎么办？保留旧值并记录失败，设置租约、重试上限和告警，不能让刷新任务无限堆积。

## 12. Stream、Pub/Sub 和 List 的可靠性差异是什么？

### 先理解

List 是简单队列，消费后没有通用 ACK；Pub/Sub 是实时广播，订阅者断线期间消息丢失；Stream 有消息 ID、Consumer Group、Pending Entries List 和 ACK。

### 原理与应用

Stream 消费顺序通常是读取、处理事实、提交事务、ACK；Pending 太久要由其他消费者认领，消息保留长度要控制内存。Kafka 更适合高吞吐、长保留和重放；RabbitMQ 更适合路由和工作队列。

### 面试准备

**推荐回答：**

> Pub/Sub 适合尽力通知，List 适合简单队列，Stream 适合需要确认、重试和积压观测的任务。即使 Stream 有 ACK，重复消费仍可能发生，业务要按 message_id/任务 ID 幂等。

### 常见追问

- Stream 的 Pending 是否等于业务失败？不一定，可能只是 ACK 尚未提交；要结合处理记录和租约判断；
- Pub/Sub 能不能补发离线消息？不能，需改用 Stream、可靠队列或事实源重建；
- List 为什么不适合关键任务？缺少通用 ACK、消费进度和重放边界，宕机后难以判断消息是否已完成。

## 13. Redis 故障时缓存、限流、会话和任务为什么不能同样处理？

### 先理解

这四类数据的丢失后果不同：缓存可以回源，限流可以按风险 fail-open/closed，会话可以短暂失败或转数据库，任务事实必须从数据库状态恢复。

### 原理与应用

缓存回源要有并发舱壁，避免雪崩；限流器 fail-open 可能放大流量，fail-closed 可能影响可用性；锁丢失后要重新读版本，不能直接重做外部副作用。恢复后连接池重建、限速预热和对账都需要监控。

### 面试准备

**推荐回答：**

> 我会先按数据的事实性和安全风险分层降级，而不是统一重启 Redis。可重建缓存限并发回源，限流器按安全等级选择开闭，会话和任务从持久事实恢复；恢复后抑制回源峰值并异步预热，确保 Redis 故障不会扩散成数据库故障。

### 常见追问

- 限流故障一定 fail-open 吗？不是，支付、登录等安全接口通常宁可 fail-closed，低风险内部读取才可能放宽；
- 任务状态丢了如何恢复？从数据库任务表、Outbox、处理记录和 lease 重新推导，而不是从 Redis 空值猜测；
- Redis 恢复后第一步是什么？先重建连接并限速回源/预热，观察数据库水位后再逐步放量。

## 14. Bloom Filter 能解决缓存穿透吗？有哪些限制？

### 先理解

Bloom Filter 用位数组和多个 hash 判断“可能存在/一定不存在”。它可以快速拦截确定不存在的 ID，但允许假阳性，不能作为最终查询结果。

### 原理与应用

容量、误判率、hash 函数、扩容和删除策略要在初始化时规划；集合变化很大时需要可扩展 Bloom/Cuckoo Filter 或重建。即使 Filter 判断可能存在，也仍要查事实库和处理空值缓存。

### 面试准备

**推荐回答：**

> Bloom Filter 适合挡住大量确定不存在的请求，降低穿透，但有假阳性，不能证明数据一定存在；还要处理容量、重建、删除和对象后来创建。参数校验、短 TTL 空值、来源限流和数据库约束仍然需要。

### 常见追问

- 假阳性会怎样？只是放行一次回源，不会把不存在的数据误当成真实结果；
- 数据删除后 Bloom 怎么处理？普通 Bloom 不支持精确删除，可重建、分层或使用支持删除的结构；
- Bloom 挂了怎么办？它只能是优化层，回退到参数校验、空值缓存、限流和事实库保护。

## 15. 令牌桶、滑动窗口和漏桶怎么选？

### 先理解

- 固定窗口：实现简单，但窗口边界可能突发；
- 滑动窗口：更平滑，保存的时间片/成员更多；
- 令牌桶：控制平均速率并允许有限突发；
- 漏桶：输出更平滑，但可能增加等待。

### 原理与应用

按用户、租户、模型和 token 预算设计 key，用 Lua/原子计数保证判断和扣减连续；超限返回 429 和 Retry-After。Redis 故障时要按安全风险决定 fail-open/closed，客户端必须退避。

### 面试准备

**推荐回答：**

> 选择算法要看是否允许突发、需要多平滑、状态大小和延迟预算。令牌桶适合模型 API 的平均 token 速率，滑动窗口更容易解释时间段内次数；算法之外还要设计租户维度、返回码和 Redis 故障策略。

### 常见追问

- 令牌桶为什么允许突发？桶中积累的 token 可以在短时间内被消费，但长期平均速率仍受补充速度限制；
- 多实例如何保证扣减原子？使用 Redis Lua/原子命令或集中式限流服务，并限制脚本和 key 数量；
- 429 后客户端怎么做？遵守 Retry-After、指数退避和抖动，不能立即并发重试。

## 16. Redis 主从切换为什么可能让读写和锁出现问题？

### 先理解

复制通常异步，主写入后副本可能未收到或未应用。切换时读副本可能是旧值，尚未复制的锁/状态也可能在新主上不存在。

### 原理与应用

写后读可以读主、等待复制位点或携带版本；锁要用 token/TTL/条件释放，但不可逆副作用仍需要数据库/fencing。Sentinel 解决故障发现与切换，不保证跨机房强一致；客户端要处理连接重建和旧主恢复。

### 面试准备

**推荐回答：**

> 主从、Sentinel 提高可用但存在复制 lag 和切换窗口。读己之写用读主或版本，锁不能因为 Sentinel 存在就获得线性一致；强正确性场景要把最终边界放事实库，并监控复制偏移和切换事件。

### 常见追问

- Sentinel 能保证锁不丢吗？不能，异步复制和切换可能让新主没有旧锁；
- 写后立刻读副本怎么办？读主、等待复制位点或使用会话粘滞/版本门槛；
- 切换后旧主恢复要注意什么？阻止脑裂写入、重建客户端连接，并核对未复制状态和幂等记录。

## 17. 逻辑过期方案为什么仍然需要版本？

### 先理解

逻辑过期让热点 key 先返回旧值、后台重建；多个刷新 worker 或旧任务可能乱序完成，后完成的旧值可能覆盖新值。

### 原理与应用

value 携带 `data_version`，回填时用 Lua/版本条件，只接受不低于当前版本的结果；刷新任务带租约和超时，失败保留旧值并告警。逻辑过期只适合可接受短暂旧值的副本。

### 面试准备

**推荐回答：**

> 逻辑过期解决热点回源峰值，不解决并发刷新乱序；我会给缓存值和重建任务带版本，旧任务不能覆盖新值，并为刷新设置租约和失败策略。余额、权限等事实不能用旧值兜底。

### 常见追问

- 只比较过期时间够不够？不够，两个刷新任务可能都在有效时间内但结果版本不同；
- 版本来自哪里？通常来自事实表或单调业务版本，不能用 Worker 本地时间戳替代；
- 刷新任务如何防止重复？用租约/single-flight 领取，并在回填时做版本条件更新。

## 18. Redis 内存满了，为什么不能直接把 `maxmemory` 调大？

### 先理解

内存水位可能来自大 key、复制缓冲、AOF rewrite、fork/COW、碎片和真实业务增长，调大上限只是推迟问题，还可能触发宿主机 OOM。

### 原理与应用

先区分可淘汰缓存与不可丢状态，检查 eviction、key 大小、过期分布、碎片率、持久化和副本；再拆分大 key、设置 TTL/淘汰策略、分离实例或扩 Cluster。删除大 key 也要避免同步阻塞。

### 面试准备

**推荐回答：**

> 我先做内存构成和增长来源分析，再决定淘汰、拆 key、分实例或扩容；直接调 maxmemory 可能把复制和持久化峰值推到宿主机 OOM。缓存和任务事实分离，淘汰策略必须和数据丢失后果匹配。

### 常见追问

- `maxmemory` 调大为什么可能更糟？宿主机还要容纳复制缓冲、fork/COW、AOF rewrite 和其他进程，最终可能直接 OOM；
- 大 key 删除会不会阻塞？同步释放可能长时间占用事件循环，应按数据结构使用渐进/异步删除并限制回收速率；
- 淘汰策略如何选择？先区分可重建缓存、会话、限流和任务事实，再按丢失后果选择 `allkeys-*`、`volatile-*` 或禁止淘汰。

# 第二部分：高频场景题

## 场景 1：热点配置同时失效，数据库被打满怎么办？

### 先判断

确认是统一 TTL、主动删除、版本发布还是 Redis 故障；看热点 key 访问分布、过期量、回源 QPS、数据库连接池和 P99。

### 原理与应用

单个热点 key 同时过期属于击穿，很多 key 在同一时间失效属于雪崩；Redis 整体不可用还会把所有 miss 变成回源。真正危险的是“重建请求数 × 单次回源成本”超过数据库和连接池的承载，而不是某个 key 的 TTL 本身。

```text
大量请求 miss
  → 同时查 DB/下游
  → 连接池排队、P99 上升
  → 超时重试再次放大回源
```

### 处理步骤

1. 对单 key 做 single-flight/互斥重建，等待者有限等待或返回旧值；
2. 回填设置随机 TTL，发布时分批失效和预热；
3. 数据库回源设置并发舱壁、限流和熔断；
4. 恢复后异步预热，观察命中率、回源和重建失败。

止损时可以短暂返回仍在有效窗口内的旧值或静态默认值，但必须标注时效并确认不包含余额、权限等强事实；对核心写入先保证数据库可用，再逐步恢复缓存填充。

### 参考回答

> 我先区分击穿还是雪崩，再对热点 key 做单飞重建和 TTL 抖动，数据库入口设置回源并发上限，必要时返回短暂旧值。锁只保护重建，不能让所有请求无限等待；最终要用命中率、回源 QPS 和数据库 P99 验证。

### 常见误区

- 只给所有 key 加同一个更长 TTL，下一次发布仍会同时失效；
- 用一个全局锁让所有请求排队，锁超时后反而形成重试风暴；
- 不区分可接受旧值的配置与不能旧读的权限、余额和支付状态；
- 只看 Redis 命中率，不看回源 QPS、数据库连接池和 P99。

## 场景 2：缓存与数据库不一致，怎么定位？

### 先判断

画出“先删后写/写库后删/并发回填/副本旧读”的时间线，确认谁是事实源、缓存版本和删除是否成功。

### 原理与应用

```text
初始：DB=A, Cache=A
写请求：UPDATE DB=B，尚未删除 Cache
读请求：读到 A
写请求：DEL Cache
后续读：miss → 读 B → 回填 B
```

如果先删后写，读请求可能在数据库更新前读 A 并再次回填 A；因此常规采用提交数据库后删除。删除失败、读回填旧值和副本延迟仍可能造成短窗口。

### 处理步骤

1. 给数据库更新、缓存删除、回填和读取记录 trace/version；
2. 检查写顺序、删除失败、TTL、空值和副本读；
3. 失效通过 Outbox/消息重试，删除操作设计成幂等；
4. 强读请求走主库或携带最小版本，普通列表接受短暂旧值；
5. 通过定期抽样对账发现长期旧缓存，避免全量无脑清缓存。

### 参考回答

> 我先用时间线判断是先删后写、删除失败、并发回填还是副本旧读。事实源提交后删除缓存，删除事件可重试、TTL 兜底；强读场景用读主/版本，普通读接受短暂旧值。延迟双删只能缩小窗口，不是绝对强一致。

### 常见误区

- 说“先删缓存再更新数据库”可以避免旧值；
- 只增加 TTL，让错误值存得更久；
- 把 Redis 持久化或主从当成数据库事务；
- 只在 API 最后一层过滤版本，回源和重排已经使用了旧值。

## 场景 3：Redis 整体不可用，业务怎样降级？

### 先判断

先把 Redis 用途拆成缓存、限流、会话、任务进度、Stream 和锁；它们的丢失后果不同。确认是连接超时、主从切换、Cluster slot 错误还是整个集群不可达。

### 原理与应用

缓存可以回源，但必须有数据库并发舱壁；限流器 fail-open 可能放大流量，fail-closed 可能影响可用性；任务最终状态和幂等记录不能只放 Redis；锁失效后不能默认旧 worker 已停止。

### 处理步骤

1. 设置 Redis 客户端超时和熔断，快速失败而不是占满 worker；
2. 缓存请求限并发回源或返回带时间的旧值；
3. 核心安全接口的限流选择 fail-closed，低风险内部任务可降级；
4. 从数据库任务表、lease 和处理记录恢复任务，重新读取版本；
5. 恢复后重建连接、分批预热，避免所有请求同时回填；
6. 观察回源 QPS、数据库 P99、熔断状态、重复任务和恢复进度。

### 参考回答

> 我不会把所有 Redis 依赖统一成重启。缓存限并发回源，限流按安全风险选择开闭，会话可暂时失败或转持久库，任务从数据库状态恢复；锁丢失后重新读版本并由事实库拒绝旧写。Redis 恢复后分批预热，防止缓存恢复引发雪崩。

### 常见误区

- Redis 连接超时就让所有接口无限等待，导致应用线程和连接池耗尽；
- 把限流、锁和任务进度当成普通缓存一起淘汰；
- Redis 恢复后立即全量回源/预热，没有并发上限和优先级；
- 认为锁丢失意味着旧 Worker 一定停止，未用版本或 fencing 保护副作用。

## 场景 4：两个 Worker 同时执行同一个 Agent 步骤怎么办？

### 先判断

区分是锁没有原子获取、锁 TTL 过期、续租失败、主从切换丢锁，还是消息 ACK 丢失造成重放。真正要保护的是“同一个 step 的外部副作用最多产生一个业务结果”。

### 原理与应用

加锁使用随机 token、`NX` 和 TTL，释放用 Lua 比较 token；步骤表保存 `status、version、request_hash、external_id`。关键写入带 fencing/version：

```text
Worker A token=A, fencing=41，执行中暂停
Worker B fencing=42，完成并写 version=8
Worker A 恢复，携带 fencing=41 写入 → 被拒绝
```

### 处理步骤

1. 获取锁后读取步骤版本和幂等状态；
2. 外部工具传同一个 request_id/Idempotency-Key；
3. 锁续租失败立即停止或转为只读，不继续产生写副作用；
4. 完成后用版本条件写回并提交，再 ACK；
5. 重放时先读步骤状态和外部结果，已完成直接返回；
6. 未知状态进入查询/对账，不盲目再创建。

### 参考回答

> 锁只减少并发，不是最终正确性。锁使用 token、TTL、续租和条件释放；任务步骤、参数 hash、版本和结果落数据库，外部调用使用幂等键，旧 worker 的写入由 fencing/版本拒绝。ACK 丢失时先读取已有结果，而不是重新调用工具。

### 常见误区

- 认为拿到 Redis 锁就可以把数据库和第三方副作用当成串行；
- 续租失败后仍继续执行写工具；
- 只在锁 key 中存 Worker ID，不在结果写回时校验版本；
- 把任务状态放在锁里，锁过期后没有可恢复的持久记录。

## 场景 5：大 Key 让 Redis p99 飙升，如何排查？

### 先判断

区分 key 本身很大、访问频率很高、返回结果很大，还是删除/持久化造成阻塞。CPU 平均值正常也可能有一个大命令堵住事件循环。

### 原理与应用

采样 key 前缀、成员数量、序列化字节、命令和返回大小，重点看 `HGETALL`、`SMEMBERS`、全量 `LRANGE`、大 JSON、同步删除和 Lua。网络输出、内存分配、复制缓冲和 COW 都会放大长尾。

### 处理步骤

1. 用慢日志、命令耗时和 key 采样定位具体操作；
2. 将全量读取改为 `HSCAN/SSCAN`、分页、字段读取或时间分片；
3. 将会话/列表按日期或 hash 拆 key，保证排序和删除语义；
4. 低峰异步删除，设置单 key 大小和集合成员上限；
5. 观察 p99/p999、网络、内存碎片、复制 lag 和后台 rewrite。

### 参考回答

> 我先区分热 Key 和大 Key，再用慢命令、返回字节、成员数和网络证据定位。修复是分页/分片/字段读取、限制无界命令和异步删除，热点则考虑本地缓存或只读副本；最后验证 P99、内存和复制，不直接只扩容。

### 常见误区

- 用 `KEYS` 或全量 `HGETALL/SMEMBERS` 在线扫描生产实例；
- 只把大 key 删除，却没有限制写入方再次生成同样的无界结构；
- 把热 Key 和大 Key 混为一谈，错误地用拆分解决单点访问热点；
- 只看 CPU，忽略网络返回、复制缓冲、AOF rewrite 和内存碎片。

## 场景 6：锁过期后出现重复扣费怎么办？

### 先判断

确认第一次扣费是否已经发生、Redis 锁何时过期、支付请求是否有 request_id、下游是否支持查询和幂等。网络超时只能说明结果未知，不能说明扣费失败。

### 原理与应用

Redis 锁过期后旧进程可能恢复；另一个 worker 获得新锁并调用支付，旧 worker 仍可能迟到调用。因此支付事实必须由支付平台/数据库的幂等键和状态机保护，必要时用 fencing 或版本条件拒绝旧写。

### 处理步骤

1. 以业务流水号查询支付平台和本地账务状态；
2. 若已成功，记录 external_id 并返回原结果；
3. 若处理中，等待回调/查询，不再次创建；
4. 确认未发生且幂等窗口有效时才允许一次重试；
5. 对账差异进入人工/补偿队列，保留 trace、锁和 request 证据；
6. 修复锁 TTL、续租、fencing 和下游幂等，不把锁当支付保证。

### 参考回答

> Redis 锁无法撤销暂停的旧进程，所以扣费不能只靠锁。超时先查询 request_id，支付平台/数据库用幂等键和状态机保证一次结果，必要时用 fencing 拒绝旧写；未知状态进入对账，不批量盲目重试。

### 常见误区

- 锁过期后重新加锁就直接再次扣款，不查询第一次调用结果；
- 用 `DEL lock` 无条件释放，误删新 Worker 的锁；
- 把“本地没有记录”当成“第三方没有扣款”；
- 只延长 TTL，不处理进程暂停、网络分区和支付平台幂等窗口。

## 场景 7：Redis CPU 正常但延迟突然升高，怎么定位？

### 先判断

先看是 Redis 服务端命令慢、客户端连接池等待、网络延迟，还是应用回源导致接口变慢。平均 CPU 不能代表事件循环没有被单个命令堵住。

### 原理与应用

Redis 的命令执行、网络读写、客户端借用和后台 fork/rewrite 处在不同阶段；任一阶段排队都会反映到接口 P99。要把一次请求拆成 `pool_wait → connect → redis_command → network_read → fallback`，分别记录耗时，否则“Redis 延迟高”可能只是连接池不足或回源慢。

### 处理步骤

1. 查看命令 p95/p99、slowlog、blocked clients 和大返回；
2. 检查连接池借用等待、连接建立、读写超时和重试；
3. 查看网络流量、fork/COW、AOF rewrite、复制 lag 和内存碎片；
4. 按 key 前缀定位热/大 key，限制无界集合和脚本；
5. 修复后用 p99/p999、错误率、回源和降级计数验证。

### 参考回答

> CPU 正常不排除单个慢命令、网络排队或连接池耗尽。我会把 Redis 命令、客户端等待、网络、后台 fork/rewrite 和回源分别测量，再按证据修复，不能只看平均 CPU 或直接扩容。

### 常见误区

- 只看实例平均 CPU，忽略事件循环被单个大命令阻塞；
- 只查 Redis 服务端，不查客户端连接池借用、重试和网络排队；
- 看到延迟上升就调大超时，让更多请求长期占用资源；
- 扩容前没有确认热点 key、fork/COW、AOF rewrite 或下游回源才是真瓶颈。

## 场景 8：发布新缓存 schema 后旧进程报错，怎么办？

### 先判断

确认是字段新增、类型改变、序列化库变化还是 key 语义变化；检查新旧进程是否并存、旧值数量、回滚窗口和哪些业务允许短暂 miss。

### 原理与应用

使用 key 版本或 value schema：

```json
{"schema":2,"version":7,"data":{...}}
```

新进程先兼容 schema 1/2，写入 v2；灰度完成后按版本失效或过期。类型改变不能只改读取代码，否则旧进程可能把新值覆盖回旧格式。

### 处理步骤

1. 发布兼容读取，记录 schema 分布和解析失败；
2. 新写入使用新 key/version，旧 key 保留回滚窗口；
3. 分批失效或异步迁移，观察命中率、回源和错误；
4. 所有消费者升级后再清理旧版本；
5. 回滚时保留旧 writer/reader 和事实源重建路径。

### 参考回答

> 我会用 key/version 或 value schema 做兼容迁移，而不是直接改变旧 key 的语义。新旧进程并存时兼容读取、灰度写入和分批失效，监控旧版本比例和解析错误；保留回滚窗口，缓存损坏时从事实源重建。

### 常见误区

- 只改 reader，不限制旧 writer 把新格式覆盖回旧格式；
- 不统计 schema 分布，直接全量删除缓存造成回源雪崩；
- 把序列化异常当成普通 miss，掩盖数据污染和版本不兼容；
- 回滚时没有保留旧 reader/writer 或事实源重建路径。

# 第三部分：一分钟总复习

## 必须能闭卷回答

- Redis 为什么快，以及单线程/大 Key/慢命令的边界；
- 六种数据结构的访问模式和可靠性差异；
- Cache Aside、穿透/击穿/雪崩、热 Key/大 Key、TTL/淘汰；
- RDB/AOF、复制、Sentinel、Cluster 的层次和丢失窗口；
- token、TTL、条件释放、续租、fencing 和数据库最终约束；
- Pipeline、Lua、Stream、限流、连接池和故障降级。

## 模块口述总结

> Redis 题先区分缓存副本、短期状态和业务事实。数据结构按访问模式选择；Cache Aside 的重点是事实源、失效顺序、回源保护和短暂不一致；穿透、击穿、雪崩分别治理。RDB/AOF 是持久化，Replication/Sentinel 是复制和切换，Cluster 是分片。分布式锁要有 token、TTL、原子释放和必要的 fencing，最终正确性仍由数据库唯一约束、版本和幂等保证。线上关注命中率、回源 QPS、P99、慢命令、热/大 Key、淘汰、复制 lag 和连接池。

# 第一部分：常规八股

## 1. 一条消息从生产到消费经历什么？

### 先理解

```text
生产者构造 message_id/schema/version
  → 序列化发送
  → Broker 写入内存/磁盘/副本
  → Producer Confirm 返回
  → 消费者读取
  → 写事实源或调用下游
  → ACK/提交 Offset
```

“接口返回成功”“Broker 接收成功”“业务处理成功”是三个不同时间点。发送超时可能已经写入，业务提交后 ACK 可能丢失，所以重复和未知结果是正常故障窗口。

### 原理与应用

消息建议包含：

```json
{
  "message_id":"01J...",
  "event_type":"document.created",
  "schema_version":2,
  "aggregate_id":"document:100",
  "aggregate_version":7,
  "trace_id":"trace-...",
  "payload":{"tenant_id":"acme","document_id":100}
}
```

message_id 用于去重，aggregate_version 处理乱序和旧写，schema_version 支持演进，trace_id 串生产与消费。

### 面试准备

**推荐回答：**

> 我会把生产确认、Broker 持久化、消费者处理和 ACK 分开。消息带 message_id、业务对象版本和 trace_id，消费者默认按至少一次处理，业务事实用唯一键、状态机和幂等记录保护。超时后先判断结果是否未知，不能简单按失败再做一次副作用。

## 2. 至多一次、至少一次、恰好一次是什么？

### 先理解

- 至多一次：先确认再处理，可能丢，不主动重放；
- 至少一次：处理成功后确认，可能重复；
- 恰好一次：必须限定资源边界，例如 Kafka 内部读写事务。

### 原理与应用

消费者处理成功后进程宕机、ACK/Offset 提交失败，Broker 会再次投递：

```text
读取 M → 业务提交成功 → ACK 丢失 → 再次收到 M
```

因此业务通常选择至少一次 + 幂等。Broker exactly-once 不自动覆盖数据库、支付、发邮件和外部 HTTP。

### 面试准备

**推荐回答：**

> 我通常采用至少一次，再用 message_id、业务唯一键、唯一约束和状态机处理重复。恰好一次必须说明作用域，Kafka 内部的事务不能保证跨数据库或外部工具的业务副作用恰好一次。

## 3. Kafka 的 Topic、Partition、Offset、Group、ISR 如何串起来？

### 先理解

```text
Topic: document-events
  Partition 0: key=doc-1, offset 10,11,12...
  Partition 1: key=doc-2, offset 20,21...
Consumer Group: indexers
  每个 partition 同时分给一个 group member
```

### 原理与应用

Partition 是有序追加日志；Offset 是分区位置；Consumer Group 内多个消费者分摊分区；ISR 是与 leader 保持同步的副本集合。相同 key 通常落同一 partition，只保证这个 key/partition 范围有序，不保证 topic 全局顺序。

消费者数超过 partition 数不会继续提高该 topic 并行度；扩 partition 会改变 key 分布和资源成本。

### 面试准备

**推荐回答：**

> Topic 是逻辑主题，Partition 是有序日志和并行单元，Offset 是某个分区的位置，Group 让多个消费者共享分区，ISR 是同步副本集合。相同业务 key 通常保证分区内顺序；Offset 提交只表示消费进度，不等于业务事实已经完成。

**常见追问：**

- `acks=1` 和更强确认的区别？等待副本越多，丢失窗口越小，但延迟和资源成本更高。
- 为什么扩 partition 会影响顺序？key 到 partition 的映射可能变化，旧消息和新消息不一定在同一分区。

## 4. Kafka Rebalance 为什么会造成延迟和重复？

### 先理解

消费者加入、退出、心跳超时或订阅变化都会触发再分配。分配期间分区可能暂停，旧消费者处理成功但没提交 offset 的消息会被新消费者重放。

### 原理与应用

长任务要控制处理时长、poll/heartbeat 设置、优雅退出和幂等；如果任务本身很长，可以让消息只触发数据库任务表，worker 在事务外执行。盲目增加消费者可能让下游连接池和模型 API 更快被打满。

### 面试准备

**推荐回答：**

> Rebalance 是消费组成员变化后的重新分配，可能造成暂停和未提交消息重放。我会设置合理心跳/拉取边界，优雅退出，拆分长任务并保证消费幂等；增加消费者前先确认 partition 数和下游容量。

### 常见追问

- 为什么加消费者仍不提速？partition 数、单分区热点或下游连接池可能已成为上限；
- 如何减少重平衡影响？稳定成员、优雅退出、合理 poll/heartbeat，并避免在回调中执行不可控长任务；
- Rebalance 后的重复如何处理？让业务按 message_id/业务键幂等，不能依赖 offset 恰好只提交一次。

## 5. RabbitMQ 的 Exchange、Queue、Confirm、ACK、Prefetch、DLX 有什么关系？

### 先理解

```text
生产者 → exchange → binding/routing key → queue → consumer
```

Producer Confirm 确认 Broker 接收/持久化，Consumer ACK 确认处理完成；Prefetch 限制未确认消息，NACK/requeue、TTL 和 DLX 决定失败路径。

### 原理与应用

RabbitMQ 的 queue 路由灵活，适合工作队列和明确订阅；Quorum Queue 提供更可靠的复制语义。Prefetch 太大可能让一个慢消费者占住大量消息，太小则吞吐下降。

### 面试准备

**推荐回答：**

> Confirm 覆盖生产端，ACK 覆盖消费端，二者不是同一个确认。Exchange 决定路由，Queue 保存和分摊任务，Prefetch 控制未确认数量，NACK/requeue、TTL/DLX 处理失败。最终仍要有幂等和毒消息上限。

### 常见追问

- Confirm 成功是否代表业务完成？不代表，只说明 broker 接收/持久化达到配置语义；
- Prefetch 太大有什么问题？消息被单个消费者预取并占住，故障时重复范围和内存压力变大；
- 为什么不无限 requeue？永久错误会在主队列高速循环，应按 attempt 和错误类型进入延迟重试或 DLX。

## 6. Kafka、RabbitMQ、Redis Stream、Celery 如何选？

### 先理解

| 组件 | 强项 | 主要边界 |
|---|---|---|
| Kafka | 高吞吐、长保留、多消费组、重放 | 分区规划、lag、rebalance |
| RabbitMQ | 路由、工作队列、ACK/NACK、死信 | 队列容量、拓扑和副本 |
| Redis Stream | 已有 Redis、轻量消费组和 Pending | 内存、保留和复杂路由 |
| Celery | Python 任务编排、重试、定时 | broker/result backend 仍要治理 |

### 原理与应用

选择先看是否需要历史回放、保留多久、吞吐、顺序范围、路由复杂度、消息大小、下游容量和团队运维能力。Celery 是任务框架，不是独立 broker。

### 面试准备

**推荐回答：**

> 高吞吐和长保留多消费组我优先比较 Kafka；工作队列和复杂路由比较 RabbitMQ；已有 Redis 且规模适中可以考虑 Stream；Python 任务编排用 Celery，但仍要单独设计 broker、结果、幂等和恢复。不能只按“都能发消息”选型。

### 常见追问

- Kafka 能不能替代所有任务队列？可以承载任务，但延迟路由、单条重试和毒消息处理需要额外设计；
- Redis Stream 何时不合适？消息保留很长、规模大或需要复杂路由/独立扩展时，内存和故障域可能成为限制；
- Celery 的可靠性由谁负责？broker、worker、result backend 和业务幂等都要单独治理，框架不会自动提供跨系统 exactly-once。

## 7. ACK/Offset 什么时候提交？如何做到幂等？

### 先理解

可靠顺序是：

```text
读取 → 处理事实源/下游 → 业务提交 → ACK/提交 Offset
```

先 ACK 再写库可能丢消息；处理成功后 ACK 丢失会重复，必须把重复当正常输入。

### 原理与应用

去重可以落在唯一约束、processed_message 表、状态机或下游幂等键：

```sql
INSERT INTO processed_message(message_id, processed_at)
VALUES (:message_id, now())
ON CONFLICT (message_id) DO NOTHING;
```

去重记录和业务更新尽量在同一事实源事务中提交；外部 API 不在本地事务内，要用 Idempotency-Key、状态查询和对账。

### 面试准备

**推荐回答：**

> ACK 只代表消费进度，不代表所有副作用绝不重复。我会在本地事务中用 message_id 做唯一处理记录，同时更新业务事实，成功提交后才 ACK；如果 ACK 丢失，第二次读取到已完成记录就返回原结果。外部调用还需要下游幂等或状态查询。

## 8. 重试、死信和毒消息如何设计？

### 先理解

临时网络错误、503、429 可指数退避加 jitter；参数、权限、格式和永久业务错误不应无限重试；下游超时且结果未知要查询 request_id。

### 原理与应用

```text
主队列 → retry-5s → retry-1m → retry-10m → DLQ
```

每次记录 attempt、错误分类、下一次时间、trace_id 和代码版本。DLQ 不是垃圾桶，修复后按类型、小批量、限速、人工确认重新投递，仍需新的重试上限。

### 面试准备

**推荐回答：**

> 重试只针对临时、可恢复且幂等的错误；退避有上限，不能每一层都重试三次。永久错误进入带原因和上下文的死信，修复后可筛选重放，毒消息不能在主队列和 DLQ 间循环。

### 常见追问

- 下游超时属于临时错误吗？结果可能已成功，先用 request_id 查询状态，再决定重试；
- 死信重放为什么仍需限速？修复后批量重放可能再次打满数据库/第三方，并触发新的副作用；
- 重试记录哪些字段？attempt、错误分类、next_retry_at、trace_id、代码版本和原始 message_id。

## 9. Outbox、CDC 和 Saga 如何解决分布式一致性？

### 先理解

数据库写成功和消息发送成功不是一个原子动作：

```text
先写库 → 宕机 → 漏事件
先发消息 → 回滚 → 事件描述不存在事实
```

### 原理与应用

Outbox 在同一数据库事务中写业务表和事件：

```text
BEGIN
  UPDATE document ...
  INSERT outbox(message_id, payload, status='pending')
COMMIT
relay 扫描 pending → publish → mark sent
```

relay 在发布成功、标记失败时会重复发送，消费者仍需幂等。CDC 可以传输 outbox，但不替代状态机。

Saga 用多个本地事务和补偿动作组成长流程：订单创建 → 预留库存 → 支付，支付失败 → 释放库存 → 取消订单。补偿不是数据库回滚，外部副作用可能只能部分撤销。

### 面试准备

**推荐回答：**

> Outbox 把业务事实和待发送事件放入同一个本地事务，再由 relay 可重试发布；它把不可见的漏发变成可观测 pending，但仍可能重复。跨服务长流程用 Saga 的本地事务和补偿，配合幂等键、状态机和对账，不强行做一个覆盖所有资源的大事务。

## 10. 消息积压、背压和容量如何排查？

### 先理解

看生产速率、消费速率、Kafka lag/Rabbit ready+unacked/Stream pending、单条处理 P95/P99、重试/死信、partition/queue 热点、Broker 磁盘网络和下游连接池。

### 原理与应用

增加消费者只有在 partition 数、prefetch、数据库连接和模型 API 都允许时才有效。生产限流、最大未确认数、队列长度阈值、优先级和暂停低优先级任务形成背压。长任务可以让消息触发任务表，避免一个消费者长时间占用分区。

### 面试准备

**推荐回答：**

> 我先用生产/消费速率确认积压是生产变快还是消费变慢，再看 partition/queue 热点、重试和下游容量。增加 worker 前先确认并行度和连接池；恢复时暂停无效重试、启用优先级和降级，并按下游承载限速回放，避免二次雪崩。

### 常见追问

- lag 下降但业务仍不完整怎么办？检查是否只提交了 offset、业务事务回滚或消息被转入死信；
- 为什么不能只扩消费者？partition、数据库连接、模型 API 限额和内存可能先达到上限；
- 背压如何传回 API？接受任务并返回 queued、限制低优先级入口或暂停生产，而不是让请求线程无限等待。

## 11. 事件顺序和状态机如何防止旧消息覆盖新状态？

### 先理解

不同 partition/queue 没有全局顺序；即使同一 partition 有序，消费者内部并发也可能先完成后来的事件。事件应携带 aggregate_id 和递增 aggregate_version。

### 原理与应用

```sql
UPDATE document
SET status = :status, version = :event_version
WHERE id = :id AND version < :event_version;
```

旧事件影响行数为 0，安全跳过；缺少中间版本的事件进入等待/补偿。状态机比布尔字段清晰：`PENDING → PROCESSING → SUCCEEDED/FAILED`，每次转移记录时间、错误和版本。

### 面试准备

**推荐回答：**

> 我不会只依赖到达顺序，而是让事件带业务版本，消费者用条件更新拒绝旧写；同一 aggregate 尽量使用稳定分区 key，缺版本时等待或补偿。状态机记录合法转移和失败原因，重复消息变成安全无操作。

## 12. 为什么“每层重试三次”会造成重试风暴？

### 先理解

API、HTTP client、SDK、消息消费者和任务框架各自重试三次时，一次故障可能被放大成多次甚至指数级调用；下游越慢，重试越多，形成反馈回路。

### 原理与应用

指定重试责任层、总时间预算、指数退避和 jitter；其他层快速失败、排队或查询状态。只有临时、可恢复、幂等的错误可以重试；429/503 要尊重 Retry-After，参数和权限错误直接失败。

### 面试准备

**推荐回答：**

> 我会统一重试责任和总预算，避免每一层叠加；临时错误做有限退避，未知副作用先查状态，永久错误进死信/补偿。重试次数、等待时间、下游容量和幂等键要一起设计。

### 常见追问

- 三层各重试三次为什么不是 9 次？嵌套调用和失败回传会产生乘法放大，实际还会叠加消息重投；
- 谁负责重试？选择最接近事实源、能判断错误和幂等边界的一层，其他层传递失败或查询结果；
- 如何验证风暴？看每个请求的 attempt 分布、下游 QPS、429/503、队列 lag 和成功率，而非只看最终错误率。

## 13. Outbox relay 在什么情况下会重复发布？如何保证不漏？

### 先理解

```text
outbox=pending → relay 发布成功 → relay 宕机 → 尚未标记 sent
```

relay 重启会再次发布，这是至少一次发布的正常窗口。

### 原理与应用

Outbox 需要 `pending/sending/sent/failed`、attempt、next_retry_at、last_error 和 lease；relay 用短事务领取，事务外发送，成功后条件更新 sent。消费者按 message_id 幂等，长期 pending age 告警并对账。

### 面试准备

**推荐回答：**

> Outbox 的目标是把漏发变成可查询、可重试的 pending，而不是保证只发布一次。relay 崩溃会重复发布，消费者用唯一键/状态机幂等；sending 必须有 lease，避免死进程永久占住事件。

### 常见追问

- 为什么 relay 发送和标记不能放在同一个数据库事务里？broker 通常不在同一个本地事务，网络等待会延长锁；
- 如何处理发送成功但标记失败？保留事件并允许重复发布，依靠 message_id 幂等和对账确认，不删除 pending；
- 长期 pending 看什么？pending age、lease、relay 错误、confirm 延迟、broker 路由和数据库连接/锁。

## 14. 什么时候使用任务表，而不是让消息消费者直接执行长任务？

### 先理解

如果任务需要进度、暂停/取消、人工审核、多个步骤或超过消费者 poll/ACK 时间，消息只负责触发，真实状态放任务表。

### 原理与应用

Worker 条件领取 `lease`，事务外执行，结果按 step_id 幂等写回；租约过期后重新认领。消息保留和重试只解决触发，不足以表达长任务的中间状态和恢复边界。

### 面试准备

**推荐回答：**

> 短小且可重复的工作可以直接消费并 ACK；长任务把消息当触发器，任务表保存状态、租约、进度和结果，Worker 以版本/租约恢复。这样不会因为 consumer rebalance 或 ACK 超时把整个长任务重复执行。

### 常见追问

- 任务表会不会和消息重复存储？消息负责唤醒，任务表负责当前状态与恢复，二者通过 task_id/message_id 关联并幂等；
- lease 过期后旧 Worker 怎么办？结果写回带版本/lease 条件，旧 Worker 影响行数为 0，不能覆盖新认领者；
- 什么时候可以直接消费？处理短、可重入、无进度要求且在 poll/ACK 时间预算内的工作。

# 第二部分：高频场景题

## 场景 1：文档已入库，但 ES 没有结果，怎么设计？

### 先判断

区分数据库事实、消息发布、解析、embedding、bulk 写入、refresh 可见和最终 ready 状态。

### 原理与应用

“文档已入库”只证明 PostgreSQL 事务提交，不证明 Outbox 已 relay、不证明消费者已完成，也不证明 Elasticsearch 已 refresh。应把状态拆成可恢复的阶段：

```text
document_saved → event_pending → parsing → embedding
              → indexed_version=N → ready
```

每个阶段都有 `document_id`、业务版本、`message_id`、attempt 和错误原因；同一文档的旧版本不能覆盖新版本，单个 chunk 失败不能让整个任务永远停在 processing 而没有告警。

### 处理步骤

业务表和 Outbox 同事务；事件带 document_id/version/message_id；消费者按版本幂等，失败分类重试或死信；所有 chunk 投影达到版本后才更新 ready；对账发现数据库与搜索漂移时补发/重建。

处理时还要区分近实时延迟和真正写入失败：检查 alias/index、bulk 每条结果、refresh、权限 filter、版本条件和队列积压。补偿应按文档版本和租户限速，不能在 ES 不可用时让 API 同步等待或无界重试。

### 参考回答

> 上传接口只承诺数据库已保存，索引完成后才标 ready。消息至少一次，消费者按版本和任务 ID 幂等；ES refresh 延迟或下游故障时状态保持 processing，恢复后限速重放。不会把“HTTP 返回成功”说成“已经可搜索”。

### 常见误区

- 把数据库提交和搜索可见混成一个状态；
- 只重试整个文档，不记录 chunk 级进度和失败原因；
- 通过 `refresh=true` 掩盖消息漏发、mapping 错误或权限过滤；
- 重放旧事件时没有版本条件，导致已删除/新版本被旧数据复活。

## 场景 2：支付回调重复、乱序、超时怎么办？

### 先判断

先区分回调是否验签通过、是否同一支付流水、事件是重复还是乱序、支付平台状态是否已终态，以及本地订单/账务是否已经提交。回调 HTTP 超时也可能代表平台已经收到并处理。

### 原理与应用

以支付流水号建立唯一键，订单状态机限制合法迁移：

```text
CREATED → PAYING → PAID
                  ↘ REFUNDED
```

`PAID → PAYING`、`REFUNDED → PAID` 等旧回调不能覆盖终态。订单和账务流水在本地事务中提交，通知、积分和发货通过 Outbox/MQ 异步；回调接口快速确认，后续用状态查询和对账兜底。

### 处理步骤

1. 验签、校验商户/金额/订单号和支付流水；
2. 插入唯一回调记录，重复则返回已处理结果；
3. 事务内按状态机更新订单和账务流水；
4. 写 Outbox 事件，提交后再异步通知下游；
5. 乱序事件按版本/支付平台时间和当前终态判断；
6. 超时先查询 request_id/支付流水，定时对账处理未知状态；
7. 监控重复率、非法状态转移、回调延迟、对账差异和死信。

### 参考回答

> 回调处理以支付流水号唯一去重，订单状态机拒绝非法回退，订单和账务在本地事务中提交，通知/积分/发货异步。HTTP 200 只表示收到回调；重复、乱序和超时都通过状态查询、Outbox 和对账处理，不能把每次回调都当成新的支付。

### 常见误区

- 以订单号做唯一键却允许多个支付尝试，导致合法重试被误判；
- 收到回调就直接发货，没有检查金额和当前订单状态；
- 回调超时后立刻再次扣款，不查询原 request_id；
- 只依赖消息顺序，不保存终态和版本。

## 场景 3：Agent 工具成功但 ACK 丢失，怎么防重复？

### 先判断

ACK 丢失只说明消费进度未知，不说明工具没有执行。先判断外部工具是否支持 request_id 查询/幂等，步骤状态是否已经写入数据库，以及重复调用的副作用是否可逆。

### 原理与应用

```text
读取消息 → 调用工具 request_id=M
          → 外部成功创建工单
          → 本地写 external_id
          → 进程宕机，ACK 丢失
          → M 再投递
```

步骤表以 `run_id + step_id` 唯一，保存参数 hash、status、external_id、attempt 和错误；重放先查本地状态，再查外部 request_id，已成功返回原 external_id。

### 处理步骤

1. 工具调用前保存/确认幂等键和参数摘要；
2. 调用下游时传同一 Idempotency-Key；
3. 外部超时先查询 request_id，不直接再创建；
4. 本地事务写成功结果和审计，再 ACK；
5. 已完成步骤的重复消息变成安全读取，处理中步骤按 lease 恢复；
6. 外部无查询接口时进入人工/对账队列，不能宣称恰好一次。

### 参考回答

> 工具调用必须有幂等键或状态查询。ACK 丢失后，Worker 重启先查步骤状态和外部 request_id，成功就返回原 external_id，未知就查询/补偿；任务状态、参数 hash 和结果落数据库，Redis 锁不能替代下游幂等。

### 常见误区

- 把 ACK 放在工具调用之前；
- 只在 Redis 记录“执行过”，重启后记录丢失；
- 重新生成 request_id，导致外部服务创建第二个资源；
- 把超时当成失败，不处理未知结果。

## 场景 4：消费者成功日志不断出现，但 lag 不下降怎么办？

### 先判断

“业务处理 success”可能只是代码返回成功，不代表 offset/ACK 已提交；也可能是同一条消息不断重试、生产速率更高、某个 partition/queue 热点或监控口径错误。

### 原理与应用

分别看：

```text
生产速率 → broker 写入 → consumer read → 业务提交 → ACK/offset
```

如果业务事务提交后 offset 没提交，消息会重复；如果 offset 提交了但 lag 指标不动，可能查错 group 或监控延迟；如果一个 partition 卡住，整体平均处理仍可能看起来成功。

### 处理步骤

1. 用 message_id 对齐生产、读取、处理、ACK、重试和 DLQ；
2. 确认监控查询的是正确 topic/queue、partition 和 consumer group；
3. 查看 offset 提交时间、unacked/pending、重试次数和业务事务；
4. 比较生产/消费速率与单 partition/queue 的处理 P99；
5. 停止无效重试，修复慢分区或下游瓶颈后再恢复；
6. 对已经成功但重复投递的消息依靠幂等记录安全跳过。

### 参考回答

> 我不会只看 success 日志。先用 message_id 串生产、broker、消费、业务提交和 ACK，确认 group/partition/queue 是否正确，再区分 offset 没提交、不断重试、生产更快还是单分区热点。修复下游和提交逻辑后，重复消息由幂等记录消化。

### 常见误区

- 把业务函数返回成功当成 offset/ACK 已提交；
- 查错 consumer group、topic、partition 或监控时间窗口；
- 只增加 worker，不检查单分区热点、重试循环和下游限额；
- 为了让 lag 下降先提交 offset，结果造成真实业务丢失。

## 场景 5：Outbox pending 越积越多，怎么定位？

### 先判断

先看 pending age、产生速率、relay 实例、sending lease、broker confirm、网络/权限和标记 sent 的数据库错误。pending 增长可能是 relay 没启动、发送慢、发送失败，或消息已经发布但标记事务失败。

### 原理与应用

relay 领取要有租约，发送在事务外，成功后条件更新：

```text
pending → sending(lease) → publish confirm → sent
                      ↘ timeout/失败 → retryable/failed
```

“发布成功、标记失败”不能删除记录，因为重试会重复发布；消费者应按 message_id 幂等。永久失败进入失败表/DLQ，保留 payload 摘要和错误。

### 处理步骤

1. 判断 pending 是否被某个死 relay 长期占用；
2. 检查 broker 磁盘、连接、权限、路由和 confirm 延迟；
3. 处理发送成功但 mark sent 失败的事务/连接问题；
4. 恢复 relay 后按时间、租户和事件类型限速；
5. 用 message_id 对比 Outbox、broker、消费记录和事实表；
6. 长期失败告警和人工处理，不能批量清空 pending。

### 参考回答

> 我会先用 pending age、relay 状态、sending lease 和 confirm 把“没发送、发送失败、发送成功但标记失败”分开。修复领取/连接/事务后，旧事件按 message_id 限速重试；消费者幂等，失败事件保留告警和对账，不能直接删除。

### 常见误区

- 直接删除 pending 让监控变绿，实际造成不可追踪的漏发；
- 发送成功但 mark sent 失败时生成新 message_id，破坏幂等；
- 没有 lease，死 relay 永久占住 sending；
- 只看 pending 数量，不看 pending age、产生速率和 broker confirm。

## 场景 6：同一订单的 Kafka 事件乱序怎么办？

### 先判断

确认乱序来自不同 partition、扩分区、消费者内部并发还是生产者重试；检查事件是否带 order_id、aggregate_version 和发生时间。到达时间不是可靠业务版本。

### 原理与应用

生产按 order_id 作为 key，尽量让同一订单进入同一 partition；消费者条件更新：

```sql
UPDATE orders
SET status=:new_status, version=:event_version
WHERE id=:order_id AND version < :event_version;
```

旧事件影响行数为 0；缺少中间版本时可以暂存等待、查询事实源或进入补偿。扩 partition 会改变 key 映射，旧数据不能自动恢复，需要按订单重放。

### 处理步骤

1. 保存乱序事件和当前订单版本，禁止直接覆盖；
2. 校验生产 key、partition、producer retry 和 consumer 并发；
3. 启用版本条件更新，旧消息记为 skipped/duplicate；
4. 缺版本消息进入等待队列或按事实源重建；
5. 扩分区后对受影响订单做定向对账和重放；
6. 监控版本缺口、旧写拒绝、等待队列和重放结果。

### 参考回答

> 顺序只在 partition 范围成立，我会用 order_id 做 key，并让事件带递增版本；数据库只接受高版本，旧消息安全跳过，缺版本等待或补偿。扩分区可能改变映射，不能只依赖时间和到达顺序。

### 常见误区

- 以消息时间戳替代业务版本，无法判断同一订单的真实先后；
- 同一 partition 内又开无界线程，完成顺序重新乱掉；
- 旧事件被跳过却没有记录，导致后续无法区分重复和数据缺口；
- 扩 partition 后不做受影响订单的对账和定向重放。

## 场景 7：RabbitMQ requeue 造成毒消息循环怎么办？

### 先判断

查看消息的 attempt、错误类型、原队列、消费者版本和 requeue 次数。参数/权限/格式错误是永久失败，网络/429/503 可能临时失败；两者不能都 NACK/requeue。

### 原理与应用

```text
主 queue → 临时错误 → 延迟 retry queue → 主 queue
         → 永久错误/超限 → DLX/失败表
```

主队列立即 requeue 会让同一毒消息高速循环，占用消费者和 CPU，还可能阻塞后续消息。DLX 记录原消息、次数、错误、trace 和代码版本，重放也要有新上限。

### 处理步骤

1. 按错误分类决定 retry、reject 或 DLX；
2. 临时错误指数退避加 jitter，限制总时间和次数；
3. 永久错误进入死信并告警，不重复占用主队列；
4. 修复代码/数据后按类型、小批量、限速重新投递；
5. 重投前检查业务幂等状态，避免已经成功的副作用再次执行。

### 参考回答

> requeue 不是通用重试策略。临时错误进入有次数和退避的延迟队列，永久错误或超过次数进入 DLX；死信保留上下文、可人工修复和重投，重投也要检查幂等，防止毒消息循环。

### 常见误区

- 所有异常都 `NACK requeue`，让毒消息高速占用主队列；
- 死信没有 attempt、错误分类和代码版本，修复后无法安全筛选；
- 重投不设置新的上限，导致 DLQ 和主队列之间再次循环；
- 把消息格式错误当暂时网络错误无限重试。

## 场景 8：消息积压越来越多，如何恢复？

### 先判断

画出生产速率、消费速率、lag/ready/unacked/pending 和单条处理 P99；确认是生产变快、消费者变慢、broker 受限、重试放大还是数据库/模型 API 下游瓶颈。

### 原理与应用

Kafka 受 partition 并行度约束，RabbitMQ 受 queue/prefetch/broker 资源约束，所有系统还受下游连接池和限额约束。增加 worker 可能使下游超时更多，重试又进一步放大积压。

### 处理步骤

1. 暂停无效重试和低优先级任务，避免继续放大；
2. 依据 lag、处理 P99、错误和资源水位定位瓶颈；
3. 在 partition/queue、数据库连接、模型 API 限额允许时扩容；
4. 启用背压、优先级和降级，接口返回 queued 而不是无限接受；
5. 恢复时按租户/时间/事件类型限速回放；
6. 监控消费速率、lag、死信、下游 P99 和二次失败。

### 参考回答

> 我先比较生产/消费速率和 lag，再判断 partition/queue、消费者、重试还是下游容量瓶颈；不盲目加 worker。先暂停无效重试、启用背压和优先级，修复瓶颈后按下游承载限速回放，避免积压恢复再次打满数据库或模型服务。

### 常见误区

- 只看总 lag，不看单 partition/queue、重试和死信；
- 在数据库/模型服务已超时的情况下继续扩消费者；
- 恢复时一次性放开所有积压，造成二次雪崩；
- 只清空队列，不核对事实表、处理记录和用户看到的状态。

# 第三部分：一分钟总复习

## 必须能闭卷回答

- 生产 confirm、Broker 接收、业务完成和 ACK 的边界；
- 至多/至少/恰好一次以及重复消费；
- Kafka Partition/Offset/Group/ISR/Rebalance；
- RabbitMQ Exchange/Queue/Confirm/ACK/Prefetch/DLX；
- 幂等键、唯一约束、状态机、Outbox/CDC/Saga；
- 重试分类、死信、顺序、背压、积压和容量。

## 模块口述总结

> 我通常采用至少一次投递，先把生产确认、Broker 接收、业务处理和 ACK 分开。发送超时或 ACK 丢失都会产生重复，所以消息带 message_id，消费者用唯一键、处理记录和状态机幂等；数据库与 MQ 双写用 Outbox/CDC，把漏事件变成可重试和可对账的 pending。Kafka 关注 Partition、Offset、Group、ISR、Rebalance 和 lag；RabbitMQ 关注 Exchange、Confirm、ACK、Prefetch 和 DLX。重试要分类、退避、限次，积压排查同时看 Broker、消费者和下游容量。

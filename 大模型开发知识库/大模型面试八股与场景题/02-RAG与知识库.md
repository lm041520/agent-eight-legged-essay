# 02 RAG 与知识库

> 目标：不仅能背出“检索后生成”，还要能设计文档入库、检索、重排、引用、评测、权限和增量更新的完整系统。

## 0. 模块地图

RAG 必须分成两条时间上不同的链路：

```text
离线入库：文档 → 解析 → 清洗 → 切分 → 元数据 → Embedding → 索引

在线问答：Query → 理解/改写 → 过滤 → 多路召回 → 融合 → 重排
          → Context组装 → LLM生成 → 引用/拒答 → 评测与观测
```

适用岗位：RAG 开发、Agent 应用、AI 后端、搜索算法、多模态文档智能。

优先级：

- ★★★★★：完整链路、文档解析与切分、混合检索、重排、引用、评测、故障分层；
- ★★★★☆：HNSW/IVF、Query Rewrite、Parent-Child、权限、版本与迁移；
- ★★★☆☆：HyDE、GraphRAG、十亿级检索的深入实现。

# 第一部分：常规八股

## 1. RAG 的完整流程是什么？

> 面试优先级：★★★★★｜学习难度：★★★☆☆｜适用岗位：应用、RAG、Agent  
> 掌握要求：能画离线/在线两条链，能说每步输入输出

### 先理解

RAG 在离线阶段把外部文档处理成可检索索引；在线阶段根据用户问题找出证据，经过融合和重排后放入模型上下文，让模型基于证据生成并返回引用。

LLM 的参数知识可能过时，也不知道企业私有资料，并且单靠参数回答很难提供可核验引用。RAG 在生成前检索外部证据，使知识能够独立更新、删除、授权和追踪来源。它的目标不是让模型“永久记住文档”，而是在回答前临时找出相关证据，从而弥补参数知识不覆盖私有文档、更新慢、无法给出精确来源这三个局限。

### 原理与应用

#### 离线链路

1. **接入**：PDF、Word、网页、数据库、工单等进入系统。
2. **解析**：提取正文、标题、表格、图片、页码和坐标；扫描件需要 OCR。
3. **清洗**：去页眉页脚、乱码、重复、无效导航和敏感内容。
4. **切分**：按标题、段落、条款或语义边界形成 Chunk。
5. **元数据**：保存 `document_id/page/section/version/permission` 等。
6. **Embedding**：将检索文本编码成向量。
7. **索引**：建立向量索引，同时可建立 BM25 倒排索引。
8. **质量检查**：检查解析、切分、向量数量和可回溯性。

#### 在线链路

1. 接收 Query、用户身份和对话上下文；
2. 做意图识别、Query Rewrite、子问题拆分；
3. 先应用租户、权限、时间和业务 Metadata Filter；
4. BM25、Dense、图检索或数据库查询多路召回；
5. 使用加权、归一化或 RRF 融合；
6. 用 Cross-Encoder/Reranker 对候选精排；
7. 去重、扩展邻居或父块，控制 Token Budget；
8. 将证据与来源组装进 Prompt；
9. LLM 基于证据回答；
10. 校验引用、执行无答案拒答；
11. 记录 Trace、反馈和 Bad Case。

### 面试准备

**推荐回答**

> RAG 分离线入库和在线检索两部分。离线先解析清洗文档，按结构切分并保存页码、版本、权限等元数据，然后生成 Embedding，建立向量和关键词索引。在线接到问题后进行必要的改写和权限过滤，使用 BM25 与向量检索召回候选，融合后通过 Reranker 精排，再按 Token 预算组装证据，让 LLM 基于证据生成答案并返回引用。生产系统还需要无答案拒答、分层评测、增量更新和可观测性。

**坑**

- 只说“切分、向量化、Top-K、生成”，遗漏解析、权限、重排和评测；
- 把向量数据库当成完整 RAG；
- 先检索再做权限过滤，造成候选越权；
- 只测最终答案，不知道检索是否正确。

## 2. Chunk 太大和太小有什么问题？如何选择？

> 面试优先级：★★★★★｜学习难度：★★★☆☆｜适用岗位：RAG、应用、多模态文档  
> 掌握要求：能解释召回粒度与生成上下文的矛盾

**一句话**：Chunking 要在语义完整性、检索精度和上下文成本之间取平衡，太小容易丢失上下文，太大又会混入无关内容，合适大小必须结合文档结构、问题类型和评测结果确定。

核心矛盾在于：检索希望 Chunk 小而聚焦，生成希望上下文完整，固定一个全局长度通常无法同时适合合同、FAQ、表格和技术手册。例如报销条款把金额上限和适用条件切到两个块里，即使召回其中一个，模型也可能给出不完整答案；反过来整章入库又会把大量无关内容塞进 Context。

**太小的问题**

- 条件与结论被拆开；
- 标题、主体和例外条款分离；
- 单块语义不完整，Embedding 不稳定；
- 召回后需要拼很多块，重复和成本增加。

**太大的问题**

- 一个向量混入多个主题，检索精度下降；
- 相关句子被大量无关内容稀释；
- Rerank 和 LLM 输入成本增加；
- Top-K 可容纳的独立证据数量减少。

**Parent-Child Chunking**：索引小块以提高召回精度，命中后返回其父章节或邻域给 LLM：

```text
父块：第十八条 市内交通费（完整条款）
├─ 子块1：超过200元需要行程说明
└─ 子块2：网约车需提供行程单和发票
```

**怎么选**

1. 先按文档结构切，而不是先拍固定 Token 数；
2. 对过长段落再递归拆分；
3. 保留标题路径作为 Chunk 前缀或元数据；
4. 用 Overlap、Sentence Window、Parent-Child 处理跨边界；
5. 在固定评测集上比较 Recall@K、答案质量、Token 和延迟；
6. 按文档类型设置策略，而不是一个值处理所有文档。

**面试怎么说**

> Chunk 太小会丢失上下文，太大会让多个主题混进同一向量并浪费生成 Token。我会先按标题、段落、条款和表格等结构边界切分，再对过长部分递归拆分。对需要小粒度召回、大上下文生成的文档使用 Parent-Child：小块建索引，命中后回取父块或邻居。最终不凭经验拍参数，而是在代表性问题集上比较召回、答案、延迟和 Token 成本。

## 3. Embedding、Query/Document 编码和相似度如何选择？

> 面试优先级：★★★★★｜学习难度：★★★★☆｜适用岗位：RAG、搜索算法  
> 掌握要求：能说明模型约定、归一化与距离的一致性

### 先理解

Embedding 模型把文本编码成可比较的向量。选择时不仅要看维度和相似度公式，还要遵守模型对 Query、Document 前缀或接口的训练约定，否则两侧向量分布可能不匹配。忽略模型训练时的前缀、归一化和相似度约定，会让本来相关的文本在向量空间中错位。

**Query 与 Document 为什么可能不同**

检索是非对称任务：

- Query 较短，表达“我想找什么”；
- Document 较长，表达“我包含什么”。

部分模型训练时使用不同接口或前缀：

```text
query: 打车超过200元怎么报销
passage: 第十八条 市内交通费单笔超过200元时……
```

这些前缀是模型输入指令的一部分。忽略模型卡约定可能造成分布不匹配。

### 原理与应用

#### Embedding 模型在做什么

它会 Tokenize 文本、查 Embedding 表、经过编码网络，再通过池化或专用位置得到固定维度向量。便宜的主要原因不是“只查表”，而是通常只做一次并行前向并输出一个向量，不需要像生成模型那样逐 Token Decode。

#### 三种常见度量

余弦相似度：

```text
cos(q,d) = q·d / (||q|| ||d||)
```

关注方向，弱化模长。

点积：

```text
score(q,d) = q·d
```

如果向量已 L2 归一化，点积等于余弦；未归一化时模长也会影响分数。

欧氏距离：

```text
distance(q,d) = ||q-d||
```

距离越小越近。归一化向量下，它与余弦具有单调关系。

**选择原则**

优先遵循模型官方训练与评测说明，并确保：

- 入库和查询使用相同模型与版本；
- 前缀、归一化和 Pooling 一致；
- 索引度量与模型要求一致；
- 记录最终送入模型的完整字符串；
- 升级时重建索引或双写迁移。

### 面试准备

**推荐回答**

> Embedding 模型不是简单查表，而是对 Token 序列完成编码并汇聚成固定向量。部分检索模型使用非对称训练，Query 和 Document 需要不同前缀或接口，所以必须遵循模型卡。相似度方面，归一化后点积与余弦等价；未归一化时点积还受模长影响。我的选择顺序是先看模型训练约定，再确保入库、查询、归一化和向量库度量完全一致，并用领域召回集验证。

**坑**

- 入库和查询用了不同模型或版本，向量不可比；
- Query 侧漏加模型要求的前缀，导致非对称分布错位；
- 索引度量与模型约定不一致（模型要点积却配欧氏）；
- 未归一化时直接把点积当余弦解释。

## 4. Exact、ANN、HNSW 和 IVF 分别是什么？

> 面试优先级：★★★★☆｜学习难度：★★★★☆｜适用岗位：RAG、搜索、向量平台  
> 掌握要求：能解释 Approximate 近似在哪里以及如何测 Recall

### 先理解

Exact Search 比较全部向量，结果准确但规模大时慢；ANN 只访问更可能接近的候选来换取速度。HNSW 用分层近邻图导航，IVF 先把向量分桶再搜索部分桶。

向量已经算好，并不代表检索一定又快又准；真正的差别在于搜索时检查全部向量，还是借助索引只访问一部分候选。可以把 Exact 看成逐本翻遍书库，HNSW 看成沿邻居网络接近目标，IVF 看成先选最可能的书架再在架内查找。

### 原理与应用

#### Exact 与 ANN

Exact Search 与全部候选计算距离，返回真实 Top-K；ANN 通过索引只访问可能接近的部分候选，以少量召回损失换延迟和资源。

“Approximate”不是随意修改向量，而是搜索过程可能没有访问真正最近的点。

#### HNSW

HNSW 构建多层近邻图：上层稀疏、负责快速接近目标区域；下层更密、负责精细搜索。

关键参数：

- `M`：每个节点连接数；
- `efConstruction`：建索引搜索范围；
- `efSearch`：查询搜索范围。

通常 `efSearch` 越大，Recall 越高、查询越慢。

#### IVF

IVF 先训练聚类中心，把向量分到不同桶；查询先找接近的中心，只搜索若干桶。

关键参数：

- `nlist`：桶数量；
- `nprobe`：查询时搜索桶数量。

`nprobe` 越大，访问候选越多，Recall 和延迟通常一起上升。

#### 如何测 ANN Recall

先在可承受的小样本上用 Exact 得到真实 Top-K，再计算：

```text
ANN Recall@K = ANN Top-K 与 Exact Top-K 的交集数量 / K
```

索引参数必须在 Recall—Latency—Memory 曲线上选择。

**对比**

| 维度 | HNSW | IVF |
|---|---|---|
| 结构 | 多层近邻图 | 聚类倒排桶 |
| 召回 | 通常较高 | 依赖聚类与 nprobe |
| 内存 | 图边开销较高 | 相对可控，可结合压缩 |
| 更新 | 动态插入较方便 | 分布变化大时聚类可能需重训 |
| 场景 | 中大规模、低延迟高召回 | 超大规模、希望控制搜索范围 |

### 面试准备

**推荐回答**

> Exact 扫描全部向量，是正确性基线；ANN 通过索引少访问候选，近似发生在搜索过程。HNSW 用多层近邻图逐步接近目标，通常召回高但图结构占内存；IVF 先聚类分桶，查询只扫描部分桶，更适合控制超大规模搜索范围。实际选型会用 Exact Top-K 测 ANN Recall，并同时比较 P95 延迟、内存、构建时间和更新需求。

**坑**

- 把 ANN 的“近似”误解为修改了向量本身；
- 只调大 `efSearch`/`nprobe` 追求 Recall，不看延迟和内存；
- 不用 Exact Top-K 做基线，无法量化 ANN 的召回损失；
- IVF 数据分布大幅变化后不重训聚类中心。

## 5. BM25 与 Dense Retrieval 如何互补？Hybrid 和 RRF 怎么做？

> 面试优先级：★★★★★｜学习难度：★★★★☆｜适用岗位：RAG、搜索、Agent  
> 掌握要求：能解释词项、IDF、长度归一化和融合

### 先理解

BM25 擅长精确关键词、编号和专有名词，Dense Retrieval 擅长语义相似表达。Hybrid Search 同时召回两路结果，RRF 可以在原始分数不可直接比较时按排名进行融合。

企业文档既包含编号、金额和专有名词，也包含用户的口语化改写。BM25 擅长原词匹配，Dense Retrieval 擅长语义匹配；混合检索是为了避免任何一类查询只依赖自己的弱项。

**BM25 的直觉**

BM25 认为：Query 中的词在某文档出现越多，文档越相关；但高频常见词区分度低，长文档也不能因为词多就天然占优。

典型形式：

```text
score(D,Q) = Σ IDF(q) ×
             tf(q,D) × (k1+1)
             / [tf(q,D) + k1 × (1-b+b×|D|/avgdl)]
```

- `tf`：词频，增加会提高分数但逐渐饱和；
- `IDF`：稀有词权重更高；
- `|D|/avgdl`：文档长度归一化；
- `k1`：控制词频饱和；
- `b`：控制长度归一化强度。

### 原理与应用

#### RRF

不同检索器分数不在同一尺度，RRF 用排名融合：

```text
RRF(d) = Σ 1 / (k + rank_i(d))
```

它不直接比较 BM25 分数和余弦分数，只奖励在多路结果中排名靠前的文档，稳健且容易落地。

**BM25 与 Dense 的优势**

| 场景 | BM25 | Dense |
|---|---|---|
| 型号、编号、专名 | 强 | 可能弱 |
| 原词精确匹配 | 强 | 不一定稳定 |
| 同义改写 | 弱 | 强 |
| 领域迁移 | 不依赖训练语义 | 依赖 Embedding 泛化 |
| 可解释性 | 可看词项贡献 | 较难 |

### 面试准备

**推荐回答**

> BM25 擅长词项精确匹配，尤其是型号、编号和专有名词；Dense Retrieval 能召回用不同说法表达的相同语义。生产中我通常并行召回，先在每一路内部取候选，再使用 RRF 或经过校准的加权分数融合，最后交给 Reranker。RRF 的优势是不要求不同检索器分数同尺度，但融合参数和各路候选数仍要用领域评测集选择。

**坑**

- 说 Dense 一定淘汰 BM25；
- 直接把未归一化 BM25 分数和余弦分数相加；
- 混合检索后不做去重；
- 只看最终答案，无法证明是哪一路提供了增益。

## 6. Bi-Encoder、Cross-Encoder 和 Reranker 有什么区别？

> 面试优先级：★★★★★｜学习难度：★★★☆☆｜适用岗位：RAG、搜索  
> 掌握要求：能解释为什么一个适合召回、一个适合精排

**一句话**：Bi-Encoder 分别编码 Query 和文档，文档向量可以预计算，适合大规模召回；Cross-Encoder 联合读取 Query 与候选，交互更充分但更慢，通常作为少量候选的 Reranker。

百万级文档无法全部交给 Cross-Encoder 与 Query 联合计算，因此需要先用可预计算的 Bi-Encoder 或 BM25 快速缩小候选范围，再用更准确但更慢的模型精排：

```text
Bi-Encoder/BM25：从百万文档召回几十到几百
Cross-Encoder：对少量候选精排
```

**Bi-Encoder**：Query 和 Document 分别编码，Document 向量可预计算，适合百万级召回。

```text
q = Encoder(query)
d = Encoder(document)
score = similarity(q,d)
```

**Cross-Encoder**：把 Query 与 Document 拼在一起输入模型，两侧 Token 可以充分交互，通常更准，但每个候选都要重新前向，无法预计算文档向量。

```text
[query, document] → model → relevance score
```

**面试怎么说**

> Bi-Encoder 分别编码 Query 和文档，文档向量可以预计算，适合大规模粗召回；Cross-Encoder 把 Query 和候选文档联合输入，Token 级交互更充分，通常相关性判断更准，但不能对文档侧大规模预计算。因此常用 Bi-Encoder 或 BM25 先缩小候选，再用 Cross-Encoder Reranker 精排。候选数需要在 Recall 和延迟之间调节。

**坑**

- 想直接用 Cross-Encoder 扫全库，导致延迟不可接受；
- 以为 Bi-Encoder 也能像 Cross-Encoder 那样做 Token 级交互；
- 重排候选数拍脑袋，不在 Recall 和延迟之间调。

## 7. Query Rewrite、Multi-Query 和 HyDE 是什么？有什么风险？

> 面试优先级：★★★★☆｜学习难度：★★★☆☆｜适用岗位：RAG、Agent  
> 掌握要求：能说明为什么改写可能提高召回也可能改变原意

**一句话**：三者都在尝试把原问题转换成更容易检索的表达——Rewrite 生成一个改写，Multi-Query 生成多个视角，HyDE 先生成假设文档，共同风险是引入原问题没有的条件导致查询漂移。

用户问题常常过短、口语化或缺少文档中的正式词汇，直接检索可能漏掉正确证据；改写和扩展可以弥补表达差异，但也可能偷偷改变原意。例如“打车钱怎么报”扩成“市内交通费报销标准”有帮助，扩成“差旅住宿标准”就发生了查询漂移。

**三种方法**

- **Query Rewrite**：把口语、省略和多轮指代改成适合检索的独立问题。
- **Multi-Query**：生成多个不同角度或关键词表达，分别检索后合并。
- **HyDE**：先生成一个假设性答案/文档，再用它的表示检索真实文档。

**治理方法**

- 保留原 Query，并与改写并行召回；
- 对金额、日期、产品型号、否定词做约束保护；
- 限制改写数量和总延迟；
- 记录每个 Query 的候选与贡献；
- 在“需要改写”的问题切片上做消融，不全量盲开。

**风险**

1. 改变时间、金额、否定和实体等关键约束；
2. 多路查询引入噪声并增加成本；
3. HyDE 生成错误假设，把检索带向错误方向；
4. 对本来很明确的编号查询，改写反而破坏关键词；
5. 无法追踪最终召回由哪个改写产生。

**面试怎么说**

> Query Rewrite 用于补全指代和改成检索友好表达，Multi-Query 从多个角度召回，HyDE 用假设文档缩小查询与文档表达差异。但改写可能改变原意，尤其是金额、时间、否定和专有名词。我会保留原 Query 作为一路召回，对关键约束做保护，记录各路贡献，并通过切片评测决定只在哪些问题上启用。

## 8. 如何组装 Context、提供引用并实现无答案拒答？

> 面试优先级：★★★★★｜学习难度：★★★★☆｜适用岗位：RAG、Agent、应用  
> 掌握要求：能设计证据 ID、引用校验和拒答阈值

### 先理解

检索 Top-K 只是候选，真正送给模型的 Context 还要去重、排序、控制 Token 并保留证据标识。引用与拒答的关键是让每个结论都能被当前证据支持，而不是只依赖模型自觉。

召回若干相关片段不等于模型已经获得可靠答案：片段顺序、重复内容、来源标识和证据冲突都会影响生成。可靠系统要让每段证据可追溯，并在证据不足时拒答，而不是让模型用常识补齐看似合理的内容。

### 原理与应用

#### Context 不是简单拼接 Top-K

需要做：

1. 去重与合并重叠 Chunk；
2. 保留标题、来源、页码和证据 ID；
3. 按相关性与文档顺序组织；
4. 必要时回取父块或邻居；
5. 按 Token Budget 截断；
6. 明确要求只依据证据回答，并区分证据与指令。

#### 引用设计

给每段证据稳定 ID：

```text
[S1] 文档：差旅报销制度，页码：8，第十八条
市内交通费单笔超过200元时……
```

模型输出：

```text
需要补充行程说明并由直属负责人审批。[S1]
```

生成后校验引用 ID 是否存在，并可检查答案关键断言是否被对应证据支持。引用不能让模型自由编造文件名和页码。

#### 无答案拒答

不能只依靠一个向量阈值。可以组合：

- 检索分数和分数间隔；
- Reranker 相关性；
- 是否存在覆盖问题关键实体的证据；
- 模型基于证据的可回答性分类；
- 引用支持校验；
- 业务高风险规则和人工升级。

阈值必须在有答案/无答案测试集上校准，观察错误回答率与过度拒答率。

### 面试准备

**推荐回答**

> 我不会把 Top-K 原样拼进 Prompt，而会去重、补父块或邻域、保留来源与证据 ID，并按相关性和 Token 预算组织。引用由系统提供稳定 ID，模型只能引用候选 ID，生成后再校验。无答案拒答会综合 Reranker 分数、关键实体覆盖、可回答性和引用支持，而不是只看单一余弦阈值；最终通过有答案和无答案混合测试集校准误答与过度拒答的平衡。

**坑**

- 把 Top-K 原样拼进 Prompt，不去重、不控制 Token；
- 让模型自由生成文件名和页码，而不是引用系统给的稳定 ID；
- 只用单一余弦阈值判断能不能答；
- 只统计拒答率，不看误答率和过度拒答率的平衡。

## 9. RAG 应该如何评测？

> 面试优先级：★★★★★｜学习难度：★★★★☆｜适用岗位：全部 RAG 相关岗位  
> 掌握要求：能分层、能构造数据、能解释指标

### 先理解

RAG 是解析、检索、重排、生成和服务组成的链路，最终答案错误可能来自任意一层。因此评测必须分层，并把每个问题与金标准证据绑定，才能定位改动到底改善了什么。只看答案是否正确无法定位是哪一层出问题，所以评测必须沿链路拆开，并为问题标注对应证据。

### 原理与应用

#### 检索指标

**Recall@K**：有多少问题的相关证据出现在 Top-K。  
**MRR**：第一个相关结果排名的倒数平均值。  
**NDCG**：考虑多级相关性和排名位置。  
**Precision@K**：Top-K 中相关结果比例。

#### 生成指标

- 答案正确性；
- 对问题的相关性；
- 对证据的忠实度；
- 引用正确率和引用覆盖率；
- 无答案误答率与过度拒答率；
- 格式、完整性和安全性。

#### 测试集构造

至少包含：

- 直接事实题；
- 跨 Chunk 和多跳题；
- 同义改写；
- 型号/编号/专有名词；
- 时间和版本敏感题；
- 无答案题；
- 权限边界题；
- OCR、表格和低质量文档题；
- 对抗或提示注入题。

每题需要标注相关证据 ID，而不只有一个自然语言答案。

### 面试准备

**推荐回答**

> 我会把 RAG 评测拆成解析、检索、生成和系统四层。检索用 Recall@K、MRR、NDCG，并标注每个问题对应的证据 Chunk；生成评估正确性、忠实度、引用和拒答；系统评估延迟、错误率和成本。测试集要覆盖直接事实、多跳、关键词、同义改写、无答案、权限、OCR和版本问题。每次只改变一个组件做消融，才能知道提升来自切分、召回、重排还是模型。

**坑**

- 只测最终答案对错，无法定位是哪一层出问题；
- 测试集没标注金标准证据 ID，检索质量无从量化；
- 一次同时改多个组件，提升无法归因；
- 只看平均分，不按问题/文档类型切片，掩盖特定弱项。

## 10. RAG、微调和 GraphRAG 如何选择？

> 面试优先级：★★★★☆｜学习难度：★★★☆☆｜适用岗位：RAG、Agent、算法  
> 掌握要求：能按“知识、行为、关系推理”区分

**一句话**：RAG 主要解决可更新、可引用的外部知识，微调主要改变稳定行为和任务模式，GraphRAG 适合实体关系与多跳结构成为主要瓶颈的场景，三者不是按“先进程度”选择。

这三种技术解决的不是同一类问题。若把员工最新制度拿去微调，更新和删除都很困难；若普通单跳问答直接上知识图谱，又会增加不必要的构建成本。

**RAG 与微调怎么分**

| 需求 | 更合适的手段 |
|---|---|
| 新知识频繁变化、需要引用 | RAG |
| 固定输出格式、语气、工具调用行为 | SFT/LoRA |
| 实时订单、库存、余额 | 业务工具/API |
| 私有事实 + 稳定行为 | RAG 与微调组合 |

微调不是稳定注入大量实时事实的首选；RAG 也不能自动教会模型稳定的复杂行为模式。

**GraphRAG 适合什么**

GraphRAG 适合问题强依赖实体关系、多跳路径和全局社区结构，例如：

```text
某供应商通过哪些子公司与风险事件产生间接关系？
```

如果问题主要是局部事实查找，普通混合检索往往更简单、更便宜。不能因为“图更高级”就引入复杂实体抽取、消歧、图更新和图检索。

**面试怎么说**

> 我先区分要解决的是知识、行为还是实时操作。频繁变化且需要引用的知识优先 RAG；稳定格式和行为模式适合 SFT/LoRA；实时状态应调用业务系统。GraphRAG 只有在实体关系和多跳推理是主要瓶颈时才值得使用，否则图构建与更新成本可能大于收益。最终选型要用问题类型切片和对照实验验证。

# 第二部分：高频场景题

> **本部分共通检查**：RAG 场景的取舍集中在召回覆盖与噪声、Chunk 完整性与粒度、质量与延迟、逻辑隔离与成本之间，通常用多阶段漏斗，而不是让一个参数承担所有目标。异常与降级要考虑解析失败、OCR/表格结构错误、索引延迟、旧版本冲突、越权召回、外部模型失败和证据不足；降级时宁可返回可核验的部分结果或拒答，也不能编造。验证统一分层：分别评估解析、切分、召回、融合/重排、Context、回答、引用和系统指标，测试集覆盖编号、同义改写、多跳、无答案、权限和版本问题，每次只改一个环节做消融。条件变化的通用应对是：文档规模扩大时调整索引和异步链路，更新更频繁时强化版本与增量，风险升高时提高引用、拒答和人工复核要求。下面每道题只写本场景特有的澄清问题和易错点，共通部分不再重复。

## 场景 1：合同、论文、扫描件、财务报表和手册如何解析与切分？

> 面试优先级：★★★★★｜学习难度：★★★★☆｜适用岗位：RAG、文档智能、应用  
> 掌握要求：能给出分流架构、元数据、失败路径和评测

**判断**：PDF 并不是统一的纯文本容器，页面可能有文本层、扫描图、双栏、表格和浮动区域。面试官考的不是会不会调某个 PDF Loader，而是你是否知道 PDF 可能只有图像/文本层/复杂版面、是否会按文档类型分流、是否理解表格与阅读顺序、是否保留可引用可更新可权限过滤的元数据、是否有质量门禁和人工兜底。正确做法是先识别文档与页面类型，再恢复结构并按业务语义切分。

**先问清楚**

- 各类文档（数字 PDF、扫描件、表格、图片）比例与总规模；
- 是否需要页码或文字坐标级引用；
- 表格、公式、图片本身是不是问答对象；
- 更新频率与版本规则；
- 是否有部门权限、多租户和审计；
- 用户主要问事实、比较、总结还是多跳关系。

**怎么办（分流主链）**

```text
PDF上传
→ 文件安全检查与去重
→ 逐页判断文本层、扫描页和版面类型
├─ 普通文本页：文本+字体+坐标解析
├─ 扫描页：图像预处理+OCR+版面分析
└─ 图文混合页：区域级路由
→ 恢复标题层级、阅读顺序、表格和图注
→ 按文档类型切分
→ 保存元数据与原始区域
→ 质量检查
→ Embedding、BM25和索引
```

**分类型切分**

| 类型 | 处理重点 | 切分方式 |
|---|---|---|
| 普通单栏 PDF | 标题、段落、列表 | 标题/段落边界，过长再递归 |
| 扫描件 | OCR 坐标、置信度、版面 | 按版面区域和语义边界 |
| 合同/制度 | 章、条、款、例外 | 保持完整条款，小块索引、父条款返回 |
| 双栏论文 | 栏顺序、公式、图表 | 先恢复阅读顺序，再按摘要/章节 |
| 财务报表 | 表头、行列、跨页 | 表头与行组绑定，保存结构化表和原图 |
| 技术手册 | 多级标题、步骤、图片 | Parent-Child，步骤与图注绑定 |
| PPT 型 PDF | 每页主题、文本框顺序 | 页为父块，页内按区域拆子块 |

**元数据**

```json
{
  "document_id": "expense-policy-2026",
  "version": "2026-01",
  "page": 18,
  "section_path": ["第三章", "第十八条"],
  "bbox": [120, 300, 900, 650],
  "content_type": "clause",
  "ocr_confidence": 0.96,
  "parent_id": "article-18",
  "tenant_id": "company-a",
  "acl": ["finance", "manager"],
  "effective_date": "2026-01-01"
}
```

**本场景特有的失败与降级**

- OCR 置信度低：标记待复核，不直接作为高风险答案证据；
- 表格结构失败：保留原始截图，可让多模态模型辅助但要标置信度；
- 双栏顺序异常：用版面模型或人工抽检；
- 加密/损坏：进入失败队列，明确告诉用户；
- 超长表格：存结构化数据，问答时通过 SQL/表格工具查询；
- 图片与图注：使用稳定区域 ID 绑定；
- 重复上传：内容哈希 + 文档版本规则；
- 新旧版本：生效时间过滤，避免同时召回冲突条款。

**本场景特有的评测**

```text
解析：字符准确率、阅读顺序正确率、表格结构准确率
切分：条款完整率、跨块答案比例、长度分布
检索：不同文档类型的Recall@K
回答：引用页码/坐标正确率、忠实度、拒答率
系统：单页解析时间、失败率、人工复核率
```

**怎么说**

> 我不会对所有 PDF 使用统一 Loader 和固定 Token 切分。首先会逐页判断是否有文本层、是否为扫描页以及版面类型；普通页提取文本和坐标，扫描页走 OCR 与版面分析，图文混合页按区域分流。切分时按文档语义结构：合同按章条款，论文按章节并先恢复双栏顺序，报表保留表头和行列关系，手册用小块索引、父章节返回。每个 Chunk 保存页码、坐标、章节、版本、权限和 OCR 置信度。低置信度、表格失败和损坏文件进入降级或人工复核。最后分别评估解析、切分、召回、回答和引用，而不是只看几个问答案例。

**别踩 & 追问**

- 错误答案：对所有 PDF 用统一 Loader 和固定 Token 切分；扫描件不做版面分析直接 OCR；不保留坐标和版本，导致答案无法引用也无法更新。
- 若要求文字坐标级引用，解析阶段就必须保留 bbox，不能等到检索时补；若扫描件占比高，OCR 和版面模型会成为主要成本和错误来源，要优先在这层建质量门禁。

## 场景 2：召回文档正确，但最终答案错误，怎么排查？

> 面试优先级：★★★★★｜学习难度：★★★★☆｜适用岗位：RAG、应用  
> 掌握要求：能从证据到 Prompt 到生成逐层定位

**判断**：“召回正确”只说明候选中出现了相关文档，不代表正确证据最终进入 Context，也不代表模型正确使用了证据。排查应继续覆盖重排、截断、上下文组装、Prompt 和生成。

**先问清楚**

- “召回正确”是指相关文档出现在初始候选，还是已经进入最终 Context？
- 错误表现是缺条件、缺例外、用错版本，还是完全答非所问？
- 是否可能有多条证据版本冲突或内容矛盾？
- 把金标准证据单独喂给模型，还会答错吗？

**怎么排查**

先明确“召回正确”的定义，需要检查：

- 正确 Chunk 是否进入最终 Context，而不只是初始候选；
- 条件、例外和版本是否完整；
- Reranker 是否把错误版本排到前面；
- Context 是否被 Token 截断；
- 多条证据是否冲突。

沿链路定位：

```text
初始召回候选
→ 融合与重排结果
→ 去重/父块扩展
→ 最终Context原文
→ 渲染后的完整Prompt
→ 模型原始输出
→ 后处理和客户端展示
```

分别做对照：

1. 只把金标准证据喂给模型：若仍错，问题在生成/Prompt/模型能力；
2. 换更强模型但保持检索：若变好，可能是阅读或推理能力；
3. 固定模型只换 Context：判断噪声、顺序和冲突；
4. 检查引用是否真正支持断言，而不是“引用存在”。

**怎么说**

> 我不会因为正确文档在 Top-K 就认定检索没问题。我会追踪它是否经过融合、重排和 Token 截断后进入最终 Context，并检查是否缺少条件、例外或版本。然后用金标准证据单独调用模型：仍然答错说明是 Prompt、阅读推理或生成约束问题；能答对则继续检查 Context 噪声、顺序和冲突。最终把问题归因到具体阶段，并为该类 Bad Case 增加回归测试。

**别踩 & 追问**

- 错误答案：看到正确文档在 Top-K 就断定检索没问题、直接归因大模型；不区分“出现在候选”和“进入最终 Context”。
- 用金标准证据单独喂仍答错，说明根因在 Prompt、阅读推理或生成约束；若能答对，则回到 Context 的噪声、顺序和证据冲突上找。

## 场景 3：产品型号、错误码和专有名词经常漏召怎么办？

> 面试优先级：★★★★☆｜学习难度：★★★☆☆｜适用岗位：RAG、搜索  
> 掌握要求：能利用 BM25、字段和字符归一化

**判断**：Dense Retrieval 擅长寻找“意思相近”的内容，但型号和错误码往往只差一个字符、语义并不丰富。此类查询更像精确查词，需要让关键词检索、字段过滤和向量检索各自发挥优势。

**先问清楚**

- 漏召的是型号/错误码本身，还是它周边的说明文字？
- 这些标识在原文里是正文文本，还是藏在表格、图片或图注里？
- 是否存在大小写、连字符、全半角、别名等变体？
- 解析阶段是否已经把型号/错误码丢失或拆断？

**怎么办**

1. 保留原 Query，不要让改写删除型号；
2. 建 BM25/倒排索引，与 Dense 并行召回；
3. 对大小写、连字符、全半角、常见别名做规范化；
4. 将型号、错误码抽取为 Metadata 字段，做精确/前缀过滤；
5. 对表格中的键值建立结构化索引；
6. 单独构造编号类测试切片；
7. 分析漏召来自解析丢失、切分、分词还是检索。

**怎么说**

> 型号和错误码通常依赖精确字符，Dense Embedding 可能把它们弱化。我会保留原 Query，增加 BM25 与字段检索，对连字符、大小写和别名规范化，并把可识别的型号抽成 Metadata 做精确过滤。之后用编号类专门测试集测 Recall，而不是只看自然语言问题的平均指标。

**别踩 & 追问**

- 错误答案：只靠 Dense 语义检索；让 Query Rewrite 处理型号导致关键词被改写掉；只看平均 Recall，掩盖编号类查询的漏召。
- 若型号藏在表格里，要建结构化字段索引再做精确过滤；若解析阶段就把型号拆断或丢失，先修解析和分词，再谈检索融合。

## 场景 4：Top-K 小了证据不足，大了噪声和延迟增加，怎么办？

> 面试优先级：★★★★☆｜学习难度：★★★☆☆｜适用岗位：RAG、应用  
> 掌握要求：能区分召回 K、重排 K、最终 Context K

**判断**：Top-K 不是越大越好，也不必在所有阶段使用同一个值。通常先用较大的召回 K 保证覆盖，再通过去重、过滤和 Rerank 压缩为较小的 Context K。

**先问清楚**

- 问题偏精确事实、宽泛比较还是多子问题？不同类型需要的证据数量不同。
- 延迟预算多少？Reranker 一次能处理多少候选？
- 证据不足是召回没覆盖到，还是被融合/重排/截断丢掉的？

**怎么办**

不要只有一个 K：

```text
各路召回 K：保证候选覆盖
融合后 K：控制进入重排数量
重排后 K：控制最终证据
Context Token Budget：最终硬约束
```

可采用动态策略：简单事实题少取，宽泛比较题或多子问题多取；去重后按文档和子问题覆盖分配名额。Reranker 批量评分，小模型或蒸馏模型可降低延迟。

**本场景特有的评测**

绘制曲线，在拐点选择，而不是只追求最大 Recall：

```text
K → Recall@K
K → Rerank P95
K → 最终准确率/忠实度
K → 输入Token与成本
```

**怎么说**

> 我不会用一个全局 K。先用较大的召回 K 保证覆盖，再通过去重、Metadata 过滤和 Rerank 压到较小的 Context K，最后用 Token Budget 做硬约束。K 值随问题类型动态调整：简单事实题少取，宽泛比较或多跳题多取，去重后按文档和子问题覆盖分配名额，Reranker 用批量评分或蒸馏模型控制延迟。选 K 时我会画 Recall@K、Rerank P95、最终准确率/忠实度、输入 Token 成本四条曲线，在拐点取值而不是一味追求最大 Recall。

**别踩 & 追问**

- 错误答案：所有阶段共用一个 K；只调大 K 追 Recall，无视噪声和延迟；固定 K 不看问题类型。
- 若 Rerank 是延迟瓶颈，先减小重排 K 或换蒸馏 Reranker；若多跳题证据不足，按子问题分配名额，而不是无脑加大全局 K。

## 场景 5：多租户知识库如何防止越权？

> 面试优先级：★★★★★｜学习难度：★★★★☆｜适用岗位：企业 RAG、AI 后端  
> 掌握要求：能说明过滤时机、索引隔离和审计

**判断**：多租户隔离的目标不是“最终回答里不显示别人的文档”，而是未授权内容从一开始就不应进入召回候选、重排、模型上下文、缓存和日志。权限必须由服务端强制执行，不能依赖 Prompt 要求模型自觉保密。

**先问清楚**

- 权限粒度是租户级、部门级还是密级？是否有行级/字段级要求？
- 权限会不会频繁变更？变更后是否要求立即生效？
- 需要物理隔离，还是逻辑 Metadata 过滤即可满足合规？
- 是否需要完整的访问审计和越权告警？

**怎么办（防线）**

1. 请求身份经过服务端鉴权，不能信任客户端传来的租户 ID；
2. Chunk 入库时绑定租户、ACL、部门和密级；
3. 检索前或索引层强制 Metadata Filter；
4. 高隔离要求下按租户/密级分索引或分 Collection；
5. Rerank、缓存、日志和引用都不能混入未授权内容；
6. 缓存键必须包含租户、用户权限版本等安全上下文；
7. 权限变更后使相关缓存和索引可撤销；
8. 记录访问审计并构造越权测试。

**为什么不能先召回再过滤**

越权文档即使最终没展示，也可能进入日志、Reranker、缓存或模型上下文，形成泄漏面。安全过滤应尽可能早，并在输出前做纵深校验。

**怎么说**

> 多租户隔离不能只靠 Prompt。身份由服务端鉴权，文档入库绑定租户和 ACL，检索时在索引或数据库层强制过滤；高隔离场景使用物理或 Collection 级隔离。缓存键、Rerank、日志和引用同样携带安全上下文，并支持权限撤销和审计。测试集中要有用户不能访问但语义高度相关的文档，验证不会召回和泄露。

**别踩 & 追问**

- 错误答案：靠 Prompt 要求模型保密；信任客户端传来的租户 ID；先召回再过滤；缓存键不含权限上下文导致跨租户命中。
- 权限变更后必须能撤销相关缓存和索引，否则旧权限仍会命中；高隔离场景要用物理/Collection 级隔离，而不是只靠 Metadata Filter。

## 场景 6：文档更新、删除和 Embedding 升级如何迁移？

> 面试优先级：★★★★☆｜学习难度：★★★★☆｜适用岗位：RAG平台、AI后端  
> 掌握要求：能设计版本、双写、切换和回滚

**判断**：原文、Chunk、稀疏索引和向量索引都是带版本的派生数据。更新或升级时应构建新版本、校验覆盖与质量，再通过别名或路由切换，并保留回滚能力。

**先问清楚**

- 更新是整篇替换，还是局部修订？影响多少 Chunk？
- 删除要求是逻辑删除即可，还是合规要求彻底物理清除？
- Embedding 升级是换模型、换维度，还是只换版本？
- 能否接受重建索引所需的时间、成本和短暂双份存储？

**怎么办**

文档版本：使用稳定 `document_id` 与独立 `version`，每个 Chunk 继承版本和生效时间。更新流程：

```text
解析新版本
→ 在暂存区完成切分、Embedding和质量检查
→ 原子切换active_version
→ 旧版本延迟回收
```

删除需要同步处理：原文件、Chunk、倒排索引、向量、缓存和审计状态。可先逻辑删除，异步物理回收。

Embedding 升级：不同模型/版本的向量通常不能混在同一空间直接比较。稳妥迁移：

```text
建立index_v2
→ 后台重算历史向量
→ 新写入双写v1/v2
→ 影子流量对比Recall和延迟
→ 灰度切读v2
→ 保留回滚窗口
→ 下线v1
```

**怎么说**

> 文档更新使用稳定文档 ID 和版本号，新版本先在暂存区完成解析、索引和质量门禁，再原子切换 active 版本，避免半更新。Embedding 升级不能把新旧向量直接混搜，我会建立新索引、离线重算、增量双写、影子对比和灰度切流，并保留回滚窗口。删除则需要贯穿原文、Chunk、各类索引和缓存，保证最终一致并可审计。

**别踩 & 追问**

- 错误答案：把新旧 Embedding 向量混在同一空间直接比较；更新时半更新，导致新旧 Chunk 并存冲突；删除只删原文，索引和缓存里仍能召回。
- 若要求零停机切换，用别名/路由做原子切换并留回滚窗口；若合规要求彻底删除，删除动作要贯穿原文、Chunk、倒排、向量、缓存和审计。

## 场景 7：知识库没有答案，如何可靠拒答？

> 面试优先级：★★★★★｜学习难度：★★★★☆｜适用岗位：企业 RAG  
> 掌握要求：能讨论误答与过度拒答权衡

**判断**：可靠拒答实际上是一个二分类问题——当前证据是否足以支持答案。阈值太宽会让模型根据相似内容编答案，阈值太严又会拒绝本来能够回答的问题，因此必须在“无答案误答”和“有答案误拒”之间用数据校准。

**先问清楚**

- 无答案是“知识库确实没有”，还是“有但没被召回”？两者修复方向不同。
- 误答和过度拒答，哪个业务代价更高？
- 高风险问题是否必须人工兜底或强制引用？
- 是否已经有真实的无答案样本，而不只是有答案集？

**怎么办**

1. 建立真实无答案题，不能只在有答案集上调阈值；
2. 分析检索/Rerank 分数、分数间隔和证据覆盖；
3. 增加“证据是否足以回答”的判定；
4. 强制关键断言带引用并做支持检查；
5. 高风险问题设置更严格阈值或人工升级；
6. 拒答时说明缺少什么信息，并允许用户澄清或转人工；
7. 分别报告无答案误答率和有答案误拒率。

**怎么说**

> 我会先准备同时包含有答案和无答案的验证集，利用检索分数、Rerank 结果和证据覆盖判断内容是否足够，再要求关键结论必须有引用支持。高风险问题使用更严格阈值或转人工。评测时分别统计无答案误答率和有答案误拒率，因为只提高拒答率并不代表系统更可靠。

**别踩 & 追问**

- 错误答案：只在有答案集上调阈值；只用单一余弦阈值判断能否回答；靠提高拒答率就宣称系统更可靠。
- 若无答案其实是“有但没召回”，要先修检索而不是加严拒答；高风险问题设更严阈值或转人工，并分别盯住误答率和误拒率两个指标。

## 场景 8：RAG 效果差，如何系统定位？

> 面试优先级：★★★★★｜学习难度：★★★★★｜适用岗位：所有 RAG 相关岗位  
> 掌握要求：能给出分层实验，而不是罗列优化名词

**判断**：不要把所有问题都归因于 Embedding 或 LLM。应沿解析、切分、召回、融合、重排、Context、生成和系统延迟逐层建立证据，找到第一个出现偏差的位置。

**先问清楚**

- 是所有问题普遍差，还是某类文档/问题类型差？
- 有没有端到端 Trace 和标注了金标准证据的测试集？
- 最近改动过哪个环节（切分、Embedding、Rerank、Prompt）？

**怎么排查**

标准定位树：

```text
问题是否可回答？
├─ 否：应拒答或调用其他数据源
└─ 是
   ├─ 原始文档是否包含且解析正确？
   ├─ 金标准证据是否形成完整Chunk？
   ├─ 是否被初始召回？
   ├─ 是否被融合/重排保留？
   ├─ 是否进入最终Context且未截断？
   ├─ 模型拿到金标准证据能否回答？
   └─ 引用与后处理是否正确？
```

消融顺序：

1. Exact/穷举或人工证据验证召回上限；
2. 固定生成，比较切分和检索；
3. 固定检索，比较 Reranker；
4. 使用金标准 Context 测生成上限；
5. 固定其他变量，只改 Prompt 或模型；
6. 按文档类型、问题类型、长度和版本切片。

**怎么说**

> 我会先建立端到端 Bad Case 的 Trace，然后沿链路问七个问题：文档有没有、解析对不对、切分是否完整、初始召回有没有、重排是否保留、最终 Context 是否包含、模型拿到金标准证据能否回答。每次只替换一个环节做对照，并按 OCR、表格、编号、多跳、无答案等切片统计。这样才能把“RAG差”定位成具体可修复的根因，而不是同时换 Embedding、Chunk 和 Prompt 后无法归因。

**别踩 & 追问**

- 错误答案：把所有效果问题都归因于 Embedding 或 LLM；同时改切分、Embedding 和 Prompt，导致无法归因；只看平均分不切片。
- 定位时按 OCR、表格、编号、多跳、无答案等切片分别统计，每次只替换一个环节做对照，才能找到第一个出问题的位置。

# 第三部分：一分钟总复习

## 必须能闭卷回答

1. RAG 离线与在线完整链路；
2. Chunk 大小矛盾和 Parent-Child；
3. Query/Document 编码与相似度一致性；
4. Exact、ANN、HNSW、IVF；
5. BM25、Dense、Hybrid、RRF；
6. Bi-Encoder 与 Cross-Encoder；
7. Query Rewrite/Multi-Query/HyDE 风险；
8. 引用、拒答和分层评测；
9. 多租户权限与索引迁移；
10. PDF 分流解析与切分。

## 模块口述总结

> 可靠 RAG 是一条可观测、可评测的数据与检索链，而不只是向量库。离线要按文档类型解析、结构化切分、保存页码版本和权限，再建立 BM25 与向量索引；在线要在权限过滤后多路召回、融合、重排和 Context 组装，并提供可校验引用和无答案拒答。优化时必须把解析、切分、召回、重排和生成分层测量，通过金标准证据与消融实验定位根因。生产还要处理增量更新、Embedding 迁移、多租户隔离和缓存一致性。

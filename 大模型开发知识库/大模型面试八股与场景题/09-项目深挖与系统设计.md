# 09 项目深挖与系统设计

> 目标：把“我用了 LangChain、向量库和大模型”升级成可以验证的项目因果链，并能在开放系统设计题中讲清约束、架构、取舍、失败与指标。

## 0. 面试官为什么总从项目开始

项目能同时检验：

- 你是否真正负责过；
- 是否理解调用链和数据流；
- 是否做过选型与权衡；
- 是否遇到失败并定位；
- 是否用指标证明效果；
- 是否知道当前方案的边界。

项目回答主线：

```text
业务问题
→ 目标与约束
→ 系统主链路
→ 我的职责
→ 关键选型
→ 最难问题与证据
→ 指标结果
→ 局限和下一步
```

不要按“用了哪些框架”开场。框架名没有说明系统为什么存在、请求怎样流动和你解决了什么。

# 第一部分：项目常规八股（高频问题）

## 1. 如何用 2 分钟介绍一个大模型项目？

> 面试优先级：★★★★★｜学习难度：★★★☆☆｜适用岗位：全部  
> 掌握要求：不看稿讲清问题、链路、贡献、结果

### 先理解

项目介绍应让面试官快速知道业务问题、系统链路、个人职责、关键难点、验证结果和当前限制，而不是按时间顺序罗列使用过的框架。

面试官需要在很短时间内判断项目解决了什么问题、你做了什么以及结果是否可信。按背景、目标、架构、职责、难点和结果组织，比按开发时间线罗列框架更容易形成清晰因果链。

### 原理与应用

按六段结构组织，每段一两句话即可：

1. **背景**：谁在什么场景遇到了什么问题；
2. **目标**：要优化什么，边界和约束是什么；
3. **架构**：一句话主链路；
4. **职责**：自己设计/实现/评测了哪些部分；
5. **难点**：选择一个最能体现能力的问题；
6. **结果**：质量、延迟、成本与不足。

### 面试准备

**推荐回答（以企业知识库 Agent 为例）**

> 这个项目解决员工查询内部制度时搜索慢、答案无法引用的问题。系统离线解析 PDF 和网页，按标题与条款切分，保存页码、版本和部门权限，同时建立 BM25 与向量索引；在线对问题做权限过滤、混合召回、RRF 融合和 Rerank，再把证据交给模型生成带引用答案。我的主要职责是文档切分、检索链路、评测集和线上 Trace。项目初期主要问题是扫描合同和产品编号漏召，我引入 OCR 版面解析、Parent-Child 和 BM25 后，在内部标注集上提高了证据 Recall，并降低了无引用回答。项目目前仍有跨表格和复杂多跳问题不足，下一步会把表格查询工具与普通文本 RAG 分流。

如果没有真实指标，不能编数字，可以说：

> 当时只做了 120 条内部测试和人工抽检，没有完整线上 A/B，这是项目的不足；我现在会补证据级 Recall、引用正确率和 P95 延迟。

**常见错误**

- 花一分钟介绍行业背景，主链路只讲十秒；
- 框架名堆砌；
- 用“我们”覆盖个人贡献；
- 只说“效果很好”；
- 把未来计划说成已经实现。

## 2. 面试官问“你具体负责什么”，怎么回答？

> 面试优先级：★★★★★｜学习难度：★★☆☆☆｜适用岗位：全部  
> 掌握要求：能区分个人决策、实现和协作

**一句话**：面试官不是要你证明整个项目一个人完成，而是确认你能否清楚说出个人边界，以及哪些技术判断、实现和结果可以继续追问。边界越具体，可信度通常越高。

大模型项目通常由多人协作，若只说“我们做了 RAG 和 Agent”，面试官无法判断你的能力边界。回答应把个人负责的设计、代码、实验和决策与团队工作分开，并准备对应证据和遇到的具体问题。按三层讲：

```text
我负责的边界：哪些模块和结果
我做的关键决策：为什么选这个方案
我亲自完成的证据：代码、实验、排障、文档、指标
```

**面试怎么说**

> 团队整体负责知识库产品，我独立完成检索服务和评测闭环。具体包括设计 Chunk 与元数据 Schema、接入 BM25/向量双路召回、实现 RRF 与 Rerank、构造证据标注集，并给每个阶段增加 Trace。前端和权限中心由同事负责，但权限过滤接口的调用时机和检索层接入是我完成的。

**坑**：不要冒领他人工作，也不要只说“参与”。明确边界反而更可信。

## 3. 为什么选择这个模型、框架和向量库？

> 面试优先级：★★★★★｜学习难度：★★★★☆｜适用岗位：全部  
> 掌握要求：能给需求、候选、实验和代价

**一句话**：选型回答要从任务约束、候选方案和实验依据出发，说明为什么当前方案在质量、延迟、成本和维护上更合适，而不是用“热门、方便”代替证据。

技术选型没有脱离约束的最佳答案。选模型看质量、延迟和部署，选框架看流程复杂度和团队维护，选向量库还要看规模、过滤和更新。回答按这条链展开：

```text
需求约束
→ 候选方案
→ 比较维度
→ 小规模实验
→ 最终选择
→ 当前局限
```

例如选择向量库时比较：数据规模和增长、HNSW/IVF 与 Metadata Filter、增量写入和删除、多租户隔离、延迟/Recall/内存、运维备份和团队经验。

**面试怎么说**

对比不合格回答：

> 因为 LangChain 很流行，Milvus 性能很好，所以我们用了。

和更好回答：

> 当时数据量只有几十万 Chunk，但权限过滤复杂、需要频繁更新，所以先选支持 Metadata Filter 且团队可维护的方案，并用 Exact 子集对 HNSW 的 Recall 和 P95 做基线。我们没有一开始上复杂分布式集群，因为现阶段瓶颈是解析和评测，不是索引容量。

## 4. 如何回答“项目中最难的问题是什么”？

> 面试优先级：★★★★★｜学习难度：★★★★☆｜适用岗位：全部  
> 掌握要求：用证据链回答，不只说加班

**一句话**：“最难”不是工作量最大，而是最能体现你怎样面对不确定性。好的回答要展示从现象提出假设、收集证据、定位根因、选择修复到验证结果的完整过程。

面试官想听的不是一句“数据很复杂”，而是你怎样定义问题、收集证据、比较方案并验证修复。按五段讲：现象、分解、证据、修复、验证。

**面试怎么说**

> 最难的问题是 RAG 对政策编号查询漏召。最初我们以为是 Embedding 不够好，但 Trace 显示编号在 PDF 解析时被换行拆开，而且 Query Rewrite 还删除了短横线。我先修复字符归一化和 Chunk 结构，再保留原 Query 走 BM25，与 Dense 结果用 RRF 融合。编号类 Recall 明显提升，而自然语言切片没有下降。这个问题让我意识到不能看到漏召就直接换 Embedding，要沿解析、切分和检索逐层验证。

**坑**

- 困难只是“时间紧、需求多”；
- 一上来换模型，没有定位证据；
- 解决方案与问题不对应；
- 没有回归，修好一个样例就结束。

## 5. 项目效果如何评估？

> 面试优先级：★★★★★｜学习难度：★★★★☆｜适用岗位：全部  
> 掌握要求：能给 Baseline、分层指标和业务结果

**一句话**：项目效果应至少分为业务或任务结果、组件质量和系统指标三层，并与 Baseline 对照。只报一个准确率无法说明用户价值，也无法定位提升来源。

“看起来回答不错”不能证明项目有效，也无法支持版本迭代。必须先定义业务目标，再拆成组件质量、端到端任务成功率、延迟、成本和安全指标，并说明测试集、Baseline 与实验条件。

分三层看指标：

- **组件指标**：Recall@K、工具参数、OCR、格式；
- **端到端指标**：答案正确、任务成功、引用、拒答；
- **业务/系统指标**：解决率、人工转接、P95/P99、成本、用户反馈。

Baseline 与消融要固定数据和模型，每次只改一个组件，并报告提升与延迟/成本代价：

```text
Baseline：Dense Top-K + 基础Prompt
实验A：+ BM25/RRF
实验B：+ Reranker
实验C：+ Parent-Child
```

**面试怎么说**

> 我先建立最简单 Baseline，再把解析、检索、生成和系统分层评测。每个改动做消融，既看质量也看延迟和 Token。线上则关注真实任务完成、人工转接和投诉等业务指标。没有指标时我会如实说明当时只做了哪些测试，并指出现在会如何补齐，而不是编造数字。

## 6. 项目规模、延迟、成本和容量怎么回答？

> 面试优先级：★★★★★｜学习难度：★★★★☆｜适用岗位：全部工程岗位  
> 掌握要求：知道真实数量级或明确没测

**一句话**：这些数字用于说明系统在什么条件下运行，而不是越大越好。要同时说测量环境和请求分布（模型、硬件、输入输出长度和并发），否则单独一个 QPS 或延迟没有可比意义。

面试官问规模是在判断架构是否与负载匹配。应把数据量、QPS、输入输出长度、并发、P95/P99、单次成本和资源上限连起来，并明确哪些是实测、哪些只是估算。

需要准备的数字：文档/页/Chunk/向量数量、每日新增和更新、QPS/并发/峰值、输入输出 Token 分布、各阶段延迟、P50/P95/P99、模型和 Embedding 调用成本、缓存命中、错误/超时/取消率。

没有生产流量时说清实验条件：

> 这是个人项目，没有真实 QPS。我用 1、5、10、20 并发做了阶梯压测，固定输入和输出长度，测了 E2E 与错误率。它不能替代生产数据，但至少给出了当前机器下的容量基线。

**面试怎么说**

> 我会先说明数据规模和增量，再给出固定硬件、模型和输入输出分布下的 P50、P95、P99、吞吐与错误率，并把检索、排队和模型耗时拆开。成本按调用 Token、Embedding 和基础设施估算。如果项目没有生产流量，我会明确这是实验压测结果，不把它包装成真实业务 QPS。

## 7. 项目没有上线或没有用户，怎么回答？

> 面试优先级：★★★★☆｜学习难度：★★☆☆☆｜适用岗位：实习、校招  
> 掌握要求：诚实说明证据和不足

**一句话**：没有正式用户并不意味着没有证据。应诚实说明项目阶段，用离线测试、组件消融、压力测试和失败用例证明工程质量，同时明确这些结果不能替代真实线上分布。

未上线不等于没有技术价值，但不能把离线实验说成生产结果。

**面试官真正想确认什么**：一是你是否诚实区分原型、测试环境和生产系统；二是没有真实流量时你是否仍建立了可验证的工程证据；三是你是否理解从 Demo 到生产还缺哪些环节。

**用什么证据替代空泛描述**：个人项目没有业务用户很正常，但不能只展示一条成功链路，至少准备——

- 一组分类型离线测试集，以及每类的结果；
- 检索、重排、Prompt 等组件的对照或消融；
- 固定环境下的并发、延迟、错误率与资源占用；
- 无答案、权限、超时、重复请求等失败用例；
- 当前限制和计划补充的生产能力。

这些数据只能证明“在给定实验条件下的表现”，不能包装成真实业务收益。

**面试怎么说**

> 项目目前是验证型原型，没有正式用户，这是事实。为了避免只做演示，我建立了包含正常、无答案、权限和 OCR 的测试集，并做了组件消融和压力测试。它仍缺少真实用户分布、长期运行和合规验证，所以我不会把离线结果说成业务收益；如果上线，我会先内测、灰度并补用户反馈与安全审计。

**常见追问**

- **离线集是谁标的？** 说明题目来源、标注规则、复核方式和局限。
- **压测数据能代表生产吗？** 不能完全代表，只是当前软硬件和请求分布下的容量基线。
- **上线第一步是什么？** 先做小范围内部用户试用，同时启用日志、反馈、权限和回滚。

**坑**

- 伪造用户量、QPS 或收益；
- 只说“项目还没来得及上线”，没有任何替代证据；
- 把离线准确率直接等同于线上满意度；
- 只谈功能，不知道生产还需要监控、安全、容量和运维。

诚实不会自动扣分，缺少验证意识或伪造证据才更危险。

## 8. 如果重新设计一次，你会改什么？

> 面试优先级：★★★★☆｜学习难度：★★★☆☆｜适用岗位：全部  
> 掌握要求：从真实限制推导改进，不全盘否定

**一句话**：这道题考察复盘能力，不是要求否定旧方案。更好的回答是保留已被数据证明有效的部分，只针对当前瓶颈提出下一步改动，并说明新方案会带来什么代价。

好的回答按五步走：保留哪些已验证设计、哪个瓶颈有证据、改动方案、预期收益与风险、如何验证。

**面试怎么说**

> 我会保留混合召回和证据 ID，因为评测证明有效。主要重构文档入库：当前解析和索引耦合，失败后要从头重跑。我会改成有状态任务和幂等步骤，并把表格路由到结构化查询。风险是链路更复杂，所以先以表格问题切片做 A/B，不会直接全量替换。

**坑**：不要回答“全部推倒重来”，也不要只罗列热门技术。先说“保留什么”，证明不是为炫技重构。

# 第二部分：系统设计通用框架

## 9. 开放系统设计题怎样回答？

> 面试优先级：★★★★★｜学习难度：★★★★★｜适用岗位：全部  
> 掌握要求：20～30分钟内形成结构化方案

### 先理解

开放题信息不完整且没有唯一架构，立即堆模型、队列和数据库往往会偏题。先澄清用户、规模、质量、延迟、安全和成本，再给主链路与关键数据状态，才能让后续选型和取舍有依据。

### 原理与应用

**九步法**

1. 明确用户、核心任务和不做什么；
2. 确认数据规模、并发、延迟、成本、更新和合规；
3. 定义 API 输入输出和成功标准；
4. 给出端到端主链路；
5. 深入核心数据模型和组件；
6. 解释选型与替代方案；
7. 设计异常、幂等、一致性和降级；
8. 设计安全、权限和审计；
9. 给出评测、压测、灰度和演进。

**先画小图**，用边界表达职责，再只深入题目核心，不要把所有技术都塞进去：

```text
Client
  ↓
Gateway/Auth
  ↓
Application/Agent Orchestrator
  ├─ RAG Service
  ├─ Tool Service
  ├─ Model Gateway
  └─ State/DB/Redis/Queue
  ↓
Streaming Response + Observability
```

### 面试准备

**推荐回答**

> 系统设计题没有唯一标准架构，关键是先澄清规模、质量、延迟、安全和成本约束，再给出主链路、数据状态、异常治理、评测和演进，而不是立即堆技术名词。

# 第三部分：高频系统场景题

> **本部分共通检查**：以下要求对本部分所有系统设计题通用，各题只写专属内容，不再重复。
> 澄清——先问清楚目标用户、核心任务与成功标准，数据规模、并发、延迟、成本、更新与合规约束，以及哪些模块由自己负责、哪些依赖团队或外部。
> 取舍——在质量、交付速度、维护复杂度、成本和风险之间做可解释选择；先给满足当前约束的最小架构，再说明规模或需求变化后的演进。
> 异常与安全——考虑依赖失败、数据不一致、越权、重复副作用、模型幻觉、容量不足和回滚；关键状态、权限、幂等、审计与人工接管由服务端保证，而不是交给模型。
> 验证——定义业务/任务指标、组件指标和系统指标，说明数据集、Baseline、实验环境、切片和限制；没有真实流量时明确使用离线与压测证据，不包装成业务收益。
> 条件变化——规模扩大时拆分容量与异步链路；风险提高时加强权限和人工；成本收紧时分层路由；需求仍不确定时保留简单可回退方案。

## 场景 1：设计企业内部知识库问答系统

> 面试优先级：★★★★★｜学习难度：★★★★★｜适用岗位：RAG、Agent、应用后端  
> 掌握要求：能覆盖入库、问答、权限、评测和更新

**判断**：企业知识库的核心是把可靠文档处理、权限过滤、混合检索、证据引用和持续评测串成闭环。回答正确之外，还必须保证绝不召回未授权内容。

**先问清楚**（共通澄清之外）：文档类型（数字 PDF/扫描件/表格各占多少）、引用粒度（页码还是文字坐标）、部门权限与多租户隔离、高风险问题如何兜底。

**怎么设计**

离线入库：

```text
上传 → 安全扫描 → 解析/OCR → 结构切分
→ 元数据/ACL → BM25+向量索引 → 质量门禁 → 版本发布
```

在线问答：

```text
鉴权 → Query理解 → ACL过滤 → 混合召回 → RRF
→ Rerank → Context → LLM → 引用校验/拒答 → SSE
```

关键点：权限在检索前强制；文档状态机和版本原子切换；编号保留 BM25、语义用 Dense；无答案要拒答并给引用；缓存键包含租户与知识版本；评测分解析、召回、生成和系统四层；Trace 串起每一步。

**怎么说**

> 离线我会先做安全扫描、解析和 OCR，按标题和条款结构切分，写入页码、版本和 ACL，再同时建 BM25 和向量索引并设质量门禁做原子版本发布。在线先用服务端身份做 ACL 过滤，再混合召回、RRF 融合和 Rerank，把证据交给模型生成带引用的答案，检索不到就拒答。权限必须在检索前生效，缓存键要带租户和知识版本，每一步都有 Trace，评测拆成解析、召回、生成和系统四层。

**别踩 & 追问**

- 十亿向量：分片、预过滤、IVF/PQ、冷热分层；
- 表格：路由到结构化查询工具，纯文本化会丢行列关系；
- 多跳关系：问题拆解或 GraphRAG；
- Embedding 升级：新索引、双写、影子、灰度，不能与旧向量混用。

## 场景 2：设计订单查询、退款和投诉 Agent

> 面试优先级：★★★★★｜学习难度：★★★★★｜适用岗位：Agent、后端  
> 掌握要求：能区分只读、写操作、确认和补偿

**判断**：此类 Agent 同时包含只读查询和有副作用写操作。设计重点是让模型负责理解与编排，服务端负责权限、确认、幂等、状态核验和审计。

**怎么设计**

工具按副作用分类：

```text
query_order(order_id)          只读
check_refund_policy(order_id)  只读
create_refund(order_id, reason, idempotency_key) 写操作
create_ticket(...)             写操作
```

主流程：

```text
用户请求
→ 身份与订单归属
→ 意图/槽位
→ 只读查询
→ 规则判断资格
→ 展示金额与影响
→ 用户确认
→ 幂等执行
→ 查询最终状态
→ 返回凭证
```

**怎么说**

> 我会把工具按副作用分成只读的查询、政策校验和有副作用的创建退款、创建工单。流程是先核验身份和订单归属，再抽意图和槽位，用只读查询确认资格和金额影响，展示给用户确认后用幂等 key 执行写操作，最后回查最终状态返回凭证。模型只负责理解和编排，退款资格和金额上限由规则引擎和业务系统裁定。

**别踩 & 追问**

- 安全红线：模型不决定退款资格和金额上限，规则引擎和业务系统才是权威；超时后先查状态不盲重试；Prompt Injection 绕不过服务端权限。
- 专属评测：任务成功率、错误退款、重复副作用、参数正确率、澄清轮数、人工转接、延迟、Token 和投诉。

## 场景 3：设计多租户 RAG 平台

> 面试优先级：★★★★★｜学习难度：★★★★★｜适用岗位：RAG平台、SaaS  
> 掌握要求：能设计租户边界和容量隔离

**判断**：多租户平台是在一套基础设施上服务多个组织。设计重点不仅是给数据加 `tenant_id`，还要保证一个租户的文档、缓存、日志和资源峰值不会泄露或拖垮其他租户。

**怎么设计**

按隔离层逐一设计：

- 身份：Token 映射服务器端租户；
- 数据：对象存储、数据库、索引的租户/ACL；
- 检索：预过滤或物理 Collection；
- 缓存：租户、权限版本和模型配置进入 Key；
- 计算：配额、并发、Token 和速率限制；
- 观测：租户级成本、错误和审计；
- 删除：租户销毁后的全链路清理。

高安全租户可用独立索引/密钥/实例；普通租户共享基础设施但逻辑强制过滤。选择取决于合规、规模和成本。

**怎么说**

> 身份由服务端 Token 映射到租户，文档入库绑定租户与 ACL，检索在索引层预过滤；高安全租户使用独立 Collection、密钥甚至实例。缓存键、日志和引用同样携带权限上下文，计算侧按租户限制并发、Token 和费用。最后补充审计、权限变更失效和租户销毁后的全链路删除。

**别踩 & 追问**：权限变更后要让缓存和会话及时失效；租户销毁要全链路删除对象存储、索引、缓存和日志，否则会残留跨租户数据。

## 场景 4：设计模型网关，支持多个模型厂商

> 面试优先级：★★★★☆｜学习难度：★★★★★｜适用岗位：AI平台、应用后端  
> 掌握要求：能抽象统一协议并处理差异

**判断**：模型网关位于业务应用和多个模型供应商之间。它向上提供统一调用方式，向下吸收各厂商在鉴权、错误码、流式输出、工具调用和计费上的差异，同时集中治理配额和观测。

**怎么设计**

网关职责：

- 统一 Chat/Embedding/Rerank 接口；
- 鉴权、租户配额和成本；
- 模型能力、上下文、工具和多模态路由；
- 超时、重试、熔断和区域切换；
- 流式协议统一；
- Prompt/Template/版本管理；
- 日志脱敏与 Trace；
- 质量、延迟和成本路由。

**怎么说**

> 网关统一 Chat、Embedding 和 Rerank 协议，并负责鉴权、配额、成本、超时、重试、熔断和 Trace。模型路由根据能力、上下文、地区、质量和成本决定。统一接口不能掩盖真实差异：工具 Schema、流式 Delta 和安全策略需要适配层，备用模型也要经过兼容回归；Embedding 切换则必须重建对应索引。

**别踩 & 追问**

- 不同厂商 Tool Schema、错误码和流式 Delta 不同，需要适配层；
- 备用模型可能质量和格式不同，切换前要兼容回归；
- Embedding 模型切换不能混用旧向量，必须重建索引；
- 流式中途失败不适合无痕拼接另一个模型；
- Provider 缓存和计费规则不同。

## 场景 5：设计大模型评测平台

> 面试优先级：★★★★☆｜学习难度：★★★★★｜适用岗位：评测、平台  
> 掌握要求：能管理数据、运行、裁判、版本和报告

**判断**：评测平台的核心不是批量调用模型，而是让每次结果可复现、可比较、可追溯。任何模型、Prompt、索引、代码和数据版本变化都要进入 Run 配置，否则分数变化无法归因。

**怎么设计**

数据模型：

```text
Dataset → Case → Run → Trace/Output → EvaluatorResult → Report
```

每次 Run 固定模型、Prompt、RAG 索引、参数、代码和数据版本。Evaluator 包含规则、检索指标、LLM Judge 和人工结果。平台能力：批量并发执行和限流、可重试但保持 Case 幂等、Judge 校准和 Prompt 版本、按标签切片/Pairwise/置信区间、Baseline 与实验差异、CI 门禁/灰度回流/Bad Case 管理、敏感数据权限与脱敏。

**怎么说**

> 我会用 Dataset、Case、Run、Output/Trace、EvaluatorResult 和 Report 组织数据，每次 Run 固定模型、Prompt、索引、参数与代码版本。执行层支持并发、限流、幂等重试；评估层组合规则、检索指标、Judge 和人工，并做 Judge 校准、切片和置信区间。结果可与 Baseline 比较，并接入 CI 门禁和线上 Bad Case 回流。

**别踩 & 追问**：分数变化必须能归因，任何模型/Prompt/索引/代码/数据版本变化都要进 Run 配置；Judge 要先校准并固定 Prompt 版本，否则评测本身就不可信。

## 场景 6：设计长文档总结系统

> 面试优先级：★★★★☆｜学习难度：★★★★☆｜适用岗位：应用、RAG  
> 掌握要求：能避免简单截断和逐块摘要失真

**判断**：长文档不能简单截断，逐块总结后直接拼接也会重复和丢失全局关系。更可靠的方法是先恢复文档结构，再分层生成局部摘要和全局摘要，并让关键事实回到原文核验。

**怎么设计**

1. 解析章节、标题、表格和图；
2. 根据目标定义摘要类型：执行摘要、章节摘要、问答式；
3. Map：按结构块生成带证据 ID 的局部摘要；
4. Reduce：按层级合并，去重并保留关键数字；
5. 关键事实由规则或第二遍核验原文；
6. 超长文档异步任务、进度和断点；
7. 输出引用章节和页码；
8. 评测事实一致、覆盖、压缩率、结构和人工偏好。

**怎么说**

> 我会先解析章节、表格和图，并根据用户需要确定摘要类型。按结构块执行 Map，生成带证据 ID 的局部摘要，再按章节层级 Reduce、去重和整合。金额、日期、否定和最终结论回查原文，输出保留页码引用。超长任务异步执行并可断点恢复，评测事实一致性、覆盖、结构、压缩率和人工偏好。

**别踩 & 追问**：局部摘要错误会层层放大，关键数字、结论和否定必须回查原文，不能只基于上一层摘要继续压缩。

## 场景 7：设计合同审核系统

> 面试优先级：★★★★☆｜学习难度：★★★★★｜适用岗位：文档智能、企业 Agent  
> 掌握要求：能结合 OCR、规则、RAG、VLM 和人工

**判断**：合同审核不是让 LLM 自由判断“有没有法律风险”，而是把文档解析、字段校验、规则匹配、证据引用和人工确认串成受控流程。LLM 更适合解释和生成修改建议，不应成为唯一裁判。

**怎么设计**

```text
上传与病毒扫描
→ OCR/版面/章条款恢复
→ 合同实体和条款抽取
→ 与标准模板/法规/规则库匹配
→ 风险分类与证据引用
→ LLM生成解释和修改建议
→ 人工审核
→ 审计与版本
```

金额、日期、主体和否定条件用规则/结构化抽取校验；LLM 负责解释和候选建议，不自动做法律结论。每个风险必须引用原条款和规则来源，低置信度进入人工。

**怎么说**

> 上传后先做安全检查和 OCR/版面恢复，抽取合同主体、日期、金额和条款结构，再与模板、法规和规则库匹配。确定性字段由规则校验，LLM 根据原条款和规则来源解释风险并给出修改建议。每个结论必须可引用，低置信度和高风险项进入人工审核，所有版本、意见和操作进入审计日志。

**别踩 & 追问**：确定性字段（金额、日期、主体、否定条件）必须用规则校验，LLM 只做解释和候选建议不做终判；每个风险都要能引用到原条款和规则来源，否则无法追责。

## 场景 8：设计高并发大模型服务

> 面试优先级：推理岗★★★★★；应用岗★★★☆☆｜学习难度：★★★★★｜适用岗位：AI Infra、平台  
> 掌握要求：能连接网关、调度、KV、扩容与SLO

**判断**：高并发模型服务的核心是在有限 GPU 和 KV Cache 下平衡吞吐、首 Token 延迟、生成速度和公平性，需要同时设计网关、排队、调度、缓存、容量和降级。

**怎么设计**

```text
Gateway/Auth/Quota
→ Model Router
→ Priority/Length Queues
→ vLLM/SGLang Replicas
→ GPU Metrics + Scheduler
→ SSE
```

关键设计：按模型/上下文/LoRA/工作负载路由；Continuous Batching、Paged KV、Chunked Prefill；长短、在线离线任务隔离；队列背压和 admission control；Prefix Cache 粘性路由；按队列、KV、TTFT 和 P99 扩容；模型预热、健康检查和优雅下线；灰度、回滚和容量压测。

**怎么说**

> 我会在网关做鉴权、配额和模型路由，用优先级和长度队列把长短、在线离线任务隔离，后端用 vLLM/SGLang 多副本配合 Continuous Batching、Paged KV 和 Chunked Prefill。通过队列背压和 admission control 控制过载，用 Prefix Cache 做粘性路由，按队列长度、KV 占用、TTFT 和 P99 扩容，并保证预热、健康检查、优雅下线和灰度回滚。

**别踩 & 追问**：不能只堆副本，先分清瓶颈在 KV 显存、调度还是通信；长短请求必须隔离，否则长 Prefill 会阻塞短请求；扩容按 TTFT/P99 和 KV 占用触发，而不是只看 GPU 利用率。

# 第四部分：完整项目追问演练

## 企业知识库 Agent 追问链

### 问：为什么不用微调？

> 公司制度频繁更新且需要引用，RAG 更适合知识更新；如果后续要让模型稳定遵循回答格式和工具协议，可以在 RAG 基础上做小规模 SFT，而不是把制度事实硬记入参数。

### 问：为什么混合检索？

> 领域问题既有“报销超过200元”这样的语义改写，也有“ERR-1042”和产品型号。Dense 负责语义，BM25 负责精确词项，RRF 避免直接相加不同尺度分数。

### 问：怎么证明 Reranker 有用？

> 固定候选和生成模型，比较无 Rerank 与有 Rerank 的 MRR、Context Gold Coverage、最终准确率和 P95；若质量提升小于延迟代价，就减少候选或使用更小 Reranker。

### 问：权限怎么做？

> 用户身份由服务端解析，Chunk 入库带 ACL，检索阶段强制过滤；缓存键含租户和权限版本，最终引用再校验。不能先把越权文档交给模型再要求它不要回答。

### 问：最大的不足？

> 当前对结构化表格和跨文档多跳支持不足。纯文本化表格会丢行列关系，下一步会把大表路由到结构化查询工具，并用表格问题切片验证，而不是简单增加 Top-K。

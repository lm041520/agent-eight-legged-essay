## 1. 线程、进程和协程如何选择？GIL 是什么？

> 面试优先级：★★★★★｜学习难度：★★★★☆｜适用岗位：所有 Python 大模型应用岗  
> 掌握要求：能按 CPU/IO、隔离和共享状态选择

### 先理解

线程共享进程内存，适合阻塞 I/O；进程拥有独立内存，可绕开 GIL 利用多核 CPU；协程在单线程中协作切换，适合大量非阻塞 I/O。选择取决于瓶颈和隔离要求。

三者都能提升并发，但适合的瓶颈不同：线程和协程主要覆盖 I/O 等待，进程能利用多核执行 CPU 密集任务。GIL 限制同一 CPython 进程内多个线程同时执行 Python 字节码，因此“开更多线程”不等于 CPU 计算会线性加速。

### 原理与应用

#### 线程

同一进程内共享内存，创建和切换相对轻，适合阻塞 IO 或调用会释放 GIL 的原生库。共享状态需要锁，容易出现竞态和死锁。

#### 进程

有独立地址空间，隔离强，可利用多核做 CPU 密集 Python 计算；但启动、内存和进程间通信成本更高。

#### 协程

同一线程中由事件循环调度，任务在 `await` IO 时主动让出执行权。适合大量网络、数据库和模型 API 等 IO 并发；不适合直接执行长时间 CPU 阻塞代码。

#### GIL

传统 CPython 中，全局解释器锁使同一进程内通常只有一个线程执行 Python 字节码。它不意味着线程完全没用：网络 IO 等待时会释放执行权，很多 C/CUDA 算子也在 Python 外执行。新版本的 Free-threaded 构建是另一运行模式，不能假设所有环境都默认无 GIL。

#### 选型

```text
大量HTTP/数据库IO → asyncio
已有阻塞IO库 → 线程池或换异步客户端
纯Python CPU密集 → 多进程/原生扩展
GPU矩阵计算 → 主要由CUDA Kernel执行，Python负责调度
强隔离任务 → 进程/容器
```

### 面试准备

**推荐回答**

> 线程共享内存、适合阻塞 IO，但传统 CPython 受 GIL 限制纯 Python CPU 并行；进程隔离强并能利用多核，代价是内存和 IPC；协程由事件循环在 await 处切换，适合大量 IO 并发，但 CPU 阻塞会卡住整个事件循环。我会先按任务是 CPU 密集还是 IO 密集，再考虑库是否异步、共享状态和隔离要求。

## 2. `async/await`、事件循环和阻塞是怎么回事？

> 面试优先级：★★★★★｜学习难度：★★★★☆｜适用岗位：应用后端、Agent  
> 掌握要求：能解释 await 不是自动多线程

### 先理解

事件循环负责调度协程，但协程只有执行到能够让出控制权的 `await` 时，其他任务才有机会运行。如果协程内部直接执行阻塞 I/O 或长时间 CPU 计算，整个事件循环仍会被卡住，因此写成 `async def` 并不自动获得并发。

**为什么写了 async 仍可能阻塞**

```python
async def bad():
    time.sleep(5)          # 阻塞事件循环
    requests.get(url)     # 同步网络库
    heavy_python_loop()   # CPU密集
```

应使用异步客户端、`asyncio.sleep`，或将不可替换的阻塞函数放入线程/进程执行器。

### 原理与应用

#### 核心模型

调用 `async def` 返回协程对象，不会自动运行；事件循环调度 Task。当 Task 遇到真正异步的 `await`，底层注册 IO 完成通知并让出线程，循环运行其他 Task。

#### 并发不等于无限创建 Task

下游有连接池、限流和容量。需要 Semaphore、队列和背压：

```python
sem = asyncio.Semaphore(20)

async def limited_call(item):
    async with sem:
        return await call_api(item)
```

### 面试准备

**推荐回答**

> `async/await` 是协作式并发，不会自动开线程。协程被包装成 Task 后由事件循环调度，在真正异步 IO 的 await 处挂起并让其他 Task 运行。如果在协程中调用 time.sleep、同步 HTTP 或 CPU 重计算，仍会阻塞整个循环。工程上还要限制并发和建立背压，因为下游连接池和模型 API 容量有限。

## 3. `gather`、`TaskGroup`、超时与取消如何设计？

> 面试优先级：★★★★☆｜学习难度：★★★★☆｜适用岗位：Agent、后端  
> 掌握要求：能说明结构化并发和清理

### 先理解

并发启动多个协程不难，真正需要设计的是：一个失败时其他任务怎么办、是否允许部分成功、父请求超时后怎样取消和释放资源。`gather` 与 `TaskGroup` 的主要区别就在这些生命周期语义上。

并发启动多个协程只是第一步，还必须定义一个失败时其他任务是否继续、超时作用于单任务还是整体，以及取消如何向下传播。`gather` 适合收集结果，`TaskGroup` 更强调结构化并发；错误语义没设计清楚，会出现任务泄漏或部分结果被误当成功。

### 原理与应用

#### `gather`

适合并发等待一组协程并按输入顺序收集结果。`return_exceptions=True` 可把异常作为结果，但容易误吞错误，需要显式分类。

#### `TaskGroup`

结构化并发：任务生命周期受代码块管理；一个任务异常时通常会取消同组其他任务，退出时等待清理并聚合异常。适合“这些子任务属于同一父任务”的语义。

#### 超时和取消

取消不是强制杀死任意代码。协程要在 await 点响应取消，并在 `finally`/上下文管理器中释放连接、锁和临时资源。第三方副作用操作超时后还要查询状态，不能认为取消等于外部操作没执行。

### 面试准备

**推荐回答**

> `gather` 适合并发收集一组结果，是否允许部分成功需要明确；`TaskGroup` 提供结构化并发，让子任务随父作用域统一完成或取消。超时会触发取消，但外部请求可能已经执行，所以协程要正确清理资源，副作用操作还需幂等和状态确认。并发语义应根据“全部成功还是允许部分成功”设计。

## 4. SSE、WebSocket 和普通 HTTP 如何选择？

> 面试优先级：★★★★★｜学习难度：★★★☆☆｜适用岗位：大模型应用开发  
> 掌握要求：能解释单向流、双向通信和代理缓冲

### 先理解

三种方式的通信方向和连接生命周期不同。普通 HTTP 适合一次请求一次响应，SSE 适合服务器持续向浏览器推送 Token，WebSocket 适合频繁双向消息；聊天流式输出通常不需要为双向能力承担 WebSocket 的额外复杂度。

### 原理与应用

#### 普通 HTTP

一次请求等待完整响应，适合短任务和非流式 API。

#### SSE

基于 HTTP 的服务器到客户端单向事件流，文本格式简单，浏览器原生支持，适合 LLM Token 流式输出。客户端到服务端仍通过普通请求。

```text
data: {"delta":"你"}\n\n
data: {"delta":"好"}\n\n
data: [DONE]\n\n
```

#### WebSocket

建立全双工长连接，适合实时协作、语音流、游戏或客户端也要持续发送事件的场景，连接治理和扩容更复杂。

#### SSE 常见坑

- 代理/CDN 缓冲，后端流式但前端一次收到；
- 服务端生成器中执行同步阻塞；
- 客户端断开后未取消模型生成；
- 心跳、重连和事件 ID 缺失；
- 错误没有结构化事件。

### 面试准备

**推荐回答**

> LLM 文本流通常使用 SSE，因为主要是服务端向客户端单向推送，基于 HTTP、实现和代理兼容较简单；需要持续双向低延迟通信时用 WebSocket。SSE 落地还要关闭代理缓冲、检测断开、传递取消，并设计正常结束和错误事件，不能只返回一个 StreamingResponse 就结束。

## 5. SQLAlchemy Session、事务、连接和连接池是什么关系？

> 面试优先级：★★★★★｜学习难度：★★★★☆｜适用岗位：AI 后端、应用开发  
> 掌握要求：能说明 Session 不是连接且 AsyncSession 不跨 Task 共享

### 先理解

Session 是一次工作单元，负责跟踪对象和组织数据库操作；事务决定这些操作怎样提交或回滚；Session 执行 SQL 时从连接池借用底层连接，结束后再归还。

业务代码需要一个工作单元跟踪对象变化和事务边界，但真正发送 SQL 仍依赖底层数据库连接。Session 会在需要时从连接池借用连接，提交或回滚后再归还，因此 Session、事务和连接不能视为同一个对象。

**Session 为什么不等于连接**

Session 可以在真正执行 SQL 时才从池中借连接，事务结束后归还；它还维护 Identity Map、对象状态和 Flush 规则，这些都不是连接本身的职责。

```text
请求创建Session
→ 执行SQL时从Pool借Connection
→ 开启/加入Transaction
→ commit或rollback
→ Connection归还Pool
→ Session关闭
```

### 原理与应用

#### 四个对象

- **Session/AsyncSession**：有状态的工作单元，跟踪 ORM 对象、Flush、查询和事务边界；
- **Transaction**：一组要么全部提交、要么回滚的数据库操作；
- **Connection**：应用与数据库之间的底层通信通道；
- **Connection Pool**：提前维护一组连接，按需借出并归还。

#### 生命周期

```text
一个请求/事务 → 一个Session
并发子任务各自有数据库事务 → 各自Session
```

单个 AsyncSession 是有状态对象，不应被多个并发 Task 共享。

### 面试准备

**推荐回答**

> Session 是 ORM 工作单元和事务上下文，不是底层连接。它跟踪对象和变更，执行 SQL 时从连接池借出 Connection，事务提交或回滚后连接归还。Web 服务通常一个请求或一个业务事务一个 Session；AsyncSession 不应在多个并发 Task 间共享，否则事务和对象状态会相互干扰。

## 6. 为什么需要数据库连接池？关键参数是什么？

> 面试优先级：★★★★★｜学习难度：★★★☆☆｜适用岗位：后端、平台  
> 掌握要求：能做容量乘法并解释等待

### 先理解

建立数据库连接需要网络握手、认证并占用数据库资源，不能每次请求都新建。连接池复用有限连接并提供等待与背压，但总容量必须结合服务实例数和数据库上限设计。

每次请求都重新建立数据库连接，需要 TCP、TLS、认证和数据库资源分配，延迟高且数据库能承受的连接数有限。连接池复用已建立的连接，并用容量和超时限制并发访问。

### 原理与应用

#### 参数

- `pool_size`：常驻连接数；
- `max_overflow`：短时额外连接；
- `pool_timeout`：等待连接最大时间；
- `pool_recycle`：连接生命周期；
- `pool_pre_ping`：借出前检查失效连接。

#### 容量

```text
总潜在连接
= 服务实例数 × 每实例(pool_size + max_overflow)
+ 其他服务/管理连接
```

必须低于数据库安全容量。池过大不会让数据库自动变快，可能增加锁竞争、上下文切换和内存。

### 面试准备

**推荐回答**

> 连接池用来复用昂贵的数据库连接并给数据库并发设置上限。关键不是单实例 pool_size，而是实例数乘以每实例最大连接，再加其他服务。池太小会排队超时，太大可能压垮数据库。事务应尽量短，commit/rollback 后及时归还，监控池使用率、等待时间、SQL延迟和数据库连接数。

## 7. 事务 ACID、隔离级别和索引需要掌握什么？

> 面试优先级：★★★★☆｜学习难度：★★★★☆｜适用岗位：后端、平台  
> 掌握要求：能联系 RAG/Agent 数据一致性

### 先理解

事务负责把一组数据库操作变成可靠的状态变化，隔离级别规定并发事务能看到什么，索引则用额外空间和写入成本换取查询速度。三者共同决定后端系统是否既正确又能在并发下运行。

多个请求同时读写数据库时，单条 SQL 正确并不代表整个业务操作一致；索引也会影响查询是否能在可接受时间内完成。事务负责一组操作的原子性与并发可见性，索引负责减少查找数据的成本。

**RAG 例子**

文档状态、Chunk 记录和异步任务不能简单依赖一个跨向量库的数据库事务。通常使用本地事务 + Outbox/消息 + 幂等消费者实现最终一致，并通过状态机暴露 `processing/ready/failed`。

### 原理与应用

#### ACID

- Atomicity：事务内要么都成功，要么回滚；
- Consistency：业务约束从一个合法状态到另一个合法状态；
- Isolation：并发事务的中间状态按隔离规则不可见；
- Durability：提交结果持久保存。

#### 常见并发现象

脏读、不可重复读、幻读、丢失更新。具体隔离行为依数据库实现和 MVCC/锁机制。

#### 索引

B+树适合范围和排序；哈希适合精确匹配但能力受实现限制；联合索引要考虑最左前缀和选择性。索引提高读但增加写入、空间和维护成本。

### 面试准备

**推荐回答**

> ACID 保证事务内操作原子提交并持久化，隔离级别控制并发可见性，但级别越强通常并发代价越高。索引应根据查询条件、排序和选择性设计，不能越多越好。RAG 文档入库还会跨数据库、对象存储和向量库，无法依赖单个事务一次提交，通常通过状态机、Outbox、幂等消费和补偿实现最终一致。

## 8. SETNX、Redis 分布式锁和 Lua 解锁是什么？

> 面试优先级：★★★★★｜学习难度：★★★★☆｜适用岗位：后端、Agent工程  
> 掌握要求：能写安全加锁/解锁逻辑

### 先理解

SETNX 表示 Key 不存在时才写入，可用于竞争锁；可靠用法还必须同时设置 TTL 和唯一 Token。释放锁时用 Lua 原子比较 Token 后删除，避免误删别人的锁。

多个进程可能同时执行同一任务，本地线程锁无法跨进程协调。Redis 锁利用原子写入争夺所有权，但还必须设置过期时间并校验随机 Token，否则旧持有者可能误删新持有者的锁。

**为什么 value 要随机 Token**

锁过期后其他客户端可能获得新锁。旧客户端恢复时不能直接 `DEL`，否则会删掉别人的锁。

### 原理与应用

#### SETNX

`SETNX key value` 表示 Key 不存在时设置，成功返回 1，已存在返回 0。单独 SETNX 后再 EXPIRE 有崩溃窗口：锁可能设置成功但没有过期。

应使用原子命令：

```text
SET lock_key random_token NX PX 30000
```

#### Lua 比较后删除

```lua
if redis.call('get', KEYS[1]) == ARGV[1] then
    return redis.call('del', KEYS[1])
else
    return 0
end
```

- `KEYS[1]`：锁 Key；
- `ARGV[1]`：当前客户端随机 Token；
- `redis.call`：在 Redis 服务端执行命令；
- 整个脚本原子执行，避免 GET 后锁被替换、再 DEL 的竞态。

#### 锁的边界

Redis 锁不是数据库事务。锁过期、网络分区、进程暂停仍可能造成并发执行。关键写入还需数据库唯一约束、版本号、幂等键或 Fencing Token。

### 面试准备

**推荐回答**

> SETNX 可以做“只有不存在才写入”，但加锁和设置过期必须用一条 SET NX PX 原子命令。锁值使用唯一 Token，释放时在 Lua 中比较 Token 相等后再删除，避免旧持有者删掉新锁。对于长任务还要考虑续租和进程暂停；关键业务不能只信任 Redis 锁，还要用数据库约束或 Fencing Token 防止过期持有者继续写。

## 9. 缓存穿透、击穿、雪崩和一致性是什么？

> 面试优先级：★★★★☆｜学习难度：★★★★☆｜适用岗位：后端、平台  
> 掌握要求：能结合 LLM/RAG 缓存安全上下文

### 先理解

缓存把常用结果放到更快的存储中，但缓存未命中、集中失效或旧数据未及时删除都会把压力和错误传回后端。穿透、击穿和雪崩描述的是不同失效形态，一致性描述的是缓存与真实数据怎样保持可接受的同步。

缓存能减轻数据库压力，却会引入几类不同故障：查不存在的数据会穿透，热点 Key 失效会击穿，大量 Key 同时失效会雪崩，更新顺序错误会读到旧值。它们现象相似但根因不同，因此空值缓存、互斥重建、随机过期和一致性策略不能混用。

### 原理与应用

#### 三类问题

- 穿透：查询不存在数据，每次都打数据库；可缓存空值、Bloom Filter、输入校验。
- 击穿：热点 Key 过期，大量请求同时回源；可互斥重建、逻辑过期、提前刷新。
- 雪崩：大量 Key 同时过期或缓存集群故障；可随机 TTL、多级缓存、限流降级。

#### 一致性

常见 Cache-Aside：读未命中查数据库并回填；写时先更新数据库，再删除缓存。仍存在并发窗口，需要按业务容忍度使用版本号、延迟双删、事件失效或短 TTL。

**LLM 缓存特殊风险**

缓存键必须包含模型、Prompt 版本、知识库版本、租户和权限上下文。相似问题的答案缓存还要考虑时效和条件差异。

### 面试准备

**推荐回答**

> 穿透是持续查询不存在数据，击穿是热点 Key 失效后并发回源，雪崩是大量 Key 或缓存服务同时失效。可以分别使用空值或 Bloom Filter、互斥重建和随机 TTL 或限流治理。更新通常采用 Cache-Aside，但仍有短暂不一致窗口。LLM 答案缓存还必须包含租户、权限、模型和知识库版本，避免返回过期或越权内容。

## 10. 重试、幂等、限流、熔断和降级有什么区别？

> 面试优先级：★★★★★｜学习难度：★★★★☆｜适用岗位：所有工程岗  
> 掌握要求：能按错误类型组合策略

### 先理解

重试处理暂时失败，幂等保证重复执行不产生额外副作用，限流控制进入系统的速度，熔断在依赖持续故障时暂停调用，降级则提供能力较弱但可用的替代路径。

它们分别处理临时失败、重复执行、流量过载、依赖持续故障和核心能力不可用。关键在于按错误类型组合：支付接口超时不能盲目重试，必须先有幂等键；下游已大量失败时继续重试只会放大压力，此时应熔断或降级。

### 原理与应用

#### 组合

```text
请求进入 → 限流
调用依赖 → 超时
临时错误 → 幂等前提下有限重试+退避
连续失败 → 熔断
不可用 → 缓存/备用模型/静态结果/转人工
```

### 面试准备

**推荐回答**

> 重试用于临时错误，但必须限制次数并使用指数退避；有副作用的操作只有具备幂等键才安全。限流在入口保护容量，熔断在依赖持续失败时快速失败，降级提供备用能力。它们不是互相替代，而是按请求生命周期组合，并通过错误码区分可重试、业务拒绝和永久失败。

## 11. Docker 和 Kubernetes 分别解决什么？

> 面试优先级：★★★★☆｜学习难度：★★★☆☆｜适用岗位：部署、应用后端  
> 掌握要求：能从镜像、容器、编排和扩缩容回答

### 先理解

Docker 把应用、依赖和启动方式封装成可重复运行的镜像与容器，Kubernetes 则管理许多容器实例的部署、扩缩容、服务发现和故障恢复。一个解决“单个应用如何一致运行”，另一个解决“集群里许多实例如何持续运行”。

### 原理与应用

#### Docker

将应用、运行时和依赖打包为镜像，在隔离进程中运行容器，解决环境一致性和交付。容器共享宿主内核，不等于虚拟机。

#### Kubernetes

在集群中编排容器：

- Pod：最小调度单元；
- Deployment：副本、滚动更新、自愈；
- Service：稳定访问入口；
- ConfigMap/Secret：配置与敏感信息；
- HPA：按指标扩缩容；
- Readiness/Liveness：接流量与重启判断。

#### GPU 服务注意

GPU 调度、驱动兼容、模型大文件、冷启动、共享存储、拓扑、健康检查和显存指标。LLM 扩容不能只看 CPU，通常要看排队、并发、KV 使用和 TTFT。

### 面试准备

**推荐回答**

> Docker 解决应用及依赖如何一致打包和运行，Kubernetes 解决多个容器在集群中如何调度、发现、自愈、扩缩容和滚动发布。大模型服务还要处理 GPU 资源、模型加载冷启动和显存容量，扩容信号不能只使用 CPU，通常结合队列长度、在途请求和延迟。

## 12. CI/CD 是什么，哪些步骤应该自动化？

> 面试优先级：★★★☆☆｜学习难度：★★★☆☆｜适用岗位：工程、平台  
> 掌握要求：能设计模型应用的质量门禁

### 先理解

CI 是每次代码变化后自动检查和构建，CD 是把通过检查的版本持续交付到测试或生产环境。它们不是“自动部署脚本”这么简单，而是把测试、安全检查、灰度和回滚组成可重复的发布流程。

代码频繁变化时，靠人工依次测试、构建和部署容易漏步骤且难以复现。CI 自动执行检查和构建，CD 把通过门禁的版本推进到环境；高风险生产发布仍可保留审批，但测试、扫描、镜像构建和部署验证应尽量自动化。

### 原理与应用

#### 流水线

```text
格式/类型/Lint
→ 单元测试
→ 集成测试
→ 安全与依赖扫描
→ 构建镜像
→ Agent/RAG小型回归集
→ 部署测试环境
→ 冒烟测试
→ 灰度
→ 监控门禁
→ 全量或回滚
```

大部分步骤可以自动进行，但生产全量、数据库破坏性迁移和高风险变更可保留人工审批。LLM 输出非确定，因此门禁应结合规则、统计阈值和人工抽样，不能要求每次文本完全一致。

### 面试准备

**推荐回答**

> 提交代码后，CI 自动运行格式、类型、单测、集成测试和依赖扫描，再构建不可变镜像；CD 将镜像部署到测试环境做冒烟和 Agent/RAG 回归，通过后灰度发布，并依据监控门禁全量或回滚。大部分步骤可以自动化，高风险迁移和生产全量可保留审批。LLM 评测应使用统计阈值和人工抽样，不能只比较输出字符串完全相等。

# 第二部分：高频场景题

> **本部分共通检查**：动手前先确认这几类约束——请求是 CPU 密集、I/O 密集、流式还是长时间后台任务；哪些操作有副作用、需要事务、幂等、锁或最终一致；并发、连接、内存、超时、可用性和部署环境的上限是多少。方案通常要在吞吐与资源上限、强一致与可用性、实时响应与异步处理、自动重试与重复副作用之间取舍，优先让状态和边界显式。异常面统一考虑超时、取消、连接池耗尽、重复消息、锁过期、依赖故障、进程重启和扩缩容，用上下文管理、幂等、状态机、队列、补偿和优雅下线治理。验证统一用单元/集成/故障注入和阶梯压测，看成功率、P95/P99、队列、连接池、内存、重试、重复副作用和恢复时间，并贯通 Trace。条件变化的通用调整：并发增加就重算连接与任务容量，写风险提高就加强事务、幂等和审计，任务变长就异步化，扩容就把关键状态移出本机。下面每题只写它专属的判断、澄清、分析和坑。

## 场景 1：文件上传成功，但向量化任务失败，状态如何设计？

> 面试优先级：★★★★★｜学习难度：★★★★☆｜适用岗位：RAG后端  
> 掌握要求：能设计状态机、重试与一致性

**判断**：上传成功只表示原文件已经保存，不代表知识库已经可检索。跨解析、切分和向量化的异步流程应使用显式状态机，记录每一步的结果、错误和可重试性。

**先问清楚**

- 是所有文档都失败，还是偶发失败、可重试？
- 失败发生在解析、切分还是向量化哪一步？
- 用户能接受“处理中”的异步状态，还是要求上传即可用？

**怎么办**

```text
uploaded → parsing → chunking → embedding → indexing → ready
             └──────────→ failed_retryable
             └──────────→ failed_terminal
```

- API 返回 `document_id` 和处理中状态，不假装立即可用；
- 原文件先可靠存对象存储；
- 数据库事务同时写文档记录和 Outbox 事件；
- 消费者按文档版本和步骤幂等；
- 每步记录错误码、重试次数和进度；
- 索引完成并通过校验后，才原子切到 `ready`；
- 失败可人工重放，不产生重复 Chunk；
- 前端轮询或事件通知状态。

**怎么说**

> 上传成功只代表原文件持久化，不代表知识库可检索。我会用显式状态机管理解析、切分、Embedding 和索引，数据库记录与 Outbox 在一个本地事务提交，再由幂等消费者执行。只有索引数量和版本校验通过后才切 ready；失败记录可重试性和错误码，支持断点和人工重放，避免半成品被查询。

**别踩 & 追问**：不要在向量化真正完成前就把文档标成 ready，否则会检索到半成品；失败态要区分可重试与终止，终止态直接重试只会反复失败。

## 场景 2：同一文件被重复上传，如何保证幂等？

> 面试优先级：★★★★☆｜学习难度：★★★★☆｜适用岗位：RAG后端  
> 掌握要求：能区分请求幂等、内容去重和版本更新

**判断**：幂等表示同一个业务请求执行多次，最终效果与执行一次相同。它与内容去重有关但不等价：同一个文件可能是重试，也可能是用户明确创建的新版本，必须结合租户、业务 ID 和版本规则判断。

**先问清楚**

- 重复上传是客户端重试，还是用户有意上传新版本？
- 判重看文件字节完全相同，还是按文件名或业务 ID？
- 同名不同内容应覆盖旧版本还是并存多版本？

**怎么办**

- 客户端或服务端生成 Idempotency Key 识别同一次请求；
- 计算内容 Hash 识别字节完全相同的文件；
- 数据库唯一约束兜底；
- 同租户同 Hash 可复用处理结果或返回已有任务；
- 文件名相同但内容不同视为新版本；
- 消费者以 `document_id + version + step` 幂等；
- 不能只用分布式锁，因为锁过期后仍可能重复。

**怎么说**

> 我会用 Idempotency Key 识别同一次上传请求，用内容 Hash 判断字节是否完全相同，并用数据库唯一约束兜底。同租户同 Hash 的重试可以返回已有任务，但同名不同内容应创建新版本。后续解析、切分和入向量库也以文档版本和步骤 ID 幂等，不能只依赖可能过期的分布式锁。

**别踩 & 追问**：不要把“重试”和“新版本”混为一谈——只按文件名判重会漏掉改动内容，只按内容 Hash 判重又会挡住用户的合法覆盖；锁只能防并发，不能替代幂等键和唯一约束。

## 场景 3：Embedding API 限流，如何重试和削峰？

> 面试优先级：★★★★★｜学习难度：★★★★☆｜适用岗位：RAG、平台  
> 掌握要求：能组合队列、批处理、限流和退避

**判断**：限流表示供应商只允许在一定时间内处理固定数量的请求或 Token。直接让所有上传请求同步重试会形成更大的流量尖峰，因此应先用队列把生产速度与 Embedding 消费速度解耦，再按配额稳定发送。

**先问清楚**

- 限流是按请求数还是按 Token 数，配额多少？
- 是初始化批量灌库，还是持续增量入库？
- 能接受异步延迟完成，还是要求上传即时可检索？

**怎么办**

- 上传链路异步化，用消息队列削峰；
- 按 API 的 Token/请求限制做客户端 Rate Limiter；
- 把相近长度的 Chunk 批量 Embedding；
- 429 或临时错误读取 Retry-After，指数退避加抖动；
- 设最大重试次数与死信队列；
- 按 Chunk ID 幂等写入去重；
- 多模型或多供应商降级时，注意向量空间不能混用；
- 监控队列堆积、配额和预计完成时间。

**怎么说**

> 我会把文档上传和 Embedding 异步解耦，用消息队列削峰，并在消费者侧按请求数和 Token 数限流。Chunk 按长度批处理，429 按 Retry-After 或指数退避加抖动重试，超过上限进入死信队列。每个 Chunk 写入幂等，监控队列积压与预计完成时间；切换供应商时不能把不同模型的向量混进同一索引。

**别踩 & 追问**：同步无退避地猛重试只会加剧限流；切换到别家 Embedding 模型时，新旧向量维度和语义空间不同，混进同一索引会让检索失效。

## 场景 4：Redis 锁过期，但任务还没完成，怎么办？

> 面试优先级：★★★★★｜学习难度：★★★★★｜适用岗位：后端、分布式任务  
> 掌握要求：能讨论续租、Fencing 与业务约束

**判断**：分布式锁只表示某段时间内谁被认为是持有者。锁过期后旧 Worker 不会被自动停止，它仍可能继续写数据，因此续租之外还需要让真正的数据写入能够识别并拒绝“旧持有者”。

**先问清楚**

- 任务最长执行多久，TTL 现在设了多少？
- 重复执行会造成什么副作用，是否已经幂等？
- 关键写入侧能否加版本号或唯一约束？

**怎么办**

- TTL 大于合理最大执行时间并留余量；
- 持有者定期续租，续租时校验 Token；
- 任务拆成小步骤并保存进度；
- 写入使用数据库唯一约束或版本 CAS；
- Fencing Token 单调递增，下游拒绝旧 Token 的写入；
- 操作本身幂等；
- 长时间的重任务可交由专用任务系统协调。

**怎么说**

> 续租只能降低过期概率，不能彻底消除进程暂停和网络分区。我会让锁值唯一、续租比较 Token，并在真正写入侧使用版本号、唯一约束或 Fencing Token 拒绝旧持有者，同时让任务幂等。Redis 锁不是业务正确性的唯一防线。

**别踩 & 追问**：真正的风险是锁过期后第二个 Worker 拿到锁、两个任务并发执行，且旧 Worker 失去锁后仍在写。只加长 TTL 治标不治本——必须让写入侧靠 Fencing Token 或版本号识别并拒绝旧持有者。

## 场景 5：数据库连接池耗尽，怎么排查？

> 面试优先级：★★★★★｜学习难度：★★★★☆｜适用岗位：后端  
> 掌握要求：能区分泄漏、慢事务和容量

**判断**：连接池耗尽表示当前所有可用数据库连接都被占用，新请求只能等待。原因可能是请求忘记归还连接，也可能是慢 SQL、锁等待或在事务中调用模型导致连接被长时间占住，不能一看到超时就只扩大池。

**先问清楚**

- 是偶发超时，还是持续耗尽？
- 是否在事务中调用了模型或外部 API？
- 每实例池大小、实例数和数据库最大连接各是多少？

**怎么排查**

- 看连接池 checked-out、等待时间、timeout 数；
- 看数据库活跃/空闲事务、慢 SQL、锁等待；
- 核对每实例池配置和实例数量；
- 检查 Session 是否在异常路径关闭；
- 检查是否在持有事务时调用慢模型或 API；
- 检查 AsyncSession 是否被跨 Task 共享；
- 看数据库 CPU/IO 和最大连接。

定位后先缩短事务、修复泄漏，再优化慢 SQL、索引和并发；必要时调整池，但必须先做数据库总容量计算。

**怎么说**

> 我会先看连接池 checked-out、等待时间和超时，再到数据库查看活跃事务、慢 SQL 与锁等待。重点检查 Session 是否在异常路径关闭，以及是否在持有事务时调用慢模型或外部 API。修复泄漏、缩短事务并优化查询后，再根据实例数计算总连接容量调整池；无限增大连接数可能把数据库本身压垮。

**别踩 & 追问**：不要一看到超时就盲目调大 `pool_size`——如果根因是慢事务或事务里调模型，扩池只会把压力转嫁给数据库；泄漏和长事务不修，池多大都会被占满。

## 场景 6：SSE 中客户端断开，服务端怎么办？

> 面试优先级：★★★★★｜学习难度：★★★★☆｜适用岗位：LLM应用后端  
> 掌握要求：能传递取消并正确计费/清理

**判断**：浏览器关闭连接后，服务端和模型供应商不一定会自动停止。若取消信号没有沿调用链传播，后台仍会继续生成 Token、占用连接和产生费用，所以断连处理属于资源生命周期的一部分。

**先问清楚**

- 下游模型供应商是否支持取消请求？
- 生成过程中是否已经产生外部副作用（写库、调工具）？
- 需要区分用户主动取消和网络断开吗？

**怎么办**

- 检测连接断开或生成器取消；
- 向下游模型请求传递取消，供应商不支持时至少停止消费并记录；
- 取消并等待 Agent 子任务；
- 在 finally 释放 HTTP 连接、Session、Semaphore；
- 对已发生、不能回滚的副作用记录状态；
- 区分用户取消、网络断开和服务错误；
- 统计 cancel rate 和无效 Token 成本。

**怎么说**

> 客户端断开后不应默认继续烧 Token。我会让流式生成器感知取消，向模型和 Agent 子任务传递取消，并在 finally 释放连接和 Session。外部副作用如果已经执行不能靠取消回滚，要查询和记录状态。日志区分用户取消、网络错误和服务失败，同时监控取消后的无效生成成本。

**别踩 & 追问**：常见错误是断开后后台还在生成、白烧 Token；取消信号只传到网关而没传给模型和 Agent 子任务也等于没取消。

## 场景 7：删除文档后，原文、Chunk、向量和缓存如何一致？

> 面试优先级：★★★★☆｜学习难度：★★★★★｜适用岗位：RAG平台  
> 掌握要求：能设计逻辑删除、事件和补偿

**判断**：一份文档在 RAG 中通常有多份派生数据，无法用一个跨数据库、对象存储和向量库的事务同时删除。安全目标应先保证它立刻不可检索，再异步清理各副本并通过扫描补偿遗漏。

**先问清楚**

- 删除要求立即不可检索，还是可接受短暂延迟？
- 原文是否有合规审计的保留要求？
- 权限过滤是在查询层强制，还是依赖物理删除？

**怎么办**

1. 数据库把文档标记 `deleting`，立即阻止新检索；
2. 事务提交删除事件；
3. 消费者幂等删除 BM25、向量、Chunk、缓存；
4. 对象存储按合规策略删除或保留审计期；
5. 全部完成后标记 `deleted`；
6. 定期一致性扫描找孤儿向量和残留；
7. 权限和删除优先在查询层强制，不等待异步物理清理。

**怎么说**

> 删除请求先在主数据库把文档标记为 deleting，并让查询层立即过滤，避免等待异步清理期间继续召回。事务同时写出删除事件，消费者幂等删除 Chunk、BM25、向量和缓存，全部完成后标记 deleted。对象存储按合规策略处理，并用定期一致性扫描发现孤儿向量和残留数据。

**别踩 & 追问**：不要指望一个事务同时删掉数据库、向量库、对象存储和缓存——跨系统没有统一事务，只能先在查询层屏蔽再异步清理；漏删的向量会造成“已删还能被检索到”，要靠一致性扫描补偿。

## 场景 8：第三方模型 API 连续失败，如何治理？

> 面试优先级：★★★★★｜学习难度：★★★★☆｜适用岗位：应用后端、模型网关  
> 掌握要求：能设计错误分类、路由和降级

**判断**：第三方 API 失败不能全部按同一种方式重试——429 和临时 5xx 可能恢复，认证错误和非法参数不会因为重试而消失。模型切换也不是无感的，不同模型的能力、格式和安全策略可能不同。

**先问清楚**

- 失败是限流、5xx、认证还是参数错误？
- 是否有能力和格式兼容的备用模型？
- 业务能接受降级为静态回答或转人工吗？

**怎么办**

- 统一模型网关和错误契约；
- 按超时、429、5xx、认证、内容安全分类；
- 临时错误有限重试，认证错误不重试；
- 熔断故障的 Provider/Region；
- 按兼容清单把任务路由到备用模型，记录质量差异；
- 流式中途失败明确结束，不把两个模型的文本无缝拼接；
- 请求幂等并核算成本；
- 降级为静态回答、排队或转人工；
- 按 Provider、模型和地区监控。

**怎么说**

> 我会在模型网关统一超时、错误码和观测，按限流、临时服务错误、认证和业务拒绝分类。只有可恢复错误有限重试并加退避，连续失败后熔断。备用模型通过能力与格式兼容清单路由，流式中途失败不拼接两个模型的文本；无法安全降级时明确排队或转人工，并记录成本和质量变化。

**别踩 & 追问**：认证错误、参数非法这类永久失败重试再多也没用，只会浪费配额；备用模型不能无脑切，能力和输出格式不匹配会带来新问题，流式切到一半更不能把两段文本拼在一起。

## 场景 9：大文件上传占满内存，如何处理？

> 面试优先级：★★★★☆｜学习难度：★★★☆☆｜适用岗位：后端、文档平台  
> 掌握要求：能使用流式上传、限制和异步处理

**判断**：如果接口一次性 `read()` 整个文件，每个并发上传都会在进程中占用一份完整内存，大文件很快就能把服务拖垮。上传阶段只应负责流式接收和校验，耗时解析交给受资源限制的后台任务。

**先问清楚**

- 单文件最大多大，并发上传多少？
- 当前是否一次性 `read()` 整个文件？
- 已经用对象存储，还是直接落本地磁盘？

**怎么办**

- 限制请求大小、文件类型、页数并防压缩炸弹；
- 流式读取直接写对象存储，不一次 `read()` 全部；
- 边写边计算 Hash；
- 上传完成后异步解析；
- 临时文件受配额限制并自动清理；
- 做病毒/恶意文件扫描；
- 支持客户端分片与断点续传；
- 解析 Worker 独立资源限制，避免拖垮 API。

**怎么说**

> 我会限制文件大小、类型和页数，通过流式读取直接写入对象存储，并边写边计算 Hash，避免整文件进入内存。上传完成后由队列异步触发解析 Worker，Worker 有独立 CPU、内存和超时限制。还需要临时文件清理、恶意文件扫描，以及大文件的分片与断点续传。

**别踩 & 追问**：一次性 `read()` 到内存是典型错误，几个大文件并发就能 OOM；把重解析放在上传请求里同步做，也会占住连接和内存，应交给独立资源限制的 Worker。

## 场景 10：服务扩容后 Session、本地缓存和后台任务怎么办？

> 面试优先级：★★★★☆｜学习难度：★★★★☆｜适用岗位：后端、K8s  
> 掌握要求：理解无状态服务和外部状态

**判断**：服务扩容后，同一用户的下一次请求可能落到另一台实例。如果关键会话、缓存或任务进度只存在本机内存中，新实例就看不到这些状态，因此可横向扩展的服务要把重要状态放到共享外部系统。

**先问清楚**

- 哪些状态目前只存在本机内存里？
- 是否有 WebSocket/SSE 等长连接需要会话保持？
- 扩缩容时在途任务能否接受中断重试？

**怎么办**

- HTTP 服务尽量无状态，会话和任务状态存外部系统；
- 数据库 Session 只在单请求内存在，不跨实例；
- 本地缓存只能做可丢失加速，需带版本或 TTL；
- 需要全局一致的缓存用 Redis 等，但仍要考虑权限和失效；
- 后台任务通过队列竞争消费并具备幂等；
- 扩缩容时做优雅下线：停止接新请求、等待或转移在途任务；
- WebSocket 等长连接需要连接路由或外部会话状态。

**怎么说**

> API 实例应尽量无状态，业务会话和任务状态放数据库或 Redis，数据库 Session 只在单请求内使用。本地缓存只能作为可丢失加速并带版本和 TTL；后台任务由队列竞争消费且必须幂等。缩容时先停止接收新流量，再等待或转移在途任务，长连接则需要连接路由或外部会话状态。

**别踩 & 追问**：把会话或任务进度放本机内存，是扩容后“时好时坏”的典型根因；缩容时直接杀进程会丢在途任务，必须先摘流量再等待或转移。

## 模块口述总结

> 大模型应用后端的核心是控制不可靠和昂贵的外部调用。Python 协程适合 IO 并发，但必须避免同步阻塞并限制下游并发。数据库 Session 是每请求工作单元，执行 SQL 时从连接池借连接，事务要短并及时归还。Redis 锁需要 SET NX PX、唯一 Token 和 Lua 安全释放，关键业务还要幂等与数据库约束。服务通过 SSE 流式返回，并用超时、重试、熔断、队列和状态机治理失败；Docker负责一致交付，K8s负责集群编排，CI/CD 加入 RAG/Agent 回归和灰度门禁。

# 01 关系数据库：从 SQL 到索引、事务、锁和日志

> 适合对象：会写 Python/SQLAlchemy，但对数据库内部机制没有系统认识的人。
>
> 学完目标：你能看懂一条 SQL 怎样找到数据，能解释并发请求为什么读到不同结果，能判断该用索引、锁、版本号还是事务，能说清楚 MySQL/InnoDB 和 PostgreSQL 的关键差异。

## 0. 先建立一张完整的图

假设我们做一个企业知识库服务。用户上传文档后，系统要保存文档记录、解析任务、分块、向量索引状态和模型用量；用户打开会话时，要按时间读取最近消息；两个请求同时扣减额度时，余额不能变成负数。

一条请求可能经过下面这些层：

```text
Python/FastAPI
  ↓ 生成 SQL
数据库连接
  ↓ 发送 SQL
SQL 解析与优化器
  ↓ 选择索引、Join 和排序方式
存储引擎
  ↓ 读取数据页、索引页、版本链
事务与锁
  ↓ 决定本次读能看到什么、写能否继续
日志与恢复
  ↓ 确保提交后故障仍可重建
复制/备份
  ↓ 支持读扩展和灾难恢复
```

> **一句话结论：** 数据库知识不是一组孤立八股，而是三条互相连接的链：索引和执行计划解决“快不快”，事务/MVCC/锁解决“并发时对不对”，redo/undo/binlog 或 WAL、复制和备份解决“故障后还在不在”。

## 1. 数据库到底在保存什么

### 1.1 表、行、列和页

表可以先理解成很多行记录的集合，列描述每行有哪些字段。数据库不会把每一行单独存成一个文件，而是把多行组织到固定大小的数据页中。查询时，数据库通常以“页”为单位从内存或磁盘读取。

这解释了两个看起来反直觉的现象：

1. 只查询一行，也可能读取包含它的整页；
2. 查询相邻记录通常比随机访问很多位置更快，因为页和缓存的局部性更好。

索引本身也是由页组成的结构。索引不是“内存里的目录”，而是需要空间、需要写入维护、需要参与缓存竞争的第二份数据结构。

### 1.2 主键与约束

主键回答“这行记录是谁”；唯一约束回答“这个业务值不能重复”；外键回答“这条引用必须指向存在的对象”；`NOT NULL` 和 `CHECK` 回答“字段必须满足什么基本条件”。

例如幂等请求表可以这样建模：

```sql
CREATE TABLE request_record (
    id              BIGINT PRIMARY KEY,
    user_id         BIGINT NOT NULL,
    idempotency_key VARCHAR(100) NOT NULL,
    status          VARCHAR(20) NOT NULL,
    result_json     JSON,
    created_at      TIMESTAMP NOT NULL,
    UNIQUE (user_id, idempotency_key)
);
```

应用代码可以先查是否存在，但真正防止两个并发请求同时创建两行的最后一道防线是唯一约束和事务。缓存里的 `SETNX`、Python 的锁和前端按钮置灰，都不能替代这个事实约束。

### 1.3 范式与反范式怎么理解

范式的直觉是：一个事实尽量只保存一次，避免更新一处却忘记更新另一处。反范式是为了减少 Join 或提高读取速度，主动复制一部分数据。

在知识库系统里，文档标题可以保存在文档表，消息表只保存 `document_id`；也可以在消息列表中冗余一个标题快照，换取读取方便。选择时要说明：谁是事实源、如何同步、旧数据是否允许、更新成本是什么，而不是机械背“必须三范式”。

## 2. 索引：为什么它能让查询变快

### 2.1 没有索引时发生什么

```sql
SELECT *
FROM message
WHERE conversation_id = 42
ORDER BY created_at DESC
LIMIT 50;
```

如果 `message` 没有合适索引，数据库可能从第一行检查到最后一行，找出 `conversation_id = 42` 的记录，再排序，最后取 50 行。数据量从一万变成一亿，工作量也可能随之增加。

索引相当于把“可能满足条件的记录位置”按某种顺序组织起来。它不直接返回最终答案，而是提供一种更少读取数据页的访问路径。

### 2.2 B+Tree 的直觉

把电话簿想象成按姓氏排序的多级目录：先通过首字母跳到一段，再通过更细的范围定位，最后顺序翻阅相邻记录。B+Tree 的内部节点存放分隔键，叶子节点保存有序键和定位信息，叶子之间通常可以顺序遍历。

它适合数据库的原因是：

- 一个节点能容纳很多键，树的高度低；
- 查找、范围和排序都能利用有序性；
- 访问相邻键时更容易命中同一页或相邻页；
- 更新时只需维护局部路径，但页满时仍可能发生页分裂。

普通二叉树可能退化，Hash 主要适合等值查找，无法自然支持 `>`, `<`, `BETWEEN` 和有序范围扫描。因此“数据库索引常用 B+Tree”不是因为它在所有场景都最好，而是因为它是通用访问模式下的平衡选择。

### 2.3 MySQL InnoDB：聚簇索引和二级索引

InnoDB 的聚簇索引可以先理解为“主键 B+Tree 的叶子节点就是整行数据”。二级索引的叶子节点通常保存二级索引列和主键值，而不是整行。

查询过程：

```text
二级索引 (conversation_id, created_at)
  ↓ 找到匹配的主键 id
聚簇索引 (PRIMARY KEY)
  ↓ 根据 id 找到整行
返回 title、content 等不在二级索引中的列
```

第二次访问就是回表。若查询只需要索引中已经包含的列，则可能形成覆盖索引，减少回表，但索引会变大，写入和更新成本会上升。

实际设计经常关注“主键要短、稳定”：因为二级索引要保存主键，主键越长，所有二级索引越胖；主键变化还会带来大量索引维护。随机 UUID 可能导致插入位置分散、页分裂和缓存局部性变差，但它在多机生成和隐藏业务规模方面也有价值，不能脱离场景绝对化。

### 2.4 PostgreSQL：heap 和独立索引

PostgreSQL 通常把表数据存放在 heap，索引保存指向 heap tuple 的定位信息。更新一行时，MVCC 可能产生新 tuple，旧 tuple 仍暂时存在；因此 PostgreSQL 的索引、可见性和 VACUUM 要结合起来理解。

Index Only Scan 的误区是“只要查询列都在索引里，就一定不读 heap”。数据库还要知道对应 tuple 对当前快照是否可见；visibility map 没有足够信息时，仍可能回到 heap 检查可见性。

PostgreSQL 的常见索引类型：

| 类型 | 适合什么 | 需要注意什么 |
|---|---|---|
| B-tree | 等值、范围、排序 | 通用默认选择 |
| Hash | 等值 | 不适合范围和排序 |
| GIN | JSONB、数组、全文等一个行对应多个键 | 写入和索引体积可能较大 |
| GiST/SP-GiST | 范围、空间和可分解搜索结构 | 依赖操作符类和数据分布 |
| BRIN | 时间序列等物理顺序与值高度相关的大表 | 不是任意乱序数据的替代品 |
| 部分/表达式索引 | 只索引满足条件的行或计算结果 | 查询写法要与索引表达式匹配 |

### 2.5 联合索引的最左前缀

假设有索引：

```sql
CREATE INDEX idx_message_lookup
ON message (tenant_id, conversation_id, created_at, id);
```

它通常适合：

```sql
WHERE tenant_id = 7
  AND conversation_id = 42
ORDER BY created_at DESC, id DESC
```

因为查询从最左的 `tenant_id` 开始，随后定位到 `conversation_id`，再按时间和 ID 顺序取数据。只有 `conversation_id = 42` 而没有 `tenant_id` 时，不能直接把这个索引当成一个只包含 `conversation_id` 的紧凑目录。

不要把“范围条件之后的列全部失效”说得过度绝对。范围条件通常结束了继续缩小 B-tree 连续区间的能力，但后续列可能仍参与过滤、覆盖或排序，具体要看数据库版本和计划。

### 2.6 索引为什么会失效或不值得用

- 对索引列包函数，例如 `DATE(created_at) = ...`；
- 发生隐式类型转换；
- `LIKE '%abc'` 的开头无法确定 B-tree 起点；
- 条件选择性太低，大多数行都匹配；
- 统计信息过期，优化器误判数据分布；
- 通过二级索引找到大量主键后回表，成本高于全表扫描；
- 索引顺序与过滤、排序、分页模式不匹配。

“索引失效”不是一个神秘开关。正确排查方式是看真实 SQL 和执行计划，判断优化器为什么认为另一条路径更便宜。

## 3. 一条 SQL 是怎样执行的

### 3.1 从字符串到结果

数据库收到 SQL 后大致经历：

1. 解析语法和对象名称；
2. 检查权限、类型和约束；
3. 优化器枚举或估计候选计划；
4. 根据统计信息估算每条路径的成本；
5. 选择扫描、Join、排序和并行方式；
6. 存储引擎读取页、应用过滤并返回结果。

优化器不是“知道业务意图的 AI”，它只根据 SQL、统计信息、配置和成本模型做选择。统计信息错误时，完全合法的计划也可能很慢。

### 3.2 读执行计划要看什么

MySQL 中重点看访问类型、候选索引、实际使用索引、估算行数、过滤比例、Join 顺序、临时表和文件排序等。PostgreSQL 中重点看节点类型、cost、actual time、actual rows、loops、Buffers、排序和并行节点。

最有价值的信号往往是：

- estimated rows 和 actual rows 相差数量级；
- Nested Loop 的外层结果比优化器预计的大很多；
- 大量 rows removed by filter，说明过滤发生得太晚；
- Sort、Hash 或临时空间发生溢写；
- 计划显示索引，但实际读取和回表量仍很大；
- 查询时间主要耗在锁等待而不是执行节点。

`EXPLAIN ANALYZE` 会执行语句，不能把它当成无副作用的查看命令；对更新、删除和带外部副作用的函数要先确认安全边界。

### 3.3 三种常见 Join

**Nested Loop**：外层取一行，内层用索引查匹配。外层少、内层有选择性索引时很好；外层变大后，重复查找次数会迅速增加。

**Hash Join**：把一侧构建哈希表，再扫描另一侧匹配。适合等值 Join 和较大的批量连接，但哈希表放不下时会溢写到磁盘。

**Merge Join**：两侧按 Join 键有序后线性合并。排序本身有成本，但大批量有序数据可能很高效。

不要背“某个 Join 永远最好”。数据量、选择性、排序、内存和统计信息都会影响选择。

### 3.4 深分页为什么慢

```sql
SELECT id, content
FROM message
WHERE conversation_id = 42
ORDER BY created_at DESC, id DESC
LIMIT 50 OFFSET 100000;
```

数据库仍要找到并跳过前 100000 条，深度越大，扫描和排序成本越高。Keyset/seek pagination 保存上一页最后一个 `(created_at, id)`，下一页用“比它更小”的条件继续扫描：

```sql
WHERE conversation_id = 42
  AND (created_at, id) < (:last_time, :last_id)
ORDER BY created_at DESC, id DESC
LIMIT 50;
```

这种方式更适合时间线和消息列表，但不适合要求任意跳到第 N 页的界面。

## 4. 事务：为什么一组操作要绑在一起

### 4.1 从扣额度理解 ACID

假设一次模型调用要同时写调用记录、扣额度和更新任务状态。若只成功写调用记录，扣额度失败，系统就出现“使用了模型却没有扣费”的不一致。

- **原子性**：调用记录、额度扣减、任务状态一起提交或一起回滚；
- **一致性**：余额不能小于零、引用的租户必须存在等不变量持续成立；
- **隔离性**：两个并发请求不能看到彼此未完成的中间状态；
- **持久性**：返回提交成功后，数据库重启仍能恢复这些变更。

ACID 不是单纯由一条 `BEGIN` 语句提供的。约束、锁、MVCC、日志和应用事务边界共同决定结果；跨数据库或外部 API 的副作用仍需幂等与补偿。

### 4.2 并发异常用时间线理解

设余额是 100，两个请求都要扣 80：

```text
请求 A：读到 100
请求 B：读到 100
请求 A：写回 20
请求 B：写回 20
```

最终余额看起来是 20，但实际扣了 160。这是典型的丢失更新/先读后写问题。正确方案是条件更新 `remaining >= cost`，或者在事务中锁定当前行并按顺序修改，再检查影响行数。

### 4.3 四种标准隔离级别

| 隔离级别 | 直觉 | 常见代价 |
|---|---|---|
| Read Uncommitted | 可能读到未提交变化 | 很少用于严肃业务 |
| Read Committed | 每次语句看到已提交快照 | 同一事务两次读取可能不同 |
| Repeatable Read | 同一事务快照更稳定 | 具体幻读/锁行为依产品实现 |
| Serializable | 尽量表现为串行执行 | 冲突、等待和吞吐成本高 |

MySQL InnoDB 默认是 Repeatable Read；PostgreSQL 默认是 Read Committed。PostgreSQL 的 Repeatable Read 不允许普通意义上的幻读，但仍要理解其序列化异常和写冲突；不能只拿教科书表格覆盖所有产品行为。

### 4.4 MVCC 的基本思想

MVCC 可以理解为：写入不把所有读者都挡住，而是保留足够的版本信息，让读者根据自己的快照判断应该看到哪一个版本。

InnoDB 会维护事务 ID、undo 记录和 Read View。当前版本如果对快照不可见，就沿 undo 版本链向前找可见版本；因此长事务会让旧版本迟迟不能清理。

PostgreSQL 更新通常创建新 tuple，旧 tuple 成为 dead tuple。普通读通过事务可见性信息判断版本，VACUUM 在安全时机回收可复用空间并维护 visibility map。长事务可能阻止旧版本清理，带来表膨胀、autovacuum 追不上和复制延迟等连锁问题。

### 4.5 快照读、当前读和锁定读

普通 `SELECT` 通常读取快照；`SELECT ... FOR UPDATE`、`FOR SHARE` 或写操作需要当前版本并加锁。扣额度、领取任务、抢占一个待处理记录时，必须明确是想“看到某个历史快照”，还是想“锁住当前事实并修改”。

乐观版本控制示例：

```sql
UPDATE document
SET status = 'INDEXED', version = version + 1
WHERE id = :id
  AND version = :old_version
  AND status = 'INDEXING';
```

影响行数为 0 时，可能是版本冲突、状态已经变化或记录不存在，应用要分别处理，不应无脑重试。

## 5. 锁：到底锁住了什么

### 5.1 为什么需要锁

MVCC 主要帮助读写并发，写写之间仍需要协调。锁解决的是“同一时刻谁可以改什么”，它不是越多越安全：锁会带来等待、死锁和吞吐下降。

共享锁允许多个兼容读者，排他锁保护写入；意向锁帮助表级和行级锁共同工作。不同数据库的锁对象和兼容矩阵不完全相同。

### 5.2 InnoDB 的记录锁与范围锁

- Record Lock：锁住索引记录；
- Gap Lock：锁住索引记录之间的间隙，阻止某些范围插入；
- Next-Key Lock：记录锁加前方间隙锁；
- Insert Intention Lock：多个插入者在间隙中的协调。

在 InnoDB 中，“锁的是一行”常常不够准确。无合适索引的更新可能扫描并锁住更大范围；非唯一索引范围查询、唯一索引等值查询和不同隔离级别下的锁范围也不同。索引设计同时影响性能和并发冲突。

### 5.3 PostgreSQL 的锁观念

PostgreSQL 的普通 MVCC 读通常不会阻塞普通写，但更新同一 tuple、显式 `FOR UPDATE` 和表级锁仍会冲突。它没有可以直接套用 InnoDB next-key lock 名称的同一机制，因此回答 PostgreSQL 锁时要说具体的行锁、表锁、事务快照和等待关系。

### 5.4 死锁如何形成

```text
事务 A：锁住订单 1 → 等待订单 2
事务 B：锁住订单 2 → 等待订单 1
```

等待图形成环就是死锁。数据库通常会检测并选择一个事务回滚；应用收到错误后要重试，但必须限制次数、退避并保证幂等。

减少死锁的方法：

1. 所有路径按同样顺序锁定资源；
2. 事务内只做数据库必要工作，不调用模型或外部 HTTP；
3. 用合适索引缩小扫描和锁范围；
4. 避免长事务和用户交互期间持锁；
5. 记录死锁日志、等待双方 SQL、索引和事务时长。

### 5.5 安全领取任务

任务表通常有 `PENDING/RUNNING/SUCCEEDED/FAILED` 状态。多个 Worker 领取时，不能先普通查询再在应用层更新，因为两个 Worker 可能同时读到同一条 pending 记录。可以使用锁定读、条件更新或数据库支持的跳过已锁行策略，并把领取动作和状态变化放在短事务中。真正的长任务在事务外执行，完成后再用任务 ID 和版本号幂等更新。

## 6. 日志：redo、undo、binlog 和 WAL 各管什么

### 6.1 MySQL 三种日志不是一回事

**redo log** 面向 InnoDB 崩溃恢复。数据页可以先在内存中变脏，提交时先保证相关 redo 持久化；宕机重启后，数据库重放 redo，把已提交但尚未写入数据文件的修改补回来。

**undo log** 面向回滚和 MVCC。事务回滚需要知道如何恢复旧值，一致性读需要沿版本链读取对当前快照可见的历史版本。

**binlog** 是 MySQL Server 层的变更日志，主要用于复制、CDC 和增量恢复。它不是 InnoDB 版本链，也不能直接替代 redo 的崩溃恢复职责。

### 6.2 PostgreSQL WAL

WAL 是 Write-Ahead Logging：与数据页修改对应的 WAL 记录必须先于数据页持久化。故障恢复从 checkpoint 位置开始重放 WAL，重新构造数据页变化。WAL 的 LSN 可用于复制位点、归档和恢复进度判断。

### 6.3 提交成功后立即宕机，数据会怎样

要把“客户端收到响应”和“所有地方都已可读”分开：

1. 本地日志是否按持久性配置刷盘；
2. 数据页是否已经写回，不影响日志恢复能否重建；
3. binlog/WAL 是否已被副本接收；
4. 副本是否已经应用并对读请求可见；
5. 备份和日志归档是否能覆盖故障点。

`innodb_flush_log_at_trx_commit`、`sync_binlog`、WAL fsync 和 checkpoint 等参数体现吞吐与持久性窗口的权衡。不要用“提交成功=所有副本都执行完”来回答。

### 6.4 备份、RPO、RTO 与 PITR

- RPO：最多能接受丢失多长时间的数据；
- RTO：故障后多久恢复服务；
- 基础备份：某个时间点的完整数据；
- 日志归档：基础备份之后的连续变更；
- PITR：恢复基础备份后重放日志到指定时间点。

高可用副本解决机器/服务故障，备份和 PITR 解决误删、逻辑错误和灾难。两者不能互相替代。

## 7. 复制、读写分离与扩展

### 7.1 MySQL 复制链路

主库产生 binlog，副本拉取到 relay log，再由应用线程执行。Row 格式记录行变化，更容易保持实际变更语义；Statement 日志量可能较小，但受非确定性语句影响；实际选型还要看 CDC、兼容性和版本。

GTID 给事务分配全局标识，帮助副本定位和故障切换。异步复制可能丢失主库尚未传出的事务；半同步通常只保证某个副本收到并持久化日志，不等于已应用。

### 7.2 PostgreSQL 物理与逻辑复制

物理流复制发送 WAL，适合同版本实例的物理副本和高可用；逻辑复制通过 publication/subscription 传递逻辑变更，适合部分表同步、迁移和 CDC。replication slot 会阻止发送端回收下游尚未消费的 WAL，下游停摆可能把磁盘撑满。

### 7.3 读写分离的一致性

写入主库后立刻从副本读取，可能读到旧值。方案包括写后短时间读主、会话粘滞、携带复制位点/版本路由，或只在接受最终一致性的路径使用副本。先说明业务要求，再选择方案。

### 7.4 分区与分库分表

分区是在一个数据库实例内按时间、范围或列表拆分逻辑表，便于裁剪、归档和局部维护；分库分表把数据分散到多个数据库服务器，换取容量和吞吐，但引入跨分片 Join、全局唯一、分页、事务、热点租户和扩容迁移问题。

进入分片前，先确认索引、SQL、归档、分区、缓存和容量优化已经不能满足需求。分片键要从主要查询模式、数据局部性、热点和迁移成本倒推，而不是因为“数据多”就直接按用户 ID 切。

## 8. Python/SQLAlchemy 中的事务边界

路由层负责参数和权限，Service 层负责业务事务边界，Repository 层负责 SQL。事务内只放需要原子提交的数据库动作；模型调用、外部 HTTP、长时间文件解析不要持有数据库事务。

常见安全流程：

```text
校验输入和权限
→ 开启短事务
→ 读取/锁定需要的行
→ 写业务状态与 outbox
→ 提交
→ 事务外发布消息或执行长任务
→ 失败时通过状态机、重试和补偿收敛
```

异常时必须回滚 Session，不能把失败后的 Session 继续当作干净连接使用；连接池大小要和数据库最大连接数、并发模型和下游延迟一起估算。

## 9. 常见误区

- **“用了 ORM 就不用懂 SQL。”** ORM 仍会生成 SQL，索引、事务、锁和执行计划依然存在。
- **“命中了索引就一定快。”** 还要看扫描行数、回表、排序、Join、锁等待和长尾。
- **“MySQL 和 PostgreSQL 都是 MVCC，所以实现一样。”** 版本结构、默认隔离级别、VACUUM 和锁范围不同。
- **“redo、undo、binlog 都是恢复日志。”** 它们服务的层次和用途不同。
- **“半同步复制代表副本已经可读。”** 收到日志不等于已经应用。
- **“事务越大越安全。”** 长事务会放大锁、回滚、旧版本和复制压力。
- **“死锁只能数据库自己解决。”** 数据库会回滚一个事务，业务仍要控制顺序并正确重试。

## 10. 这一章的整体心智模型

遇到数据库问题时，按下面顺序思考，而不是先背某个名词：

```text
业务要保存什么事实？
→ 查询要找哪些行、按什么顺序？
→ 索引能否减少数据页读取？
→ 优化器实际选择了什么计划？
→ 并发事务应该看到哪个版本？
→ 哪些写入需要锁或版本检查？
→ 提交后日志怎样支撑恢复？
→ 副本、备份和分区怎样改变一致性与容量？
```

如果这条链中任意一环没有证据，结论就可能只是猜测。例如“查询慢”可能是索引不匹配，也可能是锁等待；“数据丢了”可能是读到了滞后副本，也可能是提交持久性配置不满足需求。

## 11. 本章小结

关系数据库首先是事实存储，其次才是查询加速器。约束定义哪些数据不能错；索引定义怎样少读数据页；执行计划决定优化器怎样访问；事务和 MVCC 定义并发可见性；锁协调写入冲突；redo/undo/binlog 或 WAL 支撑恢复、复制和时间点回放。MySQL 与 PostgreSQL 的共同概念可以互相帮助，但实现细节必须分别学习。

# 90 综合实战：把数据库、中间件和 Agent 后端串成一个系统

> 这篇不是把概念再列一遍，而是沿着一个真实的企业知识库/Agent 服务，把关系数据库、Redis、消息队列、Elasticsearch、Neo4j 和可靠性策略放在同一条业务链里。阅读时重点关注：每个数据放在哪里、谁是事实源、什么时候异步、失败后如何恢复。

## 0. 业务背景和边界

系统支持多租户团队上传文档、搜索知识、发起对话，并让 Agent 调用内部工具。核心对象包括：

```text
租户 → 用户 → 会话 → 消息
  │      └→ 权限/配额
  └→ 文档 → 版本 → chunk → 向量/实体关系
```

需要同时满足：

- 租户之间严格隔离；
- 文档上传接口快速返回，解析和索引异步完成；
- 对话消息按会话顺序保存；
- 搜索结果可追溯来源和版本；
- Agent 工具调用有超时、幂等和审计；
- Redis、搜索集群或消息队列短时故障时，事实不会丢失。

## 1. 总体架构：事实、投影和协调分开

```text
                    ┌─ Redis：缓存/限流/短期锁
                    │
客户端 → API ───────┼─ PostgreSQL：事实/约束/事务/Outbox
                    │          │
                    │          └→ 消息队列：异步任务与事件
                    │                         ├→ 解析/embedding
                    │                         ├→ Elasticsearch：全文/向量投影
                    │                         └→ Neo4j：关系投影
                    │
                    └─ Agent 编排：检索、工具、状态与审计
```

这里有三种角色：

1. **事实源**：PostgreSQL 保存用户、权限、文档版本、任务状态、幂等记录和审计事实。
2. **可重建投影**：Elasticsearch 保存搜索字段和向量，Neo4j 保存实体关系；两者落后时不改变数据库事实。
3. **协调与加速**：Redis 保存可丢的缓存、短期计数和锁；消息队列保存待处理工作和事件。

这个分层让每个组件的恢复方向明确：先恢复事实，再重放事件重建投影，最后预热缓存。

## 2. 数据模型：先把不变量落到约束

### 2.1 PostgreSQL 事实表

```sql
CREATE TABLE document (
    id              BIGSERIAL PRIMARY KEY,
    tenant_id       BIGINT NOT NULL,
    title           TEXT NOT NULL,
    source_uri      TEXT NOT NULL,
    version         BIGINT NOT NULL DEFAULT 1,
    status          TEXT NOT NULL CHECK (status IN ('pending','processing','ready','failed','deleted')),
    created_at      TIMESTAMPTZ NOT NULL,
    updated_at      TIMESTAMPTZ NOT NULL,
    UNIQUE (tenant_id, id)
);

CREATE TABLE idempotency_record (
    tenant_id       BIGINT NOT NULL,
    idempotency_key TEXT NOT NULL,
    request_hash    TEXT NOT NULL,
    status          TEXT NOT NULL,
    response_json   JSONB,
    PRIMARY KEY (tenant_id, idempotency_key)
);

CREATE TABLE outbox_event (
    id              BIGSERIAL PRIMARY KEY,
    message_id      UUID NOT NULL UNIQUE,
    aggregate_type  TEXT NOT NULL,
    aggregate_id    TEXT NOT NULL,
    aggregate_ver   BIGINT NOT NULL,
    event_type      TEXT NOT NULL,
    payload         JSONB NOT NULL,
    status          TEXT NOT NULL DEFAULT 'pending',
    created_at      TIMESTAMPTZ NOT NULL,
    sent_at         TIMESTAMPTZ
);
```

`status` 的合法转移、`version` 的递增、幂等键唯一性和事件 message_id 唯一性由数据库约束或条件更新保护。应用层校验可以提供友好错误，但不能替代这些约束。

### 2.3 业务契约与版本边界

跨组件传递的不是“随便一段 JSON”，而是带身份和版本的业务契约。建议至少统一：`tenant_id`、`aggregate_id`、`aggregate_version`、`message_id`、`schema_version`、`occurred_at`、`trace_id` 和 `source`。状态字段要定义合法迁移，例如 `pending → processing → ready/failed/deleted`；旧事件、重复事件和未知字段分别有明确处理方式。

数据库事实表、Outbox、任务表和投影文档的版本含义要写在同一份契约里：数据库版本表示当前事实，事件版本表示事实发生时的序号，投影版本表示已经应用到哪一步。不能把“消息已发布”或“ES refresh 完成”误当成数据库事实版本已经推进。

### 2.2 搜索和图的投影字段

Elasticsearch chunk 至少保存 `tenant_id`、`document_id`、`document_version`、标题路径、正文、embedding、权限标签和来源位置；Neo4j 节点/关系保存 canonical ID、来源事件、置信度、有效时间和 tenant。投影中永远带事实版本，消费旧事件时可以拒绝覆盖新版本。

## 3. 案例一：上传文档到“可搜索”

### 3.1 同步请求只完成可承诺的部分

```text
POST /documents
  1. 校验 tenant/user 权限和文件摘要
  2. 检查 (tenant_id, idempotency_key)
  3. 存储文件并开启数据库事务
  4. 插入 document(status='pending')
  5. 插入 document.created outbox_event
  6. 提交事务
  7. 返回 document_id, status='pending'
```

相同幂等键重复请求返回同一个 document_id；同 key 不同文件摘要返回冲突。数据库提交成功后，即使 API 进程在返回前宕机，客户端重试也能查到记录。

### 3.2 Outbox 发布和解析任务

relay 读取 pending outbox，发布带 `message_id`、`aggregate_id` 和 `aggregate_ver` 的事件；发布确认后标记 sent。relay 超时会重复发布，消费者在处理记录表或状态条件更新中去重。

解析消费者执行：

```text
读取 document.created
  → 条件更新 pending → processing
  → 下载文件（超时/校验）
  → 解析并切块
  → 写 chunk 元数据/解析结果
  → 发布 document.chunked
   → 状态改为 processing
  → ACK
```

解析失败分为临时下载错误和永久格式错误。前者指数退避，后者写 error_code、进入死信并把文档标为 failed；死信消息可在修复解析器后按版本重新投递。

### 3.3 生成 embedding 和写入 ES/Neo4j

embedding 任务按 document_id 分区，避免同一文档的版本乱序；每条 chunk 携带版本和 chunk_id。写入 ES 采用 bulk，但批大小受内存和单批失败处理限制；写入 Neo4j 使用 canonical ID + MERGE + 唯一约束。

当所有 chunk 的投影版本达到 document.version 后，消费者才执行：

```sql
UPDATE document
SET status = 'ready', updated_at = now()
WHERE id = :id AND version = :version AND status = 'processing';
```

ES refresh 延迟或 Neo4j 暂时不可用时，数据库仍保留 `processing`，用户看到的是“正在建立索引”，而不是一个看似成功但实际查不到的文档。

### 3.4 状态机、租约与对账

长任务不把几十秒的解析或 embedding 放在一次数据库事务里。任务表记录 `status`、`lease_until`、`attempt`、`step_id`、`last_error` 和 `result_ref`；Worker 用条件更新领取，事务外执行，结果以版本和步骤 ID 幂等写回。租约过期后可以重新认领，但旧 Worker 的结果必须因版本过期而被拒绝。

对账任务按文档版本检查四类缺口：数据库没有对应投影、投影版本落后、旧删除被重新写回、Outbox/消息处理记录长期 pending。对账只生成可审计的补偿任务，不直接无条件重建全部数据；重建也要遵守租户权限、队列容量和下游限额。

## 4. 案例二：一次知识检索和问答

### 4.1 权限先于召回

API 根据用户会话得到 tenant、项目和角色，构造同一份权限过滤条件，分别传给 Elasticsearch 和 Neo4j。不能先全局召回再在应用层过滤，因为无权文档可能已经进入重排、日志或生成上下文。

### 4.2 混合召回

```text
问题：“Redis 缓存击穿怎样避免？”
  ├─ ES BM25：命中“热点 key、互斥重建、TTL”
  ├─ ES kNN：找到语义相近的缓存治理片段
  └─ Neo4j：找到 Redis、缓存组件、维护团队和相关事故
       ↓
合并 chunk_id，按版本/权限去重
       ↓
重排前 30 条，保留前 6 条证据
```

关键词分数和向量分数先做归一或分别取候选，再由重排模型判断；返回结构中带标题、chunk、版本、来源链接和关系路径。没有足够证据时，生成层应说明“不确定”，不能用模型常识替代缺失资料。

### 4.4 证据、引用与可评估性

问答接口应保留 `retrieval_trace_id`，把问题、权限 filter、BM25/kNN 候选、图路径、重排输入、最终 context 和引用 chunk 关联起来。离线评估区分“召回了正确证据”“引用指向正确来源”“答案没有超出证据”三层；线上按租户、文档版本、问题类型和 P95/P99 切片，才能知道问题来自索引、权限、上下文预算还是生成模型。

当只有低分或互相冲突的证据时，返回澄清/不确定状态比强行生成更安全。旧版本引用、无权限 chunk 和被删除文档必须在进入 prompt 前拒绝，不能依赖模型自行过滤。

### 4.3 会话消息与上下文缓存

消息事实写 PostgreSQL，最近窗口可以用 Redis Sorted Set 或按会话 key 缓存。写入顺序是数据库提交后失效缓存；如果要求用户立刻看到自己刚发的消息，当前请求可直接使用数据库结果或带版本读取主库。

大历史会话不全部塞进 Redis；按时间分页，摘要和长期记忆与原始消息分开，缓存值设置 schema/version 和 TTL。

## 5. 案例三：Agent 工具调用

### 5.1 工具调用是一次跨边界副作用

Agent 可能调用“查询订单”“创建工单”“发送通知”。模型输出的参数不可信，服务端必须做 schema 校验、权限校验、资源归属校验和超时控制。工具执行记录写入审计表，包含 tool_name、arguments_hash、trace_id、幂等键、结果摘要和错误分类。

### 5.2 读工具和写工具分开

只读查询可以在有限超时内重试；写工具需要幂等键和状态查询：

```text
创建工单 request_id=abc
  → 本地记录 processing
  → 调用工单系统 Idempotency-Key=abc
  → 超时：查询 abc 的状态
  → 成功：记录 external_id
  → 未知：进入补偿，不重复创建
```

Redis 锁可以减少同一会话的并发工具调用，但最终不变量仍由工单系统唯一键和本地幂等记录保证。

### 5.3 Agent 状态与可恢复执行

每个步骤保存 `run_id`、step_id、输入摘要、状态、重试次数和输出引用。进程宕机后，调度器可以找到 `processing` 且超过 lease 的步骤重新认领；已完成步骤不会重复产生副作用。模型上下文只保存必要结果，完整响应放在对象存储或审计表中。

## 6. 案例四：多租户与容量设计

### 6.1 租户隔离

数据库所有核心表带 tenant_id，并在查询、唯一键、索引和缓存 key 中贯穿；Redis key 使用 `tenant:{id}:...`，ES filter 和 Neo4j MATCH 都带 tenant；消息 payload 也带 tenant，消费者不能依赖上游“已经过滤”。

租户删除是一个跨投影流程：数据库写 deleted 事实和版本，发布删除事件，清理 ES、Neo4j、Redis，最后做对账确认。任何一步失败都可重试，查询默认拒绝 deleted 版本。

### 6.2 粗略容量估算

假设每天 100 万个 chunk，平均 4 KB 正文，ES 原始文本约 4 GB/天；倒排、向量、segment、复制和预留后可能是原始数据的数倍。消息吞吐按解析耗时、embedding 并发和失败重试计算；Redis 内存还要加 key/value、复制和碎片开销。

估算不是为了得到一个“准确数字”，而是发现隐藏瓶颈：向量维度是否让磁盘暴涨，批量 refresh 是否造成 merge，队列积压能否在峰值前消化，数据库连接是否足够支撑回源。

### 6.3 限流与优先级

上传、embedding、问答和后台重建不能共享无限并发。按租户设置配额，核心问答使用独立连接池和 worker，低优先级重建在高峰暂停；队列积压达到阈值时，接口返回排队状态而不是继续放大。

## 7. 一次完整故障推演

### 7.1 Redis 故障

缓存读取快速超时并熔断，回源数据库受并发上限保护；最近列表可以暂时返回数据库结果，排行榜和非核心推荐关闭。恢复后按热点异步预热，不能让所有请求同时回填。

### 7.2 消息队列积压

先比较生产速率、消费速率、lag 和处理耗时；若是 embedding 下游超时，暂停无意义重试并熔断；若是消费者版本 bug，把消息保留在队列/死信，修复后按版本重放。事实表的状态仍可查询，用户看到 processing，不把积压误报成数据丢失。

### 7.3 PostgreSQL 主库切换

停止写入或进入短暂维护，重新建立连接池，确认最后提交的 WAL/备份点和 Outbox 缺口；恢复后先处理 pending outbox，再重建缓存和搜索投影。数据库连接切换不是只改一个环境变量，还要验证事务重试、唯一约束和读写路由。

### 7.4 ES mapping 需要改变

新建 v2 索引，按数据库版本回填并处理增量事件，抽样比较分析 token、召回和权限，最后原子切换 alias。旧索引保留到回滚窗口结束，确认快照和磁盘余量后再清理。

### 7.5 运行前后的验证清单

每次发布或扩容前后都应回答：事实源是否可写、Outbox 是否持续发送、消费者是否按版本幂等、ES/Neo4j 是否达到目标版本、缓存回源是否有并发上限、跨租户测试是否通过、P95/P99/lag/磁盘/连接池是否在预算内。若某项没有指标或回滚动作，就不能把“接口返回 200”当作系统完成。

## 8. 如何判断一个设计是否完整

面对任意新功能，沿以下顺序写设计：

1. **事实**：谁是唯一真相？需要哪些唯一键、状态和版本？
2. **读路径**：哪些查询需要索引、缓存、全文或图遍历？旧值能接受多久？
3. **写路径**：数据库、缓存、消息和投影的更新顺序是什么？
4. **异步**：消息至少一次还是可丢？如何 ACK、重试、死信和重放？
5. **并发**：用唯一约束、条件更新、锁还是队列串行化？锁过期后谁能阻止旧写？
6. **容量**：热点、大 key、分片、连接池、队列和下游限额在哪里？
7. **故障**：每个超时的结果是否未知？如何降级、补偿、对账和恢复？
8. **证据**：哪些指标、日志、trace、事件和版本能复盘一次请求？

如果其中任一项只能回答“出问题再看”，设计就还没有闭环。

## 9. 本章总结

- PostgreSQL 保存事实和不变量，Redis 加速和协调，消息队列承载异步，ES/Neo4j 保存可重建投影。
- 上传和 Agent 工具调用都必须把幂等、状态机、超时、重试和审计写进业务流程。
- 搜索可见、图投影、缓存回填都可能滞后；用版本和状态向用户表达最终一致，而不是伪装成同步成功。
- 多租户边界要贯穿数据库、key、消息、搜索、图查询和日志；删除要通过事件和对账完成。
- 跨组件契约要统一身份、schema、业务版本和状态迁移；长任务用租约/版本恢复，问答保留证据 trace 和引用。
- 可靠性不是组件数量，而是事实、投影、协调、观测和恢复之间的闭环。

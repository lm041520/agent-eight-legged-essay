# 03 消息队列：从异步任务到可靠事件流

> 适合对象：知道“把耗时任务丢到队列”能提高接口速度，但还不清楚消息怎样保存、确认、重试、去重和恢复的人。
>
> 学完目标：你能把消息队列放进一条完整的业务链，区分任务队列与事件流，理解生产、路由、分区、消费、确认和重平衡，能设计至少一次投递下的幂等处理，并能解释 Kafka、RabbitMQ、Redis Stream、Celery 在可靠性和运维上的差异。

## 0. 先看一次文档上传

用户上传文档后，解析、切块、向量化可能需要几十秒。接口不应一直等待，而是先保存任务，再把事件交给后台消费者：

```text
POST /documents
  ↓
PostgreSQL 写入 document(status='pending')
  ↓
发布 document.created
  ↓
HTTP 立即返回 document_id

队列中的消费者
  ↓
下载文件 → 解析 → 切块 → 向量化 → 更新状态
  ↓
失败则重试，超过次数进入死信并通知运维
```

这一条链里，消息队列解决的是时间解耦和流量缓冲，不是自动事务和自动幂等。必须继续追问：消息发布成功了吗？消费者处理完再确认还是先确认？任务失败能否重试？重复消息会不会重复扣费？

> **核心判断：** 消息队列把“现在必须完成的工作”变成“可持久化、可重试、可观察的消息”。它通常提供至少一次投递，因此业务消费者默认要能重复执行；真正的业务正确性来自事实源、幂等键、状态机和补偿。

## 1. 队列、任务和事件不是同一个概念

### 1.1 任务队列：请某个消费者做一次工作

任务有明确的执行者和结果，例如“解析 document 100”“发送一封邮件”。任务成功后通常不需要所有历史消费者重新读取。重点是并发控制、重试、超时和结果状态。

### 1.2 事件流：记录已经发生的事实

事件描述“document 100 已创建”，索引服务、计费服务、审计服务都可以各自消费。事件常需要保留一段时间，允许新消费者从历史位置重放。

### 1.3 通知：只要求尽力提醒

站内提示、缓存失效通知有时只需要尽力到达；丢一条不会破坏核心事实。通知可以使用轻量队列，但仍应为突发流量设置缓冲和过期策略。

把三者混成“都发到 Kafka”会导致保留、重试和消费语义不清。先写出消息的事实、接收者、保留时长和失败后果，再选择技术。

## 2. 一条消息怎样经过系统

```text
生产者序列化事件
  ↓
Broker 写入队列/分区并持久化
  ↓
路由到 exchange/queue 或 topic/partition
  ↓
消费者拉取或被推送
  ↓
业务处理事实源
  ↓
提交 offset / ACK
```

每一步都可能失败：生产者在发送后超时但 broker 已写入，消费者处理成功但 ACK 丢失，消费者处理到一半宕机，broker 副本落后后主节点损坏。因此不能用“接口返回成功”推断“消息只处理了一次”。

### 2.1 消息的最小字段

建议每条业务消息至少包含：

```json
{
  "message_id": "01J...",
  "event_type": "document.created",
  "schema_version": 1,
  "aggregate_id": "document:100",
  "occurred_at": "2026-08-07T10:00:00Z",
  "producer": "document-service",
  "trace_id": "trace-...",
  "payload": {"tenant_id": "acme", "document_id": 100}
}
```

`message_id` 用于幂等，`aggregate_id` 帮助保持同一业务对象的顺序，`schema_version` 支持演进，`trace_id` 用于跨服务排查。不要把整个数据库行无筛选地序列化进事件，事件应表达稳定的业务事实。

## 3. 生产端：消息“发出去”需要哪些确认

### 3.1 生产成功不只是调用发送 API

生产者可能经历：连接建立、序列化、网络发送、broker 写盘、副本确认、回调返回。需要明确确认级别：

- 只写入内存：延迟低，但 broker 宕机可能丢失；
- 主节点确认：主节点损坏时仍可能丢失；
- 副本确认：更可靠，但写入延迟和资源成本更高。

Kafka 常见配置会关注 `acks`、幂等生产者、重试和 `max.in.flight`；RabbitMQ 通过 publisher confirms 让生产者知道消息是否被 broker 接收。确认只表示 broker 接收，不表示消费者已经完成业务。

### 3.2 发送超时与重复消息

生产者发送后等待确认超时，有三种可能：消息没有写入、已经写入但确认丢失、broker 正在处理。简单重试可能产生两条消息。

因此消息必须有稳定 `message_id`，消费者或事实源需要用唯一键去重。生产者也应使用客户端幂等能力（如 Kafka idempotent producer），但客户端幂等不能替代业务幂等，因为重试可能跨进程、跨服务发生。

### 3.3 事务消息与 Outbox

最危险的代码是：

```text
UPDATE document SET status='pending'
send(document.created)
```

数据库提交成功而发送失败，会出现“事实有了，事件没有”；发送成功而数据库回滚，会出现“事件描述了不存在的事实”。

Outbox 模式把业务变更和待发送事件写进同一个数据库事务：

```text
BEGIN
  写 document
  写 outbox_event(message_id, payload, status='pending')
COMMIT

独立 relay 读取 outbox → 发布到 broker → 标记 sent
```

relay 可能重复发布，所以消费者仍需幂等；但它把“数据库事实与事件至少最终都出现”变成了可重试、可审计的流程。CDC 工具也可以从 outbox 表读取变更，减少业务代码直接发消息的耦合。

### 3.4 Broker 持久化与副本确认

“生产者收到确认”还要继续问确认覆盖了哪一层。以 Kafka 为例，leader 接收记录后，follower 复制并加入 ISR；`acks`、`min.insync.replicas` 和副本故障会共同决定消息能否被确认。leader 已确认但尚未被足够副本保存时，发生故障仍有丢失窗口；ISR 变小后继续写入也可能需要在可用性和持久性之间取舍。

Kafka 的 topic 数据副本和集群元数据不是同一个概念。现代 Kafka 使用 KRaft 元数据仲裁组管理 controller 元数据；它解决的是控制面选举和元数据存储，不会替业务消费者做幂等，也不会把数据库事务自动纳入消息事务。RabbitMQ 的 Quorum Queue 通过复制提高队列可用性，但生产确认、消费 ACK、死信和备份仍是不同边界。

排查“消息丢了”时应分别记录：生产者是否拿到 confirm、leader/副本的持久化状态、消费组的 offset/ACK、处理记录和死信。只看客户端返回值或只看 broker 存活都不足以证明业务事实已经完成。

## 4. 路由与顺序：谁应该在同一个队列里

### 4.1 RabbitMQ 的 exchange 与 queue

RabbitMQ 中生产者通常把消息发到 exchange，由 binding key 路由到一个或多个 queue：

```text
document.created ─┬─> indexing.queue
                  ├─> billing.queue
                  └─> audit.queue
```

每个 queue 有自己的消费进度和确认；同一个 queue 的多个消费者通常分摊任务。路由键适合表达明确的订阅关系，队列数量、绑定关系和消息积压需要运维管理。

### 4.2 Kafka 的 topic、partition 与 consumer group

Kafka topic 被切成多个 partition。消息在同一 partition 内按 offset 有序；同一个 consumer group 中，一个 partition 在同一时刻通常只由一个消费者处理。增加 partition 可以提高并行度，但会改变顺序和资源成本。

```text
topic=document-events
  partition-0: document:1, document:4, ...
  partition-1: document:2, document:5, ...
  partition-2: document:3, document:6, ...
```

要保持同一文档的事件顺序，应使用 `document_id` 作为 partition key；不能只依赖时间戳，因为不同分区没有全局顺序。

### 4.3 只在真正需要的范围内保证顺序

全局顺序会把吞吐压到一个消费者；按用户、订单或文档分区通常更合理。消费者内部若再开线程并发处理同一 aggregate，仍可能打乱顺序，需要按 key 串行或在数据库用版本号拒绝旧事件。

## 5. 消费端：确认、重试和重复执行

### 5.1 为什么至少一次是默认现实

消费者应在业务处理成功后确认：

```text
读取消息 → 写入事实源/调用下游 → 成功 → ACK/提交 offset
```

如果处理成功但 ACK 丢失，消息会再次投递；如果先 ACK 再写库，消费者宕机则消息已经从队列消失而事实没有落地。因此至少一次投递通常比至多一次更安全，代价是重复。

### 5.2 幂等的三种落点

1. **业务唯一键**：`INSERT ... ON CONFLICT (message_id) DO NOTHING`。
2. **处理记录表**：先记录 `message_id=processing`，成功后改为 `done`，重试时检查状态。
3. **状态机条件更新**：只有 `pending -> processing -> succeeded` 的合法转移能成功，重复消息更新影响行数为 0。

对于外部副作用（发邮件、扣款、调用第三方），还需要把幂等键传给下游，或在本地记录“已调用/结果”，不能只靠本地数据库去重。

### 5.3 重试要区分错误类型

- 短暂网络错误、限流、数据库连接失败：指数退避加随机抖动；
- 参数校验失败、资源永久不存在：不应无限重试，进入死信；
- 下游超时但结果未知：必须用幂等键查询或补偿，不能盲目重复扣费。

重试次数、退避上限、消息最大处理时长和死信保留时间都应可观测。重试本身会放大流量，不能把“失败就立即重试”当作可靠性方案。

### 5.4 死信不是垃圾桶

死信队列保存超过重试上限或被明确拒绝的消息。进入死信时应记录最终错误、原队列、重试次数、最后处理时间和 trace_id。修复代码后，可以按消息类型筛选、人工确认、重新投递；不能直接批量清空来“恢复正常”。

### 5.5 延迟重试与毒消息拓扑

立即把失败消息重新放回主队列，会让同一条毒消息在消费者之间高速循环，既占用并发又掩盖真正的失败。更可控的拓扑是：

```text
主队列 → retry-5s → retry-1m → retry-10m → 主队列
                         └─超过次数/永久错误→ DLQ
```

重试消息要携带 `attempt`、`next_retry_at`、原始 `message_id`、最近错误和代码版本。延迟队列不是业务定时器：消息可能重复、提前或晚到，消费者仍要检查任务是否取消、截止时间是否已过以及结果是否已完成。永久参数错误、权限错误和不可解析的 schema 应直接进入死信；临时网络错误、限流和下游过载才使用有限退避。

重放死信时按事件类型、租户和时间片限速，先做小批量校验，再逐步放量。重放也会再次触发业务副作用，所以必须沿用原幂等键或先查询处理记录，不能为了“清空 DLQ”生成新的业务身份。

## 6. Kafka、RabbitMQ、Redis Stream 和 Celery 的位置

| 组件 | 强项 | 需要额外设计的地方 |
|---|---|---|
| Kafka | 高吞吐、分区日志、长时间保留、重放、多消费组 | 分区规划、再均衡、顺序范围、offset 与幂等 |
| RabbitMQ | 灵活路由、确认、工作队列、延迟/死信生态 | 队列容量、镜像/Quorum、积压和路由拓扑 |
| Redis Stream | 已有 Redis 体系、轻量消费组和 Pending | 保留、主从切换、积压内存、复杂路由能力有限 |
| Celery | Python 任务编排、重试、定时任务、结果后端 | broker 与 worker 的可靠性、任务幂等、结果保留 |

Celery 是任务执行框架，不等于某一种 broker；它可以配 RabbitMQ、Redis 等。选择时先看消息需要保留多久、是否要回放、吞吐、路由复杂度、团队运维能力，再决定组件。

## 7. 消费者并发、背压与积压

### 7.1 并发不是越大越好

消费者并发受三类资源约束：CPU、外部连接（数据库/HTTP）和消息处理内存。并发开太大，队列消费速度看似提高，却会把数据库连接池打满，导致整个系统变慢。

应为每类任务设置并发上限和舱壁：解析任务、向量化任务、通知任务不要共用一个无限扩张的 worker 池。

### 7.2 背压的含义

当下游处理不过来时，系统应降低生产速度或让消息在 broker 暂存，而不是继续堆内存。可用的手段包括：生产端限流、消费者预取上限、最大未确认数、队列长度阈值、暂停低优先级任务。

背压应能传回业务层。例如向量化队列积压时，上传接口仍可保存文档，但把状态显示为 `queued`，而不是同步等待或无限接受任务。

### 7.3 用滞后量判断系统是否健康

Kafka 看 consumer lag，RabbitMQ 看 ready/unacked 数量，Redis Stream 看 last-delivered 与 pending。只看“消费者进程还活着”是不够的；进程可能心跳正常但每条消息都在超时重试。

容量评估可以从处理时间估算：若平均每条任务 200 ms、单 worker 并发 20，则理论吞吐约 100 条/秒；还要扣除外部调用、重试和峰值余量。

## 8. 消息与数据库的一致性

### 8.1 先写库还是先发消息

没有 Outbox 时，两种顺序都有故障窗口：

```text
先发后写：消息已消费，但数据库写入失败
先写后发：数据库已提交，但消息发布失败
```

Outbox、CDC 或支持跨资源事务的系统可以缩小窗口；跨服务通常更实际的是“本地事务 + 可重试发布 + 幂等消费 + 对账补偿”，而不是强行做一个跨数据库和 broker 的大事务。

### 8.2 事件与当前状态的关系

事件记录发生过什么，状态表记录现在是什么。消费者重放历史事件时，不能假设当前状态仍处于初始值；应使用事件版本、时间或幂等状态机保证旧事件不会覆盖新状态。

例如：

```sql
UPDATE document
SET status = :new_status, version = :event_version
WHERE id = :id AND version < :event_version;
```

### 8.3 事件 schema 演进

新增字段通常向后兼容；删除或改变字段含义会破坏旧消费者。生产者应保留 schema version，消费者对未知字段容忍、对必需字段校验，并制定旧版本下线时间。事件一旦被多个服务依赖，修改成本高于内部函数参数。

## 9. 定时任务、延迟和顺序补偿

消息队列不一定擅长精确延迟。常见方案有：

- RabbitMQ TTL + dead-letter：适合有限档位的延迟；
- Kafka 中保存 `due_at`，消费者轮询到期消息；
- Redis Sorted Set 作为时间索引，真正任务仍进入可靠队列；
- 专门的调度服务负责扫描数据库任务表。

无论哪种方案，任务执行都必须再次检查截止时间、取消状态和幂等键。延迟消息可能重复、提前或晚到，不能把“到点投递”当成业务状态的唯一保证。

## 10. 可观测性与故障处理

每条消息应能通过 `message_id`、`aggregate_id`、`trace_id` 查到：生产时间、broker 接收时间、消费开始、处理结束、重试次数和最终状态。

建议监控以下关系而不是孤立数值：

```text
生产速率  ↔  消费速率  ↔  积压/lag
处理耗时  ↔  ACK 延迟  ↔  重试率
失败类型  ↔  死信数量  ↔  下游错误
```

排查积压时先判断生产变快、消费变慢、broker 限制还是下游故障；排查重复时查看 ACK/offset 提交时点和幂等记录；排查丢消息时检查 producer confirm、broker 副本、消费提交和死信转移。

## 11. 一个完整的文档索引任务

把前面的概念合起来，可以设计如下链路：

1. API 在数据库事务中写 `document` 和 Outbox 事件。
2. relay 发布 `document.created`，消息带 `message_id` 和 `document_id`。
3. 索引消费者按 `document_id` 分区，读取文件并生成向量。
4. 消费者先用处理记录表做幂等，再更新 `index_status`，最后提交 offset。
5. 临时错误指数退避，永久解析错误进入死信；重试和死信都带 trace_id。
6. 搜索服务只把 `index_status='ready'` 的文档暴露给用户；重放事件不会覆盖更高版本的状态。

这里没有承诺“消息只消费一次”，但通过事实源、幂等、版本和补偿，重复、延迟、乱序都不会破坏最终状态。

## 12. 本章总结

- 先区分任务队列、事件流和尽力通知，再选择组件。
- 生产确认、消费者确认和业务完成是三件事；至少一次投递意味着必须处理重复。
- 顺序只在队列、partition 或业务 key 的范围内成立，全局顺序代价很高。
- Producer confirm、Kafka ISR/KRaft、RabbitMQ Quorum Queue 分别属于不同的持久化与控制面边界。
- Outbox 解决数据库事实与事件发布的可靠衔接，消费者幂等仍不可省。
- 重试要区分临时错误和永久错误，延迟拓扑和死信要可查询、可修复、可重新投递。
- 背压、并发上限和积压监控保护下游；消费者“活着”不等于系统健康。
- Kafka、RabbitMQ、Redis Stream、Celery 的语义不同，不能只按流行度选择。

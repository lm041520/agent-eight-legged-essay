# 06 分布式可靠性：让失败可控、结果可恢复

> 适合对象：能把服务拆成多个组件，但还不知道超时、重试、幂等、熔断、限流、补偿和可观测性应如何组合的人。
>
> 学完目标：你能从一次跨服务请求画出失败边界，能为数据库、缓存、消息队列和第三方 API 设计超时与重试，能区分强一致与最终一致，能用 Outbox、Saga、幂等键和状态机处理重复与部分成功，并能建立从指标到日志、追踪和恢复的可靠性闭环。

## 0. 分布式系统为什么会“各自成功、整体失败”

知识库的“上传并可搜索”可能经过：

```text
API → PostgreSQL → Outbox → 消息队列 → 解析服务
                                      ↓
                                embedding 服务
                                      ↓
                         Elasticsearch / Neo4j
```

每个组件都可能单独返回成功，但整体仍可能失败：数据库提交后进程宕机、消息重复、向量服务超时但已完成、搜索索引落后、网络分区导致读取旧值。可靠性不是“某个组件可用率很高”，而是失败发生后，系统能否停止扩大损失、保留事实、自动恢复或明确告诉用户当前状态。

> **核心判断：** 分布式可靠性建立在四个动作上：给每个边界设定时间和容量，给每个副作用提供幂等身份，给每个异步状态提供可恢复记录，给每次失败提供可观测证据和补偿路径。

## 1. 先定义“成功”与不变量

### 1.1 用户看到的成功分层

上传接口可以把成功分成：

1. 文件已保存；
2. 文档记录已提交；
3. 解析任务已排队；
4. 搜索索引已可见；
5. 图关系和向量都已更新。

如果接口只负责第 1～3 步，应返回 `status=processing`，而不是假装全文搜索已经完成。状态机把“最终一致的过程”公开成可查询事实，避免用户把暂时不可搜误判为数据丢失。

### 1.2 不变量比组件名称重要

写下不能被破坏的事实，例如：

- 同一个租户不能看到另一个租户的文档；
- 同一个幂等键最多产生一个业务结果；
- 已支付订单不能回到未支付；
- 已删除版本不能被旧事件重新激活；
- 消费者失败不能让消息既丢失又无法追踪。

后续每个超时、重试和缓存策略都要检查是否会破坏这些不变量。

## 2. 超时：为等待设置边界

### 2.1 超时必须逐层递减

假设 API 总预算 2 秒：

```text
API 2000ms
  ├─ DB 300ms
  ├─ Redis 80ms
  ├─ 内部 HTTP 500ms
  └─ 预留序列化、重试和返回时间
```

下游超时大于上游，多个服务会叠加等待，最终线程/协程和连接池全部被占用。连接建立、读取、写入和整个请求都应有不同的边界；没有超时的 HTTP、数据库和 Redis 客户端等同于把故障交给资源耗尽。

### 2.2 超时后的结果是“未知”

调用第三方支付超时，不代表支付没有发生；写消息确认超时，不代表消息没有写入。超时处理应分为：查询状态、使用幂等键重试、进入人工/补偿队列，而不是简单返回失败并让用户再次扣款。

## 3. 重试：只重试可恢复的失败

### 3.1 指数退避与抖动

常用等待时间是 `min(max_delay, base * 2^attempt) + random_jitter`。退避避免故障时所有客户端同时重试；上限防止请求等待过久。重试次数要计入总预算，不能每一层都各自重试三次，形成乘法放大。

### 3.2 错误分类

| 错误 | 典型处理 |
|---|---|
| 连接短暂失败、503、429 | 有限重试 + 退避，遵守 Retry-After |
| 参数校验失败、权限拒绝 | 立即返回，不重试 |
| 数据库死锁 | 短暂重试，但限制次数并记录 SQL/事务 |
| 读超时但写入结果未知 | 查询幂等结果或对账，不盲目重写 |
| 下游持续不可用 | 熔断、降级、排队或人工处理 |

重试前先确认操作是否幂等。`GET` 通常更容易安全重试；`POST` 创建资源必须携带幂等键或使用可重复的业务状态转移。

### 3.3 防止重试风暴

重试应有全局并发上限、每个下游的舱壁和熔断状态。客户端、网关、消息消费者、任务框架不要同时对同一个错误重试；统一由最接近事实源的一层负责有限重试，其余层快速失败或排队。

### 3.4 重试预算如何落到请求链

一次用户请求的总预算应先分给“完成一次业务结果”所需的所有边界，再决定每个边界最多重试几次。例如总预算 2 秒、单次下游调用 300 ms 时，不能让 API、SDK 和消费者各自重试三次；应指定一个责任层，给它总尝试次数、最大等待和并发上限，其余层只传递失败或查询已有结果。消息任务则把预算转换成 `attempt`、`next_retry_at` 和最大存活时间，超过后进入人工/死信而不是无限延期。

重试指标要同时看“尝试次数”和“业务成功数”。如果成功率看似稳定但每个成功请求平均尝试数上升，说明下游已在退化；这时应先降级、限流或熔断，不能继续加重试。

## 4. 幂等：重复请求得到同一个业务结果

### 4.1 幂等键的生命周期

客户端为一次业务意图生成 `idempotency_key`，服务端在事实源记录：

```sql
CREATE TABLE idempotency_record (
    tenant_id       BIGINT NOT NULL,
    idempotency_key VARCHAR(100) NOT NULL,
    request_hash    CHAR(64) NOT NULL,
    status          VARCHAR(20) NOT NULL,
    response_json   JSON,
    created_at      TIMESTAMP NOT NULL,
    PRIMARY KEY (tenant_id, idempotency_key)
);
```

收到相同 key 时，若请求摘要不同，应返回冲突；若已成功，返回保存的结果；若仍处理中，返回处理中状态或让客户端轮询。幂等记录需要保留多久取决于业务重试窗口，不能无限增长。

### 4.2 消费者幂等

消息 `message_id` 可作为处理记录的唯一键。正确顺序通常是：

```text
开启本地事务
  检查/写入 message_id
  更新业务事实
  写出站事件或处理结果
提交
成功后 ACK
```

如果进程在提交后 ACK 前宕机，消息会再来，但唯一键让第二次成为无操作；如果 ACK 前业务失败，事务回滚，消息可重试。

### 4.3 幂等不等于无副作用

记录“已经调用过第三方”不一定能知道第一次调用结果。对支付、邮件、文件上传等副作用，应使用下游支持的幂等键、查询接口或本地 Outbox + 对账任务，不能只把请求 hash 存在 Redis。

## 5. 一致性：把跨组件变化拆成可恢复步骤

### 5.1 强一致、读己之写与最终一致

- **强一致**：提交后所有读者立即看到同一事实，成本和可用性约束更高；
- **读己之写**：发起写入的用户必须看到自己的最新状态，可通过读主、版本号或会话粘滞实现；
- **最终一致**：搜索索引、推荐和图投影允许短暂落后，但最终应达到指定版本。

不要只说“最终一致”，要给出最大延迟、失败补偿和用户展示状态。

### 5.2 Outbox：本地事务 + 可重试发布

数据库事务同时写业务表和 outbox；relay 发布成功后标记发送。relay 崩溃会重复发布，消费者按 message_id 幂等。Outbox 不消除失败，而是把不可见的丢事件变成可查询的待发送记录。

### 5.3 Saga：跨服务长事务的补偿

订单、库存、支付各自提交本地事务，后续步骤失败时执行补偿动作：

```text
创建订单 → 预扣库存 → 发起支付
    ↘ 支付失败 → 释放库存 → 订单取消
```

补偿不是数据库回滚；外部副作用可能无法完全撤销，必须设计状态机、超时和人工处理。每一步要有唯一业务 ID 和可重放事件。

## 6. 熔断、降级、限流和舱壁

### 6.1 熔断器

连续超时或错误超过阈值后进入 open，短时间内快速失败；经过等待进入 half-open，放少量探测请求。熔断保护调用方线程和连接池，不修复下游本身；恢复后要逐步放量。

### 6.2 降级要保留核心不变量

缓存故障时，知识库可以显示数据库中的最近文档；搜索故障时，可以返回文档列表或提示索引处理中；推荐故障时，不应阻塞核心上传。降级结果必须标注时效和权限，不能用未经授权的旧缓存代替新数据。

### 6.3 限流与舱壁

限流应按租户、用户、接口和资源区分；全局 token bucket 只能保护总入口，不能防止一个租户占满所有 embedding worker。舱壁把数据库连接、HTTP 连接、队列消费者和线程池隔离，某个下游故障不会拖垮所有业务。

收到上游限流时返回 429，并带 `Retry-After`；异步入口可以接受任务后排队，而不是让客户端同步重试。

### 6.4 熔断状态与恢复放量

熔断至少要能区分 closed、open、half-open 三种状态，并按下游、租户和接口记录失败率、超时率、拒绝数和探测成功率。open 期间快速失败或进入可靠队列，half-open 只放少量、可取消且幂等的探测；探测成功后逐步放量，不能一次恢复全部流量。熔断阈值还要避开低流量误判，可同时使用最小请求数、时间窗口和错误分类。

降级结果要标明来源和时间：旧缓存、数据库列表、排队状态与完整搜索结果不能使用同一个 `200/ready` 语义。恢复时先处理积压和缓存预热的并发上限，再逐渐开放非核心能力，避免“恢复动作”本身造成第二次雪崩。

## 7. 数据库、缓存和消息的协同

### 7.1 事实源优先

订单状态、余额、权限和幂等记录优先落在具有约束和事务的数据库。Redis 缓存只能加速读取或协调短期任务；消息队列传播变化，但不能作为唯一当前状态，除非系统明确采用事件溯源并具备重放与快照。

### 7.2 更新顺序和失效

常见 Cache Aside 方式是提交数据库后删除缓存；删除失败通过失效事件和重试补偿。缓存值带版本，读请求可拒绝低于所需版本的旧值。不要先写缓存再写库，除非能解释缓存如何回滚和处理并发覆盖。

### 7.3 事件顺序与旧写保护

消费者用 aggregate version 判断事件是否过期：

```sql
UPDATE document
SET status = :status, version = :event_version
WHERE id = :id AND version < :event_version;
```

重复和乱序都变成安全的无操作或重试，而不是靠“消息大概率按顺序到达”。

## 8. 可观测性：让一次失败能被复盘

### 8.1 三种信号连在一起

- **指标**：延迟、错误率、吞吐、队列 lag、缓存命中率、数据库连接、重试和熔断状态；
- **日志**：结构化记录 request_id、trace_id、tenant_id、message_id、版本、错误分类；
- **追踪**：把 HTTP、SQL、Redis、消息生产/消费、外部 API 放到一条 trace 中。

只看平均延迟会掩盖 p99；只看错误率会忽略大量超时后成功的请求；只看日志无法回答“积压是否正在扩大”。应把生产速率、处理速率和积压画在同一时间线上。

### 8.2 日志要能回答四个问题

1. 哪个租户、哪个业务对象受影响？
2. 失败发生在哪个边界，是否已经重试？
3. 第一次副作用到底有没有成功，结果是否未知？
4. 后续补偿、重放或人工处理有没有完成？

不要记录密码、token、完整文档和用户隐私；对 message payload 使用摘要和可追踪的存储引用。

### 8.3 SLO、错误预算与告警

可观测性要连接到可执行的服务目标。例如为“上传后 5 分钟内达到 ready”“搜索 P99”“Outbox pending age”“跨租户拒绝数”分别定义 SLI/SLO；错误预算耗尽时暂停低优先级重建、降低发布频率或提高审计级别，而不是只发一条告警。阈值应同时考虑绝对值和趋势：lag 还未很大但连续增长，也应提前告警。

告警必须指向动作和责任边界：数据库锁等待对应终止/限流 runbook，消息 pending 对应 relay/ broker 检查，索引 ready 下降对应投影重放和对账。没有负责人、证据链接和回滚步骤的告警只会增加噪声。

## 9. 部署、优雅退出与配置

服务收到终止信号后应停止接收新请求、让正在处理的请求在预算内完成、停止拉取新消息、确认已完成消息，再关闭数据库和 Redis 连接。直接杀进程会制造大量重复、半完成状态和连接泄漏。

超时、重试、批大小、并发、熔断阈值应配置化且有默认上限；发布新配置时记录版本，避免“某次性能下降但不知道当时用了什么参数”。多实例启动任务调度器时要使用租约或分布式选主，不能靠“通常只有一个副本”。

## 10. 备份、恢复与灾难演练

### 10.1 RPO 与 RTO

- RPO：故障后最多允许丢失多长时间的数据；
- RTO：从故障开始到恢复服务需要多长时间。

数据库 WAL/归档、Redis RDB/AOF、Elasticsearch 快照、消息保留和 Outbox 保留期应一起设计。只配置备份而不测试恢复，无法证明 RPO/RTO。

### 10.2 恢复顺序

通常先恢复事实源和身份/权限，再恢复消息与 Outbox，最后重建缓存、搜索和图投影。可重建投影不应成为恢复的唯一入口；重放过程要限速，避免恢复流量压垮在线业务。

### 10.3 数据校验

恢复后校验文档数、版本最大值、事件缺口、索引 ready 数和权限边界。对账任务应能列出“数据库有而索引没有”“Outbox 长期 pending”“消息处理记录与事实状态不一致”的对象，并支持安全重放。

### 10.4 恢复演练的最小闭环

演练不能只验证“备份文件存在”。应记录故障时间点和预期 RPO/RTO，按事实源、Outbox/消息、搜索与图投影、缓存的顺序恢复，并在每一步校验：唯一键是否仍成立、版本是否单调、权限边界是否完整、重复重放是否幂等。演练后保留实际恢复耗时、丢失窗口、人工步骤和未覆盖的依赖，更新 runbook 与告警，而不是只写“演练成功”。

## 11. 综合故障推演

### 11.1 embedding 服务超时

先判断请求是否已经生成向量；若结果未知，用 request_id 查询或让任务进入重试，而不是立即生成第二份收费向量。消费者保持 `embedding_pending`，重试有限；连续失败触发熔断，队列积压告警，用户看到“处理中”。

### 11.2 搜索集群不可用

数据库和 Outbox 仍接收文档，索引任务留在可靠队列；API 返回文档已保存但搜索延迟。恢复后按版本重放，旧事件不能覆盖新删除，回填过程设置并发和磁盘水位。

### 11.3 Redis 整体故障

缓存请求快速失败并熔断，回源数据库受并发上限保护；非核心排行榜暂时关闭，事实状态继续写数据库。Redis 恢复后异步预热，而不是让所有请求同时回源。

## 12. 本章总结

- 先定义成功分层和不变量，再选择一致性与降级策略。
- 每个外部调用都有连接、读取和总时限；重试必须有限、退避、分类并避免风暴。
- 重试要有总预算和责任层，熔断恢复要分阶段放量；SLO/错误预算要能触发降级或暂停低优先级任务。
- 幂等键、唯一约束、状态机和版本条件共同处理超时、重复和乱序。
- Outbox 把数据库事实与事件发布接成可恢复链路，Saga 用补偿处理跨服务长事务。
- 熔断、限流、舱壁和背压保护资源；降级不能突破权限或事实约束。
- 指标、日志和追踪要能串起一条业务对象的全生命周期，备份必须配合恢复演练和对账。
- 恢复演练要验证版本、权限、幂等和实际 RPO/RTO，而不是只确认备份文件存在。

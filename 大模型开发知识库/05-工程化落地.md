# 05 工程化落地

> 定位：把Agent/RAG算法原型变成可供多用户稳定使用、可扩展、可监控、可回滚的服务。

### 学习优先级地图

- **P0：必须掌握**——FastAPI、HTTP/SSE、API契约、数据库事务、SQLAlchemy Session、Redis基础、超时/重试/幂等、鉴权、日志与配置管理。
- **P1：需要实践**——Celery/消息队列、连接池、限流/熔断、OpenTelemetry与指标、Docker、CI/CD、Kubernetes基础和完整Agent后端。
- **P2：方向了解**——复杂服务网格、多集群容灾、平台级调度和大规模多租户治理；后端/平台岗位继续深入。

应用岗先保证单服务正确、可测试、可观测，再引入异步队列、容器编排和分布式组件。

## 零基础导读：一个能运行的Agent函数，怎样变成多人可用的服务

本地演示通常从下面两行开始：

```python
answer = await agent.invoke("总结这份合同")
print(answer)
```

它可以证明Agent逻辑能运行，但不能直接给真实用户使用。假设两个用户同时上传合同，生产系统必须回答很多新问题：

- 文件属于谁，另一个用户能不能看到？
- 请求突然中断，任务要不要继续？
- 合同解析需要5分钟，HTTP连接是否一直保持？
- 同一个请求被重试两次，会不会重复扣费和建两份任务？
- 模型服务超时后重试多少次？
- 当前系统有多少任务排队，哪一步最慢？

工程化就是把“算法可以运行”补成“系统可以长期可靠运行”。

### 场景：用户提交一份合同分析任务

前端发送：

```http
POST /v1/contract-analysis
Authorization: Bearer <token>
Idempotency-Key: request-8f31
Content-Type: application/json

{
  "file_id": "file_123",
  "questions": ["合同金额是多少？", "有哪些违约风险？"]
}
```

下面逐层解释请求会怎样流动。

### 第1层：API层接住外部请求

FastAPI路由负责HTTP协议相关工作：读取身份、校验JSON、限制请求大小，并把合法数据交给应用服务。

```python
from fastapi import APIRouter, Depends, Header, status
from pydantic import BaseModel, Field

router = APIRouter()


class AnalysisRequest(BaseModel):
    file_id: str = Field(min_length=1)
    questions: list[str] = Field(min_length=1, max_length=20)


@router.post("/v1/contract-analysis", status_code=status.HTTP_202_ACCEPTED)
async def create_analysis(
    request: AnalysisRequest,
    idempotency_key: str = Header(alias="Idempotency-Key"),
    user: User = Depends(current_user),
):
    return await analysis_service.create_task(
        user=user,
        request=request,
        idempotency_key=idempotency_key,
    )
```

为什么路由不直接写几十行数据库和Agent逻辑？因为HTTP输入输出只是系统边界之一。把核心逻辑放进Service，之后定时任务、命令行和测试也可以复用。

### 第2层：应用服务编排业务规则

Service会检查：文件是否存在、是否属于当前用户、幂等键是否已经处理，以及任务应该同步执行还是进入队列。

```python
async def create_task(user, request, idempotency_key):
    existing = await task_repo.find_by_idempotency_key(
        user_id=user.id,
        key=idempotency_key,
    )
    if existing:
        return existing

    file = await file_repo.get(request.file_id)
    if not file or file.owner_id != user.id:
        raise FileNotFoundError("文件不存在或无权访问")

    task = await task_repo.create_pending(...)
    await task_queue.enqueue(task.id)
    return {"task_id": task.id, "status": "pending"}
```

`Idempotency-Key`解决的是重复请求问题。移动网络超时后，客户端可能不知道服务器是否已经创建任务，于是重发。相同用户和幂等键应返回同一个任务，而不是重复执行。

### 第3层：数据库保存需要持久存在的事实

任务状态不能只放在Python变量里，因为进程重启后变量会消失。数据库可以保存：

```text
task_id、user_id、file_id、status、progress
创建时间、开始时间、结束时间、错误码
使用的模型版本、Prompt版本和结果位置
```

创建任务和写入关键业务记录通常需要事务。事务保证一组操作要么一起成功，要么一起回滚。例如任务记录创建成功但Outbox事件没写入，可能导致任务永远不被队列消费。

### 第4层：为什么长任务要进入消息队列

合同解析、OCR、RAG和模型生成可能持续几分钟。如果API路由一直等待：

- 反向代理或客户端可能超时；
- 服务进程被长请求占住；
- 失败后难以从中间步骤恢复；
- 无法按任务类型控制并发。

更常见的方式是：API快速返回`202 Accepted + task_id`，Worker从Celery等队列取出任务执行。

```text
API创建任务 → Broker保存消息 → Worker领取 → 执行 → 更新数据库
```

队列不是让任务本身计算得更快，而是把“接收请求”和“执行耗时工作”解耦。

### 第5层：Redis在这里能做什么

Redis可能承担：

- 缓存短期可复用的模型或检索结果；
- 保存会话状态或进度快照；
- 维护限流计数；
- 用Stream传递进度事件；
- 实现短期去重键。

但Redis不是“看到性能问题就加一层”。缓存必须回答：键是什么、多久过期、数据更新后怎样失效、是否包含租户和版本。

例如下面的缓存键不安全：

```text
analysis:file_123
```

更完整的键可能包含：

```text
analysis:{tenant_id}:{file_hash}:{model_version}:{prompt_version}
```

否则不同租户或不同版本可能错误复用结果。

### 第6层：怎样把进度返回给用户

如果只是服务端持续向浏览器发送状态，SSE通常比WebSocket简单：

```text
event: progress
data: {"task_id":"t1","stage":"ocr","percent":35}

event: progress
data: {"task_id":"t1","stage":"rag","percent":70}

event: completed
data: {"task_id":"t1","result_url":"..."}
```

如果代理层开启缓冲，即使后端已经`yield`数据，前端仍可能很久后一次性收到。因此排查流式问题要同时检查应用、Web服务器、反向代理和客户端。

### 第7层：外部依赖失败怎么办

假设模型接口超时，可以重试，但不能无条件重试所有错误：

```text
网络瞬断、429、部分5xx：通常可在退避后重试
401密钥错误、参数400：重试不会自行恢复
扣费、发消息等有副作用操作：重试前必须保证幂等
```

指数退避可以是1秒、2秒、4秒，并加随机抖动，避免大量Worker同时恢复后形成重试风暴。

### 第8层：怎样知道系统慢在哪里

一次请求的Trace可以这样展开：

```text
POST /contract-analysis       120ms
└─ auth                       8ms
└─ database.create_task       24ms
└─ queue.publish              16ms

worker.execute              48.2s
├─ download_file              0.8s
├─ parse_and_ocr             12.4s
├─ retrieve                   0.7s
└─ llm_generate              34.1s
```

没有Trace时只能说“系统大概是模型慢”；有了分层耗时，才能确认瓶颈在OCR还是生成。

### 第9层：容器和Kubernetes解决什么

Docker把应用代码、运行时和依赖封装成可重复部署的镜像；Kubernetes负责运行多个副本、健康检查、滚动更新和资源调度。它们不会自动修复错误事务和无限重试，工程逻辑正确仍是前提。

### 把完整架构串起来

```text
浏览器
  ↓ HTTPS
API Gateway：鉴权、限流、请求大小
  ↓
FastAPI：参数校验和API契约
  ↓
Application Service：权限、幂等、业务编排
  ├─ PostgreSQL：任务和业务事实
  ├─ Redis：缓存、限流、短期状态
  └─ Celery/Broker：长任务排队
          ↓
        Worker：OCR → RAG → Agent → LLM
          ↓
日志 + Metrics + Trace + 告警
```

后面的FastAPI、SQL、Redis、Celery、可靠性和部署章节，都是在放大这张图中的一个局部。

## 一、原型和生产系统的差别

原型可能是：

```python
answer = agent.invoke(user_input)
print(answer)
```

生产系统还必须处理：

- API契约和鉴权；
- 多用户和多租户；
- 数据库事务；
- 缓存和状态；
- 长任务和消息队列；
- 超时、重试、幂等、限流和熔断；
- 流式输出和客户端断开；
- 日志、Trace、指标和告警；
- 配置、Secret、部署、扩缩容和回滚；
- 数据迁移和版本兼容。

### 推荐分层

```text
API/Controller
→ Application Service
→ Agent/RAG Orchestration
→ Domain/Policy
→ Repository/External Client
→ Database、Redis、Model、Vector DB、MCP
```

API层不应直接堆满模型调用、SQL和重试；Agent节点也不应自行创建数据库连接和读取全局密钥。

# 第一章 FastAPI服务

## 1.1 请求处理链

```text
客户端
→ 反向代理/网关
→ ASGI Server
→ Middleware
→ Route
→ Dependency
→ Pydantic校验
→ Application Service
→ Response/Stream
```

理解链路有助于决定鉴权、请求ID、日志、异常和限流放在哪里。

## 1.2 路由和参数

```python
from fastapi import FastAPI, Query
from pydantic import BaseModel, Field

app = FastAPI()

class ChatRequest(BaseModel):
    session_id: str = Field(min_length=1)
    message: str = Field(min_length=1, max_length=20_000)

class ChatResponse(BaseModel):
    request_id: str
    answer: str

@app.post("/v1/chat", response_model=ChatResponse)
async def chat(payload: ChatRequest, debug: bool = Query(False)) -> ChatResponse:
    ...
```

- Path：资源标识；
- Query：筛选、分页和可选控制；
- Body：复杂输入；
- Header：鉴权、追踪和协议元数据；
- Response Model：约束输出并生成OpenAPI。

## 1.3 依赖注入

适合提供：

- 当前用户；
- 数据库Session；
- 租户上下文；
- 服务对象；
- 权限检查。

```python
from dataclasses import dataclass
from fastapi import Depends, Header, HTTPException

@dataclass(frozen=True)
class UserContext:
    user_id: str
    tenant_id: str

async def get_user_context(authorization: str = Header()) -> UserContext:
    user = await verify_token(authorization)
    if user is None:
        raise HTTPException(status_code=401, detail="invalid credentials")
    return user
```

身份来自服务端验证，不允许模型或请求Body自由指定可信`user_id`。

## 1.4 Middleware

适合处理跨路由关注点：

- Request ID；
- 访问日志；
- CORS；
- Trace上下文；
- 基础安全Header；
- 全局请求时限。

Middleware不适合塞入复杂业务和需要读取完整流式Body的重逻辑，否则增加所有请求延迟并使异常难定位。

## 1.5 全局异常处理

内部异常映射为稳定API错误：

```text
ValidationError → 422
Unauthenticated → 401
Forbidden → 403
NotFound → 404
Conflict → 409
RateLimited → 429
DependencyUnavailable → 503
UnexpectedError → 500
```

用户响应返回安全信息和Request ID；服务日志保留完整异常链。不要对所有异常返回200和`{"success":false}`，否则网关、监控和客户端难以正确处理。

## 1.6 Lifespan

应用级资源应在启动时创建、关闭时释放：

```python
from contextlib import asynccontextmanager
import httpx
from fastapi import FastAPI

@asynccontextmanager
async def lifespan(app: FastAPI):
    app.state.http_client = httpx.AsyncClient()
    app.state.model_client = build_model_client()
    yield
    await app.state.http_client.aclose()
    await app.state.model_client.aclose()

app = FastAPI(lifespan=lifespan)
```

当前FastAPI官方推荐使用`lifespan`管理启动和关闭资源。适合HTTP连接池、数据库Engine、共享模型客户端和本地模型加载。不要每次请求重新加载模型或创建完整连接池。

## 1.7 SSE与StreamingResponse

```python
import json
from collections.abc import AsyncIterator
from fastapi.responses import StreamingResponse

async def event_stream() -> AsyncIterator[str]:
    try:
        async for token in agent.stream():
            data = json.dumps({"type": "token", "text": token}, ensure_ascii=False)
            yield f"event: token\ndata: {data}\n\n"
        yield "event: done\ndata: {}\n\n"
    except Exception:
        error = json.dumps({"code": "STREAM_FAILED"})
        yield f"event: error\ndata: {error}\n\n"

@app.get("/v1/chat/stream")
async def stream_chat() -> StreamingResponse:
    return StreamingResponse(event_stream(), media_type="text/event-stream")
```

要处理：

- 客户端断开和任务取消；
- 心跳；
- 代理缓冲；
- 流开始后无法再改变HTTP状态码；
- 错误应变成协议内事件；
- 输出背压；
- 敏感Trace不要直接发送。

## 1.8 WebSocket

适合语音、多模态实时输入和双向控制。需要管理连接、认证、心跳、消息协议、并发发送、断线重连和服务多实例下的会话路由。

它和SSE的关键区别不是“谁更高级”，而是通信方向：

```text
SSE：建立连接后主要由服务器持续推送，客户端仍通过普通HTTP提交操作
WebSocket：同一条长连接中，客户端和服务器都可以随时发送消息
```

语音Agent可能一边上传音频片段，一边接收转写、模型Token和合成语音，这种双向实时流更适合WebSocket。普通文本回答只有服务器向前端持续输出时，SSE往往更简单，也更容易经过现有HTTP基础设施。

WebSocket连接建立后仍需对每条消息设计Schema，例如`audio_chunk`、`cancel`、`tool_approval`和`heartbeat`，不能把任意JSON直接交给Agent。

## 1.9 BackgroundTasks的边界

FastAPI进程内Background Task适合短、低风险、无需可靠重试的操作。长时间文档解析、Embedding和训练任务应交给可靠任务队列。进程崩溃时，进程内任务可能丢失。

例如“响应返回后异步写一条非关键访问日志”可以使用进程内任务；“上传PDF后进行20分钟OCR并把结果交付用户”不适合。部署滚动更新、进程OOM或机器重启都会让后者中断，而且没有Broker帮助重新投递。

判断问题可以问三句：

1. 任务丢失是否可接受？
2. 是否需要跨进程扩并发、重试和查看状态？
3. 任务是否包含重要副作用或运行时间较长？

任一答案偏向可靠性，就使用业务数据库加任务队列，而不是仅依赖`BackgroundTasks`。

## 1.10 OpenAPI和版本

- 为请求、响应和错误建立Schema；
- API路径或Header管理版本；
- 字段新增尽量向后兼容；
- 删除/重命名需要弃用周期；
- 客户端SDK和文档来自同一OpenAPI；
- 流式协议同样需要版本和事件Schema。

## 1.11 第一章故障排查

### 异步路由吞吐低

检查是否调用同步SDK、使用`time.sleep`、每次创建Client、连接池太小、数据库Session误共享或CPU工作阻塞事件循环。

### SSE一直不出Token

检查生成器是否逐块yield、代理是否缓冲、事件是否双换行、压缩是否合并、客户端是否流式读取。

### 服务关闭卡住

检查后台Task、未关闭Client、数据库连接、流式请求和取消异常是否被吞。

## 1.12 第一章复习卡

- 一句话：FastAPI负责HTTP边界和资源生命周期，业务、Agent和存储逻辑应分层。
- 五个关键词：Route、Dependency、Middleware、Lifespan、Streaming。

# 第二章 MCP服务工程化

## 2.1 工程边界

MCP Server应把外部能力封装为稳定协议边界，而不是简单把所有内部函数直接暴露。每个Tool需要：

- 清晰Schema；
- 用户和租户权限；
- 输入限制；
- 超时和取消；
- 幂等和副作用等级；
- 安全错误；
- 审计；
- 版本兼容。

## 2.2 Host、Client和Server生命周期

- Host管理用户、模型、审批和多个Client；
- Client维护与Server连接、能力发现和调用关联；
- Server管理工具实现和资源访问。

不要假设Server状态与用户会话天然隔离。远程多用户Server必须显式认证和授权；本地stdio Server也需要限制进程环境和文件权限。

## 2.3 工具发现与缓存

能力列表可缓存，但要考虑：

- Server版本变化；
- 用户权限变化；
- 动态工具；
- Schema失效；
- 连接重建；
- 缓存过期。

发现到工具不代表当前用户可调用，Host还需按策略过滤后再交给模型。

## 2.4 错误和取消

区分：

- 协议错误；
- 找不到工具；
- 参数错误；
- 权限错误；
- Tool内部错误；
- Transport断开；
- 超时和取消。

每类错误是否重试不同。远程Tool可能在客户端超时后继续执行，因此写操作仍需幂等和查询状态能力。

## 2.5 MCP服务监控

- 连接数；
- 能力发现成功率；
- 每Tool调用量、失败率和延迟；
- Schema校验失败；
- 权限拒绝；
- Transport断开；
- 请求和Tool Call关联ID；
- Server版本。

## 2.6 第二章复习卡

- 一句话：MCP工程化重点是把能力发现、连接、身份、权限、错误和审计变成稳定服务边界。

# 第三章 SQL数据库与SQLAlchemy

## 3.1 表设计

以Agent任务为例：

```text
agent_tasks
├── id
├── tenant_id
├── user_id
├── status
├── version
├── created_at
├── updated_at
└── error_code

agent_runs
├── id
├── task_id
├── prompt_version
├── model_version
├── started_at
└── completed_at
```

设计原则：

- 明确主键；
- 租户字段进入访问条件和索引；
- 状态使用有限集合和合法迁移；
- 大文本、Trace与核心事务数据分离；
- 时间统一时区语义；
- 删除和审计策略明确。

## 3.2 索引

索引加速读取但增加写入、存储和维护成本。适合：

- WHERE过滤字段；
- JOIN键；
- 排序；
- 唯一约束；
- 常用联合查询。

联合索引顺序影响可用性。优化前查看真实查询计划，不要为每一列都建索引。

可以把数据库表想成一本没有目录的书。没有索引时，查`user_id=42`可能从第一行扫到最后一行；B-Tree索引像按顺序组织的目录，能快速定位目标范围。

假设高频SQL是：

```sql
SELECT * FROM tasks
WHERE tenant_id = ? AND status = ?
ORDER BY created_at DESC
LIMIT 20;
```

联合索引可能围绕`(tenant_id, status, created_at)`设计。但是否有效要看数据库查询计划、字段选择性和真实数据分布。索引越多，插入任务时需要维护的结构越多，因此不是每列都建索引。

## 3.3 JOIN

理解INNER、LEFT等连接。避免N+1查询：先查任务列表，再为每个任务单独查用户或状态，会产生大量往返。可使用JOIN、批量查询或ORM加载策略。

具体例子：页面显示20个任务及创建者姓名。

```text
N+1做法：1次查20个任务 + 20次逐个查用户 = 21次SQL
JOIN做法：数据库在一次查询中连接tasks与users
```

```sql
SELECT t.id, t.status, u.name
FROM tasks AS t
JOIN users AS u ON u.id = t.user_id
WHERE t.tenant_id = ?;
```

`INNER JOIN`只保留两边匹配的行；`LEFT JOIN`会保留左表任务，即使对应用户记录缺失，右表字段为NULL。选择取决于业务语义，不是性能口诀。

## 3.4 事务与ACID

- Atomicity：事务内操作全部成功或回滚；
- Consistency：数据满足约束；
- Isolation：并发事务的可见性；
- Durability：提交后持久保存。

工具执行涉及外部API时，数据库事务无法自动回滚外部副作用，需要Outbox、Saga或补偿设计。

例如创建Agent任务需要同时：扣减一次用户配额、插入任务记录。如果只成功第一步，用户额度减少却没有任务。把两次数据库更新放进同一事务：

```text
BEGIN
  更新quota
  插入task
COMMIT
```

任一步失败则`ROLLBACK`。但如果事务中还调用了外部短信服务，数据库回滚无法让已经发送的短信消失。这就是本地事务与分布式副作用的边界。

## 3.5 隔离级别和并发更新

理解脏读、不可重复读、幻读和写冲突。业务常用：

- 乐观锁：版本字段，更新时检查版本；
- 悲观锁：数据库锁住目标行；
- 唯一约束：防重复；
- 原子更新：避免读改写竞态。

Agent状态更新适合使用版本号防止多个Worker同时覆盖。

## 3.6 Session生命周期

SQLAlchemy Session/AsyncSession代表有状态的工作单元和事务。当前官方文档明确指出，单个AsyncSession不安全地共享给多个并发Task。原则：

```text
一个请求/事务 → 一个Session
并发子任务各自需要数据库事务 → 各自Session
```

```python
from sqlalchemy.ext.asyncio import async_sessionmaker

SessionFactory = async_sessionmaker(engine, expire_on_commit=False)

async def update_task(task_id: str) -> None:
    async with SessionFactory() as session:
        async with session.begin():
            task = await session.get(Task, task_id)
            task.status = "completed"
```

不要把Session放进全局变量或LangGraph可持久化State。

## 3.7 连接池

连接池复用数据库连接并限制总连接数。关注：

- pool size；
- overflow；
- pool timeout；
- recycle/失效连接；
- 事务结束后归还；
- 服务实例数乘以每实例连接数不得超过数据库容量。

并发提高时，数据库连接池可能先成为瓶颈。连接池不是越大越好。

## 3.8 慢查询

排查：

```text
定位慢SQL
→ 查看执行计划
→ 检查扫描行数和索引
→ 检查锁等待
→ 减少返回字段和行数
→ 批量查询
→ 缓存或异步化适合的读
→ 再测整体链路
```

## 3.9 第三章复习卡

- 一句话：数据库工程的核心是正确事务、并发一致性、Session边界、索引和连接池容量。
- 五个关键词：Transaction、Index、Isolation、Session、Pool。

# 第四章 Redis

## 4.1 数据类型选型

| 类型 | 适用场景 |
|---|---|
| String | 缓存、计数器、幂等结果 |
| Hash | 会话/对象字段 |
| List | 简单队列、最近元素 |
| Set | 去重、成员关系 |
| Sorted Set | 排名、延时任务、优先级 |
| Stream | 追加事件、消费组 |

Redis当前版本的数据类型能力持续扩展，但应用设计仍应从一致性、持久性、容量和访问模式出发。

## 4.2 缓存

### Cache Aside

```text
读取缓存
→ 命中直接返回
→ 未命中读取数据库
→ 写缓存并设置TTL
```

更新时常用先更新数据库再删除缓存。仍存在短暂不一致，需要结合业务容忍度、版本号或事件同步。

以读取任务详情为例：

```python
async def get_task(task_id: str):
    key = f"task:{task_id}"
    cached = await redis.get(key)
    if cached is not None:
        return decode(cached)

    task = await task_repo.get(task_id)
    if task is None:
        return None

    await redis.set(key, encode(task), ex=60)
    return task
```

缓存命中减少数据库读取，但引入“缓存中的旧值何时失效”。如果任务状态刚从`running`变为`completed`，60秒TTL可能让用户继续看到旧状态。可以在更新数据库后主动删除键，或对状态类数据使用更短TTL/事件通知。

## 4.3 TTL

TTL防止数据无限存在，但不能替代容量治理。加入随机抖动可减少大量Key同时过期造成的雪崩。

例如一批10万个缓存都在整点设置`TTL=3600`，下一小时整点可能同时过期并回源。加入随机量：

```text
实际TTL = 3600 + random(0, 600)
```

过期会分散在10分钟范围。TTL还必须根据数据性质设置：模型列表可以较长，任务进度需要较短，权限结果变更敏感则应主动失效。

## 4.4 穿透、击穿和雪崩

- 穿透：查询不存在数据，每次都打数据库；可缓存空值、参数校验、Bloom Filter；
- 击穿：热点Key过期，大量请求同时回源；可互斥刷新、逻辑过期、预热；
- 雪崩：大量Key同时失效或Redis不可用；可错开TTL、降级、限流和多级缓存。

三者容易混淆，可以用“查用户”区分：

```text
穿透：攻击者不断查询根本不存在的随机user_id，缓存永远没有，数据库每次被打到。
击穿：一个有百万访问量的明星用户Key突然过期，百万请求同时查询同一数据库行。
雪崩：大量用户Key同时过期，或整个Redis集群不可用，大量不同查询一起回源。
```

解决方案的目标不同：穿透要阻止不存在对象反复回源；击穿要保证热点只由少量请求重建；雪崩要限制整体回源流量并保障下游不被压垮。

## 4.5 分布式锁

锁要考虑：

- 唯一随机Token；
- 原子获取并设置过期；
- 只有持有者可释放；
- 任务超过TTL；
- 网络分区和故障转移；
- 是否真的需要互斥；
- 业务数据库约束是否更合适。

不要只执行`SETNX`后无过期，也不要直接`DEL`可能属于其他持有者的锁。Redis官方文档讨论了分布式锁的安全与活性边界；高一致性业务应审查是否需要更强协调机制或Fencing Token。

## 4.6 Lua脚本

Lua可在Redis服务器端原子执行一组操作，常用于“比较Token后删除锁”和限流。脚本应短小，避免长时间阻塞Redis事件处理。

## 4.7 Pub/Sub与Stream

- Pub/Sub：实时广播，离线消费者通常无法补历史；
- Stream：追加日志，支持消费组、Pending和ACK，可用于可追踪事件处理。

Redis Stream支持消费组和至少一次语义，但持久性和复制保证取决于Redis配置。若任务不可丢失，必须审查AOF、复制、故障转移和业务幂等。

## 4.8 热Key和大Key

- 热Key：单Key访问集中，造成单分片瓶颈；
- 大Key：删除、传输、持久化和复制耗时；
- 解决：拆分、局部缓存、批量/渐进删除、限制对象大小、监控Top Key。

## 4.9 第四章复习卡

- 一句话：Redis提供高速数据结构，但缓存一致性、锁保证、持久性和热点仍需业务设计。
- 五个关键词：Cache、TTL、Lock、Stream、Hot Key。

# 第五章 消息队列与Celery

## 5.1 为什么需要任务队列

文档解析、批量Embedding、评测、训练和长Agent任务不适合占用一次HTTP连接完成。任务队列把请求接收和后台执行解耦：

```text
API创建任务并落库
→ 发布消息到Broker
→ Worker消费
→ 更新执行状态
→ 保存结果
→ 客户端查询或订阅进度
```

## 5.2 核心角色

- Producer：发布任务；
- Broker：保存和投递消息；
- Worker/Consumer：执行；
- Result Backend：可选，保存任务结果；
- Scheduler/Beat：定时发布任务；
- Dead Letter/失败存储：保存无法处理任务。

业务任务的权威状态最好保存在业务数据库，而不是只依赖队列内部状态。

## 5.3 ACK

ACK表示消息已被消费者确认。早ACK可能在Worker执行中崩溃时丢任务；晚ACK可能在崩溃后重新投递，造成重复执行。

Celery当前文档说明`acks_late=True`会在执行后确认，因此Worker中途崩溃时任务可能重复执行，任务必须幂等。

时间线例子：

```text
Broker把任务T1交给Worker
Worker调用模型并已得到结果
Worker还没ACK时进程崩溃
Broker认为T1未完成，于是重新投递
另一个Worker再次执行T1
```

这不是队列“出Bug”，而是至少一次投递为避免丢任务所做的选择。业务代码必须能安全面对第二次执行。

## 5.4 幂等任务

```text
任务开始
→ 根据business_id/idempotency_key查询状态
→ 已成功则直接返回既有结果
→ 执行前记录processing和attempt
→ 调用外部系统使用相同幂等键
→ 原子保存结果
→ 标记completed
```

仅靠分布式锁不能保证“恰好一次”，因为锁超时、Worker崩溃和网络响应丢失仍可能重复。

假设任务是“发送报告邮件”。第一次执行已经把邮件发送出去，但在写`completed`前崩溃。第二次执行看到数据库仍是`processing`，如果直接重发，用户收到两封。

改进方式包括：

- 给邮件服务传稳定业务幂等键；
- 在数据库用唯一约束记录`report_id + recipient + action`；
- 把“生成报告”和“发送邮件”拆成可独立追踪步骤；
- 对无法天然幂等的外部副作用设计查询确认或人工补偿。

幂等的含义不是“函数只能运行一次”，而是“同一业务请求重复执行后，外部可见结果与执行一次一致”。

## 5.5 重试

重试适合暂时性故障：网络、429、部分5xx。参数错误、权限错误、文件损坏通常直接失败。

需要：

- 最大次数；
- 指数退避和抖动；
- 总截止时间；
- 错误白名单；
- 每次Attempt记录；
- 超过上限进入人工/死信处理。

## 5.6 定时任务

Celery Beat等调度器负责发布，不等于任务只会执行一次。多实例调度器需要避免重复调度，任务本身仍要幂等。

## 5.7 任务路由

将不同资源任务分队列：

- CPU文档解析；
- GPU Embedding/推理；
- 高优先级在线任务；
- 低优先级批处理；
- 外部API受限任务。

避免一个超长任务阻塞所有短任务。按资源设置Worker并发、预取和超时。

## 5.8 任务取消

“撤销队列消息”不一定能停止已执行的外部调用。可靠取消需要：

- 数据库cancel_requested状态；
- Worker在阶段边界检查；
- 可取消操作传播取消；
- 不可取消操作完成后丢弃或补偿；
- 明确最终状态。

## 5.9 第五章故障排查

### 任务重复

检查ACK时机、Worker重启、发布重试、调度器多实例、可见性超时、任务幂等记录。

### 任务一直Pending

检查Broker连接、路由键、Worker监听队列、序列化、任务注册和Worker日志。

### 重试风暴

检查错误是否持久、退避是否缺失、所有Worker是否同时重试、下游是否已故障。使用熔断和全局限流保护下游。

## 5.10 第五章复习卡

- 一句话：任务队列通常提供至少一次式处理，可靠性最终依赖幂等、状态、ACK、重试和故障恢复。
- 五个关键词：Broker、Worker、ACK、Retry、Idempotency。

# 第六章 稳定性设计

## 6.1 Timeout

每个外部依赖和整体请求都有期限。超时要分层且满足：

```text
子步骤预算总和 + 处理开销 ≤ 整体Deadline
```

超时不是越长越稳定；过长会占用连接、线程、GPU槽位和用户等待时间。

## 6.2 Retry

重试条件：错误暂时、操作安全、仍在Deadline、未超过预算。加入指数退避、抖动和最大次数。

例如模型服务返回429，可在0.5秒、1秒、2秒后尝试，但整体请求只剩1秒时不应再发一个可能持续5秒的尝试。重试必须服从总体Deadline。

`401 Unauthorized`通常是配置错误，重复相同请求不会恢复；参数校验400也应直接失败。按“异常类型是否可能自行恢复”建立白名单，比统一捕获`Exception`重试安全。

## 6.3 Circuit Breaker

下游连续失败时快速熔断：

```text
Closed：正常请求
→ 失败达阈值
Open：快速拒绝/降级
→ 冷却
Half-Open：少量探测
→ 成功恢复Closed，失败回Open
```

熔断避免每个请求都等待已知故障服务，并防止重试风暴。

假设OCR服务已连续一分钟100%超时。如果每个新请求仍等待10秒并重试3次，API连接和Worker会迅速耗尽。熔断Open后，新请求立即得到“文档解析暂不可用”或走备用方案，给下游恢复空间。

Half-Open不是恢复全部流量，而是放少量探测请求。只有探测稳定成功，才回到Closed。

## 6.4 限流

按用户、租户、API、模型和Token限流。算法包括固定窗口、滑动窗口、令牌桶和漏桶。除QPS外，模型服务还应控制并发和Token吞吐。

QPS相同不代表负载相同：10个每次输入100 Token的请求，与10个每次输入100,000 Token的请求对GPU压力完全不同。大模型网关常同时限制：

```text
RPM：每分钟请求数
TPM：每分钟Token数
Concurrent Requests：同时在途请求
Max Input/Output Tokens：单请求上限
```

令牌桶允许在平均速率范围内短时突发；漏桶更强调平滑输出。对用户返回429时应给出可理解的错误和重试建议。

## 6.5 Bulkhead隔离

不同依赖使用独立连接池、线程池、队列和并发预算，避免一个慢工具耗尽全系统资源。

## 6.6 降级

例：

- Reranker失败使用融合排名；
- 高级模型不可用切备用模型；
- Memory服务失败继续无长期记忆会话；
- 在线检索失败返回明确暂不可用，而不是编造答案；
- 实时评测延迟高时转异步。

降级必须在Trace中标记，并确保备用能力满足安全要求。

## 6.7 补偿与Saga

跨服务操作不能依赖单数据库事务：

```text
创建订单成功
→ 扣库存失败
→ 执行取消订单补偿
```

补偿不是数据库回滚，可能也失败，需要可重试、幂等和人工处理。

## 6.8 Outbox

要同时更新数据库和发布事件时，直接执行两步会有中间失败。Outbox把业务更新和待发布事件写在同一数据库事务，后台再可靠发送并标记，减少双写不一致。

直接双写的两种失败：

```text
数据库提交成功 → 发布消息失败：业务已经变化，但下游永远不知道
消息发布成功 → 数据库回滚：下游收到一个实际上不存在的业务事件
```

Outbox流程：

```text
同一事务中：更新task + 插入outbox_event
提交成功后：后台Publisher读取未发送事件
发布到Broker
成功后标记sent；失败则安全重试
```

消费者仍应幂等，因为Publisher可能在“消息已发出但sent尚未写回”时崩溃，导致同一事件再次发布。

## 6.9 健康检查

- Liveness：进程是否活着；
- Readiness：是否准备接收流量；
- Startup：慢启动服务是否完成初始化。

Readiness不应因为一个非关键降级依赖暂时不可用就必然失败，也不能只检查进程存在而忽略必需数据库和模型。

## 6.10 优雅关闭

```text
停止接收新请求
→ 标记Not Ready
→ 等待/取消在途请求
→ 停止消费新任务
→ 保存Checkpoint
→ 关闭连接池和Client
→ 超过期限强制结束
```

## 6.11 稳定性检查表

- [ ] 每个外部调用有超时；
- [ ] 重试只覆盖可重试错误；
- [ ] 写操作有幂等；
- [ ] 下游故障有熔断和降级；
- [ ] 不同资源池隔离；
- [ ] 队列有上限和背压；
- [ ] 任务有死信/人工处理；
- [ ] 服务支持优雅关闭；
- [ ] 故障注入和恢复已测试。

# 第七章 安全与可观测性

## 7.1 鉴权和授权

- 网关和服务验证Token；
- 服务端构造User/Tenant Context；
- 数据查询强制租户和权限；
- 工具按身份过滤；
- 管理接口使用更强权限；
- 服务间身份独立管理。

## 7.2 Secret

- 不提交到Git；
- 不写进镜像；
- 不打印；
- 运行时注入；
- 定期轮换；
- 最小权限；
- 泄露时可快速吊销。

## 7.3 日志和Trace

统一传播Request ID、Trace ID、Task ID和Tool Call ID。记录：

- 路由、状态码、延迟；
- 模型、Prompt和工具版本；
- Token和成本；
- 重试和降级；
- 数据/索引版本；
- 错误类型。

Prompt、工具参数和文档内容可能含敏感数据，应按字段和数据等级脱敏或完全不记录。

## 7.4 指标

- 请求量和错误率；
- P50/P95/P99；
- 当前并发和队列；
- 连接池使用；
- 数据库慢查询；

# 第八章 Docker、Kubernetes与交付

## 8.1 Dockerfile

```dockerfile
FROM python:3.14-slim

WORKDIR /app

COPY pyproject.toml ./
COPY src ./src

RUN pip install --no-cache-dir .

RUN useradd --create-home appuser
USER appuser

CMD ["uvicorn", "agent_app.main:app", "--host", "0.0.0.0", "--port", "8000"]
```

这是结构示意。实际应：

- 固定基础镜像和依赖版本；
- 使用多阶段构建；
- 减小构建上下文；
- 使用非root用户；
- 不把Secret写入层；
- 安全扫描；
- 配置健康检查和优雅关闭；
- 根据CPU架构和GPU运行时选择镜像。

## 8.2 镜像分层

Dockerfile顺序影响缓存。稳定依赖放在源码前，避免每次代码变化重新下载全部依赖。合并无意义层，但不要牺牲可读和缓存。

## 8.3 容器配置

- 环境变量；
- Secret；
- Volume；
- 网络；
- CPU/内存限制；
- 只读文件系统；
- 临时目录；
- 日志输出到标准流；
- 时区和证书。

## 8.4 Kubernetes对象

- Pod：运行一个或多个紧密关联容器；
- Deployment：管理无状态Pod副本和滚动更新；
- Service：稳定服务发现和流量入口；
- ConfigMap/Secret：配置；
- Job/CronJob：批任务；
- StatefulSet：需要稳定身份/存储的工作负载；
- HPA：基于指标扩缩容。

## 8.5 Probe

- Startup Probe保护慢启动模型；
- Readiness Probe控制是否接收流量；
- Liveness Probe判断是否需要重启。

Probe配置过激会在模型加载或GC时反复重启；配置过松则故障实例持续接流量。

## 8.6 资源和扩缩容

CPU应用可按CPU、并发和队列扩容；模型推理还需要GPU显存、批处理和加载时间。HPA不能只看CPU。扩容速度必须考虑镜像拉取和模型加载。

## 8.7 发布

- Rolling Update；
- Blue-Green；
- Canary；
- Feature Flag；
- 数据库向后兼容迁移；
- 快速回滚。

Prompt、模型、工具Schema和索引也是发布版本的一部分，不应只记录代码镜像Tag。


## 8.9 第八章复习卡

- 一句话：容器和Kubernetes只是交付工具，可靠发布还依赖版本、Probe、资源、迁移、灰度、监控和回滚。
- 五个关键词：Image、Deployment、Probe、Canary、Rollback。

# 第九章 综合实践：生产级Agent后端

## 9.1 目标架构

```text
Client
→ Gateway
→ FastAPI Agent API
   ├── PostgreSQL：任务/会话/幂等/业务状态
   ├── Redis：缓存/限流/短期状态
   ├── Celery：解析/评测/长任务
   ├── Agent Runtime：LangGraph/Tools
   ├── RAG Service：检索/Rerank
   ├── Model Service：外部API或vLLM
   └── MCP Clients：外部业务能力
→ OpenTelemetry/Prometheus/Logs
```

## 9.2 API

```text
POST /v1/sessions
POST /v1/sessions/{id}/messages
GET  /v1/sessions/{id}/events
POST /v1/tasks/{id}/cancel
GET  /v1/tasks/{id}
POST /v1/approvals/{id}/decision
```

## 9.3 一次请求

```text
认证并生成Request ID
→ 校验消息和会话归属
→ 创建Run记录
→ 获取并发/速率许可
→ 调用Agent
→ 工具、RAG和模型产生子Span
→ SSE返回进度
→ 保存最终状态和Token成本
→ 异步执行评测抽样
```

## 9.4 故障场景

- 模型429；
- Reranker超时；
- Redis不可用；
- 数据库连接池耗尽；
- Worker重复执行；
- 客户端断开；
- MCP Server断线；
- 发布中Schema不兼容；
- 节点恢复重复发邮件；
- 日志包含敏感Prompt。

每个场景记录：检测、用户体验、重试/降级、状态一致性、告警和恢复验证。

## 9.5 验收

- 并发压测下错误率和延迟满足目标；
- 写操作重复请求无重复效果；
- Worker崩溃后任务可恢复；
- 客户端断开后无资源泄漏；
- 无权限数据不可访问；
- 发布可灰度和回滚；
- 通过Request ID定位完整Trace；
- 安全、质量和成本指标可查看。

# 第十章 模块总结与面试复习

## 10.1 一分钟总结

> 我会把Agent原型拆成API、应用服务、Agent编排、领域策略和基础设施层。FastAPI负责参数、鉴权、依赖、异常和SSE，数据库保存权威任务状态并通过事务、版本和连接池保证一致性；Redis用于缓存、限流和短期状态，但锁和持久性要理解边界；长任务通过Celery处理，按至少一次语义设计幂等、ACK、重试和取消。外部依赖统一加入超时、退避、熔断、隔离和降级。服务使用Docker和Kubernetes交付，通过Lifespan、Probe、优雅关闭、灰度、监控和回滚形成完整生产闭环。
